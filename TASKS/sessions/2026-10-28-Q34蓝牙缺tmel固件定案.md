# 2026-10-28 · Q34 定案：蓝牙控制器起不来的真因是缺 `qca/tmel_peach_20.elf`

- **日期**：2026-10-28
- **pi 会话 id**：`$PI_SESSION_ID`
- **主题**：设备冷起后顺手体检，发现 `bluetoothd` active 却 `No default controller available`（= 台账 Q34），
  现场复现并定案，同时把固件包的缺口变成常驻门禁。
- **结论（数字）**
  1. **不是 `bluetoothd` crash**：服务一直 `active`；`hci0` 是 `DOWN` / `BD Address 00:00:00:00:00:00`。
     `dmesg`：`hci_uart_qca serial0-0: Direct firmware load for qca/tmel_peach_20.elf failed with error -2`
     → `Bluetooth: hci0: Peripheral setup failed: -2`（`-2` = `-ENOENT`）。
  2. **设备 `/lib/firmware/qca/` 只有 4 个文件**（brhbtfw20.tlv / brhbtnv20.bin / brhperifw20.tlv / brhperinv20.bin），
     而 `hci_qca.c` 的 WCN7861 外设阶段还要 `qca/tmel_peach_20.elf`（`MODULE_FIRMWARE` 显式列出）⇒ 外设阶段直接失败、`qca_power_off()`。
  3. **修复（30 s、无重启）**：`scp backup/fw/modem/image/tmel_peach_20.elf → /lib/firmware/qca/` +
     `modprobe -r hci_uart btqca; modprobe hci_uart` ⇒ `hci0 … UP RUNNING`、
     `BD Address 22:22:62:9C:97:58`、`bluetoothctl show` 出 `Controller 22:22:62:9C:97:58 (public) Name: elden`、
     `QCA setup on UART is completed` + `HFP non-HCI data transport is supported`。
  4. **旧口径纠正**：Q34 原记「冷起偶发 crash，restart 服务即好」——本次实测**重载服务/重载模块都不解决**，
     必须补文件；「restart 就好」的历史现象与本次不同源。
  5. **根治两层**：① `elden-firmware/paths.txt` 补该文件 + 新增 `local-extras.tsv`
     （**源树没有、但驱动会 request** 的文件；仓库内副本 + sha256），解决「包源树 = 设备自身」的循环依赖；
     ② **新门禁 A2**：`git grep MODULE_FIRMWARE("…") -- drivers/` 只筛本机厂商前缀
     （`qca/ qcom/ ath12k/ awinic/ novatek`），逐条要求进包 —— 本树命中 **3 条、缺 0 条**。
     旧门禁只查 DT `firmware-name`，这次的缺口正落在「驱动代码里的名字」这条缝。
  6. **负向测试**：把 tmel 从 `paths.txt`/`local-extras.tsv` 删掉 → `MISS qca/tmel_peach_20.elf` +
     `FAIL 驱动声明的固件没进包`；恢复 → `缺 0 条`、包 **258 条目**、解包后复检全绿。
  7. **顺手修掉门禁自身 bug**：A2 首版用 `[ -d "$tree/.git" ]` 判断内核树 —— `build/vk151` 是 **worktree**，
     `.git` 是**文件** ⇒ 判断恒假、A2 静默跳过并打印"通过"（日志那句「内核树无厂商 MODULE_FIRMWARE 条目，跳过 A2」）。
     已改 `-e` + 非 git 时 WARN。同类坑一天内第二次（`PITFALLS #452` 的 IFS 折叠）⇒ 纪律：
     **门禁写完必须做负向测试**，静默跳过的门禁比没有门禁更危险。
