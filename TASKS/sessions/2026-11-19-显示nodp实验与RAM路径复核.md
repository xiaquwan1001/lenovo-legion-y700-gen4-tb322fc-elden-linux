# 2026-11-19（白天）显示 nodp 实验首次有效执行 + RAM 启动路径复核

> 角度：G1 显示 / 设备恢复。设备 = U2 `HA2EXB0E`（fastboot 在线）。
> 上一篇 = `2026-11-19-主线恢复最小Linux与显示定位.md`（结论「两条 RAM 启动都不能当否证」）。
> 本篇 = 把那条结论**改判**，并把「DP 拖死 DPU」实验**第一次真正做出来**。

## 结论一：11-18 两次「RAM 启动没枚举 USB」的成因是 cmdline 根标签错，不是实验件坏

- 实测：`strings out/boot-elden-vk192.img` → `elden_root=LABEL=linux17`；
  `out/min-restore-20261119/boot-nodp-test.img` → **同样** `LABEL=linux17`。
- 但 11-19 重建的最小根 **label = `linux`**（`findmnt -no SOURCE,LABEL /` ⇒ `/dev/sda17 linux /`）⇒
  这两个件在内核 initramfs 阶段找不到根 ⇒ `panic=15` ⇒ 回 fastboot、USB 全程不出现。
- 于是 11-19 那句「test-ctrl 没上机 ⇒ RAM 启动本身未复核」现在有了答案：
  **RAM 启动路径一直是好的**，坏的是镜像里的根标签。
  - 控制臂（`bootslot-b/boot_b-minbase-labellinux-20261119.img`，sha `740d431b…`，`LABEL=linux`）
    → `fastboot boot` 12 s OKAY，**~40 s 后 `/dev/ttyACM0/1` + `enx021e5eede102` 出现**，
    `ssh root@192.168.7.1` 通、`uname -r` = `7.3.1-debug-vk189-suspend-00005-g4bdf1711b5c0`、
    `findmnt /` = `/dev/sda17 linux /`。**两次复现**（本日 11:19 与 12:0x）。
- 判据口径（以后打包/实验必查）：`strings <boot.img> | grep elden_root` 必须与设备上
  `findmnt -no LABEL /` 一致；不一致的件**不能**当「内核/DTB 有问题的否证」。

## 结论二：`build/` 内核树已不在主机 ⇒ DTB 实验改走「镜像内 DTB 外科手术」

- `ls build/` 现在只剩 `phoc-src-*`/`phosh-src-*`；`build/daily`、`build/m3v2-7.3rc7` 均已随
  2026-11-19 清理删除（`INDEX.md` §0 运维行 / `reports/disk-cleanup-20261119-validation-impact.md`）。
  ⇒ `scripts/build-boot.sh` + `make dtbs` 那条重打路径**当前不可用**（要先把树恢复）。
- 替代路径（本轮用通，零内核树、零编译）：
  ```sh
  python3 scripts/mkbootimg.py --unpack <boot.img> --unpack-dir /tmp/un
  dtc -I dtb -O dts -o base.dts /tmp/un/dtb          # 153129 B, sha 89c9336d…
  #  编辑：只删 display-controller@ae01000/ports/port@2/endpoint 的 remote-endpoint
  dtc -I dts -O dtb -o nodp.dtb nodp.dts             # 153113 B（−16 B）
  python3 scripts/mkbootimg.py --header_version 2 --os_version 15.0.0 --os_patch_level 2025-08 \
    --kernel /tmp/un/kernel --ramdisk /tmp/un/ramdisk --dtb /tmp/un/nodp.dtb \
    --cmdline "<原 cmdline 逐字，含 elden_root=LABEL=linux androidboot.slot_suffix=_b>" \
    --base 0x0 --kernel_offset 0x8000 --ramdisk_offset 0x01000000 --second_offset 0x00f00000 \
    --tags_offset 0x100 --dtb_offset 0x01f00000 --pagesize 4096 -o boot-nodp-linux.img
  ```
- 往返保真已证：`dtc` 反编译 → 改 → 重编 → 再反编译，与原件 `diff` **只有那一行差异**。
  即「不改 DTS 源也能做单属性 DTB 实验」。

## 结论三：nodp 实验（首次有效）—— 仍然起不来，但形态变了

| 臂 | 件 | 结果 |
|---|---|---|
| 控制 | `boot_b-minbase-labellinux-20261119.img`（`740d431b…`） | 40 s 枚举 USB，ssh 通（**2/2**） |
| 实验 | `out/min-restore-20261119/boot-nodp-linux.img`（`7908e3f1…`，仅摘 `dpu_intf0_out.remote-endpoint`） | 95 s+ **USB 完全不枚举**；用户目视 = **只有背光**（无 fbcon 文字）；`panic=15` 未触发（pstore 空、设备停在原地不回 fastboot） |

- 判读：**不是 panic 而是挂死**（pstore 干净；被强制重启后才回 BL）。
- 与「DP 拖死 DPU master」假设的关系：**没有否证它，但证明「只摘图连接」不够** ——
  摘掉后 DPU 聚合可能真的 bind 了，随后卡在 DSI/enable 路径（否则 `console=tty0` 该有字）。
  下一步必须能看 early console 才能定位，见下。

## 结论四：minbase 根里的两个环境事实（与显示/外设异常同源）

- **`systemd-udevd` inactive、`ps -eo comm | grep -c udevd` = 0** ⇒ **模块不自动加载**：
  `lsmod` 只有 22 个（相机串 + `phy_qcom_edp`），`fastrpc`/`ath12k` 一类要靠 modalias 的都没起
  （这解释了「无 `/dev/fastrpc-adsp`」「ath12k MHI -110」的一半；另一半是 ADSP 未起）。
  判据 `systemctl is-active systemd-udevd` ⇒ 应为 `active`；修法 = 最小档装 `systemd-udevd` 或
  显式 `modprobe` 清单进 `/init`。
- 显示失败态**与 11-19 记录逐字一致**（复现稳定）：
  `ae01000.display-controller` = `aggregate not bound`；`ae94000.dsi`/`ae96000.dsi` = `not bound`；
  `(unknown)×2` = `not registered`；`af54000.displayport-controller` = `deferred probe pending: (reason unknown)`；
  `aux_bridge.aux_bridge.0` = `failed to acquire drm_bridge`；`pmic_glink.altmode.0` = `failed to acquire mode-switch for port: 0`。
  另：`msm-dp-display` 驱动存在但**零设备绑定**；DP 用的 `88e8000.phy`（`qcom,sm8750-qmp-usb3-dp-phy`）**绑定正常**。

## 下一步（按价值）

1. **拿 early console**（否则显示这条线只能瞎试）：三选一 —— ① 带外 UART（项目已有设施，
   人项：接串口）；② 把 `ttyGS0` gadget 提进 initramfs 最早阶段（内核 `console=ttyGS0,115200` 已配好，
   只要 gadget 在内核 init 之后立刻起就能收到 hang 前的日志）；③ `panic_on_warn=1` + `oops=panic`
   让挂死变 panic（若它其实是 WARN/oops 卡死）以落 pstore。
2. **minbase 补 `systemd-udevd`**（或 `/init` 里显式 modprobe 清单）——这是「显示/外设异常」里
   与环境相关的最大公约数，且修完可让 `fastrpc`/`ath12k`/`phy_*` 归位再判显示。
3. `slot-attr.py mark-successful b` **仍未做**（设备无 python3，`fastboot --set-active=b` 只把 retry 归 7，
   `slot-successful:b` 仍 `no`）⇒ 下次有 python3/EDL 窗口时补，或改用 `dd` 写条目 attributes。
4. `resize2fs /dev/sda17` + `daily-baseline`（桌面面）依旧待做，且**依赖 udev 修复**。

## 复现命令（本轮实际执行，可直接抄）

```sh
for v in current-slot slot-unbootable:a slot-retry-count:a slot-successful:a \
         slot-unbootable:b slot-retry-count:b slot-successful:b unlocked; do
  timeout 15 fastboot getvar $v; done
timeout 15 fastboot --set-active=b            # 只清 retry，不置 successful（实测）
timeout 240 fastboot boot bootslot-b/boot_b-minbase-labellinux-20261119.img
sudo scripts/ncm-host-up.sh && ssh -o StrictHostKeyChecking=no root@192.168.7.1
# 回 fastboot 再换件：ssh 'nohup reboot2 bootloader &' → 约 50 s 见 fastboot devices
```
