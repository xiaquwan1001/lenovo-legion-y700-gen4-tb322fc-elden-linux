## 1. 为什么这一轮值得做（上一轮的漏洞）

上一轮结论是「窗口 = (`VS_STOP(34)`, `VS_STOP(27)`)，只剩 `MarkPtnActive()` + `out:` 收尾」，
于是把首要嫌疑压到 `MarkPtnActive()`。但源码面上被漏掉的一条是：**`out:` 里那条诊断写是 R15 时代的，
它早于 `SbProbeMode` 这个开关**，所以 `sbprobe=3` 并没有关掉它：

```c
out:
  {
    CHAR8  SbBuf[96];
    UINTN  SbLen;
    SbLen = AsciiSPrint (SbBuf, sizeof (SbBuf), "[V] slot0=%d st=%r\n\r", …);
    SerialPortWrite ((UINT8 *)SbBuf, SbLen);   // ← 无条件
  }
```

而 `34` 档是 `return EFI_ABORTED`（**提前返回，不经 `out:`**）、`27` 档是「`FindBootableSlot` 正常返回」
（**必经 `out:`**）⇒ 「34 回话、27 崩」的两条解释在静态上等价：

- A：`MarkPtnActive()` 自己崩；
- B：`MarkPtnActive()` 正常，`out:` 那条屏显写把帧缓冲写穿（= 上午已定案的那条通路）。

顺带核对到一个降低 A 先验的事实：`UpdatePartitionAttributes()` 开头
`if (!IsUpdatePartitionAttributes ()) return;`，而 `IsUpdatePartitionAttributes()` 的函数体被整段注释、
直接 `return FALSE`（`PartitionTableUpdate.c:193-200`）⇒ `MarkPtnActive` **不落盘**，只跑内存属性循环。

## 3. 指令级核对（不是「补丁打了就算」）

p8 件：`0x897c cmp w8,#0x23`（35）→ `0x911c cmp w8,#0x24`（36）→ `bl 0x13b0`(AsciiSPrint) /
`bl 0x13b58`(SerialPortWrite) → `0x915c cmp w21,#0x25`（37）→ `0x9174/0x918c cmp w21,#0x26`（38）
→ `0x9184 cmp w21,#0x1b`（27）。
p9 件：同位置多出 `0x8f94 ldr w8,[x27,#0x63c]`（`SbProbeMode`）/ `0x8f98 cmp w8,#1` / `0x8f9c b.hi`。
符号归属按 `LinuxLoader.map` 核（`AsciiSPrint=0x13b0`、`SerialPortWrite=0x13b4c`，p8 件整体平移 12 B）。

## 5. 未上机的原因（重要）

板子不在 USB 上：`lsusb` 只有主机自身的 gadget 枚举，`adb devices` 出来的 `emulator-5554`
经 `getprop ro.product.model` 核实是**主机上的 Android 模拟器**（`sdk_gphone64_x86_64`），不是 TB322FC。
⇒ 本轮 `adb reboot bootloader` 那一步打到了模拟器上（无副作用，模拟器现已正常回到 `device`）；
**上机判据一律未取**。
