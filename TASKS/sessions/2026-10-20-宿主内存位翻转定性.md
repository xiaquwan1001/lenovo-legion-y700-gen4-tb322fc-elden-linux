## 2. 回答用户的问题

> 「是否是之前不稳定的内容写坏了没有当时检查？」

**不是。** 判定依据：

1. 磁盘真值用 `O_DIRECT`（完全绕过页缓存）读取，与 git index / dpkg `md5sums` 逐字一致 ⇒ 没有任何「写坏的字节」留在盘上。
2. 报出来的「坏」全部在**页缓存**，`posix_fadvise(DONTNEED)` 丢掉即可恢复 —— 这是内存内容，不是文件内容。
3. 因此「今天开机稳定 / 三轮 stress-ng 通过」**不能**证明内存已修好：`stress-ng` 默认不校验数据完整性，而翻位是概率事件（30 轮里有的轮次 0 命中）。

**但有一个真实残留**：`build/m3v2-7.3rc7` 的 git **pack 文件确有物理损坏**（与内存翻位是两件事），已修复并 `fsck` 清净。

**还没做的事（需你决定硬件侧）**：BIOS 关 XMP/EXPO 回 JEDEC、单条内存排查、`memtest86+` ≥4 轮。已写进报告 §6 与体检门的失败提示里。

## 4. 顺带修的真实故障（与内存翻位无关）

`build/m3v2-7.3rc7` 是 `build/m1-73` 的 **worktree 宿主**，其 `.git/objects/pack/pack-d19c589d….pack` 物理损坏：

- `git fsck` 报 `pack checksum mismatch` + 8 个对象 `cannot unpack`（`STREAM error` / `invalid literal/lengths set`）；
- 其中 5 个是可从工作树复原的 blob，另外 3 个是 **tree** 对象（从 `geekidos-linux` 取回）；
- 4 个 worktree 的 `index` 也坏了（`m1-73` 的 index 里出现 **`drirers/`、`drivers/s398/` 这样的翻位路径名**）；
- 修法：`git cat-file --batch` 导出全部 118 357 个对象 → 逐个重算 sha1 验证 → 用干净对象库替换 → `git reset` 重建各 worktree index；
- 结果：`git fsck`（排除 reflog）**0 错误**，工作树 diff 干净，5 个 `git bundle` 备份在 `backup/git-pack-repair-20261020/`。

> 注意：这个过程也用到了内存。事后已用三读法复核：11 个被重写的源文件磁盘内容全部 = HEAD（`corrupt=0`），即**这次没有写坏**，但这属运气；正确做法是丢缓存而不是重写。
