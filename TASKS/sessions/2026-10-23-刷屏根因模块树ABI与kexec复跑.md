# 2026-10-23 · fastrpc 刷屏根因（模块树 ABI）+ kexec vk147 复跑

- **日期**：2026-10-23
- **主题**：① 修 `fastrpc -22` 刷屏（顺带揭出 SSC 传感器从 vk127 起一直全废）② vk147 上重跑 kexec（Q11/C12）
- **结论（一句话）**：刷屏**不是驱动 bug**，是 `/lib/modules/<UTS>` 符号链接指向了 `CONFIG_SUSPEND=y` 编的另一套模块树（`struct device.of_node` 624 vs 680，**vermagic 只比 UTS 串拦不住**）；kexec 的**掉电阻塞彻底解决**，但目标仍静默挂死，且 **0154 对 kexec 路径机制性无效**。

## 1. 刷屏（已完成）

### 现象被低估了

文档记的是「7.3 线 `fastrpc -22` 刷屏，与显示无关」。实测 **23 min 内 2941 行**（稳态 ~2 行/秒），且
**`/dev/fastrpc-{adsp,cdsp}` 根本不存在** ⇒ SSC 传感器从 vk127 起**一直是废的**（`HasAccelerometer=false`）。

### 取证（kprobe，零构建）

在 `fastrpc_rpmsg_probe` 入口读 `rpdev->dev` 字段：

| 偏移 | 值 | 含义 |
|---|---|---|
| `+624` | 真实 DT 节点指针 | 正确位置 |
| `+680` | `0x0` | 驱动读的位置 |

同一批 trace 里 `qcom_glink_work` 对那个节点读 `qcom,glink-channels` → **ret=0**；
`fastrpc_rpmsg_probe` 读 `label` → **ret=-EINVAL**。同节点、同函数、两种结果 ⇒ **偏移问题**。

反汇编坐实：在机 `vmlinux` 用 `[x21,#624]`，部署的 `fastrpc.ko` 用 `[x21,#680]`。

### 根因

`/lib/modules/7.3.0-rc7-…-vk127-…` → `…-abi-suspend`（10-18 vk128/vk129 suspend 实验建的那套）。
`CONFIG_SUSPEND=y` 让 `struct dev_pm_info` 变大 ⇒ `of_node` 从 624 推到 680。
实验作废后内核回到 `SUSPEND=n`，**链接没切回来**。

### 修后（全部恢复）

| 项 | 修前 | 修后 |
|---|---|---|
| 刷屏 | ~6 行/5 s | **0** |
| `/dev/fastrpc-*` | 不存在 | 3 个全在 |
| `HasAccelerometer/Light/Proximity` | false | **true** |
| `monitor-sensor` | 失败 | `tilt: face-up` |
| 相机 | — | `1 media, 17 video nodes` |

**重启后仍生效**（模块树链接 + udev 规则都持久化）。

## 2. 同一根源的第二个症状：vk146 挂死

首次 `fastboot boot vk146` 出现「背光亮一下就掉电」——差点误判成 fastboot 假成功。
**真因**：`build/m1-73/.config` 也遗留了 `CONFIG_SUSPEND=y`（同一次实验）⇒ 编出的内核**必然复刻 vk128/vk129 的已知失败形态**。

⇒ vk146 作废，换 SSOT config 重编 = **vk147**（`#13`，`pahole` 核 `of_node` @624）。

## 3. kexec（Q11 / C12 复跑）

### 掉电阻塞：关闭 ✅

vk147 上 `kexec_dbg=1` + mask=1，串口完整：
```
[KD] stage=10 enter kernel_kexec (skip_mask=1)
[KD] stage=11a SKIP device_shutdown
[KD] stage=11 after kernel_restart_prepare
[KD] stage=12 after migrate_to_reboot_cpu
[KD] stage=13 before syscore_shutdown
[KD] stage=14 after syscore_shutdown
Starting new kernel → psci: CPU1..7 killed → Bye!
```
**零 PMIC 掉电**。

### 目标仍静默挂死 ❌

`Bye!` 后串口 0 行；`/var/tmp/kexec-marker.txt` 不存在（连 slim initramfs 的 `/init` marker 段都没到，
比 C12「跑到 udevd」更早）。自动回落 boot_b。

### 0154 对 kexec 机制性无效

| 路径 | display 继承态 | 结果 |
|---|---|---|
| 持久启动（ABL→kernel） | bootloader 遗留的活状态 | 0154 有效（STORM 0/9→0/8） |
| kexec | **另一个内核完整初始化完**的状态 | 无效 |

目标的 dispcc 仍会 probe（0154 那 27 行会执行），但它复位的是 `MDSS_CORE/INT2/RSCC`，
抵消不了 live 内核留下的 **`DSI CTRL=0x175` 自锁 + PLL 全锁 + bonded link 已编程**。

### B 臂（kexec 前 unbind display）不可行

`echo ae00000.display-subsystem > /sys/bus/platform/drivers/msm-mdss/unbind` ⇒ **整机重启**（`boot_id` 变化）。

### 裁决

**K3（建议，0 成本）**：kexec 只用于「不需显示的调试」，判据走磁盘文件。
理由：kexec 省 2–3 min 换内核，但前置（要人按键进 fastboot 起载具）把这个收益吃掉。
K1（目标 DT `status="disabled"` 后手动 bind）/ K2（kexec 前只置 `CTRL.ENABLE=0`）列低优先。
