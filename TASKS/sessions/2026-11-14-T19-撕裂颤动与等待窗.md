# T19 画面撕裂/滚动颤动 + 「等待窗比实际加载久」（2026-11-14 用户报）

**日期**：2026-11-14
**pi 会话 id**：01a1d8a6-9861-7308-aa73-7b014fc47dfe
**主题**：新增用户观测缺陷 T19（显示合成/帧节奏），本轮只做「登记 + 一线静态取证」，未改任何树/配置。

**结论**：

1. **现象（用户原话口径）**：① 部分软件垂直同步没做好——屏幕上下滚动时**画面撕裂 + 抽搐**（例：GNOME「软件」`gnome-software` 51.0）；
   ② 部分 app 的**加载等待窗比实际加载完成时间更长**，观感像卡顿。
2. **一线静态事实（本轮现查，设备在机 vk190/vk191 线，UTS `7.3.1-debug-vk189-suspend-00002-g4da9a8b69fc8-dirty`）**：

   | 事实 | 值 | 来源命令 |
   |---|---|---|
   | 当前输出模式 | **1904x3040 @ 165 Hz**（preferred、current），另可选 144/120/90/60/40/30/24 | `wlr-randr` |
   | 刷新率交叉验证 | **165.0 Hz**（10 s 内 `msm` IRQ +1650） | `grep msm /proc/interrupts` ×2 |
   | 面板接线 | 双 DSI bonded（`mixer:0/mixer:1` 各 952×3040）、`intf_mode:2`（video mode）、`core_clk_rate: 1 029 188 160` | `/sys/kernel/debug/dri/0/crtc-0/status`、`crtc-0/state` |
   | 扫描帧格式 | 当前 fb = **XR24**（8bpc，4 B/px）⇒ 165 Hz 全屏重绘 ≈ **3.8 GB/s** DPU 读 | 同上 `fb:110 image format:XR24` |
   | 面板 mode_flags | `MIPI_DSI_MODE_VIDEO \| CLOCK_NON_CONTINUOUS \| NO_EOT_PACKET \| VIDEO_BURST \| LPM \| DSC_ALL_SLICES_IN_PKT` | `build/daily` `panel-novatek-nt36536.c:530` |
   | 合成器栈 | **phoc 0.59~rc1-1 / phosh 0.59~rc1-1 / libwlroots-0.20 0.20.2-1** | `dpkg -l` |
   | 内核侧异常 | **4 行** `[dpu error]vblank timeout: 400000` + 2 行 `wait for commit done returned -110`（up≈5130 s / 5181 s 各一对，共 2 次事件） | `dmesg \| grep vblank timeout` |
   | 无 underrun/qos 报错 | `dmesg \| grep -iE "underrun\|qos\|ctlu"` 空 | 同上 |
   | 空闲态 GPU | `3d00000.gpu` `cur_freq=160000000`（最低档），CPU 温度 ~36 ℃ | `devfreq`、thermal |

3. **判读（未证实，勿当结论）**：两个症状与「帧节奏」同源是**待证假设**，不是已证事实。可判别点：
   - 165 Hz + 3.8 GB/s 全屏重绘 → 合成/GPU 跟不上 ⇒ **掉帧造成的「抽搐」**；
   - `commit_done` 等待在 400 ms 后放弃（`-110`）⇒ 该次 flush 可能落在扫描中途 ⇒ **撕裂**的机制候选（仅 2 次事件，不足以支撑「撕裂主因」）；
   - 等待窗超长 ⇒ 需先量「frame callback 到达滞后」还是「app 自身 CPU/IO 慢」，两者判别方法不同。

4. **取证计划（下一步，按代价从低到高；前三条只读）**：
   - **P1 帧节奏**：`WAYLAND_DEBUG=1 gnome-software > /tmp/gs.log 2>&1`，抓滚动 5 s，看 `wl_surface@..frame` 的**请求→回落间隔分布**（正常 = 1/165 ≈ 6.06 ms；拖到 20–50 ms 即掉帧）。
   - **P2 刷新率消元**（需用户在屏旁目视，可逆）：`wlr-randr --output DSI-1 --mode 1904x3040@60Hz` → 滚动同段；撕裂/抽搐消失 ⇒ 指向带宽/帧率；无变化 ⇒ 指向 panel/DPU 同步（升优先级查 `commit_done` 路径）。
   - **P3 渲染器消元**（需用户在屏旁目视）：`GSK_RENDERER=cairo gnome-software`（GTK4 走 cairo 软渲染）→ 若撕裂消失 ⇒ EGL/GL swap 路径（msm + wlroots 0.20）；若反而更抖 ⇒ GPU 侧。
   - **P4 内核侧**：开 `echo 0x2 > /sys/module/drm/parameters/debug` 后滚动 10 s，统计 `commit_done`/vblank timeout 是否随滚动复现（本轮 16 h 只 2 次，需负载下重测）。
   - **P5 等待窗**：对同一 app 用 `strace -f -e trace=io,network,futex -T` + 屏上目视计时，比较「磁盘/网络完成时刻」与「窗消失时刻」。

5. **纪律**：P2/P3 要**用户在看屏时**做（判据是目视，不是日志）；改刷新率可逆但会短暂黑屏，做完必须 `wlr-randr --output DSI-1 --mode 1904x3040@165Hz` 还原并记录原值。**不得**在本轮顺手改 phoc.ini 或内核树。

**已知坑（待进 PITFALLS）**：`wlr-randr --output DSI-1 --mode 1904x3040@60Hz` / `@60.000000Hz` **静默按 165 Hz 生效**（该面板 8 个模式同分辨率，wlroots 只按 W×H 匹配）；要真切刷新率必须 `--custom-mode`。另有 `phoc: Atomic commit failed: Device or resource busy` 一次（切模式时），随后恢复。

**观察方法补充**：空闲时 `msm` vblank IRQ = 0（msm 无 pending commit 时会屏蔽 vsync），**不能用 IRQ 计数判空闲刷新率**；需要制造连续 damage（如背光来回切）才看得到 tick。

## 2b. 修饰符口径澄清（2026-11-14 现查，避免误判）

- phoc 扫描 FB 的 `modifier:360287970189639681` = **`0x0500000000000001` = `DRM_FORMAT_MOD_QCOM_COMPRESSED`**
  （本树 `drm_fourcc.h:502` 的 `fourcc_mod_code(vendor,val) = (vendor<<56)|val`，QCOM=5 ⇒ `(5<<56)|1`）。
  **不是**异常值；扫描输出走 UBWC 压缩布局。
- 因此「扫描输出 = UBWC」+「客户端 buffer 带 UBWC modifier 导入」是同一条修饰符链；
  P3c 关掉客户端 modifier 导入即恢复 ⇒ 嫌疑在**导入/采样侧**的一致性或 stride 约定，而非 DPU 扫描。
