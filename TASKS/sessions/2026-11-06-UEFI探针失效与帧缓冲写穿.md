## 1. 本轮最重要的一条：**上一轮的 10 发全部无效**

`patches/uefi/20261105-vsbisect/0001` 的探针写成：

```c
#define VS_STOP(n) do { if (SbStopStage == (n)) { SbDiagAbort = (n); return EFI_ABORTED; } } while (0)
```

而 `SbStopStage` 的**唯一赋值点**在 `BootLinux()` 内（`patches/uefi/20261104R20-stage-bisect/0001`，
`[K] img sz` 之后），`CmdBoot` 的调用序却是 `LoadImageAndAuth()` → `BootLinux()` ⇒
进 `LoadImageAndAuth` 时它恒为 `-1`，**`VS_STOP(16..25)` 一次都不会命中**。

⇒ 11-05 夜那 10 发（`vs-stop20…25`、`pre-stop16/18/19`）的行为 = **未加探针的对照件**，
一律崩在同一处。「崩在 N 之前」的判读不成立，`reports/uefi-screenlog-crash-20261105.md`
§10–§12 的窗口结论（含「首要嫌疑 `FindBootableSlot`」）**作废**。

修法（`patches/uefi/20261105R2-vsstop-fix/`）：入口当场从 boot 头 cmdline 解析。
**第一版又踩一个坑**：加了 `SbStopStage < 0` 守卫 ⇒ 该全局跨 fastboot 命令保留，
同一固件会话连打第二发会沿用上一发的值（实测 `sbstop=18` 被打成 `vs-16`）⇒ R3 改**无条件重解析**。

## 3. 反汇编把「空白区间」变成「一次 `SbVProbe`」

源码上 17→18 之间只剩 `if (Info == NULL)`（RELEASE 下 `DEBUG` 编掉），看似无代码。
但 `LinuxLoader.efi` 反汇编显示：`Info == NULL` 已被编译器**删掉**（我们的解析块先解引用了 `Info`），
真实代码是：

```
8424: bl  WaitForFlashFinished
8428: ldr w8,[SbStopStage]; cmp w8,#0x11      <- VS_STOP(17)
8450: ldrb w2,[x19,#1]; ldrb w1,[x19]
8458: adrp x0,0x2b000; add x0,x0,#0xc0
8460: bl  SbVProbe                            <- SbVProbe("[V] ms=%d rec=%d")
8464: ldr w21,[SbStopStage]; cmp w21,#0x1a    <- VS_STOP(26)
```

⇒ 崩溃点 = 一次 `SbVProbe` 调用。`SbVProbe` 干两件事：`SerialPortWrite`（FrameBufferSerialPortLib
直写帧缓冲）+ `gRT->SetVariable("SbMarkR19", NV|BS)`（R19 加进来的）。

## 4. 单变量判别：元凶是帧缓冲，不是 NV 变量

引入正交令牌 `sbprobe=M`（0=完整 1=只串口 2=静默；`patches/uefi/20261105R6-probe-orthogonal/`），
并把 `BootLinux.c` 的 `SbBootProbe` 纳入同一开关：

| 件 | 结果 |
|---|---|
| `sbstop=26 sbprobe=2`（全静默） | `diag st=Aborted last=[vs-26]`，2 s，随后 `product: sun` 存活 |
| `sbstop=26 sbprobe=1`（只 SerialPortWrite） | **崩**（40 s 超时、无 diag） |

⇒ **`SerialPortWrite` / 帧缓冲控制台** 是元凶，`SetVariable` 清白。

**注意 R5 的设计缺陷**：`sbstop=9X` 把「关探针」和「取消停机点」绑在一起 ⇒ 流程继续进 `BootLinux`
（那里有自己的 `SbBootProbe` 与既有的 `ShutdownUefiBootServices` 崩溃）⇒ `sbstop=92` 崩了也无法归因。
正交令牌才解决这个问题。

## 5. 机制：屏上输出自己把帧缓冲写穿

| 量 | 值 | 来源 |
|---|---|---|
| `Display Reserved`（UEFI）/ DT `splash_region` | `0xFC800000` + `0x02B00000`（43 MiB 声明） | `PlatformMemoryMapLib.c:35`、实机 `/proc/device-tree` |
| 面板 | 1904×3040@32bpp | 实机 `/sys/class/drm/*/modes` + `PcdsFixedAtBuild.dsc.inc` |
| 实际可安全写 | **仅前 ~448 KiB** | `PITFALLS #492`（整块填充会挂死 SoC） |
| `SCALE_FACTOR 3` 下一行文字 | 36 像素行 = 36×1904×4 = **274 176 B** | `FbConPutCharWithFactor` 的 `y += scale_factor` |
| ⇒ 可容纳行数 | **~1.6 行** | 448 KiB ÷ 274 KiB |

⇒ 「17 回话、下一发必崩」不是随机崩溃，是**我们自己的调试输出**越过了可写窗口。
另记第二个未单独判别的可疑点：每次换行的 `FbConFlush()` 对整块 22.08 MiB 做
`WriteBackInvalidateDataCacheRange`。

## 6. 新通道 `sbprobe=3`：只更新 `SbLastMark`，完全不碰屏

关键认识：标记**本来就有一条不碰屏的回传通道** —— `SbLastMark[]` 被 `CmdBoot` 的诊断模式
塞进 fastboot 响应（`diag st=%r last=[%a]`）。于是新增 mode 3：

```
sbprobe=0  帧缓冲 + NV 变量 + SbLastMark（旧默认）
sbprobe=1  帧缓冲 + SbLastMark
sbprobe=2  全静默
sbprobe=3  只更新 SbLastMark（不写帧缓冲、不写 NV 变量）
```

指令级核查（R7 构建）：`0x8464 csel`（≤3 才采用）→ `0x8468 str [SbProbeMode]`；
`SbVProbe` 内 `0x9f30 cmp w8,#0x1` + `0x9f34 b.hi`（模式 >1 就跳过 `SerialPortWrite`）。

效果：`sbstop=26 sbprobe=3` → `vs-26` 存活；**不崩的档只花 1–2 s、不用断电**。
