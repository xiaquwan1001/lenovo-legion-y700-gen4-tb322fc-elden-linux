## 显示根因（本轮定位到绑定点）

`/sys/kernel/debug/device_component/ae01000.display-controller`：

```
aggregate_device name                 status
ae01000.display-controller            not bound
device name          status
ae94000.dsi           not bound
ae96000.dsi           not bound
(unknown)             not registered
(unknown)             not registered
```

⇒ DPU 组件主控**永不 bind**（两个 `(unknown)` 组件从未注册）⇒ 没有 DRM 设备 ⇒ 只有背光。
两个 unknown 的来源 = DPU 输出端点的远端接口，其中 `af54000.displayport-controller` 在
`/sys/kernel/debug/devices_deferred` 里挂着：`aux_bridge: failed to acquire drm_bridge`，
同链 `pmic_glink.altmode.0`（`failed to acquire mode-switch for port 0`）、更早还有
`ucsi_glink ... PPM init failed, stop trying`。

其它同时失败的子系统（都指向 ADSP 侧/GPR 未就绪，非显示必需）：
`qcom-apm gprsvc:service:2:3: CMD timeout`、`ath12k: failed to start mhi: -110`、
`snd-sc8280xp: Parent card not yet available`、无 `/dev/fastrpc-adsp`（`fastrpc` 模块未加载）。

**已试（负结果）**：把 DT 的 `displayport-controller@af54000` 改 `disabled` 后重打
`out/min-restore-20261119/boot-nodp-test.img`（DTB 追加在 boot.img 偏移 85 659 648）
RAM 启动 ⇒ 设备回到 fastboot，未起。**不能算否证**：DTB 追加位置/尾部填充可能被 ABL 拒
（需按 `scripts/build-boot.sh` 的口径重打，而不是手工覆盖尾部）。

## 本轮顺带修好的两个坑

1. **USB-NCM 主机侧地址**：设备 gadget 起的是 192.168.7.1/24，主机侧必须先
   `ip addr add 192.168.7.3/24 dev enx021e5eede102`（设备重启后网卡重建 ⇒ 地址丢，需重加）。
2. **`/init` 在最小根里是必需件**：缺它时 systemd 仍能起（`/sbin/init`），但
   `respawn ttyGS0/ttyGS1`、usb-gadget、`usb0_dhcp`、`elden-init-trace.log` 全都没有
   ⇒ 症状与「内核坏了」完全一致。以后所有 minbase 档都必须在 stage 里装 `/init`。

## 今晚（收尾前）显示实验的记录 —— 全部负结果，但两条控制事实已定

1. **重打路径可信（强证据）**：用 `scripts/build-boot.sh` + 原 kernel（`build/daily/.../Image.gz`）+ **原 ramdisk**
   （从 `out/boot-elden-vk192.img` 抽出，sha `3282ae6c…`）+ **原 DTB**（从同一 img 抽出，sha `89c9336d…`）重打，
   得到 `out/boot-elden-test-ctrl.img` = **`bdf47f5f…`，与 `out/boot-elden-vk192.img` 逐字节相同**
   ⇒ 打包链没有隐藏差异，以后改 DTB 实验可以直接信重打件。
2. **两次 RAM 启动都没枚举 USB**：
   - `boot-nodp-test.img`（手工把尾部 DTB 换成 `mdss_dp0` disabled 的 DTB，**未改 header 的 `dtb_size`**）→ 落到 fastboot；
   - `boot-elden-test-nodp2.img`（`make dtbs` 正规重打，sha `39c63872…`，DTB 153 097 B，节点集与原件完全一致、只少了
     `dpu_intf0_out/remote-endpoint`）→ 上机后 **USB 完全不枚举**（无 gadget/无 fastboot）。
   ⇒ 两条都**不能当否证**（既没串口也没背光闪烁观察）；而且 `test-ctrl` 今晚没上机，所以「RAM 启动本身现在还能用」
   这件事也**未复核**——明早的第一发应当是 `test-ctrl`（零风险，能起就说明 RAM 路径好）而不是实验件。
3. **实验补丁已落盘**：`out/min-restore-20261119/dp-port2-experiment.patch`（20 行，就是 `&dpu_intf0_out { /delete-property/ remote-endpoint; };`
   + 理由注释）；`build/daily` 里的 DTS 改动已用备份 `cmp` 回滚（`build/*` 不进 git）。
4. **操作坑（两条，已写成脚本避坑）**：
   - 设备每次重启 USB-NCM 网卡都会重建 ⇒ 主机侧 `192.168.7.3/24` 随之消失；用 `sudo scripts/ncm-host-up.sh`（幂等，`--check` 只报告）。
   - `ssh` 会因设备重新生成 host key 报 `REMOTE HOST IDENTIFICATION HAS CHANGED`（minbase 每次重装都换 key）⇒
     `ssh-keygen -R 192.168.7.1` 或 `-o UserKnownHostsFile=/dev/null`。
