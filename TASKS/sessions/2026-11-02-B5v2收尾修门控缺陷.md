## 1. 缺陷（本轮唯一的“新发现”）

三条事实叠起来就是一次启动崩溃：

1. `msm_dsi_6g_v2_9_host_ops` 是 **SM8650 与 SM8750 共用**（两者都报 6G v2.9）；
2. v2 把 `.bonded_cmd_xfer` 加进这张共用表，manager 侧门控只写 `ops && ops->bonded_cmd_xfer`；
3. 钩子第一句就是 `bonded = msm_host->cfg_hnd->cfg->bonded` 后取字段，而 SM8650 的 `.bonded == NULL`。

⇒ 树内 `sm8650-ayaneo-pocket-s2`（`qcom,dual-dsi-mode` + `qcom,sync-dual-dsi` + `qcom,master-dsi`，
面板 `ayaneo,wt0630-2k`）任何面板 DCS 写都会走
`msm_dsi_manager_cmd_xfer` → `dsi_mgr_use_bonded_write` → `dsi_mgr_bonded_cmd_xfer` →
`dsi_bonded_xfer_prepare` → `dsi_cmd_error_prepare` → **NULL 解引用**。

**为什么 v1 没有**：v1 的门控是 `msm_dsim_glb.is_sm8750 && IS_BONDED_DSI()`（SoC 特判）。v2 按
reviewer 意见去掉 `is_sm8750`、改成「问 per-SoC 数据」——方向正确，但只把数据搬进 cfg 表，
没有把它接到判断上，于是把 v1 那道丑而有效的门一起删了。已记为 `PITFALLS #489`（可推广：
「钩子在不在」只在「一表一 SoC」时才等价于「本 SoC 支持」）。

**修法**：`ops` 存在 **∧** `msm_dsi_host_get_bonded_cfg(host) != NULL`（新增 accessor）。
没有抽第二份 v2.9 ops 表 —— 那要为表达一个 bit 复制整张表；理由写进 3/4 的 commit message 与 cover。

## 2. 方案 A（补 DTS 当使用者）为什么不做

`reports/m6-b5-v2-parent-review-20261102.md` §1 推荐的 A = 把 P4 的 bonded DSI DTS 合成一枚追加。
实测不可行：

- v7.4-rc1 里 `qcom,dual-dsi-mode` 的板子共 **6 块**（`sm8650-ayaneo-pocket-s2`、
  `sm8250-xiaomi-elish-common`、`sdm845-db845c`、`sdm845-mtp`、`sm8150-hdk`、`qrb5165-rb5`），
  **没有一块是 SM8750**，也没有一块需要 command-mode bonded（本路径只对 command 模式有意义）；
- elden 的薄板级 DTS 是**整块新产品**（面板 + 供电 + 触控全套），塞进一个驱动系列不是选项；
- 往既有板上加 `qcom,master-dsi` 属伪造型号，不做。

⇒ 落地为 B：cover 如实声明「使用者板级件另发」，并把 data-gate 缺陷讲成正面证据
（证明这段代码在树内**确实可达**，只是不该被误入）。发送状态 = **不发（保留意见）**，
理由是本系列自己设的发布条件（树内要有需要它的使用者）仍未满足。
