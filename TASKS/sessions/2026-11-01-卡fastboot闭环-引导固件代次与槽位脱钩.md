## 结论（6 条）

1. **根因 = 引导固件代次与活动槽脱钩**，非 AVB：本机**双代引导固件并存**
   —— `*_a` + **LUN1** = 259 原厂（`uefi_a`/`abl_a`/`xbl_a`/`xbl_config_a` 与官方包逐字节相同，
   UEFI `6.0.260611` Jun 11 2026），`*_b` + **LUN2** = 上一版（`uefi_b` 差 550 846 B，
   UEFI `6.0.260514` May 14 2026）。ABL **按活动槽选 boot LUN**，故槽位与 LUN 必须配对。
2. **卡死那次是 `slot=b` 却跑在 `UFS Boot LUN: 1`**：`logfs` seg0 = `POST Time [2828] OS Loader`
   → 1 行 `VB: RWDeviceState: Succeed using rpmb!` → `Start EBS [7845]`，**无 `Booting from slot`**、
   无 `KeyPress:/BootReason:/Fastboot=/SilentBoot` 段，总 7.8 s（正常 13.3 s）。
3. **修复 = 一条命令**，双向复现：`--set-active=a` → 进 Android；`--set-active=b` → 回 Linux。
4. **旧候选全部否定**：`vbmeta_a` = 官方包逐字节同（AVB 无关；b 槽公钥拒绝在能正常启动的日志里也存在）；
   `misc` 全 0；`devinfo` = `ANDROID-BOOT!` + 三个正常标志位（差点被误清）；主备 GPT header+entry CRC 全 OK。
5. **`logfs` 判读纠错**：10 段里只有 **seg0** 是本机的；seg1–9 的 ECID 属另一台 12+256 机器
   且与官方包 `logfs_ufs_8mb.bin` 9/10 段逐字节相同（工厂模板）⇒ 11-01 事故事故报告 §4 整段作废。
6. 附带修好 `check-doctor` 的既有 FAIL：`out/` 三个「内核段不可读」镜像实测**均可正常解压**
   （UTS `…vk172`），身份表重生成后 **FAIL=0 / WARN=4**。

## 教训

- **「不可恢复」结论要留余地**：#483 断言「断电/刷回/切槽全无效」，8 小时后被一条 `--set-active` 推翻。
- **备份不足 ≠ 原因在备份之外**：#483 把「刷回原件无效」解释成「不可见持久状态」，实际只是 LUN + 槽位属性两个**可读**量。
- **别按第一直觉动手**：本轮原计划「清 `devinfo` 的 `u.1.1.1` 三字节」，核对布局后发现那正是三个正常标志位。
- **改槽位就是改 LUN**：跨代次切槽可能再触发同类现象；动槽位前先抓 `logfs` 基线（只看 seg0）。
