## 2. 实证轮（PASS）

序列：`fastboot boot out/boot-elden-vk134.img` → `echo 1 > /sys/kernel/kexec_diag/kexec_diag` → `kexec -s -l Image --initrd=标记包 --command-line="… panic=15 nokaslr kexec_dbg=1"` → `kexec -e`。

**取证（磁盘文件，绕开串口丢包）**：目标内核在 `/dev/sda17` 写了 `/var/tmp/kexec-marker.txt`（跑前已 `rm` 并确认不存在）：

```
alive uptime=131.59 927.35 kernel=7.3.0-rc7-debug-vk127-00002-g24223e44ad80-dirty
ts=1970-01-04T15:21:35Z
cmdline=console=ttyGS0,115200 console=tty0 loglevel=7 panic=15 nokaslr kexec_dbg=1
```

- 文件里的 `cmdline` = **我给 kexec 的目标 cmdline**（含 `nokaslr`、`kexec_dbg=1`）
- 回到的 live 内核：`nokaslr` 计数 **0**、`kexec_diag` 计数 **0** ⇒ **回来的不是目标**（是 ABL 起的 boot_b）
- 串口新段仅剩 `psci: probing for conduit method from DT.`（gadget 太晚，丢包照旧）

⇒ **kexec 交接 + 目标执行 init 代码成立**。record：`reports/trials/20261022T013253Z-kexec-c9-marker-survived-vk134.json`（verdict PASS）。

**关键数字（改写了历史叙事）**：目标 `uptime=131.59 s` 才写出标记。此前几轮 slim 实验按 20 s 窗口判「挂死」，实际是**目标还活着、在等 `/dev/sda17` 枚举**。slim initramfs 无 udev，`sleep 0.1` 在 busybox 下精度差，UFS probe 又慢 ⇒ 观测窗口必须 ≥150 s。

## 3. 反证轮（FAIL，代价 = 手动按键）

同一晚想顺带验「跳到磁盘根」，但**漏了重新打开 mask=1**（`kexec_diag` 每次开机归零），于是走了完整 `device_shutdown()`。串口实证：

```
adreno 3d00000.gpu: Timeout waiting for GPU to suspend
WARNING: drivers/gpu/drm/msm/adreno/adreno_device.c:293 at adreno_shutdown+0x2c/0x48
  adreno_shutdown → platform_shutdown → device_shutdown
  → kernel_restart_prepare → kernel_kexec → __do_sys_reboot
sd 0:0:0:4: [sde] Synchronizing SCSI cache
===== serial closed /dev/ttyACM0 =====
```

之后设备**整体掉出 USB**（无 fastboot / 无 ttyACM / 无 gadget），必须人工按键。

⇒ 两条结论：
1. **mask=1 是这台机上 kexec 的必要条件**（不是优化项）—— 与 `PITFALLS` #154 同向，且把「多触发叠加」收窄出一个**具体硬挂点：`adreno_shutdown` 的 GPU suspend 超时**。
2. 「跑 kexec 前先确认 `cat /sys/kernel/kexec_diag/kexec_diag` = 1」应作为**硬门前置**（`kexec_diag` 每次开机归零，跨轮不继承）。

record：`reports/trials/20261022T014407Z-kexec-c10-diskroot-nomask-hang-vk134.json`（verdict FAIL）。

## 4. 仍未解

- **目标能否 switch_root 到磁盘根并起用户态服务**（本轮只证到「目标执行 init 代码」，用的是纯 RAM cmdline；磁盘根那条本轮因漏 mask 未测成）。
- 目标 uptime 131 s 的组成（UFS probe 慢 vs busybox sleep 精度）未分离；若要缩短，需在目标侧用 `/proc/uptime` 打点而非 `sleep` 计数。

## 5. 续轮（13:33–13:55，四轮对照）

| 轮 | initrd | 目标 cmdline | 结果 | 证据 |
|---|---|---|---|---|
| C9 | slim 1 MB 标记包 | `console/loglevel/nokaslr/kexec_dbg` | **PASS**：目标写标记文件，uptime 131.59 s | 文件内容含目标 cmdline |
| C10 | slim 标记包 | 同上但**漏开 mask=1** | FAIL：`adreno_shutdown` GPU suspend 超时 → 整机掉出 USB | 串口 WARNING + 调用栈 |
| C11 | 完整 64 MB | 完整磁盘根 cmdline | FAIL：32 s 回 boot_b | `kexec_diag=0`、bootargs 无 nokaslr |
| C12 | slim 1 MB 标记包 | 完整磁盘根 cmdline | FAIL（**但走得更远**）：目标 switch_root 成功、跑到 `udevd`、`msm_dsi` bonded timing 正常，死于 `panel-novatek-nt36536` init `-110/-5` + `drm vblank timeout` WARNING | 串口新段有 `udevd[940]: starting eudev-3.2.14`（slim initramfs **没有** udev ⇒ 必为磁盘根） |
| C13 | slim 1 MB 标记包 | C9 的 cmdline **只加** `elden_root=LABEL=linux17` | FAIL：23 s 回 boot_b，无 marker、无 udevd | 串口新段只有残片 |

**判读**：`C9 活 / C12 活到用户态但死于显示栈 / C13 早死` 三态并存 ⇒ **不是 initrd 大小问题，也不是单一 cmdline 变量能解释**；
最可能的机制是**目标早期的内存/时序非确定性**（C9 与 C13 差一个 `elden_root=` 却结果相反）。真正阻塞 = **串口在目标早期丢 ~65 KB**，使早死轮次完全不可见。

**C12 的正面价值**：这是本项目第一次证明 **kexec 能把内核跳到磁盘根并跑起用户态**（`udevd` 是磁盘根才有的）。它死于 Q28 同一个 bonded DSI 面板初始化，与 kexec 本身无关。

## 6. 结论与下一步

- **Q11 可判为已解**：kexec 交接、目标执行 init、目标 switch_root 到磁盘根**三项都有直接证据**。
- **不可作为日常快环**：目标早期死因不可见（串口丢 65 KB），且失败会落到 Q28 显示栈；收益（省 2–3 min 换内核）不抵调试成本。
- **要收口只剩一条路**：给目标专用**第二个 ramoops 节点**（`reports/kexec-plan-20261021.md` §D3，DTS ~8 行）——让 panic 落 DRAM 而非串口。本轮未做（避免引入新变量）。

## 7. 可见性攻坚（ramoops）：根因定位 + 一条硬边界

目标：让「kexec 目标 panic」可见。结论：**根因找到了，但这条路需要写 boot 槽，不划算**。

| 实验 | 做法 | 结果 |
|---|---|---|
| C14 | 当前内核 `echo c > sysrq-trigger` | `boot_id` 变了（确认真重启）但 `/sys/fs/pstore` **全空** |
| 定位 | 读 `fs/pstore/ram.c` / `ram_core.c` | DTS 只有 `console-size`/`pmsg-size`，**缺 `record-size`** ⇒ 内核根本没有独立的 panic/oops 持久区，唯一出口是 console 环形缓冲，被下一次启动的 printk 立刻覆盖 |
| C15 | DTS 扩到 8 MiB + `record-size=0x200000` | `dmesg` 首次出现 `pstore: Using crash dump compression: deflate` + `ramoops: using 0x800000` ⇒ **record 区生效** |
| C15b | `kernel.panic=0` 让 panic 停住 | **方法错误**：设备卡死在 panic 里，USB 掉出、串口关闭、SSH/fastboot 全不可达，每轮都要人工按键；且 panic 文本仍没进 ramoops |
| C16 | vk135（8 MiB）+ `panic=20` 暖复位 | panic 栈**第一次被串口完整抓到**（`Kernel panic - not syncing: sysrq triggered crash` + `dump_stack/vpanic/panic/sysrq_handle_crash`），20 s 自恢复无需按键。**但**恢复后 `ramoops: using 0x400000` = 4 MiB ⇒ 自复位回 boot_b，而 boot_b 的 DTB 仍是旧的 |

**硬边界（`ram_core.c:persistent_ram_post_init`）**：ramoops 用 `sig`（含 zone type）校验旧内容，签名不匹配即 `zap`。
⇒ **只有「恢复启动的那个内核」也带 `record-size`，panic 内容才可回收**。

而自复位永远走 ABL → boot_b（旧 DTB），所以唯一出路 = **把新 DTB 写进 boot_b**（`fastboot flash boot_b`，`/dev/sde45`）。

**裁决：不做**。理由：
1. 收益已知 —— C12 已实证目标死于 Q28 bonded DSI 面板初始化（`panel-novatek-nt36536` init `-110/-5`），栈能告诉我们的信息增量很小。
2. 代价不对等 —— 写 boot 槽是「会让设备不可用」的操作，为一个已知原因的栈承担变砖风险不划算。
3. 这个 DTS 修复本身是**正确的主线修复**（不是 kexec 专用），应该并进 M2 上游化资产，而不是为 kexec 打补丁。
