# 2026-10-27 · UEFI 线：原定对照实验作废 + 两条新事实

- **日期**：2026-10-27
- **pi 会话 id**：`$PI_SESSION_ID`
- **主题**：用户问「UEFI 启动的任务能做吗」，先复核再执行「用 `Droid-VM/edk2-gunyah` 做对照件」的提案。
- **结论**：
  1. **提案作废（自我更正）**：`edk2-gunyah` 是 **crosvm guest 固件**（`PcdFdBaseAddress=0x80000000`、`VirtioMmioDeviceLib`、模拟 NS16550、无
     UFS/SCM/PMIC/NPA），README 的「Tested tb322fc」= 在该机 Android 宿主上起 VM 可用，**不是裸机载荷** ⇒ 不能 `fastboot boot`，
     无法把「打包/交棒」与「Mu 平台支持」分开；照做只会得到假阴性。
  2. **`0xFF300000` 是 ABL 眼里的可用 RAM**：取到本机 ABL 日志，`Final RAM Partitions` 有 `Add Base 0xFF300000 / Length 0x500000`
     （5 MiB ≥ `UEFI_SIZE` 4 MiB），且 `sm8750.json` 与 `sm8850.json` 的 `bootshim.UEFI_BASE` 相同 ⇒ 「拷贝地址不可用」候选权重下降。
  3. **ABL 日志通道可得但救不了失败那一次**：`/dev/sde68`(`logfs`) 的 `UEFILOG1.TXT` 覆盖 PBL→fastboot→cmdline→RAM 表→`Start EBS`，
     但**每次启动重写**；交棒失败会回落 stock（= 新启动）⇒ 覆盖。⇒ 只能取证「ABL 侧真值」，不能取证「载荷死在哪」。
  4. **真实门槛 = 早期可见性**：`USE_UART_*=0`、无 `UsbSerial*Dxe`、屏幕输出依赖 GOP（当前正死在 DXE 之前）⇒ 串口（硬件）或上游
     `mu_wide_platforms#12` 给层级答案之前，新镜像实验只能是黑箱二值。**维持搁置，不重启**（与 10-21 / 10-24 裁决一致）。
