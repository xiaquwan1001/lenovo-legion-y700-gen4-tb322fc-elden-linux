# #481 · UEFI「交棒（HANDOFF）」**不等于**载荷被执行 —— 半年前唯一真执行证据仍是 10-05 屏上出字

- 日期：2026-11-01（上机对照，零写盘；详见 `reports/uefi-ddr-blackbox-20261101.md` §7）

## 新判据：`fastboot boot` 之后其实有**三种**终态，历史把 ①③ 混成了「交棒」

| 终态 | 主机侧看到 | 真实含义 |
|---|---|---|
| ① **拒**（旧称 NOJUMP） | `Booting OKAY [10.1 s]`，fastboot 仍应答、bus/device 不变 | ABL 拒绝该镜像，继续按槽位启动 |
| ② **复位回落**（旧称 HANDOFF） | 0.05 s 内 `usb_read failed`，设备从 USB 消失，**~20 s 后**以 Android gadget（`17ef:7f3d`）重新出现 | ABL 拆 USB → 校验/加载失败 → **复位** → 启槽位。**载荷没跑** |
| ③ **挂 logo**（新发现，旧口径没有这一类） | 同样 0.05 s 内 `usb_read failed` + USB 消失，但**再也不回来**，屏上卡联想 logo，`lsusb` 空 | ABL 自己**挂死**在加载/解压里，需物理断电 |

## 决定性对照（`scripts/uefi-usb-gap.py`，50 ms 轮询 USB）

| 载荷 | 体积 | USB 黑屏间隙 |
|---|---|---|
| 对照：cachefix shim + Mu FD（不写任何 DDR） | 2.4 MB | **20.53 s / 20.05 s** |
| 自旋：`b .` 死循环（只有看门狗能打断） | 8 KB | **20.20 s / 19.99 s** |

两者在噪声内完全相同 ⇒ 若载荷真执行了 `b .`，看门狗那一截（#480 目视 1–2 s）必须叠上去；没有 ⇒ **载荷未执行**。

旁证：三块「Android 不踩」的 carveout（`dsm-1`/`dsm-2`/`video`，实测存活 77–88%）在真 HANDOFF 之后**仍全 0**；
FB 上从未出现过任何色条；`fastboot boot` 的接受与否取决于**另一个槽是否 bootable**（`qbootctl -u a` 后 3/3 被拒，
`-m a` 恢复后立刻交棒）⇒ ABL 在这条路径上确实在校验，不是盲跳。

## 结论与用法

- **判据改写**：`usb_read failed` 只说明「ABL 接手了」，**不能**再当作「载荷被执行」。要判执行，必须另有独立通道
  （DDR 标记 / 串口 / EUD-SWD / 屏上输出），并且**该通道的空结果要能与「没跑」区分开**（本项目的 DDR 标记做到了）。
- **11-01「干净 header 下 7/7 载荷被执行」作废**（那 7 发只是被 ABL 接手；且同镜像同 header 三次结果不同 ⇒ 判定还有非确定性）。
- **历史唯一真执行证据** = 2026-10-05 **v3 header + NoSb + SCALE_FACTOR 3** 那批屏上出字（`reports/uefi-text-console-archaeology-plan-20261030.md` §1）⇒ 要复现「载荷真的跑起来」，应从那条配方入手，而不是继续调 v0 header。
- 第 ③ 类终态（挂 logo）是**新失败模式**：82 MB 的 Linux 镜像走 `fastboot boot` 时出现，退回必须物理断电。
