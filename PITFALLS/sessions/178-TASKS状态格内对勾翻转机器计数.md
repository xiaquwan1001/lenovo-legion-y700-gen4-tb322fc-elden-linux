## #548 `TASKS` §1 状态格里混入 `✅` ⇒ 机器完成度静默 +1（脚本按 emoji 优先级取，不看位置）

### 现象

本轮把 UEFI 那条（G1-29）状态格从「🟡 进行中…当前口径只读 11-06 崩溃块」改成
「🟡 进行中（2026-11-07：**✅ 间接引导已打通** …）」。人看着仍然是「进行中」，
但 `scripts/check-progress-counts.sh` 立刻从 **G1 34/36** 变成 **35/36**（✅31→32、🟡2→1），
与 `TASKS` §0 手写的 `34/36` 与「未完成 2 项」直接打架；`check-doctor` 的
`STALECOUNT` 门不管这条（它只核「N 节」这类显式计数），所以**不跑计数脚本就发现不了**。

### 根因

`check-progress-counts.sh` 的取标记是**按 emoji 优先级**、不是按出现位置：

```python
EMOJI = ['✅', '🟢', '🎯', '🟡', '🆕', '⬜', '❌', '⛔']   # 顺序即优先级
st = next((e for e in EMOJI if e in (cells[2] ...)), None) or next((e for e in EMOJI if e in first), None)
```

所以状态格（第 3 列）里**任何位置**出现 ✅ 都会胜出，哪怕打头的是 🟡。
口径本身是对的（「✅ 完成 / 🟡 部分」），坑在**写作习惯**：把 ✅ 当「好消息」加重语气。

### 规则

- **`TASKS` §1/§2 的状态格只用文字表达「已做到哪一步」**（「已打通」「已投」「静态 PASS」），
   **不要用 ✅/🟢/🎯 当语气符号**；需要打勾的地方放到备证列或正文。
- 改完 §1 必须立刻跑 `bash scripts/check-progress-counts.sh`，与 `TASKS` §0 的
   `完成 N / 在范围 M` **逐字对比**；两者不一致就是错，不是「脚本口径问题」。
- 同族教训：§0 的数字**不许手推**（2026-11-02 就为此写了 3.5 KB 推导过程），机器算的是真值。

### 成本

发现靠运气（我改了 §1、又在收尾时顺手跑了一次计数）；若当时直接 `git commit`，
会留下「§0 说 34/36、脚本说 35/36」的静默漂移，下一轮整理又会把它当新问题重查一遍。

### #548b（同族，同一轮踩到）`PITFALLS/sessions/*.md` 里以 `N. **粗体**` 开头的编号列表会被当成 `#N` 的定义

`scripts/doctor/s07-08-docs.py` 的「定义」识别除 `## #NNN` 标题外，还认行首 `NNN. ` + 粗体：

```python
m = re.match(r'^(\d{1,3})\.\s+\*\*', line)   # 非标题行也算定义
```

本轮在 `#548` 正文里写了 `1. **状态格只用文字…**`、`2.`、`3.` ⇒ doctor 判
`PITFALLS 正文 #1/#2/#3 被多处定义（01-引导fastboot重启交接.md | 178-…）`，**FAIL=1**。
对策：PITFALLS 正文里的条目列表一律用 `-` 无序列表（或全角 `1）`），**不要**用 `1. **粗体**`。
