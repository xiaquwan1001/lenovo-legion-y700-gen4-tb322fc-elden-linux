## 五十四、构建机「静默文件损坏」与坏对象（2026-10-19/20 实受；**2026-10-20 晚归因更正**）

> 触发场景：`q24`/`n5b` 需要重建 `out/boot-elden-vk64.img`，内核编译反复失败。
> 起初判为「交叉编译器坏了」，实为**两个独立问题叠加**。
> ★★ **2026-10-20 晚更正：错的不在磁盘，而在内核页缓存 ⇒ 根因 = 内存侧位翻转。**
> 判据、证据与处置见 `reports/host-memory-bitflip-rootcause-20261020.md`；
> 本节 #282/#284 的「现象」成立但「归因/处置」已改（下面逐条标注）。

282. **★「编译随机 ICE/段错误」在这台机器上默认怀疑 **内存位翻转污染了读到的字节**，不是源码、不是编译器版本、也不是磁盘。**
    - 现象序列（同一晚）：
      1. `aarch64-linux-gnu-gcc -O2 -c hello.c` → `internal compiler error: in scev_initialize, at tree-scalar-evolution.cc:3017`（**连 hello 都编不过**）；
      2. 重装 `gcc-15-aarch64-linux-gnu` 包后 hello 恢复，但内核树里仍有 2~4 个文件 ICE/段错误；
      3. 之后 ld 报 `bad reloc symbol index (0x827 >= 0x60) ... in section '.debug_info'` / `member ... in archive is not an object`，**每次换一个文件**。
    - 当初步的证据：逐文件比对 `sha1("blob <len>\0"+内容)` 与 git index 的 blob sha —— vk83-tree 报出 4 个 tracked 文件被**单字符改写**、大小与 mtime 都不变：
      `mmhub_9_4_1_offset.h`（多了一个反引号）、`nbio_7_11_0_sh_mask.h`、`bnx2x_reg.h`（`MSTAT_REG` → `M[TAT_REG`）、`trace_probe.c`；
      更早有 `nfstrace.h`（`__field(int, error)` → `__field(int( error)`）与 `serial_bcm63xx.h`（`UART_FIFO` → `IUART_FIFO`）。
    - ★★ **2026-10-20 晚定性：上面 sha1 用的是「普通读」，它读的是页缓存。** 用 `dd iflag=direct`（绕页缓存）
      复核同一批文件 ⇒ **磁盘字节与 git index 逐字相同**；`posix_fadvise(DONTNEED)` 丢页缓存后重读立刻恢复。
      实测 4/4 文件 `disk == git` 而 `buffered != git`。⇒ **改写只发生在内存里**。
      连编译器本体都被命中：`/usr/libexec/gcc-cross/aarch64-linux-gnu/15/cc1` 的页缓存 md5 ≠ `dpkg` md5sums，
      而磁盘 md5 == `dpkg` md5sums ⇒ 这正好解释「重装 gcc 后好一阵又坏」（重装只是重新填了页缓存）。
    - ⇒ 判据改成**三读法**：`scripts/detect-memory-corruption.py <path|--tree>`
      （buffered / 丢缓存再 buffered / `O_DIRECT`；三者不一致且后两者相同 ⇒ MEMORY）。
      全树 96 k 文件 ≈ 9 s；单发阴性不算通过（30 轮实测 17 轮命中、每轮不同文件）。
    - ⇒ **禁止用「重写文件」当修复**：重写同样经过内存，可能写回错字节，还会覆盖掉本来正确的磁盘副本。
      正确动作 = 丢页缓存（工具已做），然后修硬件（BIOS 关 XMP/降频/单条排查/memtest86+；长期换 ECC）。
      本机 `EDAC ie31200: No ECC support`、`/sys/devices/system/edac/mc/` 无 `mc0` ⇒ **硬件不会报告 CE/UE**。
    - ⇒ `verify-tree-integrity.py` 已改：输出分 `CORRUPT`（绕缓存仍错 = 磁盘真坏）与 `CACHE`（页缓存翻位，**不算失败**）；
      构建脚本前后两处门改调 `scripts/kbuild-sanity.sh`（树完整性 + 多轮污染率 + 工具链探针）。
      参见 `reports/host-memory-bitflip-rootcause-20261020.md`、`reports/host-file-corruption-20261020.md`。

283. **★`ld` 报「bad reloc symbol index」时，被告的那个 `.o` 是坏的，但它**不代表**源码/编译器有问题 —— 删掉串行重编即可，且必须**逐个验证**才知道收敛没有。**
    - 手段：`aarch64-linux-gnu-ld -r -o /tmp/x.o <候选.o>`（对 aarch64 对象做局部链接）；报错即坏。
    - 全树批量检查要**排除 host 工具对象**：`scripts/` 下的 `.o` 是 x86-64（`Relocations in generic ELF (EM: 62)` 是误报），只校验 `readelf -h` 为 AArch64 的对象。
    - 破坏是**持续产生**的：一轮修好后下一轮链接又冒出新的坏对象（`libps2.o`）⇒ 必须按「链接 → 定位 → 删 → 串行重编 → 再链接」迭代到收敛，一次通过不代表干净。

284. **★`gcc -O0` 能过而 `-O≥1` 崩，且换同版本重装后行为改变 ⇒ 先查**读到的字节可信吗**，再查包完整性/输入文件，最后才怀疑源码。**
    - 判据顺序（省时间）：① `-O2` 编 hello（3 行）→ 崩则是工具链**或内存**；② `scripts/detect-memory-corruption.py <cc1>` 三读法判是不是页缓存翻位（**先做这步**，比 `dpkg -V` 可靠：`dpkg -V` 自己也会被翻位误导）；③ `dpkg -V <包>` / 包目录 mtime vs 上次成功构建时间；④ 换 `-O0`、`-fno-ipa-*`、`-fno-tree-*` 是否改变 —— 本例全部无效，说明不是优化选项交互；⑤ 三读法查源码树（见 #282）。
    - 反例警示：不要把「重装包后 hello 好了」当成根因确认 —— 本例重装只重新填了 `cc1` 的页缓存（`PITFALLS` #282）。

285. **★`m1-73` 的三处 `M`（`sm8750.dtsi` fastrpc `qcom,non-secure-domain`、`gc08a8.c`/`s5kjns.c` AGC 增益修）是**有意的未提交修改**，不是损坏。**
