在此要补反面：**单次读错也不代表文件坏**。

## 判据命令（装进收尾巡检）

```bash
# 基线复算（正确读法；O_DIRECT 绕过页缓存）
awk -F'\t' 'NR>3{print $1"  "$7}' versions/out-images-sha256-20261105.tsv \
  | while read -r want path; do
      got=$(dd if="$path" iflag=direct bs=1M status=none | sha256sum | cut -d' ' -f1)
      [ "$got" = "$want" ] || echo "MISMATCH $path  want=$want got=$got"
    done
# 单件分诊：普通读与直读各算一次，二者不同 = 缓存/内存问题，不是文件问题
sha256sum <file>; dd if=<file> iflag=direct bs=1M status=none | sha256sum
```

判读表：

| 普通读 | 直读 | 结论 |
|---|---|---|
| 一致 | 与基线一致 | 文件好 |
| 不一致 | 与基线一致 | **页缓存/内存位翻转**（文件好，机器有病） |
| 一致 | 与基线不一致 | 磁盘内容真被改过（按 `#512` 流程修复） |
| 两次普通读互相不一致 | — | 内存/缓存层不稳定，同上 |

## 危险动作（不要再发）

- **`echo 3 > /proc/sys/vm/drop_caches`**：2026-11-05 15:36 实测 → 主机冻结、自动重启、会话上下文丢失。
  要「清缓存」就去重启，或用 `O_DIRECT` 读，别用 drop_caches。
- 与之同因的推论：**任何「把整个文件读进内存再校验」的一步到位脚本**都可能被污染；
  大文件校验优先流式 + 直读，避免二次读缓存。

## 为什么这一轮要单独立条（不是上一条的重复）

`#512` 讲的是**持久层**（git pack、文件名）损坏，修复对象是磁盘数据；本条讲的是**读路径**
（页缓存/内存）不可信 —— 它改变的是**校验方法学**：前一轮完整性巡检「129 镜像 0 真损坏」的结论
仍然成立（磁盘层），但那次结论是**在可能被污染的缓存上**得出的，必须在冷启动/直读下复核。
本轮已用 `O_DIRECT` 全量复核：129/129 与基线一致 ⇒ 磁盘侧依然「真损坏 0」。
