## #517 「只测可达」的等待 = 假成功

`cycle.sh --wait` / `flash-b.sh --wait` / `kexec-boot.sh` 旧判据都是 `ping` 或
`ssh 'true'` 通就算「新系统起来了」。实测问题：复位/`kexec -e` 命令发出后的**头几百毫秒内
旧系统仍在正常应答**，于是脚本立刻打印 `up (~0s)`、继续做后续判据（读版本、置槽标志），
而新内核这一轮可能根本没起来 —— 后面所有结论都建立在一台「没重启的机器」上。

对策（`scripts/lib-wait.sh`）：
- `wait_reboot`：**先拍 `boot_id`**，之后只认它**变了**（`wait_boot_capture` + `wa_boot_changed`）；
- `wait_fresh_boot`：拿不到指纹（从 fastboot 重启、切槽恢复）时，用 `uptime < 上限` 证明
  这是**这一次**开机；
- 两者都失败才降级为「可达性判定」，并**显式告警**「勿据此判『新内核已跑』」。
自检里有一条专门钉这个：boot_id 未变期间必须不返回。

## #518 探针串里的 `$( )` 用双引号 ⇒ 在主机展开

`lib-boot-ready.sh` 改成「一条远端命令取多个状态」时，探针串写成
`probe="echo up=$(cut -d. -f1 /proc/uptime)"` —— 双引号让 `$( )` 在**本机**就地执行，
远端收到的是常量 `up=1769`（主机 uptime）。于是 `BOOT_READY_MIN_UPTIME=1200` 的门在
uptime=600 的设备上**静默放行**：判据失效但输出正常，最难发现的一类。

对策：远端要执行的部分一律**单引号**拼接（`probe='echo up=$(cut ...); '`），
并在 `scripts/test-lib-wait.sh` 里用假 `ssh`（把远端命令在本机 `bash -c` 执行、
`/proc/uptime` 重定向到控制文件）钉住「uptime=600 必须拒绝」。

## #519 工具缓存放在仓库根 = 撞 §14 布局门

`vk-identity.py` / `check-modular-config.sh` 第一版把缓存写到 `$ROOT/.cache/`，
`scripts/check-layout.sh`（§14）立刻把 `.cache` 判成「顶层条目未登记」⇒ **工具自己把门禁弄红**，
而且清理时还会被误当成工作区目录。

对策：缓存默认落 `${XDG_CACHE_HOME:-~/.cache}/elden-doctor/<root 路径哈希>/`
（每棵树一份，lane/worktree 不串；可再生产物跟机器走、不跟 git 走）。
判据：任何新增根目录条目都必须先进 `versions/layout.tsv`，所以**工具别往根目录写东西**。
