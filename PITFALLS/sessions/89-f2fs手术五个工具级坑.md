# 89 · f2fs 路线 A 手术的五个工具级坑（#400–#405）

**日期**：2026-10-25 · **pi 会话 id**：宿主会话 · **主题**：ext4→f2fs 并存在机手术时，**每一条都让「看起来正确的脚本」静默走错**
**证据**：`scripts/f2fs-migrate.sh`（本轮修完的版本）、`TASKS/sessions/2026-10-25-f2fs路线A落地.md`、设备 `/sys/fs/ext4/`、`/var/log/elden-serial/ttyACM0.log`

> 共同点：失败点**全在 ramdisk（RAM root）侧**。宿主机上的 dry-run/静态检查一条都发现不了，
> 因为 ramdisk 是 Ubuntu-busybox 拼的最小系统：`tar`/`dd` 都是 busybox、没有 `python3`、没有 `/dev/stdin`。
> **教训：凡是「在 RAM root 里跑的脚本」，工具能力必须先实测（`--version` / 真跑一次），不能按主机假设写。**

## #400 RAM root 的 `tar` 是 busybox ⇒ `--xattrs --acls` 不受支持，会静默丢 capability/ACL

RAM root 的 `bin/tar -> busybox`（1.37.0），`--xattrs` 直接报未知选项（有 `set -e` 才会停；
写成 `tar … || true` 就是**静默降级**，rootfs 的 `security.capability`/ACL 全丢，`ping`/`setcap` 类工具事后才坏）。

**正解**：从 **ext4 侧取 Alpine 的 GNU tar（musl）+ `libacl.so.1`**，用 ramdisk 自带的 musl loader 跑：

```sh
mount -t ext4 /dev/sda17 /mnt/ro            # 见 #402：ro 可能挂不上，退 rw
cp /mnt/ro/bin/tar /tmp/e2tools/tar
cp -L /mnt/ro/usr/lib/libacl.so.1 /tmp/e2tools/lib/
umount /mnt/ro
printf '#!/bin/sh\nexec /lib/ld-musl-aarch64.so.1 --library-path /tmp/e2tools/lib /tmp/e2tools/tar "$@"\n' > /tmp/e2tools/gtar
chmod +x /tmp/e2tools/gtar && /tmp/e2tools/gtar --version   # 必须打印 GNU tar 1.35
```

判据：`/bin/ld-musl-aarch64.so.1` 在 ramdisk 里（apk 用的那份），`ldd /mnt/ro/bin/tar` 只依赖 `libacl` + musl。
`resize2fs/e2fsck/dumpe2fs` 同法取（ramdisk 里只有 `mkfs.f2fs/fsck.f2fs/partprobe`）。

## #401 「两股 tar 流 sha 相等」是**错判据**，`tar --compare` 才是

同一份数据两边各生成一次 `tar --xattrs --acls --sort=name -cf - .` 再比 `sha256`，实测**不相等**，
但 `tar -d`（compare：逐成员 size/mtime/mode/uid/gid + 内容 + xattr/ACL）**零差异**。
归档头里有 `.` 目录项、设备号、块化补齐等噪声，流 sha 不是内容指纹。

**正解**：`gtar … -cf - . | gtar --xattrs --acls -C /mnt/new -df -`，输出行数必须为 0。
（顺带：socket 文件 tar 两侧都跳过，所以「old files / new files」差值 = socket 个数，属正常，不是丢文件。）

## #402 内核拒绝 `-o ro` 挂一个"上次 rw 挂过/留痕"的 ext4（`would change RO state`），随后整盘 `dd` EBUSY

ramdisk 启动时会把 `linux17` **自动 rw 挂到 `/mnt/dbg`**（dmesg 捕获钩子）。此后：
`umount` 看似成功、`/proc/mounts` 也空了，但 **`/sys/fs/ext4/sda17` 还在** ⇒ 超级块没释放 ⇒
① `mount -o ro` 报 `Can't mount, would change RO state` 并 EBUSY；② `e2fsck` 报 `/dev/sda17 is in use`；
③ 往整盘 `/dev/sda` 写 GPT 也 EBUSY。

真凶是 `/init` 里的 `exec 9>/mnt/dbg/…/m1-73-dmesg.txt`：**fd 9 被 init 的后代继承**，
`ls -l /proc/<pid>/fd` 里显示成 `/root/m1-73-dmesg.txt`（detach 后路径以被卸挂载点为根），
所以按 `/mnt/dbg/*` 匹配**一个都抓不到**。

**正解**（已进脚本 step 1b）：匹配 `*m1-73-dmesg*` 且 **父进程 = init** 才 kill（避免把自己的 ssh shell 也杀了，
见技能 `pkill-self-match`）→ 再 `umount` → 轮询等 `/sys/fs/ext4/<dev>` 消失，不消失就报错退出。

## #403 busybox `dd` 不认 `oflag=direct`，ramdisk 里也没有 `/dev/stdin`

`dd if=/dev/stdin … oflag=direct` 在 ramdisk 上必失败（`Invalid argument` / `can't open '/dev/stdin'`），
而脚本里 `2>/dev/null` + `|| die "主表写入失败"` 把原因吞掉 ⇒ 只剩一句"写失败"，会误判成设备忙。

**正解**：`dd of=/dev/sda bs=4096 seek=… conv=notrunc,fsync`（不写 `if=`，默认读 stdin；用 `conv=fsync` 代替 `oflag=direct`）。
**并且**：写盘步骤不要 `2>/dev/null`——诊断信息比"干净输出"值钱。

## #404 设备侧没有 `python3` ⇒ 用 `python3 -c` 算 dd 偏移会静默产出 **0 字节** dump

`skip=$(( $(python3 -c 'print(123871231)') - 4 ))`：设备无 python3 ⇒ 算术变空 ⇒ `dd` 失败 ⇒
重定向出去的 GPT 备份文件是 **0 字节**，后面 `parse_header()` 才在几十行外报 `no GPT header`（误导性极强）。

**正解**：偏移在**主机**解析主表头算（`alternate_lba` 在 header 偏移 32 处，`last_usable` 在 48，别记反），
并且**每一步 dump 都断言尺寸**（主表 24576 B / 备份 20480 B）+ 断言备份第 5 扇区是 `EFI PART`。
`PITFALLS` 老账：写死数字 + 静默 `2>/dev/null` = 一定会在换机/换布局时爆。

## #405 USB NCM 重枚举后主机侧静态 IP 不会自己回来（每次 reboot 都要补）

设备 `reboot -f` 后 `enx…` 接口重新枚举（新 `lsusb` 设备号），NetworkManager 的 DHCP 常拿不到地址
（"IP 配置无法保留"），于是 `ssh root@192.168.7.1` 直接超时——**别急着判设备没起来**。

判据顺序：`lsusb | grep 1d6b:0104`（gadget 在不在）→ `ip -br addr | grep 192.168.7`（主机有没有地址）→
`ip neigh`/`ping`（链路）→ 才轮到"设备是否启动失败"。
本轮一次"完全失联"（gadget 不在、无 fastboot/adb、串口停更）**事后证明是 gadget 没枚举，不是系统没起**：
用户按键后设备**直接落在 fastboot**（说明 ABL/系统正常）→ `fastboot boot out/boot-elden-f2fs-root.img` 5 s 内起 f2fs、
`slot-attr` 仍 `boot_b succ=1 unbootable=0 retry=6` → `qbootctl -m b` → `reboot -f` 后 POR 一切正常（gadget/ssh/桌面全回）。
**判据顺序**：① `lsusb | grep -c 1d6b:0104`（gadget 有没有）② 串口日志 `/var/log/elden-serial/ttyACM0.log` 尾部时间戳
（唯一不依赖 USB 网络的观测面）③ `fastboot devices`（设备是不是落在 bootloader）④ 最后才是"系统起没起"。
**结论写死**：「ssh 不通」≠「设备没起来」，这两件事本轮各发生过一次，混判会白等十分钟。
