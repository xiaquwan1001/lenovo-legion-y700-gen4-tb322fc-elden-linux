## 282. ★ 裸 `make`（不带 `ARCH=arm64`）会按**主机 x86** 求值 Kconfig，静默删掉整个 QCOM 栈

- **实踩（2026-10-15 晚）**：在 `build/m1-upstream/clean-tree-73` 只想 dry-run 看哪些模块要重编，
  跑了 `make -n modules`（**没带 `ARCH=`**）。它触发 `syncconfig`，把 `.config`
  从 **4954 行压到 2881 行**：`CONFIG_ARCH_QCOM`、`CONFIG_DRM_MSM` **整行消失**；
  `.config` 与设备 `/proc/config.gz` 的 diff 从 **0 跳到 5265 行**。
- **机制**：Kbuild 按**主机架构**的 Kconfig 树求值 ⇒ 产出 x86 配置。与 `PITFALLS #162`
  （`olddefconfig` 删 `ARCH_QCOM` → vk81/82/83 死内核）、`#247`（`olddefconfig` 必须带 `ARCH=`）
  **同源**，但本条的触发面**更宽**：**任何**会走 `syncconfig` 的 `make` 目标都算，
  不限于 `olddefconfig`/片段合并——**连 `-n`（dry-run）也会**。
- **连带污染**：`include/config/auto.conf` 与 `include/generated/autoconf.h` 一并被改坏。
  且 **`make syncconfig` 再跑一次不会自愈**——它从已被污染的 `auto.conf` 反推，会**继续错**。
- **恢复**：`cp .config.old .config`（好档通常就是上一次 `syncconfig` 前的 `.config.old`）
  → 然后**一律带 `ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-`** 重跑 `syncconfig`。
- **判据（改配置后、开编前必查）**：
  ```sh
  grep -cE '^CONFIG_ARCH_QCOM=y' .config                 # 必须 = 1
  diff <(sort .config) <(zcat /proc/config.gz | sort) | wc -l   # 必须 = 0（跨树对账）
  ```
- **本文档新增的更硬判据**：**与设备实读 config 对账（diff=0）**比只看单行 `ARCH_QCOM` 更强，
  能同时抓住"没删但改了值"的静默漂移。

## 283. ★ vermagic 末尾多一个 **`+`** ⇒ `depmod` 全绿、但**上机 `insmod` 必被拒**

- **实踩**：编出的模块 vermagic = `7.3.0-rc7-debug-ged6f232d10e3+`，
  而设备 `uname -r` = `7.3.0-rc7-debug-ged6f232d10e3`（**无 `+`**）⇒ 两者**不等**，加载必失败。
- **机制**（`scripts/setlocalversion`，`LOCALVERSION_AUTO=n` 分支）：
  > 若环境变量 `LOCALVERSION` **未设置**，且仓库不在带**注解 tag**的干净态，则追加 `+`。

  本树是 git **worktree**（`.git` 是 `gitdir:` 指针文件），`git describe --always` 给出 `95c899a885`
  ⇒ 命中 `+`。**注意 `git status` 可以是完全干净的**（0 dirty），仍会命中。
- **修复**：构建时**显式导出空 `LOCALVERSION=`**：
  ```sh
  export LOCALVERSION=
  make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) modules
  ```
  速验：`LOCALVERSION= make -s ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- kernelrelease`
  ⇒ 应输出 **无 `+`** 的串。
- **★ 通用教训（比本条本身更重要）**：
  **`depmod` 成功不代表模块能加载** —— `depmod` 只建 `modules.dep`/`modules.alias` 索引，
  **不校验 vermagic**。所以"部署完 depmod 全绿"是**假 GREEN**。
  过门判据必须是：
  ```sh
  modinfo <ko> | grep -oP 'vermagic:\s+\K.*'   # 与设备 `uname -r` 逐字比对
  ```
  本文档生效后，9/9 相机模块的 vermagic 均与 `uname -r` **逐字相等**。

## 284. 相机栈首次在 M1-7.3 上跑通；出流失败可**单变量定位到 VFE/RDI 实例**

- **已达成的**（`build/m1-upstream/clean-tree-73`，部署 1497 `.ko` 后）：
  `CAM_FORCE=1 camera-modules-load.sh` ⇒ **`/dev/media0` + 17 个 `/dev/video*`**；
  后摄 `s5kjns 12-0056`（4080×3072 SGRBG10）与前摄 `gc08a8 13-0031` **双双绑定且 link `ENABLED`**，
  `gt9764`（AF VCM）在位。此前 7.3 树上**从未有过**（缺模块 ⇒ 全部 `=m` 驱动不加载，见 `#248`/§31）。
- **未达成**：`STREAMON` 失败。**单变量判别（同会话、仅换 VFE/RDI 实例）**：

  | 通路 | VFE | `line_num` | RDI | `STREAMON` | `Pixel clock is too high for VFE` |
  |---|---|---|---|---|---|
  | `csiphy3→csid4→vfe4_rdi3` | VFE4 (Lite) | 4 | **RDI3** | `EINVAL` | **✅ 报**（dmesg 计数 2） |
  | `csiphy3→csid0→vfe0_rdi0` | VFE0 (Full) | 3 | **RDI0** | `EPIPE` | **❌ 不报**（计数仍 2） |

- **两条硬结论**：
  1. **clock 报错与 VFE 实例强相关**，且 `min_rate` 定量上**只有 ~87–100 MHz**
     （`pixel_rate 558 933 333` × `bpp 10` / 64），**远低于** `vfe0` 表上限 833 MHz 与
     `camnoc_rt_axi` 480 MHz ⇒ **不是真的"时钟太高"**，
     指向 `camss-vfe.c:994` 的 `pixel_clock[]` 在 `line_num=3` 时**不覆盖 RDI3** ⇒ **未初始化栈值**。
  2. **但还有第二层**：VFE0 路径不报 clock 错，**却 `EPIPE`**（无任何 dmesg 打印）
     ⇒ **"改 `line_num` 就能出流"是错的**；至少两道障碍叠加。
- **拓扑事实（本轮澄清，值得记）**：CSID*N* 与 VFE*N* 是**固定 1:1 配对**
  （`msm_csid0` 只连 `msm_vfe0_rdi{0,1,2}`；`msm_csid4` 只连 `msm_vfe4_rdi{0,1,2,3}`）；
  但 **csiphy3（后摄所在）可路由到任意 CSID** ⇒ 换 VFE 的可行手法 = 换 csiphy 的**下游 CSID**。
- **判据教训**：`media-ctl -p` 里 link `ENABLED` + 传感器实体在位 **≠ 能出流**；
  与 `#251/#255`（DRM GOOD ≠ 面板有画面）同型的"伪 GREEN"，出流必须 `STREAMON` 拿到帧才算。
