## 282. ★ 裸 `make`（不带 `ARCH=arm64`）会按**主机 x86** 求值 Kconfig，静默删掉整个 QCOM 栈

- **实踩（2026-10-15 晚）**：在 `build/m1-upstream/clean-tree-73` 只想 dry-run 看哪些模块要重编，
  跑了 `make -n modules`（**没带 `ARCH=`**）。它触发 `syncconfig`，把 `.config`
  从 **4954 行压到 2881 行**：`CONFIG_ARCH_QCOM`、`CONFIG_DRM_MSM` **整行消失**；
  `.config` 与设备 `/proc/config.gz` 的 diff 从 **0 跳到 5265 行**。
- **机制**：Kbuild 按**主机架构**的 Kconfig 树求值 ⇒ 产出 x86 配置。与 `PITFALLS #162`
  （`olddefconfig` 删 `ARCH_QCOM` → vk81/82/83 死内核）、`#247`（`olddefconfig` 必须带 `ARCH=`）
  **同源**，但本条的触发面**更宽**：**任何**会走 `syncconfig` 的 `make` 目标都算，
  不限于 `olddefconfig`/片段合并——**连 `-n`（dry-run）也会**。
- **连带污染**：`include/config/auto.conf` 与 `include/generated/autoconf.h` 一并被改坏。
  且 **`make syncconfig` 再跑一次不会自愈**——它从已被污染的 `auto.conf` 反推，会**继续错**。
- **恢复**：`cp .config.old .config`（好档通常就是上一次 `syncconfig` 前的 `.config.old`）
  → 然后**一律带 `ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-`** 重跑 `syncconfig`。
- **判据（改配置后、开编前必查）**：
  ```sh
  grep -cE '^CONFIG_ARCH_QCOM=y' .config                 # 必须 = 1
  diff <(sort .config) <(zcat /proc/config.gz | sort) | wc -l   # 必须 = 0（跨树对账）
  ```
- **本文档新增的更硬判据**：**与设备实读 config 对账（diff=0）**比只看单行 `ARCH_QCOM` 更强，
  能同时抓住"没删但改了值"的静默漂移。

## 283. ★ vermagic 末尾多一个 **`+`** ⇒ `depmod` 全绿、但**上机 `insmod` 必被拒**

- **实踩**：编出的模块 vermagic = `7.3.0-rc7-debug-ged6f232d10e3+`，
  而设备 `uname -r` = `7.3.0-rc7-debug-ged6f232d10e3`（**无 `+`**）⇒ 两者**不等**，加载必失败。
- **机制**（`scripts/setlocalversion`，`LOCALVERSION_AUTO=n` 分支）：
  > 若环境变量 `LOCALVERSION` **未设置**，且仓库不在带**注解 tag**的干净态，则追加 `+`。

  本树是 git **worktree**（`.git` 是 `gitdir:` 指针文件），`git describe --always` 给出 `95c899a885`
  ⇒ 命中 `+`。**注意 `git status` 可以是完全干净的**（0 dirty），仍会命中。
- **修复**：构建时**显式导出空 `LOCALVERSION=`**：
  ```sh
  export LOCALVERSION=
  make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) modules
  ```
  速验：`LOCALVERSION= make -s ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- kernelrelease`
  ⇒ 应输出 **无 `+`** 的串。
- **★ 通用教训（比本条本身更重要）**：
  **`depmod` 成功不代表模块能加载** —— `depmod` 只建 `modules.dep`/`modules.alias` 索引，
  **不校验 vermagic**。所以"部署完 depmod 全绿"是**假 GREEN**。
  过门判据必须是：
  ```sh
  modinfo <ko> | grep -oP 'vermagic:\s+\K.*'   # 与设备 `uname -r` 逐字比对
  ```
  本文档生效后，9/9 相机模块的 vermagic 均与 `uname -r` **逐字相等**。

## 284. 相机栈首次在 M1-7.3 上跑通；出流失败可**单变量定位到 VFE/RDI 实例**

- **已达成的**（`build/m1-upstream/clean-tree-73`，部署 1497 `.ko` 后）：
  `CAM_FORCE=1 camera-modules-load.sh` ⇒ **`/dev/media0` + 17 个 `/dev/video*`**；
  后摄 `s5kjns 12-0056`（4080×3072 SGRBG10）与前摄 `gc08a8 13-0031` **双双绑定且 link `ENABLED`**，
  `gt9764`（AF VCM）在位。此前 7.3 树上**从未有过**（缺模块 ⇒ 全部 `=m` 驱动不加载，见 `#248`/§31）。
- **未达成**：`STREAMON` 失败。**单变量判别（同会话、仅换 VFE/RDI 实例）**：

  | 通路 | VFE | `line_num` | RDI | `STREAMON` | `Pixel clock is too high for VFE` |
  |---|---|---|---|---|---|
  | `csiphy3→csid4→vfe4_rdi3` | VFE4 (Lite) | 4 | **RDI3** | `EINVAL` | **✅ 报**（dmesg 计数 2） |
  | `csiphy3→csid0→vfe0_rdi0` | VFE0 (Full) | 3 | **RDI0** | `EPIPE` | **❌ 不报**（计数仍 2） |

- **两条硬结论**：
  1. **clock 报错与 VFE 实例强相关**，且 `min_rate` 定量上**只有 ~87–100 MHz**
     （`pixel_rate 558 933 333` × `bpp 10` / 64），**远低于** `vfe0` 表上限 833 MHz 与
     `camnoc_rt_axi` 480 MHz ⇒ **不是真的"时钟太高"**，
     指向 `camss-vfe.c:994` 的 `pixel_clock[]` 在 `line_num=3` 时**不覆盖 RDI3** ⇒ **未初始化栈值**。
  2. **但还有第二层**：VFE0 路径不报 clock 错，**却 `EPIPE`**（无任何 dmesg 打印）
     ⇒ **"改 `line_num` 就能出流"是错的**；至少两道障碍叠加。
- **拓扑事实（本轮澄清，值得记）**：CSID*N* 与 VFE*N* 是**固定 1:1 配对**
  （`msm_csid0` 只连 `msm_vfe0_rdi{0,1,2}`；`msm_csid4` 只连 `msm_vfe4_rdi{0,1,2,3}`）；
  但 **csiphy3（后摄所在）可路由到任意 CSID** ⇒ 换 VFE 的可行手法 = 换 csiphy 的**下游 CSID**。
- **判据教训**：`media-ctl -p` 里 link `ENABLED` + 传感器实体在位 **≠ 能出流**；
  与 `#251/#255`（DRM GOOD ≠ 面板有画面）同型的"伪 GREEN"，出流必须 `STREAMON` 拿到帧才算。

## 285. ★ `cam-mode.sh off` 会在**卸载失败时反而把熄屏打开** ⇒ 亲手激活 Q24 掉电条件

- **实踩（2026-10-15 晚）**：在 7.3 树上跑 `cam-mode.sh off`，输出里夹着
  `rmmod gt9764: ERROR: Module gt9764 is in use`，**但它接着照样执行了 `blank_restore`**：
  ```
  camera modules = 9   media = 0   video = 0
  dpms = On   idle-delay = uint32 300      ← 自动熄屏被恢复！
  ==> 状态 = CAM-ON：**不要熄屏**（相机在位时熄屏掉电是常态）
  ```
  ⇒ **9 个相机模块仍在位 + 自动熄屏已打开** = Q24（相机 × 熄屏 → 整机硬复位）的**完整触发条件**被这条命令自己凑齐了。
- **两个独立缺陷**（都在 `do_off()`）：
  1. **用 `rmmod` 而非 `modprobe -r`**：`rmmod` 不看依赖，被依赖的模块一律 `in use` 报错跳过
     ⇒ 留下一半栈（本机实测剩 9 个）。
  2. **无条件 `blank_restore`**：`do_off()` 最后一行不看卸载结果就恢复熄屏。
     这是本条**真正危险**的地方 —— 失败方向朝着"掉电"而不是"安全"。
- **修复**（`scripts/cam-mode.sh`，2026-10-15 已上机验证）：
  - 卸载改 `modprobe -r`（依赖感知）+ **两轮**（首轮后 refcount 会沉降）；
  - **条件恢复**：只在 `cam_n == 0` 时才 `blank_restore`；
    未清零则显式 **FAIL + 列出仍在位的模块 + 保持熄屏关闭**（安全侧）。
- **附带修的同源缺陷**：`blank_disable()` 把 gsettings 的**带类型前缀**回读
  （`IDLE=uint32 300`）直接写进 `$STATE`，而 `blank_restore()` 用 `. "$STATE"` source 它
  ⇒ 把 `uint32` 当命令执行，报 `/var/lib/elden-cam/blank.env: line 1: 300: not found`
  （值靠 `${IDLE:-…}` 兜底才没出错，属**静默降级**）。现改为：存档**裸数值**，恢复时统一补 `uint32 ` 前缀，并兼容旧存档。
- **教训（通用）**：**"恢复原状"类清理函数必须由"清理是否真的成功"来把关** ——
  否则失败路径会把系统推进比不动它更危险的状态。与 `#157`（守卫静默 `exit 0` 把配置态读成驱动坏）同族，
  但后果更重：`#157` 是**误判**，本条是**主动动作**。

## 286. ★★ 「死前最后看到的日志」被当成死因：`mxc.lvl → 0` 其实是**常规关轨**

- **背景**：`reports/q24-repro-20261011.md` §0/§2 把 **`mxc.lvl`(addr `0x300a0`) → 0x0**
  记为 Q24 的**「死前最后一笔 RPMh 电源票」**，长期被当作死因线索读。
- **实踩（2026-10-15 晚，N1c）**：在**完全健康的设备**上、**不熄屏**，仅执行
  `modprobe -r` 两 CC（`cambistmclkcc-sm8750` + `camcc-sm8750`），用
  `rpmh_send_msg` tracepoint 直读投票：
  - 配对**加载**：**2 条**（只有 `0x300a0`）；
  - 配对**卸载**：**54 条**，模式 `0x300a0 data:0x2` ↔ `0x300a0 data:0x0` **反复振荡**，
    **没有任何其它轨参与**；
  - 设备**全程存活**（uptime 连续、无复位）。
- **地址解码**（`reports/q24-r9-20261012.md` §2 cmd-db 实读）：**`0x300a0` = `mxc.lvl`**。
- **⇒ 结论**：`mxc.lvl → 0` 是**相机 GDSC 轨的常规 runtime-PM 关轨行为**，
  **不是死亡签名**。把它读作死因属 **post hoc ergo propter hoc**（事后归因）。
  这与 `reports/q24-r9-20261012.md` §2 已得出的「死亡窗口与存活窗口**同址同型** ⇒ 投票是伴随现象」
  **一致**，本轮**独立复现并加强**；也解释了 `#210`（NoC/BCM 靶否证）为何成立。
- **★ 通用教训（本条的真正价值）**：
  **「复位/崩溃前最后一条日志」是时序上的"最后"，不是因果上的"原因"。**
  间歇性硬复位场景里，**必须先在健康态复现同一个签名**，才能把它当线索用；
  否则会把"伴随现象"升级成"根因"，代价是整条排查线跑偏。
  本项目已有同类前科：`#197`（死前签名 = probe 伪影）、`#210`（票不区分死活）。
- **同轮否证的另一条**：`reports/q24-causal-audit-20261015.md` 的 `rpmhpd sync_state` 线，
  其核心预测（配对绑定 ⇒ pending 清零 + 轨重投）在**运行期配对**下**未兑现**
  （详见 `reports/q24-n1-syncstate-falsified-20261015.md`）。
  仍开放的是 **N1b**：**开机态**配对是否不同（绑定时机变量，未验）。

## 287. ★ `sync_state` 类门控是**一次性、只在开机窗口生效**的 —— 运行期 `modprobe` 测它会得到假否证

- **实测对照（2026-10-15 晚，同一设备同一内核，单变量 = 绑定时机）**：

  | | N1（运行期 `modprobe` 两 CC） | **N1b（开机态自动绑定两 CC）** |
  |---|---|---|
  | `dmesg \| grep -c "rpmhpd.*pending"` | **2**（且是 `t=18.17 s` 开机旧消息） | **0 —— 整个 boot 一条都没有** |
  | 同 boot 其它 provider pending | — | **13**（照常打印） |
  | 两 CC bound | 2/2 | 2/2 |
  | `mx`/`mxc`/`mmcx` | `on`/`off-0`/`on` | `on`/`off-0`/`on`（**相同**） |

- **机制**（`drivers/pmdomain/qcom/rpmhpd.c`）：provider 的 `.sync_state` 由 driver core
  **在所有消费者都 bound 之后**调用**一次**。运行期再 bind 新消费者**不会重新触发**它。
  于是：
  - **开机态绑定** ⇒ provider 求值前消费者已齐 ⇒ 直接 `state_synced=true`、按真实票投票、**不打印 pending**（N1b）；
  - **运行期绑定** ⇒ provider 早已求值完毕（当时缺这两个消费者）⇒ 日志不新增、轨不变（N1）。
- **★ 通用教训**：**用"运行期加载模块"去测 `sync_state`/`probe` 顺序类机制，会得到假否证。**
  这类机制的判据必须在**开机窗口**取（`/etc/modules-load.d/` 或 cmdline），否则测的是"机制不再重跑"，
  而不是"机制不存在"。本项目同类前科：`#195`（构建身份/版本串变量）、`#248`（缺 `=m` 模块被误判为代码回归）。
- **同时暴露的判据盲区**：两时机下 `mx/mxc/mmcx` 读数**完全相同**
  ⇒ 再次印证 `#279/#280`「`pm_genpd` 零判别力」；**不能**用 genpd 状态区分 sync_state 是否已释放。
- **未越界**：N1b **未复现死亡**（全程未熄屏）⇒ 该机制与 Q24 **致死**的因果关系**仍未建立**。
  据 N1b 浮出的下一个可判别实验 = **N2'**（开机态配对构型 + 一次真熄屏）。
- 证据：`reports/q24-n1b-boottime-pairing-20261015.md`、
  `reports/q24-n1-syncstate-falsified-20261015.md`、`reports/q24-causal-audit-20261015.md`

## 288. ★★ `reboot` 在本机当前状态**会挂起** ⇒ `sleep-sweep.sh` 的 "ALIVE" 是**假阳性**

- **实踩（2026-10-15 晚，N2' 第一轮）**：用 `scripts/sleep-sweep.sh "camcc-sm8750 cambistmclkcc-sm8750" 3`
  跑 Q24 熄屏扫掠，得 **`run1 ALIVE / run2 ALIVE / run3 ALIVE`**。
  但核对后发现：**三次重启一次都没发生** ——
  `uptime` 单调增长（不归零）、`/proc/sys/kernel/random/boot_id` **全程不变**、
  `camera.conf` 里的两 CC **根本没被加载**（`lsmod` 为空）。
  ⇒ **那 3 发 "ALIVE" 什么都没测**（熄屏时相机栈压根不在位）。
- **根因**：`/sbin/reboot` = 项目自写的 `elden-powerwrap` 包装（665 B shell 脚本），
  `/etc/elden-init-mode` = `openrc` ⇒ 走 `exec /bin/busybox reboot "$@"` 分支。
  实测该路径**会挂起**（`timeout` 到期 `rc=124`，设备不重启）；
  `/bin/busybox reboot -f` 同样挂起。**`sysrq-b` 是当前唯一可靠通道**：
  ```sh
  echo b > /proc/sysrq-trigger      # 实测有效：uptime 归零 + boot_id 换新
  ```
  证据：`/root/powerlog.txt` 里最近多条 `USERLAND-reboot … boot_id=<同一个>` ——
  **boot_id 相同**证明那些 reboot 全部没生效（该文件本身是 `elden-powerwrap` 写的，
  设计意图正是"区分用户态重启 vs 硬复位"，本轮它恰好自证了 reboot 失败）。
- **★ 通用教训**：**自动化 harness 的 verdict 必须用"不可伪造"的判据独立复核。**
  `sleep-sweep.sh` 的判据是"SSH 还能跑 `echo ALIVE`"，这在**重启根本没发生**时**必然为真**
  ⇒ 假阳性。**可靠的死活判据 = `/proc/sys/kernel/random/boot_id` 是否变化**
  （`uptime` 次之；"SSH 还在"最不可靠）。与 `#251/#255`（DRM GOOD ≠ 面板有画面）、
  `#284`（link ENABLED ≠ 能出流）同族：**"看起来正常"不是判据**。
- **本轮的处置**：N2'/N3 全部改用 `boot_id` 判据 + **显式确认 `dpms` 真的发生了 `On→Off` 跃迁**
  （否则 `SetActive(true)` 在已熄灭状态下是 no-op，会得到第二个假阳性）。
  修正后重跑见 `reports/q24-n2prime-both-arms-survive-20261015.md`。
