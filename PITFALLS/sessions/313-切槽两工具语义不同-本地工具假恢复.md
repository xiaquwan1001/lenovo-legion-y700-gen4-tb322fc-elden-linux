## #677 「切槽」在两个工具里语义不同：`fastboot --set-active`（ABL 实现，**会**清 bit7 + 补 retry=7）vs 本地 `eldroid-bootctl slot set-active`（只写 active/retry，**不清 UNBOOTABLE**）⇒ 后者是「假恢复」

**现象（2026-11-18 脚本审查 R2 静态定案 + 11-17 实测对照）**：设备停在 fastboot、`boot_a` 为 UNBOOTABLE 时，
用本地工具「切一下槽」看起来成功（属性显示 active=1、retry=7），但 ABL 仍然拒绝尝试、还是回 fastboot。
而 `fastboot --set-active=b` 之后 `slot-unbootable` 从 `yes` 变 `no`、retry 0→7（`reports/bl-stuck-20261117-device-window.md:35` 实测）。

**机制**：`fastboot --set-active` 由 **ABL 自己的实现**处理，它按 AOSP `gpt-utils` 语义把槽标成
「active + successful + retry=7 + 非 unbootable」；而 `scripts/eldroid-bootctl slot set-active` 只是
调 `slot-attr.py set <slot> --active --retry 7`，**字节 6 的 bit7 原样保留** ⇒ 属性看着改了，`UNBOOTABLE` 还在。

### 判据

任何「切槽当恢复」的动作，**必须回读 bit7**，不能只看 active：

```sh
python3 scripts/slot-attr.py show        # 或 fastboot getvar slot-unbootable:<slot>
# 期望：active=1 succ=1 retry=7 unbootable=0；出现 unbootable=1 就是假恢复
```

- 恢复顺序（本机）：`fastboot -s <SN> --set-active=<slot>`（ABL 清位）→ `getvar slot-unbootable:<slot>` 确认 `no`
  → 起来后 `mark-successful <slot>`。**别在 `slot-unbootable: yes` 上做「镜像能不能起」的实验**（#672）。
- 本地工具若要当恢复入口，`set-active` 必须带 `--no-unbootable` 且写后回读（2026-11-18 已修，见下）。

### 已落地的修法（同轮脚本审查，全部未上机）

- `scripts/eldroid-bootctl`：`slot set-active` 增加 `--no-unbootable`，写完 `_slot_verify()` 回读；
  `_backup_gpt()` 现在**主备两表都 dump**（原来只 dump LBA0..33，回滚后主备不一致）。
- `scripts/slot-attr.py`：写序改**先备表后主表**（断电窗口里至少剩一张自洽表）；`_pwrite` 加短写循环；
  写后 `_verify()` 逐字节 + entries CRC 读回；**主备两表都找不到条目时 rc≠0**（旧行为是打印 `written + CRCs fixed` 并 rc=0，#669 同族的「静默成功」）。
- 离线回归（64 MiB 合成 GPT，`boot_a=0xf7`）：`mark-successful a` → `0x7f`/retry=7/读回校验通过；
  抹掉两表 `boot_a` 后 `set a --retry 7` → **rc=1**。

**推广**：同一个动作有两条实现路径时（ABL 的 fastboot 命令 vs 我们自己的 GPT 编辑器、`qbootctl -m` vs `slot-attr.py`），
**必须逐位对照它们写的字节**，并约定谁是恢复入口。只比「命令 rc=0」或「属性界面看着对」不算验证。

`scripts/slot-attr.py` 头注释（byte6 位定义）、`TASKS/sessions/2026-11-18-安卓最小线刷包-*.md`。
