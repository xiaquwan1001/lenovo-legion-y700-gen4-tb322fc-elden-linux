# 43 — 相机 AE 正解（libcamera sensor helper）落地：交叉编译、签名、设备时钟

> 2026-10-17 晚实测。报告：`reports/camera-ae-helper-20261017.md`。

## #299 设备冷起时钟 = **1970** ⇒ 所有 HTTPS 立刻失败，容易被读成「没网/镜像坏」

- 现象链：`curl https://…` 返回 `rc=60`（证书校验失败）；`apk update` 报
  `APKINDEX.tar.gz: file format is invalid or inconsistent`（其实是拿不到）；
  `curl -k` 立刻 200 ⇒ 不是网络问题，是 **系统时间早于证书 notBefore**。
- 判据：`date -u` 先看，`ls -l /etc/ssl/certs/ca-certificates.crt` 是 Sep 2026 而设备是 1970。
- 治法：`date -u -s "YYYY-MM-DD HH:MM:SS"`（本机无 RTC/NTP 兜底，**每次冷起都要设**）。
- 另：本机**HTTPS 出站被封、HTTP 被校园网关劫持**（返回 `<html>redirecting to http://202.141.180.1`），
  所以「http 200」也不代表网络通；要出网只能走**主机代理**（见 §代理）。

## #300 交叉编 libcamera IPA 的三个硬点

1) **只需替换 `ipa_soft_simple.so`**：`camera_sensor_helper.cpp` 属 `libipa`（`static_library`），
   静态链进 IPA `.so`；`libcamera.so.0.7` 不动（`grep -rl CameraSensorHelper src/libcamera` 为空）。
2) **工具链**：设备是 Alpine/aarch64/**musl** ⇒ 必须 `aarch64-linux-musl-*`（musl.cc 预编译即可）；
   用主机 `aarch64-linux-gnu-gcc`（glibc）会链不过。sysroot 只需设备取来的 **libyaml** 三件套。
   `meson` 的 `dependency('dl')` 在 musl 下靠工具链自带 `libdl.a`；`NEEDED [libc.so]` 在 musl 里等价自我。
3) **签名**：0.7.1 的 IPA 加载**不校验** `.so.sign`（`IPAManager::isSignatureValid()` 只给 `ipa-verify` 用，
   隔离只看 license：LGPL ⇒ 同进程）⇒ 替换 `.so` 后删掉失效的 `.sign` 不会阻止加载。
   ⚠ 但**别拿 `ipa-verify` 判可用性**，它必然报签名无效。

主机侧还差一个纯 Python 依赖 `ply`（控制代码生成）：`pip3` 不存在时可直接从设备
`/usr/lib/python3.14/site-packages/ply` 拷到主机 + `PYTHONPATH`。

## #301 「设备失联」先看 USB 里它是什么形态，别先怀疑网卡/Q28

2026-10-17 22:14 设备失联：`enx021e5eede102` 消失 + `lsusb` 出现 `18d1:d00d`
⇒ 设备是**在 fastboot**，不是 RNDIS 掉线。`fastboot devices` 一行就能判定，`fastboot reboot` 无写盘、24 s 回 `boot_b`。
（本次成因已由用户澄清：**平板原生 `ninja` 编译过热，用户手动重启到 BL** —— 所以「呈 fastboot」不能自动读成「系统坏/掉电」；
**归因前先问/先看 `fastboot getvar product`，别写进 Q24 样本**。）

## #302 平板不做重编译（过热）

在平板上跑 `ninja`（8 核满载）会过热，用户需手动断电/重启。**所有内核/用户态编译一律主机交叉**
（libcamera IPA：主机 28 核 **8.7 s** vs 平板 >30 min 未完）。平板只做 `apk add`（轻量、有代理时可用）。

## #303 软 ISP 的 AE 收敛慢是设计（统计每 4 帧一次），别当故障

`SwStatsCpu::kStatPerNumFrames = 4` ⇒ 统计每 4 帧才产出一次，AGC 每次只调 10%（曝光或增益）。
后摄 720p ~1.2 fps ⇒ **每 3.3 s 才前进一步**；从冷启动到收敛要 **60–150 帧**。
判据：看 `IPASoftExposure` 的 `exposureMSV` 是否落进 `target*5 ± 0.2`，**不要用一两次抓帧的均值判 AE**。
（现象：短跑抓到的帧可能是几十帧前的暗帧 ⇒ 误判「AE 坏了/全黑」，2026-10-17 复现三次。）

## #304 相机 A/B 实验必须控「场景」和「起点」

- 现场灯/平板位置一变，前后两跑的均值就不可比（本次同一台机 3 小时内 mean 210/162/70/5 都出现过）。
- 起点也会污染：手动 `v4l2-ctl --set-ctrl exposure=2` 后，下一次 AE 从 2 行开始爬，
  短跑看起来「一直很暗」。
- 可控做法：① 用 `test_pattern`（数字恒定）做基准；② 或固定手动曝光/增益做对照；
  ③ 每次实验前把子设备曝光/增益复位到中值再让 AE 收敛。
- **测 pedestal（黑电平）的巧法**：`exposure` 设最小 + `gain` 设 1x 抓 raw 一帧，光信号≈0，
  直方图众数就是 pedestal（本次 s5kjns = **64@10bit**，验证 `blackLevel: 4096` 正确）。

## #305 libcamera-devel 是 **members-only**：不订阅直接投 = 被 hold

2026-10-17 实测：3 封补丁全部收到
`Your message to libcamera-devel awaits moderator approval … Post by non-member to a members-only list`。
投前必须：① 发 `subscribe` 到 `libcamera-devel-request@lists.libcamera.org`；
② 收回确认信（本次一次订阅会得到**两个** token），把 `confirm <token>` 发回 `-request`（或原样回复确认信）；
③ 收到 `Welcome to libcamera-devel` 再投。
另外 libcamera 提交标题习惯带文件名：`ipa: libipa: camera_sensor_helper: add …`（`ipa: libipa: add …` 可能被要求改）。
归档在 **Pipermail**（`lists.libcamera.org/pipermail/libcamera-devel/`），不是 lore。
