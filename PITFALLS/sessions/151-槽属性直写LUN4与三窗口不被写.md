## 操作性教训（可直接复用）

- **`qbootctl -u a` 在活动槽 `b` 时必失败**：`gpt_disk_commit: Invalid args` → `update_slot_attribute: Failed to commit disk`
  → `Failed to set as unbootable`。原因 = 改 `a` 的属性要写 LUN1 的 GPT，需切 UFS boot LUN，ioctl 失败即整笔放弃
  （`-i` 可强写但那是拿错 LUN 的风险动作，别用）。
  **正解** = `scripts/slot-attr.py set a --unbootable`：直接写 `/dev/sde`（= LUN4）的**主/备双表 + 重算两处 CRC**，不碰 LUN 切换；
  写后 ABL 立即采信（`fastboot getvar slot-unbootable:a` = `yes`）。清回 = `set a --no-unbootable`（`0xf2 -> 0x72`）。
- **写 GPT 会让内核重扫 `/dev/sde`**：分区节点短暂消失约 3 s（`dd: failed to open '/dev/sde'` 然后再出现），
  **不是写坏**——等 3 s 复测即可，别急着回滚 GPT。
- **`fastboot flash boot_b` 的 `Writing OKAY [0.056s]` 是正常的**（96 MiB 只在 `Sending` 阶段 2.2 s），
  写后判据只认「回 Linux 后 `dd if=/dev/disk/by-partlabel/boot_b | sha256sum` 与备份逐字节一致」。
- **恢复一条链（无需 EDL）**：`fastboot flash boot_b <备份件>` → `fastboot --set-active=b`（自动清 unbootable + retry 回 7）→
  `fastboot reboot` → 约 15 s 回 Linux。

## 三条实测硬事实（本轮新增）

- **① 三块 carveout 窗口在整个启动链里不被写**：`0x84A00000`/`0x9C300000`/`0x89300000` 经 `blackbox.ko` 清零后，
   走完「载荷写 boot_b → reboot → ABL 失败 → fastboot → `flash boot_b` → reboot → Linux」整圈，**仍逐页为 0**。
   ⇒ 0x00 是稳定态，`stage=0` 是可信判据；「回落启动把 marker 清掉了」这一假设**作废**。
   附：prep 之前这三块**本就有非零数据**（`0x84A00000`/`0x89300000` 整页高 popcount）⇒ 「干净 0」不是唯一形态，
   读到的非标记数据不能当「没人写过」的证据。
- **② `fastboot boot` 在另一槽 unbootable 时 3/3 被拒**（`Failed to load/authenticate boot image: Invalid Parameter`），
   同镜像同 header 连续三次同形 ⇒ 支持 #482 的「接受与否与另一槽 bootable 相关」，但仍**不是充分条件**。
- **③ 槽位正常启动路径上，UEFI 载荷同样没执行第一句指令，且不留 `logfs` 段**：`boot_b` = 载荷（签后 `98b19671…`，读回一致）
   + `sysrq-b` 后数秒进 fastboot，三窗 `stage1` 全 0；`logfs` 10 段里没有这发的记录（seg0 = 当前 Linux、seg1–9 = 历史 Android 启动）。
   ⇒ 下一步必须先判别「ABL 加载层就拒」还是「跳了但首条指令即异常」，实验单见报告 §4。

## 追加（2026-11-02 上午，实测更正）

- **用「a 槽 unbootable」切断回落只能挡住一次**：b 槽载荷失败后，**ABL 会自己把活动槽切到 `a` 并清掉 `a` 的 unbootable 位**，
  然后正常启动 Android（实测：`getvar current-slot` 变 `a`、`slot-unbootable:a` 变 `no`，设备进 Android/MTP）。
  ⇒ 「切断回落」必须让 a 槽**内容**不可用（如临时写坏 `boot_a`，`backup/stock-259/boot_a.img` 可回滚），**只改属性位不够**。
- **`17ef:7f3d` = Android MTP 模式**（class 255 / sub 66 / proto 1），**不是** vendor 下载模式：`lsusb` 见到它 + `adb devices` 有设备
  ⇒ 设备其实正常进了 Android；别把它误判成「挂死/失联」（本轮据此下了一个错结论并已撤回）。
