# AVB 免签 + KSU —— 本机实测分析与刷写方案（2026-09-29 深夜）

> 结论先行：**abl 不用刷**（唯一砖点），只刷 a 槽的 4 个分区即可拿到"自洽链 + KSU"。
> 所有原厂分区已备份到 `backup/stock-259/`（含 `SHA256SUMS`），回退路径完整。

---

## 一、实测证据（全部用 `tools/avbtool.py` + 设备 dd 得到）

### 1.1 设备当前 a 槽 / b 槽的签名密钥

| 分区 | 公钥 sha1 | 说明 |
|---|---|---|
| `vbmeta_a`（设备） | `2597c218…f011` | 与 `~/下载/tb322fc/vbmeta.img` 完全一致（stock） |
| `boot_a`（设备） | `2597c218…` | sha256 `d4772c11…` = 社区 `重签包/boot_a.img` = 官方 boot |
| `recovery_a`（设备） | `2597c218…` | ⚠️ 但 `vbmeta_a` 的 chain descriptor 写的是 `8fcb864f…`（本来就不一致，能启动） |
| `vbmeta_system_a`（设备） | `8fcb864f…` | 与 `vbmeta_a` 的 descriptor 一致 |
| **`vbmeta_b`（设备）** | **`8fcb864f…`** | ← **b 槽是另一套固件/另一把密钥**，所以 b 槽 chain key mismatch，永远起不来 |
| `init_boot_a`（设备） | 无 vbmeta | **已经是 KSU 补丁版**（见 1.3） |
| `init_boot_b`（设备） | 无 vbmeta | 是 **Magisk** 补丁版 |

→ a 槽顶层 `vbmeta` 的密钥就是 `2597c218`，**这是设备本来就信任的 key**；
社区"重签包"和"KSU 包"用的也是同一把 key（`2597c218`）。

### 1.2 社区的三个 vbmeta 差别（只有这三处不同）

| | `vbmeta_a`(设备 stock) | `重签包/vbmeta_a.img` | `KSU/vbmeta.img` |
|---|---|---|---|
| 公钥 | 2597c218 | 2597c218 | 2597c218 |
| Flags | 1（hashtree disabled） | 0 | 0 |
| chain → recovery | `8fcb864f` | `2597c218` | `2597c218` |
| chain → vbmeta_system | `8fcb864f` | `2597c218` | `2597c218` |
| init_boot 描述符 | 2465792 B / `22a95107…`（stock） | 同 stock | **2850816 B / `900054a4…`（KSU）** |

`重签包/vbmeta_system_a.img` = 用 `2597c218` 重签（原 stock 是 `8fcb864f`）。
`重签包/recovery_a.img` = 用 `2597c218` 重签。

**校验通过**：`sha256(salt ‖ KSU/init_boot.img[:2850816])` = `900054a4…` = `KSU/vbmeta.img` 里 init_boot 描述符的 Digest ✅
（即 KSU 的两个文件是**自洽的一对**。）

### 1.3 `init_boot_a` 其实已经是 KSU 版

`strings backup/stock-259/init_boot_a.img` 含：
`/data/adb/ksud`、`description=Android KernelSU`、`kernelsu.ko`、`KSU_FEATURE`、`Hello, KernelSU!`
—— 但它的内容与 `restore-259/KSU/init_boot.img` **不同**（前者 2465792B 段 digest `8ddb0cfb…`），
说明是**另一个版本/另一次修补**（版本未知，未与任何 vbmeta 配套）。

### 1.4 本机其实已 unlocked，AVB 早已是"宽松态"

ABL 传给内核的 cmdline（实测）：
```
androidboot.verifiedbootstate=orange   androidboot.veritymode=disabled
androidboot.vbmeta.device_state=unlocked
```
→ **dm-verity 已 disabled、verified boot = orange**。
社区"免签"的核心价值是**在 BL 锁定的机器上 root**；本机已解锁，所以：
- `abl_a`（改过的引导器）**不是必需的**；它同时是**唯一有砖风险的步骤**。
- 只刷 a 槽那 4 个分区，就能得到"全链 `2597c218` 自洽 + KSU 配套"。

## 二、刷写方案（按风险从低到高）

> 前置：`fastboot --set-active=a`（**每次进 fastboot 都要先确认槽位**，
> 见 `PITFALLS §60`：`fastboot boot` 失败会让 current-slot 翻到 b）。

### ✅ 方案 A（推荐）：不刷 abl 的"完整免签 + KSU"

```bash
cd ~/y700-elden
fastboot --set-active=a
fastboot flash init_boot_a        restore-259/KSU/init_boot.img
fastboot flash vbmeta_a           restore-259/KSU/vbmeta.img
fastboot flash vbmeta_system_a    restore-259/重签包/vbmeta_system_a.img
fastboot flash recovery_a         restore-259/重签包/recovery_a.img
fastboot flash dtbo_a             backup/dtbo_a.img          # 原厂 dtbo（dummy 是给主线的）
fastboot reboot
```
刷完：a 槽全链 = `2597c218`（与设备本来就信任的顶层 key 一致），init_boot 与 vbmeta 严格配套。
`boot_a` 不动（设备上就是 `d4772c11…`，与官方/重签包一致）。

**进系统后**：装 `restore-259/KSU/KernelSU_v3.2.5_32525-release.apk`（用 adb 推或拷到存储），
打开 → 授权 → 确认"已安装 / 工作中"。

### ⭕ 方案 B（最小改动）：只刷 KSU 的 init_boot

```bash
fastboot --set-active=a
fastboot flash init_boot_a restore-259/KSU/init_boot.img
fastboot flash dtbo_a      backup/dtbo_a.img
fastboot reboot
```
保留 stock `vbmeta_a` → init_boot 摘要不匹配（**但今天设备就是这个状态，能正常启动**，见 1.3）。
适合"只想 root、不想动 vbmeta"。

### ⚠️ 方案 C（README 原版，含 abl）—— 只在 A 失败时才用

```bash
fastboot flash abl_a              restore-259/重签包/abl_a.img   # ← 唯一砖点，1 MiB
fastboot flash boot_a             restore-259/重签包/boot_a.img
fastboot flash recovery_a         restore-259/重签包/recovery_a.img
fastboot flash vbmeta_a           restore-259/重签包/vbmeta_a.img
fastboot flash vbmeta_system_a    restore-259/重签包/vbmeta_system_a.img
fastboot reboot
# 之后按 README 再刷 KSU 两个文件
```
`abl_a.img` 与 stock `abl.elf` 有 22% 字节不同（是另一个 build / 打过补丁的引导器）。
**刷它之前确认 EDL 救砖链路可用**（`qdl/build/qdl` + `restore-259/xbl_s_devprg_ns.melf`，已就位）。

## 三、回退（任何一步出错都能原样还原）

```bash
cd ~/y700-elden/backup/stock-259
fastboot --set-active=a
fastboot flash init_boot_a     init_boot_a.img
fastboot flash vbmeta_a        vbmeta_a.img
fastboot flash vbmeta_system_a vbmeta_system_a.img
fastboot flash recovery_a      recovery_a.img
fastboot flash boot_a          boot_a.img
fastboot flash dtbo_a          ../dtbo_a.img
fastboot reboot
# 极端情况（自编 boot/recovery）：
fastboot flash abl_a ~/下载/tb322fc/abl.elf
```
EDL 兜底：`~/y700-elden/qdl/build/qdl -s ufs restore-259/xbl_s_devprg_ns.melf write abl_a ~/下载/tb322fc/abl.elf`
（进 EDL：fastboot 下 `fastboot oem edl`）。

## 四、回主线（Android 里）

```bash
adb reboot bootloader      # 或 电源+音量减
# 主机：
cd ~/y700-elden
fastboot --set-active=a                # 兜底确认
fastboot flash dtbo_a out/dtbo-dummy.img
fastboot flash dtbo_b out/dtbo-dummy.img
fastboot boot out/boot-elden-vk12.img
```

## 五、待验证 / 风险

1. 方案 A 是否会被 ABL 因为 `vbmeta_system` 的 chain key 变化而拒绝 —— **中低风险**
   （证据：device 的 a 槽 chain 本来就有一处 key 不一致却照常启动）。
   失败表现 = 回到 fastboot（不是砖），直接按第三节回退。
2. 首次进 Android 会重建 `/data`（146.4 GiB）—— 这一步是 GPT 手术的收尾，必须做。
3. KSU 生效需要：init_boot 配套 + 装 apk + 首次授予 root（无 logind，KSU 是内核态 root，不依赖 logind）。
