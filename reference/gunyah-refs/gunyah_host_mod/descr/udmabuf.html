Why it's needed

For GPU acceleration, the VM's graphics memory must pass through the kernel's /dev/udmabuf feature to become something the GPU can use directly, and a single buffer is often 128 or 256 MB. Phone kernels break this in three different ways:

  1. some were built without udmabuf at all, so /dev/udmabuf does not exist;
  2. most have a flawed one: creating a large buffer needs a contiguous chunk of memory for an internal list, which fails once memory is fragmented (fixed upstream, but GKI 6.6 has not caught up);
  3. all of them cap a single buffer at 64 MB by default — far under what a GPU buffer needs.

What it does

At load time the module detects which of the three cases this kernel is in, and treats exactly that one:

1. no udmabufit provides /dev/udmabuf itself
2. flawedit repairs it, using an allocation that tolerates fragmentation
3. already fineit leaves the kernel's code alone

In every case it raises the 64 MB per-buffer cap and the buffer-count limit to what GPU acceleration needs, and restores everything when unloaded.

原因

GPU 加速时，VM 的绘图内存需要通过内核的 /dev/udmabuf 功能，转换成 GPU 能直接使用的形式，而且单块常常要 128MB、256MB。手机内核在这里有三种常见问题：

  1. 有些内核根本没有编译 udmabuf，/dev/udmabuf 不存在；
  2. 大多数内核的 udmabuf 有缺陷：建立大块时，内部需要一段连续内存来放清单，内存零碎时会失败（上游已修复，但 GKI 6.6 尚未跟上）；
  3. 所有内核都把单块上限默认在 64MB，远小于 GPU 缓冲区需要的大小。

功能

模块加载时自动判断内核属于上述哪一种情况，对症处理：

1. 没有 udmabuf自己提供一个 /dev/udmabuf
2. 有但有缺陷修复它，改用不怕内存零碎的分配方式
3. 一切正常不动内核的代码

无论哪种情况，都会把 64MB 的单块上限和块数限制调大到 GPU 加速够用，卸载时全部复原。
