Why it's needed

When the 6.1 kernel's Gunyah driver prepares memory for a VM, it first builds a page list — one entry per 4KB of VM memory. The bigger the VM, the bigger the list: a 2GB VM needs several MB for the list alone.

It allocates that list with kcalloc, which demands one physically contiguous block. As a phone runs, its free memory scatters into small pieces, and a contiguous block that large becomes impossible to find — so creating a large VM fails with Out of memory even though plenty of memory is free.

What it does

It switches the allocation to kvcalloc, which falls back to stitching scattered pieces together (vmalloc) when no contiguous block exists, and switches the matching free path to kvfree.

This is exactly the fix the kernel adopted upstream (commit b6ff6203e4bc); the module applies it without modifying the kernel, so VMs above 2GB can boot. On a kernel that already carries the fix, loading this module changes nothing.

原因

6.1 内核的 Gunyah 驱动在准备 VM 内存时，会先建立一张页面清单——VM 每 4KB 内存一条。VM 内存越大、清单越大，2GB 的 VM 光清单就要好几 MB。

它用 kcalloc 来分配这张清单，而这种方式要求一整块连续的物理内存。手机用久了，空闲内存会碎成小块，这么大的一整块常常找不到，于是建立大内存 VM 就失败、显示 Out of memory——即使手机明明还有很多可用内存。

功能

把分配方式换成 kvcalloc：找不到整块时，自动改用可拼凑零散内存的方式（vmalloc），释放端也配套换成 kvfree。

这正是内核上游采用的修复（提交 b6ff6203e4bc）；本模块不改内核就套用同样的修复，让 2GB 以上的 VM 能正常开机。若内核本身已含此修复，加载本模块不会有任何改变。
