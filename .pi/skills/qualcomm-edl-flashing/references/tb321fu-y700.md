# Lenovo Legion Y700 Gen3 (TB321FU) — device & firmware notes

SM8650 (Snapdragon 8 Gen 3), 256 GB UFS, 6 LUNs, A/B slots, BL unlockable.

## Partition layout (verified via fastboot getvar all + EDL printgpt, 107 partitions)
- LUN 0 holds `super` (13.00 GiB, dynamic) and `userdata` (218.47 GiB f2fs, LAST partition,
  sectors 3613096–60884986) plus bootloader-adjacent parts.
- LUN 4 holds the A/B boot set: boot_a/b & vendor_boot_a/b 96 MiB each, init_boot_a/b 8 MiB,
  dtbo_a/b 24 MiB, vbmeta_a/b 64 KiB, recovery_a/b 100 MiB, vm-bootsys_a/b 537 MiB.
- Super dynamic partitions (from vendor fstab): system, system_ext, product, vendor,
  vendor_dlkm, system_dlkm, odm — all `logical,first_stage_mount`.

## Firmware packages
- ROW zips: `mirrors.lolinet.com/firmware/lenowow/2024/Y700_2025/TB321FU/`
  (e.g. TB321FU_ROW_OPEN_USER_Q00002.0_W_ZUI_17.5.10.031_ST_251125.zip ≈ 6.99 GB).
- CN: `.../TB321FU_CN/` (17.0.10.032/.138/.308, 16.1.11.132). CN 7z packages may ship PLAIN
  XMLs (16.1.10.027 does) while ROW zips encrypt them as `.x` (AES-CBC, 16-byte IV prefix,
  length % 16 == 0; decrypt tool: XDA Breed43214, `pip install cryptography` + decrypt_batch.bat).
- ⚠️ lolinet throttles multi-GB downloads from CN networks (~33 KB/s measured — a 5.6 GB
  package would take ~47 h). Prefer CN CDNs (ONFIX rom sites), GDrive direct links, or
  gh-proxy for releases; test speed with a short curl before committing to a big download.
- Package `image/` contents: `xbl_s_devprg_ns.melf` (engineering loader, ~1.57 MB — use as EDL
  programmer, NOT prog_firehose_ddr.elf which fails on TB321FU), `contents.x`, `rawprogram*.x`,
  `patch*.x`, `gpt_*.bin` (all-zero placeholders — real GPT lives on device), `super_1..8.img`
  = split filesystem images: ext4 `system`(unlabeled, ~5.2G)/`product`/`system_dlkm`/`system_ext`
  + erofs `vendor`/`odm`/`vendor_dlkm` + zero placeholder. Restoring super needs the rawprogram
  XML offsets (decrypt .x / plain-XML package / lpmake rebuild).

## GUF296 Ubuntu scheme (github.com/GUF296/ubuntu-y700-build-ci)
- Boot chain (as documented by GUF296): ABL → boot_a/b UEFI boot.img → GRUB reads a FAT32
  image (`search --file /Image`) → `linuxdirect /Image root=PARTLABEL=userdata` (GRUB built
  with custom `linuxdirect`/`rampartition` modules; direct-boot GRUB named QCOMRAMP.EFI,
  outer menu GRUB BOOTAA64.EFI).
- ⚠️ PAYLOAD ANALYSIS 2026-08 (corrects earlier "gzip GRUB EFI payload" assumption): the
  boot.img kernel section is NOT a GRUB EFI. v3 header, kernel_size 2,413,234 (gzip) →
  decompresses to 4,194,416 B ARM64 "Image" with magic `0x10000381` (NOT the standard Linux
  Image magic 0x644d5241), contains the string `uefiplatLA.cfg` and an MZ at ~0x29F26.
  Header cmdline region reads empty. Byte-identical to GUF296 release asset `kernel.bin`.
- QCOMRAMP.EFI variants — do NOT mix up (sha256s from 2026-08 downloads):
  - **embedded-config version** (in GUF296 template FAT + old super FAT, 2becf94f…): strings
    show `menuentry "Qualcomm direct boot (RamPartition memory, userdata root)" { linuxdirect
    /Image root=PARTLABEL=userdata rw rootwait drm_client_lib.active=none }`. This is what
    makes the device boot root=userdata regardless of FAT-side config.
  - **CONFIGFILE version** (GUF296 release `QCOMRAMP-CONFIGFILE.EFI`, 4,018,176 B, 41115b43…):
    no embedded root string; carries qcomfdtmem/rampartition modules; GUF296's
    build-grub-image.sh writes its external config at EFI/BOOT/qcomramp.cfg; its embedded
    startup script is compressed (invisible to plain strings).
  - **BOOTAA64.EFI** (753,664 B, 4d078771…): outer menu GRUB ONLY — contains `/boot/grub/`
    path, has NO linuxdirect/qcomfdtmem modules (cannot direct-boot by itself). Identical in
    template FAT and fresh grubfat builds.
- ⚠️ UNRESOLVED (2026-08, evidence log — do NOT treat as workflow): after super was replaced
  with rebuilt Android partitions (super FAT gone; grubfat = the only FAT, holding outer
  grub.cfg + CONFIGFILE QCOMRAMP.EFI + qcomramp.cfg root=PARTLABEL=ubuntu), the device STILL
  booted `root=PARTLABEL=userdata`. So either the boot.img payload chain never reads the
  FAT's grub.cfg/qcomramp.cfg, or the chainload→configfile read fails silently and falls back
  to an embedded userdata config. Next diagnostic: does a GRUB menu appear at boot (proves
  outer GRUB reads the FAT config) or does it boot straight through (payload chain is
  self-contained → must rebuild boot.img with GUF296's grub-mkstandalone build dir, or
  byte-patch the embedded `root=PARTLABEL=userdata` string — untested ideas, not validated).
- FAT32 boot image: label Y700GRUB, default `BOOT_IMAGE_SIZE=14G` (that size is for flashing
  into SUPER in the single-OS scheme; a dedicated partition needs only ~256M–1G). Contains
  `/Image` (kernel), `/dtb/sm8650-lenovo-tb321fu.dtb`, EFI/BOOT/{BOOTAA64.EFI,QCOMRAMP.EFI},
  grub.cfg, BOOT-INFO.txt.
- Dual-boot design (super stays Android): boot_a = Android boot.img, boot_b = GRUB UEFI
  boot.img, new `grubfat` FAT32 + `ubuntu` ext4 partitions from shrinking userdata,
  `fastboot set_active a|b` / Android `bootctl set-active-boot-slot b` to switch.
- `root=PARTLABEL=` resolves from GPT partition name.

## Rootfs migration (userdata → ubuntu partition) — verified on this device
Desktop Linux (kubuntu rootfs) is NOT an adb device — no adbd runs, `adb devices` shows
nothing. Transfer files to the tablet via an HTTP server on the PC
(`python3 -m http.server 8000 --bind 0.0.0.0`) + `curl` in a Konsole terminal; the tablet
needs to be on the same LAN as the PC.
- Device path differs from Android: desktop Linux uses `/dev/disk/by-partlabel/ubuntu`,
  NOT `/dev/block/by-name/ubuntu` (Android-only symlink layout). GPT entry N maps to
  `/dev/sdaN` (e.g. ubuntu = sda17, grubfat = sda18).
- Migration recipe (run as root on the tablet):
  `mount /dev/disk/by-partlabel/ubuntu /mnt/ubuntu` then
  `rsync -aHAX --exclude=/proc --exclude=/sys --exclude=/dev --exclude=/run --exclude=/tmp
  --exclude=/mnt --exclude=/media --exclude=/lost+found --exclude=/swapfile / /mnt/ubuntu/`
  then `sync; umount`. ~5–10 min at UFS speeds (123 MB/s observed).
- fstab may have NO explicit root entry (kernel cmdline `root=PARTLABEL=` drives it) — leave
  it alone; verify the copy via `/mnt/ubuntu/etc/hostname` before unmounting.
- Safe order for the super swap (each step keeps a boot path alive): ① GPT rewrite (shrink
  userdata, add ubuntu+grubfat) → ② `fastboot format:ext4 ubuntu`, flash grubfat + boot_b=GRUB
  → ③ migrate rootfs → ④ verify boot from the new partition (`df -h /` must show /dev/sda17)
  → ⑤ ONLY THEN flash the rebuilt super (wipes the FAT that old GRUB paths depended on).
- Flashing grubfat (contains /Image) BEFORE ③ breaks boot: GRUB `search --file /Image` may
  pick the new FAT whose config points at an empty rootfs → A/B retry exhausts →
  slot-unbootable → fastboot loop. Recovery: `fastboot erase grubfat` + `fastboot set_active <slot>`
  (clears unbootable + resets retry count), reboot, then re-flash grubfat after migration.

## GSI / AVB notes
- Vendor fstab mounts system/system_ext/system_dlkm with
  `avb_keys=/avb/q-gsi.avbpubkey:...:u-gsi.avbpubkey` → vendor is GSI-ready; GSI system images
  signed with AOSP/GSI test keys are accepted.
- ABL trusts the AOSP test key up to ZUI 17.5.10.170 (LTBox docs); keep firmware ≤ that for
  test-key-signed images to verify.
- vbmeta: `fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img` disables
  AVB (breaks OTA/Widevine L1).
