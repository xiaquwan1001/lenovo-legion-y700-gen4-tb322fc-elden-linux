# Qualcomm Android Device Flashing & Modding

Class-level playbook for EDL-mode flashing, secure-boot workarounds, unbrick, AVB handling, and Linux-on-Android dual boot on Snapdragon phones/tablets (Lenovo ZUI tablets especially).

## When to use
Any task on a Qualcomm Android device: unlock/modify bootloader, EDL (9008) flashing, unbrick after cross-region flash, disable AVB, boot Linux alongside Android, or evaluate what an "engineering firmware" can actually do.

## Hard facts (shape every plan)
1. **Secure-boot fuses are one-way.** Production Snapdragon units (SM8xxx) have secure boot permanently fused. No firmware "unlocks" it — an *engineering loader* only bypasses the signature check at the EDL/Sahara stage, giving full partition read/write (equivalent to engineering-unit access). Say this plainly to the user; don't sell "secure boot unlock" as permanent.
2. **Lenovo ABL trusts the AOSP test key** on recent models up to a firmware cutoff (e.g. TB321FU <= ZUI 17.5.10.170). Inside the window you can AVB-sign custom images with `avbtool` + AOSP test key and they pass verification. Do NOT OTA past the cutoff. Outside the window, use `fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img`.
3. **A/B slots ARE a dual-boot mechanism.** boot_a = Android, boot_b = UEFI GRUB, switch with `fastboot set_active a|b` or (Android root) `bootctl set-active-boot-slot b`. No partition-table change needed for boot selection itself.

## Region lock: "系统与硬件不兼容 / not compatible with hardware" is the ABL EBS gate (2026-08-08)
**This SUPERSEDES the earlier "kernel crash / LP-geometry" attribution for attempts A3–A6 on TB321FU.** Read `references/tb321fu-region-lock.md` for the full forensics.
- **logfs marker `Start EBS [<ms>]` = entry to the Emergency Boot Screen, NOT "passed ABL to kernel".** A logfs record that ends at `Start EBS` with NO `Load Image boot_a` line means the device never left the ABL gate. All A2–A6 "kernel stage" readings were wrong; the minidump/rawdump analyzed earlier was a stale dump from an earlier real boot.
- **The gate is a REGION check**: CN (PRC) hardware + ROW firmware = EBS "不兼容" + auto-shutdown. Region marker lives in the **vendor_boot DTB** as an FDT node named `product_region` whose property value is `PRC` or `ROW` (TB321FU ROW 17.5.10.031 vendor_boot carries 4× `IROW`; no `.ROW`).
- **Fingerprint strings are NOT the check target**: patching `ZUI_17.5.10.031_251125_ROW` → `_PRC` in boot/vendor_boot/dtbo/init_boot (equal-length) did NOT pass the gate. Only the DTB node matters.
- **misc partition in this state reads `ffbm-00`** (factory-mode marker; XDA threads tie it to the same "not compatible" bootloop family). If EBS persists after region conversion, try clearing misc (EDL `edl w misc` with a zeroed 1 MiB image) to remove FFBM influence.
- QSEE log noise `QseeResponse->result = 0xE / Status = 0x7` appears in the same records but is not itself the gate (also seen on panel/TA side).

### Region conversion fix path (LTBox method — gate PASSED 2026-08-08, see reference for the follow-on blocker)
Community tool **LTBox** (github.com/miner7222/LTBox, Rust) does CN↔ROW conversion for gen-3 Y700s; its `crates/ltbox-patch/src/region.rs` defines the exact mechanism (reverse-engineered this session). **Status 2026-08-08: LTBox is now a full GUI tool (v3.2.2, active dev, wiki miner7222.github.io/ltbox/en) that automates region conversion + rollback bypass + .x→XML decryption + EDL partition/LUN flashing — no longer just reference source. DEPLOYED at `~/.local/bin/ltbox` (official prebuilt tarball; udev rules + desktop entry installed, pkexec auth). Survey + full deployment record incl. DynoBox (undeployed) + TWRP b0006 (downloaded) + CN ZUI→ZUXOS switch: `references/community-tool-status-2026-08.md`.**
The conversion steps (from its source):
1. **Patch ONLY vendor_boot**: replace `.ROW`→`.PRC` and `IROW`→`IPRC` (equal length, all occurrences; ROW→PRC direction for a CN unit). **Marker search tip**: the literal FDT node name `product_region` may NOT exist in a given firmware (0 occurrences in TB321FU 17.5.10.031) — the markers are the FDT_PROP property VALUES `IROW`/`IPRC` themselves (byte pattern `03 00 00 00 04 00 00 00 <val>\0` = FDT_PROP token, len=4). Grep for `IROW`/`.ROW` values, not the node name.
2. **Re-sign the patched vendor_boot** with the AOSP test key via avbtool (ABL trusts testkey up to ZUI ≤ 17.5.10.170 — see Hard facts).
3. **Rebuild vbmeta** signed with the same testkey, refreshing the vendor_boot hash descriptor; keep the original rollback index (main vbmeta rollback=0 on TB321FU) and flags=0.
4. Keep vbmeta_system flags=2 (disable) and **drop the chain descriptor** for vbmeta_system from the rebuilt main vbmeta so system/vendor inside super are NOT verified — this is what lets a GSI run. (Unreferenced vbmeta_system is inert.)
5. A1 still stands: a GSI project's OWN boot/vendor_boot images are rejected; use stock boot stack + GSI system only.
6. **EMPIRICAL RESULT (2026-08-08): the EBS region gate PASSES after this fix** — the "系统与硬件不兼容" message disappears once the vendor_boot DTB region values are PRC. Fingerprint-string patching alone does NOT pass (wasted cycle, confirmed). **Follow-on `prevent flash verify` gate — RESOLVED same evening by the official MOD combo (verified: passes fastboot, shows BL "未验证" warning, kernel loads then black-screens only because super still held the hand-built GSI).**
7. **Ready-made alternative (PREFERRED, verified working 2026-08-08)**: XDA user ahnoriku ships pre-converted **MOD ROW→PRC firmware packages** for TB321FU — incl. `ZUI 17.5.10.031 mod ROW->PRC` (6.63 GiB, Google Drive id `1X6OP5QoNBUsJyhRsSojN_Qm5RqT5Ws9q`), plus 17.0.12.183 / 17.0.12.136 MODs; each is a complete EDL flash package (Flash.cmd + image/ + optional Magisk/KernelSU root). XDA thread "Lenovo Y700 Gen 3 CN Rom to ROW Rom Guide" (4744907) has the full toolchain: decrypt_x_to_xml (Breed43214), `TB320FC_ROW_fastboot_prc_v2.x.zip` (vendor_boot modifier), hitin911 modified XMLs, QFIL v3. **USB rule from that guide: USB 2.0 port + USB 2.0 cable + device LONG-side USB-C port** — else device detection in fastboot/EDL is unreliable (matches the EDL USB-Overflow wedges seen this session). **Boot combo that passes prevent-flash (see `references/tb321fu-mod-package-boot.md`)**: MOD package's own PRC vendor_boot + testkey-signed boot (pixel_pkg/boot.img IS this) + MOD testkey vbmeta (chain vbmeta_system to OEM key) + OEM vbmeta_system — flashed via EDL. Critical difference vs manual avbtool re-signing: **avbtool add_hash_footer rewrites the vendor_boot EMBEDDED vbmeta field (@0xd5f012: 0x00800100 → 0x00024002… +8 B), which triggers prevent-flash; the official tool only patches region bytes and leaves the embedded vbmeta untouched.**

### avbtool rebuild recipe (LineageOS `android_external_avb`, single-file `avbtool.py`)
- Clone: `git clone --depth 1 https://github.com/LineageOS/android_external_avb` (aosp-mirror path 404s). Test key: `test/data/testkey_rsa4096.pem`.
- Sign images: `avbtool.py add_hash_footer --image <img> --partition_name <name> --partition_size <GPT size> --key testkey_rsa4096.pem --algorithm SHA256_RSA4096 --rollback_index <rb> --flags 0`. Re-signing an image that already carries an OEM footer preserves its original hash range (image_size) — fine, ABL hashes the same range.
- Rebuild vbmeta: `avbtool.py make_vbmeta_image --output vbmeta.img --key testkey_rsa4096.pem --algorithm SHA256_RSA4096 --rollback_index 0 --flags 0 --include_descriptors_from_image boot.img --include_descriptors_from_image vendor_boot.img --include_descriptors_from_image init_boot.img --include_descriptors_from_image dtbo.img`. No `--chain_partition` = vbmeta_system unreferenced.
- Reference values (TB321FU ROW 17.5.10.031): main vbmeta rollback=0; vbmeta_system rollback=1759622400 (RSA2048 OEM key); boot.img carries its own AVB footer rollback=1759622400; vendor_boot/init_boot/dtbo have NO footer (hashed by main vbmeta, image_size 14020608/2105344/20222888).
- OEM vbmeta structure to replicate/understand: main vbmeta = chain descriptors (boot loc3, recovery loc1, vbmeta_system loc2) + hash descriptors for vendor_boot/dtbo/init_boot/odm/vendor_dlkm/etc + fingerprint props; vbmeta_system = hash/hashtree descriptors for system/vendor/product/system_ext/pvmfw.
- Manual AVB header parse (when no avbtool): `AVB0` magic; header = magic(4) minor(4) auth_block_sz(8) aux_block_sz(8) algorithm(4) hash_off(4) hash_sz(4) sig_off(4) sig_sz(4) pubkey_off(4) pubkey_sz(4) rollback_index(8)@52 flags(8)@60 release[64]@68; aux block at 32+auth_sz; vbmeta flags=2 at byte 60 = verification disabled.

## KernelSU on Lenovo ZUI (LKM route — the ONLY viable root on TB321FU family)
- **GKI mode (KernelSU official boot.img swap) = DEAD END on Lenovo**: replacing boot.img's kernel with the GKI Image triggers the same ABL "系统与固件不兼容" gate that rejects GSI-project boot images (verified 8/7). Self-compiling the kernel is blocked too — Lenovo GPL tarball is incomplete (no DTS, wrong version; lenovo/gplcc issues #4/#5).
- **LKM mode works**: KernelSU ≥1.0 / KernelSU-Next patch the **init_boot** ramdisk only (inject ksud + ksu.ko), kernel stays stock → ABL gates not triggered. Community-proof: ahnoriku MOD packages ship `init_boot_kernelsu.img` inside the official Flash.cmd flow; Bilibili BV1XQQkBuEmv (y700 三代 LKM), BV1x442197cv.
- **KMI must match the RUNNING kernel — NOT vmlinux strings (2026-08-10 correction)**: `strings vmlinux | grep '^Linux version'` reported `6.1.84-android14-11`, but the ACTUALLY BOOTED kernel (LTBox-flashed stock boot.img) is `6.1.112-android14-11` (`adb shell uname -r`). The package vmlinux is a stale symbol file, not the shipped kernel. **Authoritative KMI source = the booted system** (`adb shell uname -r`) or unpacking the package's own boot.img ramdisk; patch with `--kmi android14-6.1.112`. Note: patching the same stock init_boot with `--kmi android14-6.1.84` vs `--kmi android14-6.1.112` produced byte-identical output images (same sha256) — the ksu.ko carries its own KMI; the --kmi flag is advisory. KernelSU-Next v3.3.0 releases publish per-KMI modules (`android14-6.1_kernelsu.ko`, `android15-6.6_...`, etc.) + `ksud-<arch>-unknown-linux-musl` (PC patcher) + Manager APK.
- PC patch: `ksud boot-patch -b init_boot.img -m android14-6.1_kernelsu.ko --kmi android14-6.1.84 --out-name init_boot_ksu.img -o <dir>` — **`-o` may only be given once** (argparse error "cannot be used multiple times"). Output keeps ANDROID! magic + v4 header; ramdisk grows ~2.1MB → ~2.5MB.
- **CN firmware is EASIER than ROW** (2026-08-10): native PRC (no region conversion), vbmeta already AOSP-testkey-signed (sha1 2597c218), **plaintext rawprogram/patch XML** (no .x decryption). Name quirk: zip filename says `ZUI_17.0.10.138` but inner dir is `TB321FU_ZUX_1.1.10.138` (ZUXOS line, Android 14).
- **Anti-rollback check before flashing a DIFFERENT line**: read the target boot.img's AVB footer rollback (`avbtool info_image`) and compare against rpmb's stored value (≈ last successfully-flashed firmware's rollback). CN ZUXOS 1.1.10.138 boot rollback=1746403200 < rpmb 1759622400 (ROW 17.5.10.031 era) → ABL rejects (logfs: `boot_a: Image rollback index is less than the stored rollback index`).
- **disable vbmeta does NOT bypass rollback on CN ABL (2026-08-10 correction — earlier ROW-era claim refuted)**: swapping vbmeta_a/vbmeta_system_a for disable (flags=2, alg=NONE) images does NOT skip avb_slot_verify on the CN 1.1.10.138 ABL — logfs still shows the boot_a rollback error AND dtbo/vendor_boot hash errors AND then `run into prevent flash verify!!!` → EBS/fastboot loop. The CN ABL treats an unsigned (alg=NONE) vbmeta as "modified chain". **Only LTBox's full-flash wizard with its built-in Bypass Rollback Protection passed both walls** (official toolchain re-signs vbmeta properly; verified booting 2026-08-10). Manual avbtool chains remain a dead end for cross-line downgrade flashes on TB321FU.
- **vbmeta disable image must be padded to partition size** (vbmeta_a = 16 sectors = 64KB on TB321FU) before qfil — rawprogram XML writes the whole partition, a 4KB file leaves a short write.
- CN package quirks: `super.img` referenced in rawprogram0.xml but only `super_1..7.img` splits ship → cat + pad to 3407872×4096 = 13,958,643,712 B, then remove the XML super entry and flash via `edl.py w super` (avoids sparse conversion). `vm-bootsys.img`/`vm-persist.img` referenced in rawprogram4.xml but ABSENT from the package → clear `filename=""` on those entries (skip write; harmless without dual-boot). Full prep recipe + file inventory: `references/kernelsu-lkm-zui-cn.md`.
- **qfil partial-write RECURRED on CN package (2nd time, 2026-08-10)**: after `edl.py qfil rawprogram0-5` all exited 0, readback revealed vbmeta_a/vbmeta_system_a/init_boot_a were NOT written (kept previous MOD content) while boot/dtbo/vendor_boot WERE correctly written — the qfil progress bar and exit code give NO per-partition truth. **Readback-verify EVERY partition after any qfil; a post-write `Connection detected, quiting.` wedge is EXPECTED and does not mean the write failed** (device-side USB controller wedges; power-cycle back into EDL for the verify pass). vbmeta_a/vbmeta_system_a are 16-sector (64KB) partitions — pad any hand-built vbmeta to 65536 B before qfil.
- **Fresh CN flash has USB debugging OFF by default**: after first boot, `adb devices` is empty even with 17ef udev rules present — user must enable Developer options (tap build ×7) + USB debugging + accept the RSA prompt AND set USB mode to file transfer/MTP before adb enumerates. Don't debug the host rules first; check the device's USB mode toggles.
- **A cable with poor electricals can kill adb+fastboot enumeration TOGETHER (TB322FC 2026-08-17)**: the old cable had a USB-Overflow history; after the ZUX OS 1.1 OTA, `adb devices` AND `fastboot devices` were both empty while `lsusb` still showed `17ef:7f40 Lenovo Y700` — but its USB role enumerated as **PTP (Imaging class)**, i.e. the ADB interface was never exposed. Diagnosis order: (1) `lsusb` — is the device present at all? (2) USB role — PTP/charging = wrong role; fix on the device's USB-mode notification (choose file transfer/debug, NOT PTP). (3) Only then suspect the cable — swapping cables fixed it instantly. A post-OTA USB-mode/authorization reset can mask the real cause; the cable's earlier Overflow pattern is the tell.
- Verify big firmware zips BEFORE building a plan: two same-name downloads may differ in tail bytes (a zero-filled tail = preallocated-but-incomplete download; `7z l` reports "Headers Error" on the bad copy while the `(1)` copy opens fine).

## Engineering loader pattern (xbl_s_devprg_ns.melf)
- The generic `prog_firehose_ddr.elf` often does NOT work on newer Snapdragon (SM8650+): Sahara/QSahara errors. Use `xbl_s_devprg_ns.melf` (XBL no-signature DevPrg) as the QFIL programmer instead — for the whole Lenovo family it is the working one.
- The melf ships INSIDE official firmware packages (`image/xbl_s_devprg_ns.melf`); also mirrored at temblast.com/ref/loaders.htm and archive.diablosat.cc/firmwares/amt-dumps/FirehoseLoaders/. Prefer the package's own copy (per-version).
- QFIL (Windows) also needs a fixed `contents.xml` for some packages (XDA attachments). Linux routes (bkerler/edl, qdl-rs) don't use contents.xml — prefer them on Linux.
- EDL entry: power off -> hold Vol+ -> plug USB (Y700: use the LONG-side USB-C port). From system: `adb reboot edl`. From fastboot: `fastboot oem edl` (not always present).
- bkerler/edl: **NOT installable via `pip install edl`** — that PyPI name is an unrelated video/monitoring tool (its setup imports `timecode`). Install from GitHub source: tarball (CN network: gh-proxy.com proxy — see china-mirror skill) -> extract -> `python3 -m venv venv-edl && venv-edl/bin/pip install -r requirements.txt` (PEP 668 hosts need the venv; pyusb imports as `usb`, verify `import usb, serial`). Commands: `edl.py -l <melf> printgpt` (real GPT incl. LUN layout), `secureboot`, `r`/`w` partitions, `rl <dir>` backup-all, `gpt <dir>` write GPT, `ws <start_sector> <file>` raw-sector write, `qfil <rawprogram> <patch> <imagedir>` QFIL-XML flash, `setactiveslot <a|b>`. qdl-rs: `qdl-rs --loader-path <melf> --storage-type ufs --backend serial --dev-path <COM> --phys-part-idx 4 write <part> <file>`.

## fastboot channel wedge (diagnose before blaming the device)
Symptom: `fastboot devices` lists the serial, but getvar/flash/oem commands hang (even with timeout) — or a long `getvar all` run wedges the channel afterwards. Fix: **physically unplug/replug USB or power-cycle the tablet back into fastboot**. Re-verify with a single quick `fastboot getvar product` (should return in <1s). Use `timeout 8 fastboot <cmd>` per probe; batch probes into one shell loop.

## Getting the real partition table
- `fastboot getvar all` prints `partition-type:<name>` and `partition-size:<name>` (hex) for every partition — the AUTHORITATIVE layout, even when the package's `gpt_*.bin` files are zeroed placeholders (Lenovo ships empty gpt_mainN.bin; real GPT is built from rawprogram XML at flash time).
- Lenovo `.x` files (rawprogram/patch/contents) are encrypted XML; decrypt with the XDA tool (`pip install cryptography` + decrypt_batch.bat).
- Parse Android boot images (v3/v4) in python: magic `ANDROID!`, header_version at 0x28; v3: kernel_size@8, ramdisk_size@12, hdr_size@20, cmdline@36. A UEFI-GRUB boot.img is v3 with gzip'd GRUB as the "kernel" section and NO ramdisk.

## Linux dual-boot on Qualcomm Android (GRUB UEFI route)
Verified architecture + working example: `references/grub-uefi-dual-boot.md` (Y700 Gen3/TB321FU, GUF296 CI pipeline) and `references/uefi-boot-chain-vm-bootsys.md` (EMPIRICALLY verified chain, corrects the model below).
**SM8750-era devices (no vm-bootsys, e.g. Y700 Gen4/TB322FC): the Gen3 GUF296 chain does NOT carry over.** Resurvey 2026-08-16: the working UEFI route for SM8750 is **Project Silicium Mu-Silicium** (github.com/Project-Silicium/Mu-Silicium, Project-Mu-based ARM64 UEFI; supports OnePlus 13/13s; its Y700 entry = 2023 9707f only, Inactive) → EFISTUB/GRUB → mainline kernel; a device port (memory map/UFS/panel/touch) sits on an existing SM8750 base. Mainline kernels to build from: `sm8750-mainline/linux` (master v6.16) and `renhiyama/pagani-linux` (Linux 7.1, display/touch/ath12k working); TB322FC DT patch (Pengyu Luo) pending in linux-arm-kernel. Fallback without UEFI: package mainline Image.gz+dtb+initramfs as Android boot.img (mkbootimg) → `fastboot boot` / `flash boot_b` (ABL acceptance on unlocked Gen4 unverified). Device detail: `../qualcomm-edl-flashing/references/tb322fc-y700-gen4.md` + bootloop/GPT forensics in `../qualcomm-edl-flashing/references/tb322fc-bootloop-gpt-mismatch.md`.
Key insight: **GRUB splits into two pieces** — (a) a UEFI boot.img flashed to a boot slot; (b) a FAT32 partition holding `/Image` (kernel), `/dtb/<model>.dtb`, `EFI/BOOT/BOOTAA64.EFI` + grub.cfg. GRUB uses Qualcomm-custom modules: `linuxdirect`, `rampartition`, `qcomfdtmem`.
**Corrected (verified 2026-08-07):** the boot.img "kernel" section is NOT gzip'd GRUB EFI — it decompresses (7z) to a COMPLETE Qualcomm UEFI firmware environment (EDK2 DXE drivers: BdsDxe, DxeCore, LinuxLoader.efi = ABL variant, RamPartitionDxe, Fat.efi, UFSDxe), magic 0x10000381. Its BDS loads GRUB from a FAT on the BOOTLOADER LUN: `vm-bootsys_a` (537 MB, label Y700BOOT, Linux `sde19`). A grubfat you add on LUN 0 is NEVER read — the root that boots is decided by the QCOMRAMP.EFI variant inside vm-bootsys_a (embedded `root=PARTLABEL=userdata` vs CONFIGFILE reading `EFI/BOOT/qcomramp.cfg`).
Deadlock that kills naive plans: the FAT image is often sized to fill `super` (13-14G), which destroys Android's dynamic partitions (system/vendor/product live in super) -> Android won't boot. Fix: keep super for Android, **shrink `userdata` (huge, often last) via GPT rewrite and add dedicated `ubuntu` (ext4 rootfs) + `grubfat` (1G FAT32) partitions**. GRUB kernel args use `root=PARTLABEL=<name>`.
**Verified end-state (TB321FU): DUAL-BOOT COMPLETE 2026-08-10** — see `references/tb322fc-dualboot-2026-09.md` (TB322FC dual-boot working recipe, hashes, and slot-switch commands) for the full working recipe, hashes, and slot-switch commands. Both sides boot:
- Ubuntu chain VERIFIED: UEFI env → vm-bootsys_a FAT → GRUB → QCOMRAMP CONFIGFILE → `root=PARTLABEL=ubuntu` (sda17).
- Android chain VERIFIED: a-slot official boot.img → ABL → Pixel GSI (system-only, NindoS path).
- **Slot model: a = Android (official boot.img), b = Ubuntu (GUF296 boot.img). Switch = `fastboot set_active a|b`.**

- **The two sides are fully isolated**: Ubuntu's kernel/GRUB live on vm-bootsys_a + the ubuntu partition, NOT on super — so super can be re-flashed (ZUI restore, GSI swap) without touching Ubuntu, and vice versa. This isolation is what made the failed Android experiment free (set_active b → Ubuntu always works).
- AVB: on this unlocked device custom UEFI boot.img boots with vbmeta flags=0 (verification effectively non-enforcing); still verify empirically per device before assuming.
- Linux rootfs never marks the slot boot-successful → `slot-retry-count` drains every boot → after 7 boots `slot-unbootable:yes` → fastboot loop. Fix each time: `fastboot set_active <slot>` (clears flag, resets retry). Permanent fix = a boot-successful marking service in the rootfs.
Restoring super: OEM packages ship the dynamic partitions as **individual fs images** (ext4/erofs) + rawprogram XML giving LP-metadata offsets — NOT one sparse super.img. ROW zip packages encrypt those XMLs (`.x` extension); CN 7z packages historically ship plain XMLs — an old CN package's offsets can flash newer images (super content is not rollback-indexed). Alternatives to the `.x` decrypt: XDA Breed43214 tool (`pip install cryptography` + decrypt_batch.bat), or rebuild super with lpmake from the fs images (Python-lpmake recipe in `qualcomm-edl-flashing`).
**QFIL super_1~8 split-image shortcut (verified 2026-08-08)**: the `super_1.img..super_8.img` splits are NOT Android sparse and NOT LP images — they are **contiguous raw data segments**; `cat` them in order to get the full super image (splits total < partition size; tail is zero-filled). Lenovo LP metadata sits at NON-standard offsets in the concatenation (GEOM @ ~218 MB, LPML @ ~3.3 GB — scan the file for `GEOM`/`LPML`, do NOT assume AOSP head layout). **super is a PHYSICAL partition — bootloader-mode `fastboot flash super` works directly** (fastbootd is only needed for super-INTERNAL logical partitions like system/vendor). Pad to `fastboot getvar partition-size:super` bytes (TB321FU = 0x340000000 = 13,971,390,464) with `dd if=/dev/zero of=pad bs=1 count=0 seek=<size>` + `dd if=full of=pad conv=notrunc`; build on DISK not /tmp (tmpfs quota). Verify EDL writes by read-back sha256 (note: `Connection detected, quiting.` often prints AFTER a successful EDL write — read back before judging failure).

## Pitfalls
- Relocking the bootloader on cross-region/custom ROMs = brick. Never suggest it.
- GPT rewrite interrupted (power loss) = hard brick; recoverable via EDL 9008 but require full battery first.
- AVB: any custom boot/vendor_boot image needs vbmeta with verification disabled OR AOSP-test-key-signed vbmeta chain.
- ZUI anti-rollback: never flash OLDER firmware packages (bootloop/region-lock). Always use the newest 9008 package for rescue.
- Shrinking userdata destroys its content: if the current Linux rootfs lives on userdata (common GUF296-style setup, root=PARTLABEL=userdata), back up or plan to re-flash to the new partition BEFORE shrinking.
- fastboot format: `fastboot format:ext4 <part>` / `fastboot format:vfat <part>` for newly created GPT partitions.
- EDL over USB3.x fails on many boards (~100% per Y700 community reports): use a USB2.0 port or a USB2-only cable for EDL/QFIL work.
- **bkerler/edl firehose sessions die after 1–2 partition writes with `USB Overflow`** ("Connection detected, quiting."). Re-trying the same command never recovers; the fix is a physical USB re-enumeration — unplug/replug the cable (device stays in EDL) — then continue the remaining writes one pair at a time. For BL-unlocked devices, prefer `fastboot flash <part>` over EDL for boot/vendor_boot/dtbo/init_boot/vbmeta writes (fastboot channel is stable where EDL firehose wedges). Note `edl w <partition> <img>` writes by GPT partition name (boot_a, not boot).
- **logfs "Start EBS" ≠ kernel handoff**: a logfs record ending at `Start EBS` with no `Load Image boot_a` line means the ABL gate rejected the boot (region lock, etc.). Capture logfs IMMEDIATELY after the first failed boot (`edl r logfs`) before retries overwrite the ring buffer; read misc (`edl r misc`) for the `ffbm-00` factory-mode marker.
- Before probing a device, consult `fastboot -h` for the supported op set (client v36: `fetch`, `flashing get_unlock_ability`, `oem`, `format:FS[:SIZE]`, `set_active`, snapshot/gsi/wipe-super...). Don't guess commands that may hang or return 'unknown command'.
- Lenovo custom ABL "系统与固件不兼容 / system not compatible with the firmware, auto-shutdown": two distinct triggers — (a) a NON-OEM standard-Linux-kernel boot.img (a GSI project's OWN boot.img) even with BL unlocked + disable-verification vbmeta; (b) **REGION MISMATCH** (CN hardware + ROW firmware, checked via vendor_boot DTB `product_region` node — see the Region lock section; the earlier "AVB/dtb/os_version ruled out" list missed this). The GSI README fix: flash the GSI system ONLY, on top of the STOCK boot/vendor_boot/init_boot/dtbo/vbmeta. Do NOT flash a GSI project's bundled boot/vendor_boot images.
- **Boot stack version matching**: boot/vendor_boot/init_boot/dtbo (and vendor inside super) must all be the SAME firmware version. A device with a long mixed flash history (e.g. abl=CN ZUXOS 1.5.10.038, A-slot images=CN ZUI 17.0.10.338, super vendor=17.5.10.031) will pass the ABL gate with an OEM boot.img but crash at kernel stage if boot and init_boot/vendor_boot ramdisks are from different versions. Never trust an EDL backup's version — verify by unpacking init_boot ramdisk (LZ4 frame → `lz4 -d` → cpio → `build.prop` → `ro.bootimage.build.version.incremental`).
- GSI flash: use **fastbootd** (userspace fastboot, `adb reboot fastboot`) for `fastboot flash system <GSI.img>` — the bootloader-mode fastboot may not accept system writes the same way; stock boot stack stays untouched.
- When the user names an obscure boot/tool (e.g. 'tirith' as a GRUB-like loader): verify it exists on PyPI/GitHub FIRST. `pip install tirith` pulls an unrelated remote-monitoring package; no bootloader project by that name exists — confirm before installing, then clarify with the user.
- **GitHub API rate-limit escape (shared IPs 403)**: scrape HTML release pages instead — `curl -sL <repo>/releases/latest` (follow redirect → tag), then `curl -s <repo>/releases/expanded_assets/<tag>` and `grep -oE 'href="[^"]*download[^"]*"'` for asset URLs. Tags with spaces need URL-encoding (`%20`); if expanded_assets is empty, grep the releases page for `/releases/tag/` links to find the real short tag (e.g. TWRP tag is `b0006`, not its long title). Verify downloads with `file <img>` (expect "Android bootimg") before archiving/flashing.
- **iced/Rust-GUI tools swallow `--help`** (exit 0, no output): find hidden flags with `strings <bin>`; e.g. LTBox's `--install-udev` (needs root — `pkexec ./ltbox --install-udev` pops a graphical auth dialog; non-root run prints the exact command) and `--install-desktop` (no root). GUI health check: `timeout 8 <app>; echo $?` — 124 = healthy (ran until timeout), other = startup crash.
- **LTBox "Qualcomm kernel USB driver is missing" on Linux = qud-package check in kernel driver mode, NOT a real problem**: LTBox defaults `qcom_driver_mode: "kernel"` (`~/.config/ltbox/settings.json`) and warns when the `qud` package (source-compiled kernel-module .deb) is absent — even when `qcserial` is already loaded. Do NOT install qud (needs root + compile against the running kernel, risky on new HWE kernels). Fix: set `"qcom_driver_mode": "userspace"` in the settings file — userspace = plain libusb, the same transport the bkerler/edl chain uses. No root, no reboot; relaunch to verify the banner is gone. Detail: `references/community-tool-status-2026-08.md`.
