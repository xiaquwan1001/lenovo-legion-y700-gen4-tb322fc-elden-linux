## 1. Q28：第一次拿到「好发 vs 坏发」的同口径差分（本轮主要产出）

### 1.1 先立判据（之前一直在用 mdss 中断增量猜）

坏发的真实失败序列（串口 t=8.8→9.2 s，`logs/q28-BAD-live-20261009-221729/serial.log`）：

```
[8.862] msm_dsi ae94000/ae96000: timing 1904x3040@165Hz … (bonded=1 dsc=1 wide=1)
[9.090] msm_dsi ae94000.dsi: command DMA timeout: status=0x2200200
[9.097] msm_dsi ae96000.dsi: peer command DMA timeout: status=0x2200200
[9.097] msm_dsi ae94000.dsi: bonded command DMA failed: master=-110 peer=-110
[9.097] panel-novatek-nt36536: sending dcs data ff 20 failed
[9.097] panel-novatek-nt36536: panel init attempt 1 failed: -110, resetting and retrying
[9.127] panel-novatek-nt36536: sending dcs data ff 20 failed: -5      → attempt 2 failed
[9.161] dpu error enc35 intf1 ctl 1 reset failure: -22 → frame done timeout → vblank 风暴(109 条)
```

⇒ 断点**不在 DPU modeset**，在**面板初始化第一条 DCS 写（`ff 20`）走 bonded 命令 DMA 时超时**；面板没起来 ⇒ 没 vsync ⇒ vblank 风暴。

同批对照（同一次实验窗口，主机侧计数，`logs/q28-*/*/dmesg.txt`）：

| 样本 | `command DMA timeout` | `panel init attempt` | 结果 |
|---|---|---|---|
| q28-control-coldboot-181758（好） | 0 | 0 | 有桌面 |
| q28-cycle-20261009-182030（好） | 0 | 0 | 有桌面 |
| q28-cycle-173857 / 174115 / 174204 / 174256（vk74 四连坏） | 2 | 2 | 只剩背光 |
| 今晚 live 坏发（vk64，boot_b） | 2 | 2 | 只剩背光 |
| 今晚 vk75 坏发（RAM） | 2 | 2 | 只剩背光 |

⇒ **判据：坏发 ⟺ dmesg 出现 `command DMA timeout` + `panel init attempt … failed`（5 坏 / 2 好，零误报）**。
`vblank timeout` **不能单独当判据**：好发也出现过 4 条，且正常熄屏也会产生（本轮实测）。

### 1.2 寄存器差分（vk75 诊断内核，坏发一发到手）

产物：`logs/q28-BAD-vk75dump-20261009-22*/{dmesg.txt,q28-dumps.txt,state.txt}`，对照 `logs/q28-BASELINE-good-vk75-dmesg.txt`。

| 寄存器 | 好发 | 坏发 | |
|---|---|---|---|
| `STATUS0` | `0x0` | **`0x20003`** | 差 |
| `CLK_STATUS` | `0x2343` | **`0x3743`** | 差 |
| `cmd_dma_busy` | 0 | **1** | 差 |
| `cmd_engine_busy` | 0 | **1** | 差 |
| CTL / CMD_DMA_CTRL / DMA_BASE / DMA_LEN / TRIG_CTRL / TRIG_DMA / INTR_CTRL / PHY_RESET / CLK_CTRL / LANE_STATUS / FIFO / TIMEOUT_STATUS / ACK_ERR_STATUS / pll_unlock | 完全一致 | 完全一致 | — |

位解码（`drivers/gpu/drm/msm/generated/dsi.xml.h`）：

- `STATUS0 0x20003` = `CMD_MODE_ENGINE_BUSY(0x1)` + `CMD_MODE_DMA_BUSY(0x2)` + bit17(`0x20000`，本头文件 STATUS0 组未命名；同值位在 `DSI_FIFO_STATUS` 是 `DLN0_HS_FIFO_FULL`，**DSI 版本不同不能硬套，待查手册**）。
  ⇒ 命令 DMA **触发后再也没完成**（引擎一直 busy），不是"没触发"。
- `CLK_STATUS` 差的两位正好是 `0x400 DSI_DYN_PCLK_ACTIVE` + `0x1000 DSI_DYN_CMD_PCLK_ACTIVE`：
  **坏发在跑第一条命令 DMA 时，动态像素时钟域（DYN pclk / DYN cmd pclk）是"正在活动"的；好发不是。**

⇒ 收窄到的假说：**首次 modeset 时"命令引擎"与"DYN 像素时钟域切换/门控"撞在一起**，命令 DMA 永不完成。
这跟上一轮"只剩开机首次 modeset 的某个状态"的结论接得上，且第一次给出了**具体是哪两个状态位**。

### 1.3 下一步（按代价排序，都还没做）

1. **单变量延时**：在 `dsi_host.c` 命令 DMA 触发前插 `usleep_range()`（或首条 DCS 前等 DYN pclk 稳定），
   若坏发率显著下降 ⇒ 确认是 settle 竞态，再谈正经修法（而不是把 delay 当修复）。
2. **busy 时重触发**：命令 DMA 超时后读 `STATUS0`，若 engine busy 未清 → 先 reset 引擎再重试一次（对照现在直接放弃）。
   这条若有效，等于把「坏发」变成「慢一点的好发」，可日常可用（但仍是缓解，需与上游讨论）。
3. **谁在开 DYN pclk**：坏发时 `clk_summary` 里 DYN pclk 的 prepare/enable 计数与消费者（`state.txt` 已存），
   比对好发——这决定它是 fbcon/早期 console 提前推帧，还是 dpu_kms 上电顺序。

## 2. 重启通道：本轮把三条坑踩全了（详见 `PITFALLS` #150/#151）

| 通道 | 坏发（有 vblank 风暴）下的实测 |
|---|---|
| `reboot` / 包装脚本 `reboot -f` / `busybox reboot -f` | **全挂**：ssh 卡住、设备不动（内核 restart 路径被 DRM 卡死，`-f` 也躲不掉，因为卡在内核 notifier/device_shutdown） |
| **`echo b > /proc/sysrq-trigger`** | ✅ 25 s 回来（常驻装弹已开 sysrq=1） |
| **`/usr/local/sbin/reboot2 <mode>`**（RESTART2 syscall） | ✅ 5 s 进 fastboot，**坏发下也管用**（不经过关机链）⇒ 上机循环该用它 |
| `reboot bootloader`（OpenRC 模式） | ⚠️ **不进 fastboot**：走 openrc → halt → **VBUS 自动开机回 boot_b**。极可能就是 #143「reboot2 bootloader 后设备从 USB 完全消失」的真身（那次 VBUS 没把它叫醒） |
| `reboot2`（**无参数**） | ⚠️ ABL 当成"进 fastboot"⇒ 设备停在 fastboot 不动（本轮就停在这儿，被误判成"启动次数耗尽"） |
| 离开 fastboot | 用 **`fastboot reboot`**（会正常引导 current slot b） |

## 3. A/B 槽位险情：真的差点 unbootable（已修，附备份）

- 事实链：`fastboot getvar all` → `slot-retry-count:b:7 / slot-unbootable:no / slot-successful:no`；
  但设备侧 GPT 实测 `boot_b byte6=0x37 → retry=6 succ=0`（**每次真开机扣 1，`fastboot boot` 不扣也不置 succ**）。
  本轮为了 Q28 连打十几次温启 ⇒ **再 6 次就归零被 ABL 置 UNBOOTABLE、永久停 fastboot**。
- 处置（技能 `qbootctl-slot-management` 口径）：
  1. 先备份 LUN4（`/dev/sde`，4096 B/扇区）两表 → `backup/HA2EXB0E-16+512/slotfix-20261009-223928/gpt-lun4-{head,tail}.bin`（各 34 扇区）；
     ⚠️ busybox `dd` 的 `skip` 按 512 B 计、`/usr/bin/dd` 不存在 ⇒ 用 `python3` 读，别硬试 dd。
  2. `python3 /usr/local/sbin/slot-attr.py mark-successful b`（`0x37 → 0x7f`，primary+backup 都写、CRC 重算）+ `set b --retry 7`。
  3. **独立复核**（不信任脚本自报）：自己解析 primary(lba) 与 backup GPT 的分区条目 ⇒
     `PRIMARY/BACKUP #44 boot_b byte6=0x7f retry=7 active=1 succ=1 unbootable=0`，boot_a 仍是 `0x3a` 未动，`by-partlabel` 齐全。
- **改进（待落地）**：任何温启循环脚本（`q28-boot-cycle.sh` / `sleep-sweep.sh`）每轮开头应自带
  `mark-successful b`（或至少 `getvar slot-retry-count` 预检，<3 就停并上报）。现在没有 ⇒ 谁跑循环谁吃雷。

## 4. 模块化线：真因找到 + 在机验收通过

### 4.1 上一轮"lsmod 空"的真因不是"持久根缺模块"

从**产物镜像**读回 ramdisk 逐项核对：vk77-modular 里 `/init` **有** payload 钩子、39 个 payload `.ko` **都在**，
但 **`/usr/local/sbin/payload-modules-load.sh` 不在包里** ⇒ 钩子里 `[ -x … ]` 判假 ⇒ **静默不加载**。
（顺带：`patches/fragment-modular.config` 的目标项在 `linux/.config` 里确实已是 `=m`，但在机的 boot_b=vk64 是**模块化之前**构建的，那些驱动仍是 `=y`——上一轮"设备 vk63+ 实机证明加载链正常"的说话**不成立**，本轮作废。）

### 4.2 落地

- 修 `/init` 门控错误：payload 加载**不再**挂在 `elden_nocamera` 上（WiFi/音频不该被相机开关关掉）——`initramfs/init`、`rootfs/persistent-overlay/init` 两处。
- 新增 `scripts/build-payload-hook.sh`：往 base ramdisk 追加最小一层（`/init` + loader），**并自带 VERIFY：从产物里把 `/init`、loader、`.ko` 数量读回来断言**（不再信构建脚本"应该会装上"）。
- 构建 **vk78-modular**（`out/boot-elden-vk78-modular.img`，sha `02826a88f81c`，86 061 056 B < 96 MiB，cmdline 带 `elden_nocamera=1` 避免 Q24）；
  从镜像 unpack 读回：`init copies=2 / loader=1736 B / ko=39 / 钩子无条件` ✅。

### 4.4 迭代快环 `mod-loop.sh`：两条真 bug（自报"可用"没经得住实测）

1. `tar czf … kernel` 失败（`kernel：无法 stat`）——`M=<dir> modules_install` 对单目录 **不产出 `kernel/` 前缀**，改为按相对路径 `find -name '*.ko' -print0 | tar --null -T -`。
2. `payload-modules-load.sh` 结尾计数用带连字符的模块名去 grep `lsmod`（lsmod 里是下划线）⇒ 7 个只报 4。已修并注释原因。

修完实测：`scripts/mod-loop.sh drivers/input/misc --reload aw86927` 全绿——
增量编译+推送+`rmmod/modprobe` **总计 6.9 s**，设备侧 `loading out-of-tree module taints kernel` + 新 `input9/input10`，
`lsmod` 里 `aw86927` 在。**这才是模块化的真正收益**（改一个驱动 → 7 s 上机，不用重编内核/重做镜像/fastboot）。
