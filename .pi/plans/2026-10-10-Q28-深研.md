## 0. 结论速览（四条，都会在下文给证据）

1. **「谁开了 DYN 像素时钟」这个问题在驱动层面没有答案**：`CLK_STATUS` 的 `DYN_*_ACTIVE` 是**纯状态位**，
   软件侧唯一的控制手段是 `CLK_CTRL` 的 force-on 位（bit 8/9/11/20/21，厂商名 `DSI_CTRL_DYNAMIC_FORCE_ON`），
   而我们整个内核只在 `dsi_sw_reset_v2_9()` 里用过一次。「查驱动里谁 enable 了 DYN pclk」这条路走不通（§1.1 表）。
2. **当前好/坏差分的四项差异只有一个自由度，不足以支撑「命令引擎撞 DYN pclk 域切换」这个假说**：
   好发样本是在 **DMA 已完成（idle）** 的时刻取的（一次成功 DMA <150 µs，见 §1.2 时间戳证据），坏发样本是在
   **DMA 卡死（busy）** 的时刻取的。`STATUS0.BUSY` 与 `CLK_STATUS.DYN_*_ACTIVE` 是同一件事的两种写法，
   二者不是四个独立证据。**现有数据无法区分「DYN 域切换导致卡死」与「只是没跑完」**——需要一次同状态取样（§3 实验 E0）。
3. **「只有开机首次 modeset 触发」这个前提被高估了**：(a) 面板 init 每个 boot 只跑一次（DPMS 只走 bridge
   enable/disable，不会重跑 panel prepare），所以 80 轮 DPMS 0 命中**根本不构成证据**；(b) `dsi_bonded_cmd_failed`
   是**单向 latch，永不复位**（`dsi_manager.c:41/54/375/642`），失败后本 boot 所有后续 DCS 直接返回 `-EIO`
   ——坏发里 attempt 2 的 `-5` 就是它，不是第二次独立故障；这也解释了「只有背光无桌面」为什么永久化。
4. **真正值得打的三个源码级候选（都可单变量验证，比原三实验更贴根因）**：
   ① `DMA_SCHEDULE_CTRL` 竞争：本面板是 **video 模式**（`dsi_display0=…dsc_vid`，`mode_flags` 含
   `MIPI_DSI_MODE_VIDEO`），而 `dsi_host.c:2493` 的分支会在 **video engine 恰好 busy** 时把命令 DMA 排到某个
   schedule line；**这个寄存器恰恰不在现有 dump 里**（§1.4d）。
   ② 我们缺厂商的「force-on 动态时钟」括号：厂商每次动 `DSI_CTRL.ENABLE`（`ctrl_en`）/soft reset/phy sw reset
   都先 `CLK_CTRL |= 0x23F|BIT(8)|BIT(9)|BIT(11)|BIT(21)`（`dsi_ctrl_hw_cmn.c:22/312-327/803-826`），
   我们在 `dsi_ctrl_enable()`（`dsi_host.c:978/1000`）与 `bonded_xfer_prepare()`（`dsi_host.c:2394`）动 `DSI_CTRL`
   时**没有**这个括号。
   ③ bonded 触发的语义偏差：厂商在 cmd 模式下给 **master 写 `TRIG_CTRL=…0xc`、给 slave 写 `DMA_TRG_MUX=1` +
   `DMA_SCHEDULE_CTRL2` 窗口**（`dsi_ctrl_hw_2_2.c:224-259`），我们两边都清 MUX、都写 SW(0x4)、都清窗口，
   并且**额外 SW 触发 slave**。现有一致性（好发能出画面）只能说明它「通常能工作」。

**最优先实验（§3）＝E0：一次 `fastboot boot` 的诊断内核，把 dump 改成「触发后时间序列 + 补 `DMA_SCHEDULE_CTRL/2` +
双 host 对称 + 修预算 bug」。** 零风险（RAM 直启、只读寄存器），一次坏发就能同时判 §0.2 与 §0.4① 的死活，
比现有三个实验里任何一个的信息量都大，且是它们的前置条件（不做它，①②无论什么结果都还能被解释掉）。

## 1. 机制链：源码层面到底发生了什么

### 1.0 失败签名（复核过，与文档一致）

```
[8.788] dsi timing 1904x3040@165Hz …(bonded=1 dsc=1 wide=1)     ← 两颗 host 都完成 timing 编程
[9.090] ae94000: command DMA timeout: status=0x2200200          ← 200 ms 完成超时（wait_master）
[9.097] ae96000: peer command DMA timeout                        ← 500×10 µs 轮询也超时
[9.097] bonded command DMA failed: master=-110 peer=-110         ← 置 dsi_bonded_cmd_failed（单向 latch）
[9.097] panel-novatek-nt36536: sending dcs data ff 20 failed
[9.127] … dcs data ff 20 failed: -5                              ← 是 latch 给的 -EIO，不是第二次故障
之后    intf1 ctl 1 reset failure -22 → vblank 风暴 → 只有背光
```

时间账：8.788→9.090 = 302 ms，其中 200 ms 是完成等待、5 ms 是 slave 轮询 ⇒ 触发前准备只花了几十 ms，
**没有** 70 ms 的 `wait4video_done`（那条会打 `wait for video done timed out`，日志里没有）⇒ **触发时 video engine
并未 busy（或 busy 位为 0）**。这条时间账是后面 §1.4d 竞争假设的立足点，不是可忽略的细节。

### 1.1 谁置位 `DYN_PCLK_ACTIVE`？——软件里没有人；它是硬件自动门控的读数

寄存器语义（`drivers/gpu/drm/msm/registers/display/dsi.xml`、生成头 `generated/dsi.xml.h`）：

| 寄存器 | 方向 | 位 | 含义 |
|---|---|---|---|
| `CLK_CTRL`(0x118) | **写** | 0–5 `AHBS/AHBM/PCLK/DSICLK/BYTECLK/ESCCLK_ON` | 静态（AON 侧）时钟请求 |
| | | **9** `FORCE_ON_DYN_AHBM_HCLK` | 强制打开 DYN ahbm hclk |
| | | （mainline 未命名）**8 / 11 / 20 / 21** | 其余 DYN 域的 force-on（厂商在用） |
| `CLK_STATUS`(0x11c) | **只读** | 0/2/4/6/8/9 = `AON_*_ACTIVE` | 静态侧正在跑 |
| | | 1/3/5/7/**10**/**12** = `DYN_*_ACTIVE`（含 `DYN_PCLK`=10、`DYN_CMD_PCLK`=12） | **动态侧正在跑（逻辑有请求时硬件自动开，空闲自动关）** |
| | | 13 `CMD_PCLK_ACTIVE` / 14 `VID_PCLK_ACTIVE` / 16 `PLL_UNLOCKED` | 功能域 pclk |

厂商侧证据（`stock-src/…/display-drivers/msm/dsi/dsi_ctrl_hw_cmn.c`）：

- `:22` `#define DSI_CTRL_DYNAMIC_FORCE_ON (0x23F|BIT(8)|BIT(9)|BIT(11)|BIT(21))`，注释直白：**「Force On all dynamic clocks」**；
- 只有三处用它，且都是「逻辑即将空闲/正在复位，但必须让目标时钟域看到寄存器变化」的场合：
  `dsi_ctrl_hw_cmn_soft_reset()`（`:312-327`）、`dsi_ctrl_hw_cmn_ctrl_en()`（动 `DSI_CTRL.ENABLE`，`:803-826`）、
  `dsi_ctrl_phy_reset` 路径（`:1779` 写 `0x100a00`）；
- 反之 `dsi_ctrl_hw_cmn_cmd_engine_en()`（`:836-850`，动 `CMD_MODE_EN`）**不带**括号 ⇒ 命令引擎使能本身不要求 force-on。

我们的树里对 `CLK_CTRL` 的全部写点（`grep REG_DSI_CLK_CTRL`）：

| 位置 | 写什么 | 与厂商对应 |
|---|---|---|
| `dsi_host.c:99` `DSI_CLK_CTRL_ENABLE_CLKS` | 0–5 位 + **bit9**（=0x23f） | 等于厂商 `host_setup` 的 `0x23F`（`dsi_ctrl_hw_cmn.c:142`）——注意厂商 0x23F 里**已含 bit9** |
| `dsi_ctrl_enable()` `:978` | 0x23f | 同厂商 host_setup |
| `dsi_sw_reset_v2_9()` `:1203-1229` | `旧值 \| (0x23f-等价 \| BIT(8)\|BIT(9)\|BIT(11)\|BIT(21))`，脉冲后恢复 | **逐字对齐**厂商 `soft_reset` |

**⇒ 结论 1：软件里没有任何「打开 DYN pclk」的动作（除了 soft reset 期间的临时 force-on）。`DYN_*_ACTIVE` 是硬件按
内部逻辑请求自动门控的**状态**。所以 TASKS/INDEX 里写的「③查是谁开了 DYN pclk（比对 clk_summary/消费者）」
在驱动层拿不到答案；`state.txt` 的 `disp_cc_mdss_pclk0/1_clk`（prepare 1/enable 2、172 972 734 Hz）是**输入时钟**，
好发里同样是 enable 态（前一轮 `dsi1vco rate=0` 的教训正是「只有坏发样本」）。**这条实验应按 §3 的 E0 改写。**

### 1.2 四项差异 = 一个自由度：好发是在 idle 取的样

坏发 dump（`q28-dumps.txt`，卡死时刻）：`STATUS0=0x20003`（bit0 CMD_ENGINE_BUSY + bit1 CMD_DMA_BUSY + **bit17**）、
`CLK_STATUS=0x3743`（比好发多 bit10 `DYN_PCLK` + bit12 `DYN_CMD_PCLK`）。

好发 dump（`q28-BASELINE-good-vk75-dmesg.txt:991`）取自 `msm_dsi_host_bonded_cmd_wait_master()` 的
**成功返回前**（`dsi_host.c:2688` 的 `q28_dump_cmd_regs_ok`），即 **DMA 已经 done、busy 已清零**之后。
时间戳证明这条路径极快：

```
[8.818591] ok-master #1 …… STATUS0=0x0 CLK_STATUS=0x2343 busy=0/0
[8.818733] ok-master #2 …… STATUS0=0x0 CLK_STATUS=0x2343 busy=0/0     ← 两条 dump 相距 142 µs
```

⇒ 一条成功 bonded 命令的完整周期（prepare→stage→trigger→wait→poll→restore）**远小于 1 ms**。
好发样本必然落在「引擎已停、动态时钟已自动回 gating」的时刻，坏发样本必然落在「引擎还挂着请求」的时刻。
**于是「STATUS0 多 busy」与「CLK_STATUS 多 DYN_*」在逻辑上是同一个观测的两种表述**，
「首次 modeset 命令引擎撞 DYN pclk 域切换」目前**不是**由这四项差分推出来的，而是由「样本取样时刻不同」造成的
必要伴随现象。这正是本项目 PITFALLS 里「只有坏发样本的差分看起来像证据」的复现（本轮已经栽过一次：
`dsi1vco rate=0`、`dsi_isr=0`、byte clk 108 MHz）。

**唯一 bit17（`STATUS0 0x20000`）目前没有任何已知解释**：mainline `dsi.xml` 的 `STATUS0` 只定义 bit0–4、31；
同值位在 `FIFO_STATUS` 是 `DLN0_HS_FIFO_FULL`，但两颗核寄存器不同、且坏发 `FIFO_STATUS=0x11111010`（DLN0..3
HS/LP FIFO 全 EMPTY）与好发逐位相同，**不能**读成「FIFO 满」。它是四项差异里唯一可能与 busy 无因果的位，
所以 E0 必须把它的时间序列打出来（是 t=0 就有，还是卡在半途才有）。

### 1.3 `cmd_dma_busy` 恒 1 的硬件含义（逐寄存器排除）

`STATUS0.CMD_MODE_DMA_BUSY` 由 SW trigger 接受时置起、由 `CMD_DMA_DONE` 完成时清除；`CMD_MODE_ENGINE_BUSY` 是命令引擎
总体忙。坏发在 200 ms 后仍双双为 1，配合其余读数可做的排除：

| 读数（坏发） | 值 | 排除/指向 |
|---|---|---|
| `INTR_CTRL=0x2200200`（混合 status/W1C+mask 寄存器，`dsi.xml:77-88`） | bit0 `CMD_DMA_DONE` 状态=0；bit24 `ERROR` 状态=0 | **中断线不是嫌疑**：done 状态位本身没置起来，不是「完成但 IRQ 丢了」 |
| `ACK_ERR_STATUS=0`、`TIMEOUT_STATUS=0` | 无协议层错误、无 LP/ULPS 超时 | 没有 ECC/CRC/BTA 类错误 ⇒ 不是链路咬到坏包 |
| `FIFO_STATUS=0x11111010` | 4 条 HS FIFO + LP FIFO **全空** | 既不是「数据卡在 FIFO 发不出去」（那会满），也不是 DMA 写不进 FIFO（那会触发 watermark/underflow，且 `DMA_FIFO_CTRL` 两个 watermark 已被 disable） |
| `LANE_STATUS=0x1f1f`、`PHY_RESET=0`、`pll_unlock=0` | 与好发逐位相同 | PHY 不在复位、PLL 锁、lane 状态正常 ⇒ 不像 PHY 侧问题 |
| `CTL=0x175`（ENABLE+CMD_MODE_EN+LN0-2+CLK_EN）、`CMD_DMA_CTRL=0xd4000000`（BROADCAST_EN|MASTER|FROM_FB|**LOW_POWER**）、`DMA_BASE=0xff300000`、`DMA_LEN=4`、`TRIG_CTRL=0x80000004`(TE=1, DMA_TRIGGER=SW)、`TRIG_DMA=1` | 与好发逐位相同 | 描述符正确、trigger 已写入。**说明「参数没配好」这类原因可以排除** |

⇒ 硬件语义 = **「trigger 被接受、引擎进入忙态，但内部 FSM 再没有向前走」**；不是「没触发」、不是「触发了没中断」、
不是「协议错误」。剩下的可能只有三类：(i) 内部触发/窗口/门控仲裁把这次传输永久挂起（§1.4d、§1.5①②）；
(ii) 与 peer（DSI1）的 broadcast 握手等不到对方（两颗 host 同时超时，见 §1.5③）；
(iii) 内存侧取数永不返回（VBIF/SMMU）——可能性低但不为零，因为 `VBIF_CTRL`/`SFPB` 都不在 dump 里。

### 1.4 「首次 modeset」与后续的真实路径差异（源码事实）

**(a) 面板 init 每 boot 只跑一次 → 80 轮 DPMS 0 命中不具证明力。**
panel 的 prepare（`drivers/gpu/drm/panel/panel-novatek-nt36536.c:71-125`，reset 脉冲 + init 序列）只在**完整 modeset**
时跑；DPMS 开关只走 bridge enable/disable（`dsi_manager.c:382-410`），不会重跑 DCS init。
⇒ 「只有开机首次 modeset 才触发」的正确表述是「**只有 panel init 会走到 bonded 命令 DMA，而它每 boot 只走一次**」。
用它反推「必须有开机特有状态」是过度推理。

**(b) 失败即单向熔断，本 boot 再无第二次机会。**
`dsi_manager.c:41` `static bool dsi_bonded_cmd_failed;` 只有 `WRITE_ONCE(…, true)`（`:375`、`:642`），**没有任何地方清 0**。
一旦置位：`msm_dsi_manager_cmd_xfer()` 直接 `-EIO`、`dsi_mgr_bridge_pre/post/enable` 全部早退、`power_off` 也跳过。
后果：①「只有背光无桌面」永久化；② attempt 2 的 `-5` 是它给的（不是新的失败模式）；③ 想验证「卡死可恢复」
（原实验②）**必须同时清 latch**，否则代码根本不会再碰硬件。

**(c) 真正只在首次成立的东西**（也就是候选「一次性遗留状态」的全部清单）：
regulator 首次真正上电（`dsi_host.c:3103` `regulator_bulk_enable`）、PHY 首次 reset+enable
（`dsi_mgr_phy_enable()` 的 bonded 特殊路径）、`dsi_link_clk_set_rate_6g_v2_9()` 首次把 byte/pixel 源 reparent 到 DSI PLL
（`msm_dsi_host_power_off()` 会把 parent 还原，所以 DPMS 循环其实也会重做——**这条并非首次特有**）、
以及 **ABL/UEFI 遗留的 DSI/DPU 寄存器内容与 DYN 门控状态**（`clk_ignore_unused`/`pd_ignore_unused` 让上游状态原地保留）。

注意 `dsi_sw_reset_v2_9()` 的一个细节：它读出旧 `DSI_CTRL`、清 ENABLE/VID/CMD、脉冲复位、**最后把旧值写回**
（`:1226`）。在首次 power_on 路径（`dsi_host.c:3144-3146`：`timing_setup → sw_reset → ctrl_enable`）里，
「旧值」是 **ABL 留下的 `DSI_CTRL`**（含 ENABLE/CMD 位），于是复位脉冲之后、我们自己的 `dsi_ctrl_enable()` 之前，
存在一小段「以 ABL 配置 + 已恢复自动门控」运行控制器的窗口。厂商同样这么写，但厂商紧接着会走带 force-on 括号的
`ctrl_en()`；我们不会（§1.5②）。

**(d) 最可疑的首次特有竞争：video 面板 + `DMA_SCHEDULE_CTRL` 条件分支。**
本面板是 **video 模式**（cmdline `msm_drm.dsi_display0=qcom,mdss_dsi_elden_nt36523_csot_3k_dsc_vid`；
`panel-novatek-nt36536.c:530` `mode_flags = MIPI_DSI_MODE_VIDEO | …`）。而
`msm_dsi_host_bonded_cmd_init_trigger()`（`dsi_host.c:2493-2527`）在

```c
if (!(mode_flags & MIPI_DSI_MODE_VIDEO) || !mode ||
    !(STATUS0 & DSI_STATUS0_VIDEO_MODE_ENGINE_BUSY))
        return;                 /* 不排程 */
schedule_line = vtotal - (vsync_start - vdisplay) + 1;
DSI_DMA_SCHEDULE_CTRL = ENABLE | LINE(schedule_line);   /* 排到某一行的窗口里触发 */
```

也就是说：**如果那一刻 video engine 恰好 busy，这次 DCS 命令 DMA 会被安排到「等某一行的窗口到来」再触发**。
而 DRM 本树的提交顺序是 `commit_crtc_enable()` → `commit_encoder_bridge_pre_enable()` →
`commit_encoder_bridge_enable()`（`drivers/gpu/drm/drm_atomic_helper.c:1759-1769`，CRTC/INTF 先起、桥与面板 init 后跑），
所以 **panel init 期间 INTF/DSI video engine 是否已经 busy 是一个真正的时序竞争**：
它取决于 DPU 首帧是否已经推进到 DSI（首次 modeset 时 GPU/CDSP/时钟状态与 ABL 遗留态都还新鲜 ⇒ 抖动最大），
DPMS 循环则根本不跑 panel init。窗口如果因为任何原因不再到来（引擎被 `xfer_prepare/restore` 的 `DSI_CTRL` 抖动打断、
line counter 未推进、schedule 与 SW trigger 二义），命令 DMA 就**永远 busy 但从不报错** ——
与 §1.3 的读数完全吻合，且这是目前**唯一能同时解释「首次特有 + 无任何错误位 + 两颗 host 同时卡死」的机理**。

**关键取证缺口：现有 dump 没有读 `DMA_SCHEDULE_CTRL`(0x0fc)/`DMA_SCHEDULE_CTRL2`(0x100)。**
一次坏发就能定生死，只是我们没打。（其余缺口：`LANE_CTRL`、`ERR_INT_MASK0`、`DMA_FIFO_CTRL`、`VBIF_CTRL`、
`6G_HW_VERSION`；另外 slave 侧的 dump 因预算 bug 从未取到，见 §2 E0。）

### 1.5 与厂商实现的四处可验证偏差（比原三实验更贴根因）

| # | 偏差点 | 厂商 | 我们 | 风险评级 |
|---|---|---|---|---|
| ① | 动 `DSI_CTRL.ENABLE` 的 force-on 括号 | `ctrl_en()` 前后包 `CLK_CTRL \|= 0x23F\|BIT(8)\|BIT(9)\|BIT(11)\|BIT(21)`（`dsi_ctrl_hw_cmn.c:803-826`），soft reset / phy sw reset 同理 | `dsi_ctrl_enable()`（`:978` 写 `CLK_CTRL=0x23f`，`:1000` 写 `DSI_CTRL`）与 `bonded_xfer_prepare()`（函数 `:2394`，实际写点 `:2422`）都**无括号**，只有 `dsi_sw_reset_v2_9()` 有 | 中：符合「DYN 域正被 gating 时使能边沿丢失」的偶发形态 |
| ② | cmd 模式 bonded 的 DMA 窗口/触发语义 | 每条 cmd 都走 `configure_cmddma_window()`：master `TRIG_CTRL` 低 4 位 = **0xc**、slave 清 0 并置 **`DMA_TRG_MUX=1`**、master 写 `DMA_SCHEDULE_CTRL2 = line \| window<<16`（`dsi_ctrl_hw_2_2.c:224-259`，由 `dsi_ctrl.c:1402-1452` 调用） | `bonded_cmd_init_trigger()` 两边都清 `DMA_TRG_MUX`/窗口、只写 `DMA_TRIGGER=SW(0x4)`（低 4 位 0x4，缺 bit3） | 中-高：0xc 与 0x4 的 bit3 差异是 6nm 4-bit trigger-select 字段未被 mainline xml 解码的部分 |
| ③ | 触发次序 | `dsi_display_broadcast_cmd()`：prepare 全部 → 编程 master → 编程 slave → **先 trigger slave、最后 trigger master**（`dsi_display.c:3291-3360` + `dsi_ctrl.c:3727-3760`：非 master 才 `trigger_command_dma()`） | 次序一致（`dsi_manager.c:630-635`），**但我们额外 SW 触发 slave**，而厂商在 cmd 模式下 slave 的触发来自 `DMA_TRG_MUX=1` 的 broadcast 侧 | 中：给 slave 多一次 SW trigger 是否与 broadcast 通道打架，取决于 HW；这是「两颗 host 同时卡死」的自然解释候选 |
| ④ | 面板 init 全部以 **LP（LOW_POWER）** 发送 | `use_lpm = msg->flags & MIPI_DSI_MSG_USE_LPM`，DT on-list 的 init 写**不带** LPM ⇒ HS 发送 | 面板 `mode_flags` 含 `MIPI_DSI_MODE_LPM` ⇒ `drm_mipi_dsi.c:456-457` 给**每条** DCS 写补 `MIPI_DSI_MSG_USE_LPM` ⇒ `CMD_DMA_CTRL` bit26 `LOW_POWER=1`（dump 实测 0xd4000000 含 bit26，好发/坏发一致） | 低-中：好发能出画面 ⇒ 不是充分因，但整条 init 走 LP 是长期边缘化因素，也是「LP→HS 转换期被窗口/门控打断」的潜在放大器 |

**诊断内核自身的三个取证 bug（下次跑之前必须修，否则会再次拿到不可解释的样本）**

1. `q28_dump_cmd_regs()` 先 `atomic_dec_if_positive(&q28_cmd_timeout_dumps)`，再进
   `q28_dump_cmd_regs_body()` **又减一次**（wrapper `dsi_host.c:2659-2665` vs body `:2619`）⇒ 预算 2 实际只出 1 次。
   这直接导致坏发时 **peer(DSI1) 的寄存器一组从未被打印**（只有 master 四行）——两颗 host 同时超时的场景里，
   我们只看了一半。
2. `q28_dump_cmd_regs_ok()` 检查 `q28_cmd_ok_dumps`，但 body 里减的仍是 **timeout** 预算 ⇒
   **好发的头两次成功 dump 会吃掉坏发用的预算**；混合日志（同一台机器先好后坏）里坏发可能一条都不打。
3. dump 只在 `wait_master`/`poll_slave` 与成功返回处 ⇒ **没有任何「触发瞬间/半途」的样本**（§1.2 的根因）。

## 2. 对剩余三个单变量实验逐一论证（含新增 E0/E4/E5）

> 上机代价统一记 1 个单位 ≈ 「改码→编内核→`fastboot boot`（零写盘）→抓串口→`reboot2 warm`」一轮。
> 统计口径：坏发基线 ~65–71%。要把「降到 ≤20%」与基线区分开，Fisher 精确检验大约需要 **每组 ≥12 boot**；
> 要证明「100% 消除」，6–8 boot 足够（`(0.65)^8 ≈ 3%`）。**任何 delay/重试类实验按 ≥10 boot 预算，别用 1–2 boot 下结论。**
> 每轮预检 `slot-attr.py`（`succ=1`）+ 用 `reboot2`（坏发有 vblank 风暴，`reboot` 会挂）。

### E1（原①）「命令 DMA 触发前插 delay」——**拆成 E1a/E1b，否则结论不可归因**

现在的描述（「在 `REG_DSI_TRIG_DMA` 写入前插 `usleep_range()`」）有个设计缺陷：触发前的写序是
`bonded_xfer_prepare()`（pm_runtime、link clk、`DSI_CTRL |= CMD_MODE_EN|ENABLE`）→ `cmd_init_trigger()` →
`cmd_stage()` → `trigger()`。delay 插在哪一段，测的是完全不同的机理：

| 子实验 | 改动位置 | 检验的机理 | 预期观察 | 能否证伪现假说 | 代价/风险 |
|---|---|---|---|---|---|
| **E1a** panel 侧 | `panel-novatek-nt36536.c:83` 之后、首条 `ff 20` 之前插 `mipi_dsi_msleep(ctx, 120)`（现仅 10 ms） | 面板内部 boot 未完成 ⇒ 不响应 | **只有** 面板侧 ESD/无 ACK 类错误会改善；本签名里没有 ACK/timeout 错误位（§1.3）⇒ 预期**无效**；若有效说明我们对签名的理解要改 | 不能证伪 DYN 假说 | 1 单位；风险≈0（panel 侧延时，最坏多花 120 ms） |
| **E1b** host 侧 | `dsi_host.c:2569` `bonded_cmd_trigger()` 之前插 `usleep_range(500,1000)`（并镜像到 slave） | `DSI_CTRL`/描述符写入后 DYN 域需要 settle 才吃 trigger | 若坏发率显著下降 ⇒ 支持「settle 竞态」；若不变 ⇒ **削弱** §1.5① 与 DYN 假说 | 部分证伪（对「引擎需要空闲时间」这一族有效，对 §1.4d 窗口竞争**无效**，因为窗口与 delay 无关） | 1 单位；风险低（多 ms 级延时，最坏整条 init 慢 60×1 ms） |

**判定**：E1 是**筛查**（screening），不是根因判定；阴性不销案、阳性也只是缓解（作者自己在原计划里写明「delay 不算修法」）。
排在 E0/E4 之后，且只有在 E0 显示「busy 位在 t=0 就为 1、窗口寄存器为 0」时才值得跑。

### E2（原②）「超时后若 engine 仍 busy → reset 引擎并重触发一次」——**信息量最大、且顺带产出可用缓解**

改动（三处，缺一不可，否则代码根本走不到第二次）：

1. `dsi_manager.c:642` 之后**不要**立刻把 `dsi_bonded_cmd_failed` 当终态；或在
   `dsi_mgr_bonded_cmd_xfer()` 失败分支里加一次「恢复 + 重试」：`dsi_sw_reset()`（两颗 host 都来，走
   `dsi_sw_reset_v2_9()`，它本身**自带**厂商式 force-on 括号）→ 清 `STATUS0`/`TIMEOUT_STATUS`/`FIFO_STATUS` →
   `WRITE_ONCE(dsi_bonded_cmd_failed, false)` → 重跑一次 `bonded_cmd_xfer`。（latch 清零是硬前提，见 §1.4b。）
2. 超时时刻额外打印：重试前 `STATUS0/CLK_STATUS/DMA_SCHEDULE_CTRL` 一组，重试后一组（与 E0 复用）。
3. 重试仍失败才真正熔断（保持现有安全行为）。

预期观察与归因力度（**这是本表里判定力最强的一条**）：

| 重试结果 | 结论 |
|---|---|
| 重试 100% 成功出画面（N≥6） | 卡死是**纯内部 FSM/门控锁死**，软复位可清除 ⇒ 强烈支持 §1.5①/§1.4d，**排除**「面板侧没就绪」与「PLL/PHY 坏」两类（它们不会被 ctrl 软复位治好） |
| 软复位后仍失败，但**去掉 latch 后第二次 modeset 能成** | 一次性遗留状态（ABL 残留）被第二次完整 power_on 清掉 |
| 重试照样失败 | 不是简单门控锁死 ⇒ 往 §1.5②③（窗口/mux/broadcast 握手）与 panel 侧转 |

风险与代价：1–2 单位。**只在已经失败的路径上生效**，不会把好消息变坏；但要注意 `dsi_sw_reset()` 会连带清
`CMD_MODE_EN` 并恢复 `DSI_CTRL`，重试前必须重新 `bonded_xfer_prepare()`（现成函数即可，别裸调）。
另一个副作用要写进观察项：重试成功后仍会出现「vblank 风暴已启动/panel 已 init 到第 1 条」的状态，建议同时在
`dsi_mgr_bridge_enable()`（`dsi_manager.c:372` 的 `panel->prepared` 检查）观察是否还需要 `dsi_bonded_cmd_failed` 复位才不拒绝 video enable。

### E3（原③）「查是谁开了 DYN pclk」——**按 §1.1 改写：驱动层无解，必须改成同状态取样**

- 原样执行（读 `clk_summary`、找消费者、比对 `state.txt`）**不可能得出结论**：`state.txt` 里
  `disp_cc_mdss_pclk0/1_clk`（enable 2）、`byte0/1_clk`（enable 2）都是 disp_cc 的**输入时钟**，
  与 `CLK_STATUS.DYN_PCLK_ACTIVE`（DSI 核内部动态门控实例）不是同一层；且好发/坏发这些计数一样
  （前一轮同类差分已全部被否的教训）。
- 有意义的改写 = **E0**：在同一引擎状态下（触发后 µs 级）同时读 `STATUS0/CLK_STATUS/INTR_CTRL/DMA_SCHEDULE_CTRL`，
  看好发在 busy=1 的那一刻 `DYN_*_ACTIVE` 是不是**也为 1**。
  - 若好发在飞时同样是 `STATUS0=0x20003 / CLK_STATUS=0x3743` ⇒ **DYN 假说当场证伪**（四项差异塌缩成一个），
    资源全部转 §1.5①②③；
  - 若好发在飞时 `DYN_*` 仍为 0（即 DYN 位只属于坏发）⇒ 假说复活，且 bit17 的来源也要一起看。
- 代价：0.5–1 单位（只加打印）；风险：0（纯读寄存器，`dev_err` 打印量可控）。

### E4（新增）「补上厂商的 force-on 括号」——**第一个因果性修复实验**

改动（单变量，10 行内）：把 `dsi_ctrl_enable()` 中 `DSI_CTRL` 的写入、以及
`msm_dsi_host_bonded_xfer_prepare()`（`dsi_host.c:2422` 的 `DSI_CTRL |= CMD_MODE_EN|ENABLE`）包进
厂商式括号：

```c
u32 clk = dsi_read(msm_host, REG_DSI_CLK_CTRL);
dsi_write(msm_host, REG_DSI_CLK_CTRL, clk | DSI_CLK_CTRL_ENABLE_CLKS | BIT(8)|BIT(9)|BIT(11)|BIT(21));
wmb();
dsi_write(msm_host, REG_DSI_CTRL, …);        /* 原有写 */
wmb();
dsi_write(msm_host, REG_DSI_CLK_CTRL, clk);
wmb();
```

观察：坏发率（≥10 boot 判据）+ `CLK_STATUS` 是否还出现「坏发专属」组合。
判定力：直接检验 §1.5①，且**它本身就是候选真修**（与上游讨论时是「按厂商做法补齐动态时钟 force-on」，不是插 delay）。
风险：低（force-on 只在写序期间存在，写完即恢复；厂商在同等路径上做了同样的事）；代价：1 单位 + 10 boot。

### E5（新增）「init 写走 HS，不带 LOW_POWER」——最小改动的边缘化因素剥离

改动：在 `msm_dsi_host_bonded_cmd_stage()` 里对 panel init 阶段（`!msm_host->enabled` 或首 N 条）清掉
`DSI_CMD_DMA_CTRL_LOW_POWER`（或在 panel driver 的 `mode_flags` 去掉 `MIPI_DSI_MODE_LPM`，影响面更大，不推荐）。
观察：`CMD_DMA_CTRL` 从 0xd4000000 → 0xd0000000，坏发率。
判定：若坏发消失 ⇒ 与厂商的 LP/HS 差异是真因之一（可写成「DT/驱动标志不该对 DSC video 面板开 MODE_LPM」，
是个可上游化的独立结论）；若不消失 ⇒ 划掉一项。风险：低-中（LP→HS 改动会让 init 时序变紧，需要真出画面才算过），
代价 1 单位 + 少量 boot。
**注意**：`MIPI_DSI_MODE_LPM` 同时影响读路径，只改 stage 更安全。

## 3. 最优先：E0 —— 把 dump 从「事后单点」改成「触发后时间序列 + 补寄存器」

**具体改动草案（写码者照抄即可，全部在 `drivers/gpu/drm/msm/dsi/dsi_host.c`）**

1. 新增 `q28_trace_cmd(struct msm_dsi_host *m, const char *tag)`：读
   `STATUS0, CLK_STATUS, INTR_CTRL, DMA_SCHEDULE_CTRL, DMA_SCHEDULE_CTRL2, FIFO_STATUS, ACK_ERR_STATUS,
   TIMEOUT_STATUS, DLN0_PHY_ERR, VBIF_CTRL, DMA_FIFO_CTRL, LANE_CTRL`（后四项补齐缺口）。
2. 在 `msm_dsi_host_bonded_cmd_trigger(master)` 之后立刻（`dsi_manager.c:635` 与 `dsi_host.c:2569` 两处之一，
   取 master 侧）跑：
   `for (i=0;i<40;i++){ q28_trace(“t0”“t1”…); if (INTR_CTRL & DSI_IRQ_CMD_DMA_DONE) break; udelay(50); }`
   ⇒ 好发最多打 3 行就 break（<150 µs 完成，见 §1.2），坏发打满 40 行 ≈ 2 ms；
   然后照旧进 200 ms `wait_for_completion_timeout`，超时分支再各打一次（master **和 slave**）。
3. 修预算：`q28_dump_cmd_regs_body()` 内部**不再**减计数（只在 wrapper 减）；ok 路径改减 `q28_cmd_ok_dumps`；
   **master 与 slave 各一份预算**（否则永远看不到 peer，见 §1.5 bug①②）。
4. 打印 `6G_HW_VERSION` 一次（确认两颗核版本，决定 `configure_cmddma_window` 是否适用）。
5. 可选加料（同一镜像，一次搞定）：在 `msm_dsi_host_bonded_cmd_init_trigger()` 里打印
   「进入函数时的 `STATUS0`（看 `VIDEO_MODE_ENGINE_BUSY`）」+「最终写入的 `DMA_SCHEDULE_CTRL` 值」
   ⇒ **直接验证 §1.4d 竞争是否发生**，不用另开实验。

**为什么是它（而不是原三实验之一）**

- **判定力**：它是唯一能让「DYN pclk 域切换」这个当前假说**可证伪**的观察（E3 的正解形式），同时顺手判定
  §1.4d 窗口竞争（现有 dump 缺的那对寄存器）与 bit17 的性质。E1/E2/E4 的任何结果都不足以在评审时关掉这条假说。
- **代价与风险**：一次 `fastboot boot`，零写盘、零硬件动作（只读寄存器 + `dev_err`），不需要 10+ boot 的统计样本；
  坏发率 ~65% 意味着 2–3 轮就够取到 1–2 个坏样本。
- **顺序依赖**：E0 的输出直接决定 E4/E5/E1 的取舍与解释框架；反过来先跑 E1/E4 会把「缓解」当成「根因」，
  正是本项目 PITFALLS 反复记录的失败模式（把可用当结论）。
- **附带收益**：修好的诊断内核同时是 E2 的载体（同一镜像里加软复位重试即可，第二轮再开）。

## 4. 残余风险 / 不要做的事

- **不要**再基于「四项差异」推进任何 DYN pclk 相关的**代码**改动；它目前是取样时刻差异（§1.2）。
- **不要**用 `vblank timeout` 当判据（好发也有）；继续用 `command DMA timeout` + `panel init attempt … failed`，
  并可加 `bonded command DMA failed: master= peer=` 这条更硬的行。
- **不要**把 `STATUS0 bit17` 读成 `DLN0_HS_FIFO_FULL`（寄存器不同，且坏发 FIFO_STATUS 显示 FIFO 全空）。
- 任何温启循环脚本仍须自带 `slot-attr.py` 预检（`succ=1`）与 `reboot2`（坏发有 vblank 风暴，`reboot`/`reboot -f` 全挂）。
- E2 若落地为长期缓解，需要与「上游化」口径对齐：清 latch + 软复位重试属于**行为改变**，上游更可能接受
  E4（补齐厂商动态时钟 force-on）或 E5（mode_flags/LPM 语义）这一类根因修复。
- 仍未被本轮触及的两个点：`(iii)` 内存侧取数 stall（`VBIF_CTRL`/SFPB/SMMU 不在 dump 内，E0 已补）、
  以及 peer(DSI1) 侧从未取到寄存器（E0 已修预算，下次能拿到）。
