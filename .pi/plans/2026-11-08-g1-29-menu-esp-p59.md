# G1-29 后半 · p59：ESP + GRUB 菜单 + 绕开 boot.img（计划）

> 前提事实（2026-11-08 已核，见 `reports/uefi-grub-menu-qemu-smoke-20261108.md`）：
> ① p58 已让 UEFI 交棒到用户态；② arm64 GRUB 可在本机造（`scripts/grub-arm64-standalone.sh`，sha 可复现）；
> ③ 该 GRUB 在 QEMU 里端到端跑通「FAT 里的 BOOTAA64.EFI → 读 ext4(linux17) 的 /boot → 起 vk184 内核」；
> ④ **本机 GPT 尾部有 1024 MiB 空闲**（`sgdisk -p /dev/sda`：linux17 末扇区 123609082 / last usable 123871226）。
> 只读侧已完成；**本文件之后每一步都要写盘或上机，需用户批准**（`.pi/AGENT-OPS.md` §2）。

## 1. 目标与排他判据

- 目标：开机进 UEFI 后**先出 GRUB 菜单**，从 **ext4(linux17)** 读 kernel/initrd 启动；`boot_b` 不再是启动源。
- 排他判据（上机一发即可判）：
  1. 屏上出现 GRUB 菜单（不是直接进 Linux，也不是 UEFI fastboot）；
  2. 内核起来后 `/proc/cmdline` 含 **只写在 `/boot/grub/grub.cfg`** 的令牌（建议 `elden_bootmenu=grub`）；
  3. `sha256sum /dev/block/by-name/boot_b`（或 `dd if=/dev/sda… | sha256sum`）与发前相同 ⇒ 未走 boot.img；
  4. `findmnt /` = `/dev/sda17`（linux17）。

## 2. 设备侧步骤（D 系列，按顺序；每步有回退）

### D1 建 ESP（纯追加，不动任何现有分区）

```bash
# 备份 GPT（项目既有约定）
scripts/gpt-dump.sh            # 产出 backup/<SN>-<容量>/gpt_main0.bin + gpt_backup0.bin
# 追加 512 MiB ESP：起始 = linux17 末扇区 + 1（对齐 1 MiB = 256 扇区）
sgdisk -n 18:123609083:+512M -t 18:ef00 -c 18:eldenesp -v /dev/sda
sgdisk -p /dev/sda             # 核对：新分区在尾部空闲区内，其它分区号/起止未变
mkfs.vfat -F32 -n ELDENESP /dev/sda18
```

- **回退** = `sgdisk -d 18 /dev/sda`（删分区；因为不移动任何分区，回退无数据风险）。
- 风险表：写 GPT 属结构性操作。已知安全垫：① 追加在末尾空闲区；② 不动 linux17/其它分区；
  ③ 先备份 GPT；④ 写后 `sgdisk -v` 校验。**若 `sgdisk -v` 报错 ⇒ 立刻用备份回写，不继续**。
- ⚠ 分区号 18 假设空闲；先 `sgdisk -p` 确认 18 未被占用（现表用到 17）。

### D2 装 GRUB 与启动文件

```bash
# 主机侧：把 GRUB 放到 ESP
mkdir -p /mnt/esp && mount /dev/sda18 /mnt/esp
mkdir -p /mnt/esp/EFI/BOOT
cp build/grub-arm64/grubaa64.efi /mnt/esp/EFI/BOOT/BOOTAA64.EFI
sync && umount /mnt/esp

# 主机侧：把 Image/initrd.img/elden.dtb + grub.cfg 落到 linux17 的 /boot（只写文件，不动分区）
bash scripts/grub-bootfiles.sh --boot-img out/boot-elden-vk184.img \
     --device root@192.168.7.1 --apply
```

- GRUB 是**前缀桩**：ESP 上的 EFI 永不改，菜单在 `/boot/grub/grub.cfg`（改菜单不用重打 EFI）。
- `/boot` 需要 ~130 MB（Image 63 MB + initrd 64 MB + dtb 0.15 MB）；linux17 现 23G/188G，够。
- 回退 = `rm /boot/{Image,initrd.img,elden.dtb}` + `rm -r /boot/grub`（不碰其它）。

### D3 固件侧：让 BDS 走 ESP 而不是强启 LinuxLoader（新一代 p59）

现状（p58）：`R13`（`20261104R13-loaderstart`）在 `BdsEntry` 入口按 GUID 强启 FV 里的 `LinuxLoader`
（该树 `BootIntoFastboot=TRUE`）⇒ BDS 菜单/默认项根本没机会跑。

p59 建议补丁（二选一，推荐 A）：

- **A（推荐）`R54-espfirst`**：把 `R13StartLinuxLoader()` 改成
  「先扫 `SimpleFileSystem`，找到 `\EFI\BOOT\BOOTAA64.EFI` 就 `LoadImage+StartImage` 它；
  找不到再退回原 R13 行为」。理由：① 确定性，不赌 BDS 的 BootOption 排序（现表里还有个
  FAT 的 `modem_b` LUN4，绝不能让它当默认项，见 `TASKS` 11-04 记录）；② 不依赖 NVRAM 变量持久化
  （我们是 `fastboot boot` 的 RAM 固件，Boot#### 存不下）；③ 屏上可打一行 `[K] esp=found/…` 作判据。
- B：撤销 R13 并设 `PcdPlatformBootTimeOut`，靠 BDS 自己枚举 ESP ⇒ 但排序不可控 + 会落到 `modem_b`，不取。

纪律：摘/改 BDS 行为不动三处清单；但要在 `patches/uefi/README.md` 的世代表里新增 p59 世代
（从 `p58-recipe.txt` 派生 + R54），并造 `p59-kept.sha256`（`--gen p59` 需先在脚本表里加一行）。

### D4 上机一发（判据见 §1）

```bash
scripts/uefi-boot-trial.sh ... out/r21-sbstop-p59/uefi-preamble59-r1.img   # 现有流程：fastboot boot + continue
```

- BDS 若先出 UEFI 侧 fastboot 循环（`BootIntoFastboot` 那条路），说明 R54 的 ESP 扫描没命中
  ⇒ 先查 `[K] esp=` 行（FS 有没有被枚举）再动手，不要盲改。
- GRUB 菜单里加一项「同内核 + `initcall_debug`」便于现场排障（已内置）。

## 3. 未定项（上机后一次定案）

| # | 问题 | 现状口径 / 如何判 |
|---|---|---|
| Q1 | Mu UEFI 是否经 EFI config table 把 DT 传给 OS？ | 现 `grub.cfg` **显式** `devicetree /boot/elden.dtb`（有文件才加），最稳；若 QEMU/上机证明 config table 已有，可去掉该行 |
| Q2 | `SdccDxe` 摘掉后 SD 卡是否还能给 UEFI 用（ESP 若放 SD 卡就依赖它） | 本计划 ESP 放在 **UFS**，不依赖 SD；SD 仍归内核 |
| Q3 | GRUB 是否会因 UFS 的 `BlockIo` 只报 512 B 逻辑块而读错 | QEMU 已证逻辑通；上机若 ext4 读失败，先查 GRUB `ls (hd0,gpt17)/` 能否列目录 |
| Q4 | 落地持久化：ESP 有了、固件仍是 `fastboot boot` 的一次性件 | 写 `uefi_a`/BDS 默认项属**另一件事**，单独批准；本计划只到「菜单 + 绕开 boot.img」 |

## 4. 不做/不承诺

- 不写 `uefi_a`（固件落盘），不改 `boot_b`，不动 `userdata`，不缩任何现有分区。
- 不把 GRUB 打进 FV（路线 A）：尺寸虽够（xz 后 ~1.2 MB），但那样菜单就不能改，且与 ESP 方案重复。
