## 1. 为什么用熄屏循环复现（而不是反复重启）

Q28 的坏发现象是「背光亮、无画面、`vblank timeout -110`」，近因假设是 DPU/DSI **上电**（runtime-PM
resume）瞬时失败被吞。而**熄屏→亮屏走的正是同一条 power-on 路径**，且不用重启——样本密度高两个
数量级。历史观测也支持（「熄屏异常态下命令行触发熄屏有概率只剩背光」）。

**零构建**即可做的关键原因：本机内核已编进 rpm tracepoints——
`/sys/kernel/debug/tracing/events/rpm/{rpm_resume,rpm_return_int,rpm_status,rpm_suspend,rpm_idle}`。
`rpm_return_int` 记录 `pm_runtime_*` 的真实返回值 ⇒ **被吞的错误会直接现形**，不需要诊断内核。

工具 = `scripts/q28-race-hunt.sh`（设备上跑；布防 ftrace → 循环熄屏/亮屏 → 每轮判 dpms 与新增
`vblank timeout` → 命中即停并存现场 + trace）。主机侧务必 `timeout -k` 包一层（时间盒纪律）。

判据（命中定义）= 唤醒后 `dpms != On` **或** 布防后新增 `vblank timeout`；命中即 dump
`dpms/亮度/runtime_status/pm_genpd current_state/dmesg 增量/trace`。

## 2. ★ 结果：80/80 无命中（关键否定结果）

```
CYCLES=80 EFFECTIVE=80 HITS=0 FIRST_HIT=0
VBLANK_TIMEOUT_TOTAL=0 NEW_SINCE_ARM=0
tracelines=23024  rpm_resume 返回 8148 次，负返回 0
```
证据：`logs/q28-hunt-20261009-171759/`（trace-tail.txt 2.9 MB + dmesg 前后 + summary），
主机侧日志 `logs/hunt-171759.log`。

**推论（一次正反判断，不重复论证）**：把「上电失败」当作**稳态竞态**的形态被削弱；
Q28 的触发条件必须包含**开机首次 modeset 特有的东西**（ABL 遗留的 DSI/面板/时钟状态、
`clk_ignore_unused` 带进来的孤儿时钟、genpd 初始态）。因此：
- ✅ 保留：在三个上电点检查/传播返回值（**这是无论哪种触发方式都成立的上游规范修复**，
  而且让坏发的 dmesg 自己说话）；
- ❌ 不再投入：在 DPMS 循环上继续加样本碰运气。

**顺带取得好基线**：以后任何一次 vk74 坏发，只要 `rpm_resume … ret=-X` 出现即可一锤定音
（好发里 8148 次全为非负）。

## 3. 踩坑（已入 PITFALLS 候选，先记这里）

1. **greetd 起的桌面会话跑在 UID 1000**，其 `dbus-run-session` 临时总线**拒绝 root 连接**：
   `Error connecting: The connection is closed`。熄屏/亮屏必须 `setpriv --reuid=<会话 UID>` 降权执行
   （`scripts/sleep-sweep.sh` 里那套 root 直连写法在新会话形态下会静默失效 ⇒ 假样本）。
2. **root 写 `/sys/class/drm/card0/card0-DSI-1/dpms` = Permission denied**（DRM 拒绝），
   所以**没有 sysfs 退路**，真实路径只有 `org.gnome.ScreenSaver.SetActive`。
   ⇒ 复现脚本必须先做 `PATHCHECK`（blank→Off、wake→On）再跑，否则全轮样本作废。
3. `iio-sensor-proxy` 的属性挂在**管理器对象本身**（`/net/hadess/SensorProxy` 上的
   `HasAccelerometer/HasAmbientLight/HasProximity/AccelerometerOrientation`），
   没有 `net.hadess.SensorProxy.Accelerometer` 这个接口 ⇒ 用 `busctl --system get-property` /
   先 `busctl --system introspect` 看真实接口，别照抄文档里的对象路径。

## 4. vk74（`boot-elden-vk74-q28power.img`）改了什么

内核 `ca81318f2`（`patches/q28-poweron-propagate.patch`）——三处吞错点改为
`pm_runtime_resume_and_get()` 并上报/传播：

| 位置 | 改动 | 坏发时会在 dmesg 出现 |
|---|---|---|
| `dpu_kms_enable_commit()` | 检查返回值并 `DRM_ERROR` | `dpu_kms_enable_commit: display power-up failed: -X` |
| `dpu_crtc_enable()` | 检查返回值并 `DPU_ERROR`（不改变后续流程，避免半使能态） | `crtcN: power-up failed: -X` |
| `msm_dsi_host_power_on()` | 检查返回值 → `goto fail_disable_reg`（与既有 regulator 失败同处理，无 PM 引用泄漏） | `msm_dsi_host_power_on: failed to resume dsi host, ret=-X` |
| `dpu_kms_wait_for_commit_done()` | 失败点 dump DPU 的 runtime-PM 状态 | `dpu pm: status N usage N rpm_disabled N` |

镜像口径：UTS 刻意 = `7.2.0-debug-vk64-gd02658e63cf6`（≡ 设备 `/lib/modules` 目录名），
这样 `fastboot boot` 零写盘也能加载已装模块；该「刻意复用」已登记
`versions/vk-ledger-known-issues.tsv`（含清理条件），号见 `versions/vk-registry.tsv` vk73/vk74 行。

## 5. 上机步骤（下一步，需用户在场合）

```
# 1) 进 fastboot（G1-24 已验证机制，无需按键）
ssh root@192.168.7.1 'reboot2 bootloader'        # ~22 s 后 fastboot devices 可见
# 2) 零写盘跑 vk74
fastboot boot out/boot-elden-vk74-q28power.img   # 命令拆单条（PITFALLS #3）
# 3) SSH 取证（坏发也只是黑屏，SSH 仍活）
ssh root@192.168.7.1 'dmesg | grep -E "power-up failed|resume dsi host|dpu pm:|vblank timeout|Q28"'
#    顺带把 ftrace 布防在首个 modeset 之前（把脚本放 boot runlevel），坏发即有 ret 证据
```

判读：① 出现 `power-up failed: -X` ⇒ 近因坐实为「上电失败被吞」，vk75 再上**有界重试**治本；
② 完全无新错误但仍无画面 ⇒ 回到「ABL 遗留态」路线（去 `clk_ignore_unused` 单变量 / probe 期读寄存器）。

**风险与兜底**：坏发=屏幕黑但 SSH 活，可 `reboot` 或 `echo b > /proc/sysrq-trigger` 复位；
但**连续温复位会累积面板失败**（Q28b 已证），彻底恢复要**冷启（断电）=物理动作，请用户执行**。
