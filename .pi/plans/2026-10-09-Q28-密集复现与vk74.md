## 1. 为什么用熄屏循环复现（而不是反复重启）

Q28 的坏发现象是「背光亮、无画面、`vblank timeout -110`」，近因假设是 DPU/DSI **上电**（runtime-PM
resume）瞬时失败被吞。而**熄屏→亮屏走的正是同一条 power-on 路径**，且不用重启——样本密度高两个
数量级。历史观测也支持（「熄屏异常态下命令行触发熄屏有概率只剩背光」）。

**零构建**即可做的关键原因：本机内核已编进 rpm tracepoints——
`/sys/kernel/debug/tracing/events/rpm/{rpm_resume,rpm_return_int,rpm_status,rpm_suspend,rpm_idle}`。
`rpm_return_int` 记录 `pm_runtime_*` 的真实返回值 ⇒ **被吞的错误会直接现形**，不需要诊断内核。

工具 = `scripts/q28-race-hunt.sh`（设备上跑；布防 ftrace → 循环熄屏/亮屏 → 每轮判 dpms 与新增
`vblank timeout` → 命中即停并存现场 + trace）。主机侧务必 `timeout -k` 包一层（时间盒纪律）。

判据（命中定义）= 唤醒后 `dpms != On` **或** 布防后新增 `vblank timeout`；命中即 dump
`dpms/亮度/runtime_status/pm_genpd current_state/dmesg 增量/trace`。

## 2. ★ 结果：80/80 无命中（关键否定结果）

```
CYCLES=80 EFFECTIVE=80 HITS=0 FIRST_HIT=0
VBLANK_TIMEOUT_TOTAL=0 NEW_SINCE_ARM=0
tracelines=23024  rpm_resume 返回 8148 次，负返回 0
```
证据：`logs/q28-hunt-20261009-171759/`（trace-tail.txt 2.9 MB + dmesg 前后 + summary），
主机侧日志 `logs/hunt-171759.log`。

**推论（一次正反判断，不重复论证）**：把「上电失败」当作**稳态竞态**的形态被削弱；
Q28 的触发条件必须包含**开机首次 modeset 特有的东西**（ABL 遗留的 DSI/面板/时钟状态、
`clk_ignore_unused` 带进来的孤儿时钟、genpd 初始态）。因此：
- ✅ 保留：在三个上电点检查/传播返回值（**这是无论哪种触发方式都成立的上游规范修复**，
  而且让坏发的 dmesg 自己说话）；
- ❌ 不再投入：在 DPMS 循环上继续加样本碰运气。

**顺带取得好基线**：以后任何一次 vk74 坏发，只要 `rpm_resume … ret=-X` 出现即可一锤定音
（好发里 8148 次全为非负）。

## 3. 踩坑（已入 PITFALLS 候选，先记这里）

1. **greetd 起的桌面会话跑在 UID 1000**，其 `dbus-run-session` 临时总线**拒绝 root 连接**：
   `Error connecting: The connection is closed`。熄屏/亮屏必须 `setpriv --reuid=<会话 UID>` 降权执行
   （`scripts/sleep-sweep.sh` 里那套 root 直连写法在新会话形态下会静默失效 ⇒ 假样本）。
2. **root 写 `/sys/class/drm/card0/card0-DSI-1/dpms` = Permission denied**（DRM 拒绝），
   所以**没有 sysfs 退路**，真实路径只有 `org.gnome.ScreenSaver.SetActive`。
   ⇒ 复现脚本必须先做 `PATHCHECK`（blank→Off、wake→On）再跑，否则全轮样本作废。
3. `iio-sensor-proxy` 的属性挂在**管理器对象本身**（`/net/hadess/SensorProxy` 上的
   `HasAccelerometer/HasAmbientLight/HasProximity/AccelerometerOrientation`），
   没有 `net.hadess.SensorProxy.Accelerometer` 这个接口 ⇒ 用 `busctl --system get-property` /
   先 `busctl --system introspect` 看真实接口，别照抄文档里的对象路径。

## 4. vk74（`boot-elden-vk74-q28power.img`）改了什么

内核 `ca81318f2`（`patches/q28-poweron-propagate.patch`）——三处吞错点改为
`pm_runtime_resume_and_get()` 并上报/传播：

| 位置 | 改动 | 坏发时会在 dmesg 出现 |
|---|---|---|
| `dpu_kms_enable_commit()` | 检查返回值并 `DRM_ERROR` | `dpu_kms_enable_commit: display power-up failed: -X` |
| `dpu_crtc_enable()` | 检查返回值并 `DPU_ERROR`（不改变后续流程，避免半使能态） | `crtcN: power-up failed: -X` |
| `msm_dsi_host_power_on()` | 检查返回值 → `goto fail_disable_reg`（与既有 regulator 失败同处理，无 PM 引用泄漏） | `msm_dsi_host_power_on: failed to resume dsi host, ret=-X` |
| `dpu_kms_wait_for_commit_done()` | 失败点 dump DPU 的 runtime-PM 状态 | `dpu pm: status N usage N rpm_disabled N` |

镜像口径：UTS 刻意 = `7.2.0-debug-vk64-gd02658e63cf6`（≡ 设备 `/lib/modules` 目录名），
这样 `fastboot boot` 零写盘也能加载已装模块；该「刻意复用」已登记
`versions/vk-ledger-known-issues.tsv`（含清理条件），号见 `versions/vk-registry.tsv` vk73/vk74 行。

## 7. ★★ vk74 上机：第一发就复现，且**当场否掉两个假说**（4/4 全坏）

通道 = `scripts/q28-boot-cycle.sh`（`reboot2 bootloader` → `fastboot boot` 零写盘 → SSH 取证）。
证据 `logs/q28-cycle-20261009-{173857,174115,174204,174256}/`。

| 轮 | 判定 | 关键读数 |
|---|---|---|
| vk74-1 | BAD | `bonded command DMA failed: master=-110 peer=-110` → `Failed to initialize panel: -5` → `vblank timeout: 4208c0`，**`dpu pm: status 0 usage 3 rpm_disabled 0`** |
| vk74-2/3/4 | BAD ×3 | 同一签名，逐项一致 |

**否证 1（本轮修复所依据的假说）**：新加的三处返回值检查一次都没报
（`POWERUP_FAIL=0`）⇒ **这次坏发不是 `pm_runtime` 上电失败被吞**。
**否证 2（Q28b「断电态」假说）**：`dpu pm: status 0`（= RESUME_SUCCESS）`usage 3`
⇒ vblank 超时时 **DPU 是 active/带供电的**，不是没上电。

**新的头号线索（4/4 完全一致的差异项，待好发对照）**：
```
dsi1vco_clk  enable=0 prepare=0 rate=0        ← DSI1（slave host）的 PLL/VCO 从未被编程
dsi0vco_clk  enable=1 prepare=0 rate=756755712
/proc/interrupts:  dsi_isr(host0)=0  dsi_isr(host1)=0   ← 两个 host 的 ISR 整轮一次都没进
8× "DSI PLL(0) lock failed, status=0x00000000"（probe 期，历来当良性）
disp_cc_mdss_byte{0,1} = 108.107 MHz（=864.86 Mbps）≠ 本轮 timing 要求的 133.08 MHz（bitclk 1.0646 GHz/8）
```
⇒ 形态从「上电竞态」改写为：**bonded 从机 host 的 DSI PLL 从未锁定/编程**，
它在 bonded 命令 DMA 上必然不完成，master 等 peer ⇒ 双方 -110；面板 init 随之 -5（锁存）。
配套可疑点：`clk_ignore_unused`/ABL 遗留 + `fastboot boot` 的 ABL 不初始化面板，
所以「开机首次 modeset」的 PLL 编程路径可能整条被跳过（`dsi_pll_7nm_vco_set_rate` 没跑 ⇒ rate=0）。

**粘性（重要，影响实验设计）**：连着 4 次温复位 **4/4 全坏**，不再是历史 ~50% 温启率
⇒ 与 Q28b「连续温复位会累积/粘住面板状态」一致。**要拿好发对照必须物理冷启**（断电），
这是物理动作，需用户执行。

## 10. 事故记录：`reboot2 bootloader` 后设备从 USB 完全消失

vk75-2 第 1 步 `reboot2 bootloader`（从 RAM 内核发起）之后 **90 s 内无 fastboot 设备**，
且随后 SSH 不通、`lsusb` 无任何 18d1/05c6 设备、ping 不通 ⇒ 设备**不在任何 USB 模式**
（既不是 fastboot，也不是 EDL 9008，也不是 NCM）。等 45 s 复测仍无。
⇒ 远程通道全断，只能物理处理（长按电源 20 s 强制关机 → 短按开机，**不要带音量键**）。
待恢复后需要判定：是掉电/低电、还是 `reboot2` 的 vendor reset 在 RAM 内核下偶发把设备打进无 USB 的复位态。
**下一轮实验设计要防这个**：`reboot2 bootloader` 之前先把「回不来就物理冷启」写进时间盒，
并考虑改用 `reboot bootloader`（标准 reboot 标志）或 kexec 进诊断内核以避开该路径。

## 11. 本轮收尾（2026-10-09 深夜）：一条推进、一条改道、两条教训

**Q28（推进）**：vk74 4/4 复现 → 否掉「`pm_runtime` 吞错」与「DPU 没上电」两假说；冷启对照又否掉 3 个自造差异项；
vk75（成功侧也 dump）拿到好发基线。**当前唯一缺口 = 一发坏发的同段寄存器对拍**（`CLK_STATUS`/`LANE_STATUS`/
`CMD_DMA_*`）。温启循环已脚本化（`scripts/q28-boot-cycle.sh`，单轮 ~2.5 min），但**连败会粘住**（4/4），
要连着拿好/坏各一发就得中间插一次物理冷启。

**#106 进 GUI 死挂（改道）**：今天复发一次（桌面显示正常后挂），历史上一直「未定性」的真实原因不是难复现，
而是**抓到也带不回栈**（硬看门狗禁用 + 只能物理断电）。对策已从「反复复现」改成「**让现场自己能回来**」：
`/etc/sysctl.d/99-freeze-trace.conf`（softlockup_panic + all_cpu_backtrace + panic=20 + sysrq）
+ `pstore-catch`（开机把 ramoops 归档到 `/var/log/pstore/`）常驻；此后你正常使用就能自动收栈。
60 轮合成负载压测未复现（**峰值 66.1 ℃ / load 1.8** 顺手记给 thermal 线当数据点）。

**教训两条（已进 PITFALLS #144–#147）**：① 差分必须有对照——只看故障现场推的「差异项」4 个里 3 个是假的，
所以诊断补丁要**同时给成功路径加探针**；② 复现/压测脚本先做 PATHCHECK，且判据要选**真能代表负载生效**的量
（本机：用 mdss vsync 中断增量，别用 `gfx` 电源域；`SetActive` 极性反 + 3 s 延迟）。

**资产清单（本轮新增）**：内核补丁 3 份（`q28-poweron-propagate` / `q28-dsi-regdump` / `q28-dsi-regdump-with-baseline`）、
镜像 vk73–vk76（账本+已知例外齐）、脚本 `q28-boot-cycle.sh` / `gui-freeze-watch.sh` / `gui-stress.sh` / `q28-race-hunt.sh`、
好发基线 `logs/q28-BASELINE-good-vk75-dmesg.txt`、坏发 4 组 `logs/q28-cycle-*`、持久装弹 2 个文件（含 `restore.sh` 真源）。
