## 1. 调查得到的三条静态结论（本计划的前提）

### 1.1 p13 的四行 banner **定位不到这次的死点**

`patches/uefi/20261106R6-eb-banners/0001-forced-banners-pre-post-eb.pph.patch` 把
`A:pre-EB / B:post-EB / C:post-PPH` 全部插在 **`BootLinux()` 内部**，配 p12 的 `D:JUMP-BANNER`。
而本轮死点在 `BootLinux()` **之前**（`[K] JUMP-BANNER` 都没出现）⇒ **p13 上机只会「四行全无」**，
信息量 = 0。⇒ 顺序必须是 **p14 先**，p13 只在「已确认进到 BootLinux」之后才有用。

### 1.2 三个候选调用里，两个已被静态排除，嫌疑集中到 `FastbootUsbDeviceStop()`

`Platforms/QcomModulePkg/Library/FastbootLib/FastbootCmds.c:2887-2892`：

```c
  ExitMenuKeysDetection ();
  FastbootOkay ("");          // = FastbootAck("OKAY","")，与诊断回传同一函数
  FastbootUsbDeviceStop ();   // Fbd.UsbDeviceProtocol->FreeTransferBuffer(×2)  ← 两次函数指针调用
  ResetBootDevImage ();       // BootDevImage = FALSE; 一条 bool 存储
  BootLinux (&Info);
```

- **`FastbootOkay` 排除（高置信）**：它就是 `FastbootAck`，而诊断模式在 `LoadImageAndAuth` 之后
  用同一条 `FastbootFail → FastbootAck` 回话成功过 9 档（`vs-18/19/26/27/28/35/36/37/38` 全 `diag st=Aborted`）。
  同一函数、同一时刻、同一 USB 状态 ⇒ 不是它。
- **`ResetBootDevImage` 排除（确定）**：`BootLinux.c:1518` 只有 `BootDevImage = FALSE;`。
- **`FastbootUsbDeviceStop` = 首选嫌疑**：`FastbootMain.c:229` 两处 `Fbd.UsbDeviceProtocol->FreeTransferBuffer(...)`，
  即**经全局结构体的函数指针调用**；且它只在**真启动分支**被调（`PITFALLS #524` 已证诊断/真启动是两条路径），
  时间点正好落在屏上「USB 重初始化噪音之后、异常之前」。

### 1.3 ★SSOT 更正：「ELR 落在 DXE Heap ⇒ 跳进堆」这条推理**不成立**

`Platforms/PakalaPkg/Device/lenovo-y700g4/Library/PlatformMemoryMapLib/PlatformMemoryMapLib.c:34`：

```c
{ "DXE Heap", 0xB90C0000, 0x1D500000, AddMem, SYS_MEM, SYS_MEM_CAP, Conv, WRITE_BACK_XN },
```

类型是 **`Conv`（conventional memory）**，即 DXE pool/`AllocatePages` 的来源 ⇒ **所有 DXE PE 映像的代码也分配在这里**。
反证现成：`[L04]` 记的 `DxeCore` 装载基址 **`0xD4CA6000`** 本身就在 `[0xB90C0000,0xD6610000)` 内。

⇒ ELR ∈ DXE Heap 只说明「落在某个 DXE 映像里」，**不能推出指针被破坏**。
`TASKS/README.md` §5（11-06 傍晚块）与 `reports/uefi-onboard-walkthrough-20261106.md` §3 的
「⇒「跳进堆」」需要改口径（改为「ELR 落在某 DXE 映像内，需用装载表把地址映射到模块」）。
好处：这**不会**改变下一步动作（p14 照打），但会**去掉一条错误的先验**，避免后面把正常的协议调用误判成崩溃机制。

## 2. 方案：p14 = p12 + 「进度字符」（而不是 `SbForceDiagPath`）

原计划 p14（`SbForceDiagPath` 跳过三个调用）是**二分**：只能回答「是不是这三个」。改成**进度字符**后
**同一发同时给出位置**，代价还更低：

| 方案 | 屏预算 | 一发能定到 |
|---|---|---|
| 四行 banner（p13） | 4 × 91 200 B = 365 KiB（splash 只前 ~448 KiB 可写，`PITFALLS #492`） | 只能定到 BootLinux 内四段，**且本轮的段根本到不了** |
| `SbForceDiagPath` | 1 行 | 三个调用「全体 / 不是全体」 |
| **进度字符（本方案）** | 1 行 × 7 字符 ≈ **2 KiB** | **单次调用级** |

成本依据（现查源码，`Platforms/AndromedaPkg/Library/FrameBufferSerialPortLib/FrameBufferSerialPortLib.c`）：

- `FbConPutCharWithFactor()` 单字符只写 `FONT_WIDTH+1`×`FONT_HEIGHT`×scale² 像素 ⇒ scale 1 下 **≈ 288 B/字符**；
- **只有 `'\n'` 才触发 `FbConFlush()`**（整屏 `gWidth*gHeight*4` ≈ **23.1 MB** `WriteBackInvalidateDataCacheRange`）
  与 `p_Position->y += scale`（越过 ~448 KiB 预算的元凶）。
⇒ 全部字符打在**同一行、不带 `\n`**，屏预算从 91 KiB/字符降到 0.3 KiB/字符。

### 2.1 打点位置（一个字符一步，顺序即屏上顺序）

| 字符 | 位置（`FastbootCmds.c` / `BootLinux.c`） | 出现即证明 |
|---|---|---|
| `a` | `LoadImageAndAuth()` 返回且 `Status == EFI_SUCCESS` 之后 | AVB/装载/`FindBootableSlot` 整段通过 |
| `b` | `ExitMenuKeysDetection()` 之后 | 按键栈退出正常 |
| `c` | `FastbootOkay("")` 之后 | USB 回 `OKAY` 发送成功 |
| `d` | `FastbootUsbDeviceStop()` 之后 | 两次 `FreeTransferBuffer` 成功 |
| `e` | `ResetBootDevImage()` 之后 | （几乎必过，作 sanity） |
| `f` | `BootLinux()` 入口 | 控制权进 BootLinux |
| `g` | `ShutdownUefiBootServices()` 之前 | BootLinux 前导（`LoadAddrAndDTUpdate` 等）通过 |
| 行尾 | 保留 p12 的 `[K] JUMP-BANNER`（`\n\r`，触发一次 flush） | 走到跳内核 |

**判据 = 屏上最后出现的那个字母**（`[K] abcdefg` 前缀只打一次）。异常 dump 会从光标处继续刷屏，
所以字母串本身在异常首屏之前，拍照窗口充足。

### 2.2 变体 B（只在变体 A 出现「一刷新就崩」时用）

字母落内存后若不做 `FbConFlush()`，异常 handler 自己刷屏时会顺带 flush 整块；若 dump 在 flush 前就崩，
字母可能只在 cache 里。因此：

- **A（默认）**：每个字符后调一次 `FbConFlush()`（补丁里 `extern void FbConFlush (VOID);`，
  该函数非 static，见 `FrameBufferSerialPortLib.c:289`）。代价 7 × 23 MB cache op（毫秒级）。
  ⚠ 已知待查项：报告里「`FbCon` 的 22 MiB `WriteBackInvalidateDataCacheRange`」本身列在嫌疑清单里。
- **B（备选）**：不显式 flush，靠异常 dump 的自然 flush。若 A 恰好**崩在 `a` 刚打完**（即第一次 flush 处），
  换 B 立刻可分辨「是 flush 崩还是 `ExitMenuKeysDetection` 崩」。

## 4. 风险与取舍

| 风险 | 影响 | 处理 |
|---|---|---|
| 真启动件崩 ⇒ USB 端点死 | 每次崩要**物理断电**（用户在场） | 本方案把「定位」压到 1 发；最多 2 发 |
| 屏显写穿帧缓冲（`PITFALLS #492/#515`） | 越界写可能挂死 SoC | 全部字符**同一行不带 `\n`**，≈2 KiB ≪ 448 KiB |
| `FbConFlush` 23 MB cache 维护自身可疑 | 可能引入新崩溃点 | 备好变体 B（不显式 flush）；A/B 一次可分辨 |
| 构建不逐字节可复现（`PITFALLS #510`） | sha 不能当跨构建判据 | 只记本轮 sha；关键字串 + 反汇编核对 |
| `SbProbeMode` 在真启动件里恒 3 | 任何走 `SbVProbe` 的打点都静默 | 进度字符**绕开**该开关，直接 `SerialPortWrite` |
| 设备不在场 | 一切上机项阻塞 | Task 1–3 先做完（纯主机），上机等插线 |
