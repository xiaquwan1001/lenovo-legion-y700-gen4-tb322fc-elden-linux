## 0. 已坐实的事实基线（本文据此推演）

来自 `TASKS.md` §1 G1-22/G1-33、§5 Q24、上游报告：

- 触发体 = **单模块 `cambistmclkcc-sm8750`**（相机 BIST MCLK 时钟控制器）单独加载（无消费者、全 clock usecount=0）；`qcom-camss`/`camcc-sm8750`/`i2c-qcom-cci`/`wl2868c-regulator` 各 3/3 **存活**；零相机对照 3/3 存活；`system_heap` 无罪。
- 触发事件 = 用户态 **DPMS blank**（`ScreenSaver.SetActive(true)`，仅熄屏，不进 s2idle/mem）。
- 死法 = **无痕硬复位/掉电**：pstore/kmsg 全空，无 panic、无 ramdump 原因位 → 内核视角“瞬间没电”，是 **PS_HOLD 掉 / NoC Nosync 硬复位** 一类，而非软件崩溃。
- 变体存活率（≥3 轮）：

  | 变体 | 改了什么 | 结果 |
  |------|----------|------|
  | H0 原始 DT | `power-domains=<&rpmhpd MMCX>,<&rpmhpd MX>`+low_svs | **3/3 掉电** |
  | H1 | 去 `power-domains`/`required-opps`（对齐厂商 `vdd_mx-supply`） | 7/9 存活（~20% 间歇掉） |
  | H2 | 单挂 `RPMHPD_MX`（当前 vk63/vk64 用的） | 手测 2/2；自动扫测 **3 轮 2 掉** |
  | D1 | 驱动 `use_rpm=false` | 6/9（无改善） |
  | D2 | 去 `critical_cbcrs`（SLEEP_CLK 0x40f8） | 7/9（无改善） |
  | 对照 camcc+camss | camcc=`MMCX+MXC`，有 GDSC、有消费者 | **存活** |

**判据结论**：凡是**只改“投票/轨名/运行时计数”**的开关（H1/H2/D1/D2）都把掉电概率往下压了一档，但**没有一个能清零**——这正是“降低频率而非根治”的特征，说明根因不在这些单点上。

## 1. 电源域层根因：为什么 cambist 单加载 + 熄屏 = 掉电

### 1.1 关键源码事实（本树实测）

**(A) cambist 是一个“裸时钟控制器”：有 DT 电源域，但没有 GDSC，也没有消费者。**
`drivers/clk/qcom/cambistmclkcc-sm8750.c`：
- `cam_bist_mclk_cc_sm8750_desc` = `.use_rpm = true`，`driver_data` 带 1 个 `critical_cbcrs = { 0x40f8 /* SLEEP_CLK */ }`、1 个 PLL（`cam_bist_mclk_cc_pll0`，RIVIAN_ELU，960 MHz）。
- **`desc` 里没有 `gdscs`/`num_gdscs`** —— 与 `camcc-sm8750.c`（`gdscs = cam_cc_sm8750_gdscs`，`:2623/:2681`）形成硬对比。
- 该节点在真实相机链路里目前**无 DT 消费者**（MCLK 未被 camss 请求），probe 后全部 clock usecount=0。

**(B) probe 生命周期：把块“点亮并编程”后，probe 结尾又把电源运行时引用还给 genpd——留下“已编程但电源交回 genpd 管”的半成品块。**
`drivers/clk/qcom/common.c::qcom_cc_really_probe()`：
```
:340  devm_pm_domain_attach_list(dev, NULL, &cc->pd_list);   // 按 DT 挂上 MX/MMCX（genpd 消费者）
:344  if (desc->use_rpm) {
:345      devm_pm_runtime_enable(dev);
:349      pm_runtime_resume_and_get(dev);                    // 把 DT 声明的轨按 corner 拉起来（low_svs）
      }
:357      qcom_cc_clk_pll_configure(...)   // 写 CONFIG_* 并 COM_ENABLE PLL0（clk-alpha-pll.c:2998 → clk_rivian_evo_pll_configure）
:359      qcom_cc_clk_regs_configure(...)  // qcom_branch_set_clk_en(0x40f8) 常开 SLEEP_CLK CBCR（common.c:317-318）
...
:430  if (desc->use_rpm)
:431      pm_runtime_put(dev);             // ★ probe 结束即 put：运行时引用→0，DT 轨的“活跃票”被释放
```
因为 cambist **没有 GDSC、没有消费者**，`pm_runtime_put` 之后**没有任何东西再把这条引用拿起来**。于是块停留在：**PLL0 已使能 + SLEEP_CLK CBCR 已开 + RCG/branch 状态已改**，但其 **MX/MMCX 供电票已回到 0**。这正是最危险的“半成品”窗口。

**(C) 该块的寄存器总线被 GCC 永久使能，硬件把它当“常上电”块。**
`drivers/clk/qcom/gcc-sm8750.c::gcc_sm8750_probe()` `:3226`：
```
 * Keep clocks always enabled:
 *   gcc_cam_bist_mclk_ahb_clk   ← 本块的 AHB 寄存器接口时钟
 *   ...
 qcom_branch_set_clk_en(regmap, 0xa0004);   // GCC_CAM_BIST_MCLK_AHB_CLK
```
即：**寄存器接口时钟恒开**（Linux 侧也关不掉），块被设计成“寄存器接口一直可达”。这要求它所在的电轨在 SoC 眼里**不能塌**。

**(D) DT 侧把 cambist 的“非 MMCX 那一票”挂在了可关断的 `RPMHPD_MX` 上。**
`sm8750.dtsi:2092` cambist（当前 H2）：`power-domains=<&rpmhpd RPMHPD_MX>; required-opps=<&rpmhpd_opp_low_svs>;`
`clocks = <&gcc GCC_CAM_BIST_MCLK_AHB_CLK>, ...`
对照 `sm8750.dtsi:3725` **camcc**：`power-domains=<&rpmhpd RPMHPD_MMCX>,<&rpmhpd RPMHPD_MXC>;`（第二票是 **MXC**，上游 v3→v4 changelog 明写 “MXC is always ON rail and can sustain this usecase”）。
且 `RPMHPD_MX/MMCX/MXC` 在 `drivers/pmdomain/qcom/rpmhpd.c:646-665`（SM8750 域表）都是**可关断域**——每个还各带一个 `*_AO` 恒开对等体（`RPMHPD_MX_AO`/`RPMHPD_MXC_AO`/`RPMHPD_MMCX_AO`，`active_only=true`，`rpmhpd.c:29-31/52/178-187`）。

### 1.2 掉电链条（最可能的机制）

把 (A)–(D) 合起来：

1. insmod cambist → probe 把 MX（原始还有 MMCX）拉到 low_svs、使能 PLL0、常开 SLEEP_CLK CBCR，然后 `pm_runtime_put` 交回电源票（§1.1-B）。块进入“**寄存器接口恒活（GCC 恒开 AHB）+ PLL/CBCR 已编程 + 但 MX/MMCX 的 Linux 活跃票=0**”的悬空态（§1.1-A/C）。
2. 用户熄屏（DPMS off）：显示侧把 **MMCX**（显示直接 gate 的那条可关断轨）的活跃票撤下，RPMh PDM/ARC 在深空闲路径上重估并尝试 **collapse MMCX**（原始 H0 还叠加 MX）；此时 cambist 块——
   - 原始 DT：本身就是 **MMCX 消费者**（H0），且被留在半成品态；
   - H2：仍留在半成品态，且 MX 被声明成**可关断**（low_svs、非 AO）；
   在轨塌下去的一刻，其恒活的 AHB/PLL/SLEEP_CLK 接口对**正在掉电的域**发起/维持事务 → **访问未上电块 → NoC Nosync/总线挂死**。
3. NoC 硬故障被 SoC 升级为 **PS_HOLD 拉低 → PBL 硬复位**（表现＝瞬间没电、无 pstore/ramdump 原因）。

**为什么 camcc 不死、cambist 死？** 三条同时成立的差异：
- camcc 第二票是 **MXC（常开语义）**，cambist 是 **可关断 MX**；
- camcc **有 GDSC + 有真实消费者**（camss 在用时经 genpd 持引用），不会出现“票=0 却已编程”的悬空态；cambist **无 GDSC、无消费者**，probe 后必落进该悬空态；
- 二者都被 GCC 恒开 AHB——但只有 cambist 处在“恒开接口 + 无引用 + 可关断轨”的三重叠加里。
（旁证：`gpucc` 也挂 MX+low_svs（`sm8750.dtsi:3961`），但 GPU/Adreno 恒有显示侧消费者持 MX，同样不落悬空态。）

### 1.3 为什么 H1/H2/D1/D2 只能降频、不能根治

- **H1（去 power-domains）**：Linux 不再对 MX/MMCX 声明票 → RPMh 重新独占该块电源（≈厂商模型）。掉电从 3/3→7/9。但**没有 quiesce 块本身**（PLL0/CBCR 仍被 probe 编程）；RPMh 自主 collapse MMCX 时偶尔仍撞上接口事务 → 残留 ~20%。**去票，不去半成品态。**
- **H2（单挂 MX）**：解除了与**显示直接 gate 的 MMCX**的耦合——最强杠杆，所以手测 2/2 看着好。但 MX 仍是**可关断**轨（low_svs、非 AO），深空闲/自动扫测路径上 RPMh 仍可塌 MX（或与之共享的 NoC 切片），半成品块依旧在 → 3 轮 2 掉。**去掉一条轨，不解决悬空块。**
- **D1（use_rpm=false）**：只是让 probe 不做 `resume_and_get`/`put`；但 `devm_pm_domain_attach_list` 仍把 genpd 挂上，域在 `sync_state`/他消费者下照样塌，块照样半成品。改的是引用时序，不碰悬空态本身 → 6/9，落在噪声内。
- **D2（去 critical_cbcrs）**：只动了 SLEEP_CLK 一条 branch 的开关，不碰 PLL/RCG/AHB 编程态、也不碰轨票 → 7/9，噪声内。

**共同点**：四个开关都只在“票 / 轨名 / 运行时计数”层面动，**没有一个同时满足“quiesce 块 + 让轨在塌前对块安全”**。这就是它们止于“降频”的根本原因。

### 1.4 硬复位最可能来自哪一层

| 候选层 | 判据 | 结论 |
|--------|------|------|
| **内核 panic / 看门狗软复位** | 会留 pstore/ramoops/console | 否（pstore 全空） |
| **PIL / TZ（subsystem SSR / SMC 触发重启）** | 会有 SSR 事件、`SET_SUBSYS`/ramdump 原因、PON reason | 否（无 ramdump 原因位、无痕） |
| **PMIC 硬看门狗 bite** | 会置 WDog PON/复位状态位 | 否（无 PON 异常位；现象是“瞬间没电”而非咬狗时序） |
| **RPMh PDM/ARC 触发的轨塌 → NoC Nosync → PS_HOLD 掉 → PBL 硬复位** | 无软件痕迹、瞬时、与 idle/blank 强相关、随轨票变化 | **最可能** |

> 一句话：**执行掉电的是 PMIC/SPC 的 PS_HOLD，但触发它的权威是 RPMh 电源域 collapse**（因 cambist 被留在“恒活接口 + 已编程 + 悬空票”态，轨塌时对未上电块的事务引发 NoC 硬故障）。**不是 TZ/PIL/Panic。**

## 2. “驱动侧真修”具体指什么：3 个可落地方案

> 真修的定义：**不是靠时序运气降低概率，而是消除“塌轨 vs 恒活半成品块”这对矛盾**——要么让该轨在本块生命周期内**根本不塌**，要么让块在**无人用时彻底静默**。三个方案都满足其一，且都比 H1–H2 更接近厂商意图。

### FIX-1（DT 改挂 RPMh 恒开轨 · AO floor）— 代价最低、最能“一击定音”
把 cambist 的非 MMCX 票从**可关断** `RPMHPD_MX` 改成**恒开对等体**：
```dts
power-domains  = <&rpmhpd RPMHPD_MX_AO>;   /* 或 RPMHPD_MXC_AO；对齐 camcc 的 MXC 常开语义 */
required-opps  = <&rpmhpd_opp_low_svs>;
```
- **源码依据**：`rpmhpd.c:646-665` SM8750 暴露 `RPMHPD_MX_AO`/`RPMHPD_MXC_AO`；`active_only`/`.peer`（`:29-31/52/178-187`）语义 = AO 对等体持有 RPMh 的 **sleep/wake（always-on）票**，使 ARC 在深空闲也**不让该轨塌到该 corner 以下**。这正对应上游 changelog “MXC/MX 是 always-ON rail”。
- **机制**：把“塌轨”这一侧从根上去掉——轨对块恒在 → 半成品块不再有被塌的风险 → 与 GCC 恒开 AHB（`gcc-sm8750.c:3226`）自洽。
- **预期风险**：① MX（或 MXC）被 low_svs **永久 floor**，深空闲功耗上升（省电代价）；② 若厂商固件本就用另一套 AO 票管理该轨，可能与固件的轨管理**双重持有**（需确认不与 cmd-db 的既有 AO 票冲突）。**安全性：高**（不会复位，最差是费电）。

### FIX-2（驱动侧：块生命周期内一直持票，别“put”掉）— 与 FIX-1 等价的驱动表达
让 cambist 在 probe 拉起票后**不再在 probe 末尾 put**（或设无限 autosuspend / 视作永久-on 时钟控制器，正如厂商对该块的处理）。
- **源码依据**：`common.c:349` `pm_runtime_resume_and_get` 之后 `:431` 无条件 `pm_runtime_put`。对该块，这个 put 制造了“票被释放而块仍已编程”的悬空窗口。改法＝对 cambist 这一路**不做 put**（或在 `qcom_cc_really_probe()` 之后由驱动自己 `pm_runtime_get_noresume` 兜住），使 genpd 消费者票常持。
- **机制**：从“票”这侧根治——Linux 恒持 MX/MMCX 票 → 轨不塌（等价 FIX-1 的效果，但票由驱动持而非 DT-AO 持）。
- **预期风险**：① 与 FIX-1 同样费电；② Linux 成为该轨的**常持票主**，可能与厂商固件对该轨的自主管理冲突（不如 FIX-1 的 AO 语义干净）；③ 需要小心 `sync_state`：常持票要保证 genpd 状态机不被 late-init 的 sync_state 抢先塌陷。**安全性：高**，但比 FIX-1 略“脏”。

### FIX-3（驱动侧：延迟使能 + 挂起时 quiesce · 架构最正、可上游）— 从“块半成品”这侧根治
probe **不要**无条件编程 PLL0 / 不要开 critical SLEEP_CLK CBCR；把上电+配置搬进 **`runtime_resume`（且必须在持票状态下）**，在 **`runtime_suspend` 里彻底关掉 PLL+CBCR**（回到全静默）。
- **源码依据**：`qcom_cc_really_probe()` 里 `qcom_cc_clk_pll_configure`（`:357`）+ `qcom_cc_clk_regs_configure`（`:359`）是**无条件**在 probe 里执行的；这是“无人用也半编程”的源头。且 cambist **无 GDSC**（`cambistmclkcc-sm8750.c` 的 `desc` 无 `gdscs`）——它唯一的电源管理抓手就是这条 DT 电源域，配合 `pm_runtime_put` 后 0 消费者，必然停在半编程态。
- **机制**：无人用（熄屏常态）时块**完全静默 + Linux 不持票** → RPMh 干净地 collapse，不再有对未上电块的事务；只有相机 sensor 真正经 camss 请求 `cam_bist_mclk` 时才在持票下把块带起来。这是“**从 camcc 拆出独立 clock controller**”思路的真正落点——本树里 cambist **已经**是独立驱动/节点，缺的不是“拆分”，而是**正确的 PM 生命周期（lazy-on + quiesce-on-suspend）**。
- **预期风险**：① 时钟 provider 顺序：`clk_rcg2_shared_ops` + DT provider 在 PLL 尚未起来时不得被解引用（需 lazy-init / `CLK_OPS_PARENT_ENABLE` 之类防护），比 FIX-1/2 侵入大；② 要保证“首次消费者请求”原子地在持票下完成 PLL 锁定，别出现半锁；③ 回归面比 DT 一行大。**这是最像可上游合并的驱动补丁，也是 H1 残留 20% 的正解**（H1 只去票没 quiesce，FIX-3 才补上 quiesce）。

> **三者取舍的本质**：FIX-1/FIX-2 从“**让轨别塌**”根治（安全、费电、易落地、可作上游答复里 Q1/Q2 的答案）；FIX-3 从“**无人用时把块彻底关掉**”根治（最省电、最正确、工作量最大）。H1–H2 之所以不够，是因为它们**两头都没做满**。

**理由总述**：路线按“**每单位风险换最大信息**”排序。FIX-1 是 DT 一行、可安全先测的**机制判定器**：成功即证明“RPMh 塌 MX/MMCX × 悬空半成品块”为因，并顺带产出可提交上游的修法；失败即把根因逼到 GCC-AHB/NoC 更底层，从而正当化 FIX-3 的驱动改动。因此 **FIX-1（判定+快修）→ FIX-3（正解）→ FIX-2/FIX-1a（备胎）** 是代价与确定性最优的序。
