## 1. 必须先同步的更正（有实机证据）

**"相机与 DP 不能共存"不成立；真正互斥的是"相机模块常驻 ⇄ 熄屏不关机"。**

证据（本次会话实测，`vk47clean` 内核 + `dp5` DTB + full ramdisk，零写盘 `fastboot boot`）：

1. 未加载 `fsa4480` 时：`displayport-controller@af54000: deferred probe pending` →
   `msm_drm_bind` 不完成 → 连 `card0` 都没有（= `PITFALLS #128` 的真因面）。
2. `insmod fsa4480.ko`（vermagic 恰为 `7.2.0-debug-vk47clean-gbd114ca335e1`）后：
   `fsa4480` 注册 `mode-switch` → `msm_dpu ... bound af54000.displayport-controller` →
   `card0` / `card0-DSI-1 connected` / `card0-DP-1` / `typec port0,port1` 全部出现；
   **同一次启动中** `qcom_camss/s5kjns/gc08a8/system_heap` 等相机模块已在载、17 个 `/dev/video*`、
   media graph ENABLED。
3. ⇒ dp5 之所以"相机不工作"，直接原因是 **dp5 内核没有对应 `/lib/modules/<release>`**（模块版本不匹配），
   而 dp5 的 DP 能通是因为该内核把 typec/fsa4480 编进了 built-in。
4. `PITFALLS #130` 已记录 `cma_heap` 不加载（`camera-modules-load.sh` 也已遵守），故 dma-buf 侧不是新变量。

**结论**：dp5 内核 + 现成模块 = 拿不到相机；要"DP+相机同镜像"，只有两条：
- **C-1（推荐）**：内核换成 `vk47clean`（模块目录齐全，`uname` 一致），DTB 用 `dp5` 的 →
  即已构建的 `out/boot-elden-vk47clean-camdp.img`（sha `94d5dbaf…`）。DP 已验，相机模块齐。
- **C-2（严格保持 dp5 内核）**：为 release `g26cd13b1c4a2` 重建相机模块包并部署（源码提交 `26cd13b1c`，
  强制 LOCALVERSION 使 vermagic 一致）。工作量 ~1 次构建 + 部署。

## 4. 加速度计（重力）—— 可行性与选项

**硬件拓扑（证据）**：

- 器件：厂商 config 列 `lsm6dso`（备选 `icm4x6xa`）；U2 locked 基线 `sensorservice` 实报
  `icm4x6xa Accelerometer / Gyroscope`（TDK-InvenSense），二者都属 SLPI/SSC 传感器核配置集。
- 总线：**SLPI/SSC 私有 I2C（`bus_instance=3`，`bus_type=1`）**，不在 AP 任何 I2C 上。
- 现有 AP I2C 设备（实测）：`i2c-5/6/9/10/11`，全为 typec 复用 / 触觉 / 功放 / 相机 PMIC / 背光，**无 IMU**。
- 厂商 DT（`elden.dts` 与基础 SoC dtb）**无任何运动传感器节点**。
- 厂商 vendor_dlkm 含 **`qti_qmi_sensor_v2.ko`** ⇒ 下游走 QMI-SNS（SLPI）。
- 主线：`CONFIG_IIO_ST_LSM6DSX=m`（支持 `st,lsm6dso`）、`inv_icm42600` 都在树，但**无 QMI-SNS/SLPI IIO 桥**；
  设备侧 `/sys/bus/iio/devices/` 为空。

**判定**：传感器被 SLPI 吞掉 ⇒ 普通 IIO 驱动永远匹配不到设备。
选项：

| 选项 | 内容 | 代价 | 可行性 |
|---|---|---|---|
| A0 | 静态可行性探针（**建议先做**）：从 SLPI 固件/配置定位该 I2C/I3C 对应的物理 QUP/SE 与 TLMM 中断，判断 AP 能否在 ADSP 在跑时接管该 QUP | 一次静态分析（不动设备/不动 SLPI） | 可做；结论可能是否 |
| A1 | AP 接管传感器 QUP（忽略 ADSP 冲突） | 需 ADSP/SLPI 让出该 QUP；与音频（ADSP）冲突；私有固件 | 低，风险高 |
| A2 | 完整 SLPI/QMI-SNS bring-up | 数周–数月；固件闭源；无主线参照 | ❌ |
| B | 硬件外挂 IMU（USB/I2C 飞线） | 板级改动 | ❌ 不合目标 |
| C | 归档为架构性不可做 | 0 | ✅ 若 A0 结论为否 |

**建议**：先做 A0（限定 1 个时间盒、纯静态、零设备风险），据结论决定 A1 还是 C。

## 4.5 待登记项（用户 2026-10-07 指示「先标记」）

- **[待登记 T1] 无法从 Linux 直接重启到 fastboot/bootloader**：
  - 事实：`reboot bootloader` 在本项目的 mainline 分支上只做普通重启（dp5.dtb / HEAD DTS 均无 `mode-bootloader` 属性；vk41 的 PSCI vendor-reset 钩子只存在于 `elden/vk41-psci-reboot` 分支，未并入 vk47clean/vk53-hw）。
  - 后果：每次 `fastboot boot` 迭代后若要换镜像，必须物理按键进 fastboot；`fastboot` 命令拆单条、掉电后 USB 不自动恢复时尤其疼。
  - 修法（后续）：把 PSCI vendor reset 钩子（`mode-bootloader`/`mode-edl`）+ DTS 属性合入主线分支，再实测 `reboot bootloader`；或退而求其次确认 `qbootctl`/BCB 在四代是否真不被采纳（G1-24 结论）。
- **[待登记 T2] 当前 boot_b 不可启动**：
  - 事实：本轮两次 `reboot`（普通重启）后设备从 USB 完全消失，既非 fastboot 也非 Linux ⇒ boot_b 内的镜像起不来（或 AVB/内容异常）。
  - 影响：任何 Linux 侧 `reboot` 都会“失联”，必须物理恢复；也解释了排查中掉电后为何回不来。
  - 处置：下一次上机时把 boot_b 刷成已知可启动的 `out/boot-elden-camdp-nocam.img`（已有多个回退资产 `out/boot_b-before-cdsp-20261007.img`、`bootslot-b/boot_b-clean.img`、`bootslot-b/boot_b.img`），使重启/掉电后能自动回到受控 Linux，从而把熄屏二分变成全自动（改 `camera.conf` → `reboot` → 熄屏 → 自动回来）。

## 6. 收尾总结（2026-10-07）

**Q24（相机 × 熄屏）结论**：

- 根因 = 单模块 **`cambistmclkcc-sm8750`**（相机 BIST MCLK 时钟控制器）；它单独加载就触发熄屏→硬复位，其余相机模块/`system_heap` 全无罪；零相机对照安全。
- 修复进度：**H1（DT 去 `power-domains`/`required-opps`）把 cambist 单独从 3/3 掉电降到 7/9 存活**；**D1 驱动 `use_rpm=false` = 6/9、D2 去 `critical_cbcrs` = 7/9，两者均无改善** ⇒ MMCX/MX 耦合是主因之一，**残留 ~20% 间歇未根治**（G1-33 续）。
- 当前基线 **vk62**：H1 DTB + `elden_nocamera=1` + 空 `/etc/modules-load.d/camera.conf` ⇒ **DP 可用、零相机自动加载、熄屏安全**；相机改按需（手动 `camera-modules-load.sh`，但加载后熄屏仍可能掉电）。

**加速度计（G1-34）结论**：不是架构死路；主线有 QRTR-as-bus + `qcom_smgr` IIO 族（本树未含）+ registry 前置；SLPI 已在跑但 `/proc/net/qrtr` 未现。下端。
