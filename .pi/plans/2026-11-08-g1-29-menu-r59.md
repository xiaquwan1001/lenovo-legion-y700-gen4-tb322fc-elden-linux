## 0. 为什么先「键选」再加 UI

| 事实 | 出处 |
|---|---|
| ESP 路径已能从 FAT 读 `\boot\boot.img` 起完整 Linux | R58b（`ESPBOOT_TAGGED`） |
| 面板（`SerialPortWrite`）**不是可靠通道**：同一份代码一发能打印、一发 ASSERT 掉电 | `PITFALLS #567` |
| Mu 的按键抽象成熟：`SCAN_UP`=音量上 / `SCAN_DOWN`=音量下 / `SCAN_SUSPEND`=电源（`GetKeyPress` + `MenuKeysDetection.c`） | `BootLib/KeyPad.c`、`MenuKeysDetection.c` |
| GRUB 菜单在本机可用同一组按键操作 | `reports/uefi-grub-esp-handoff-wall-20261108.md` §2b |

⇒ 分两步，风险递增：
**R59 = 只做「键选 + 落盘日志」**（不给屏上 UI，证据走 `\loader.log`），先证明**输入事件在本 App 里真的收得到**；
**R60 = 再加屏上 UI**（复用 `BootLib/DrawUI.c` 的 `DrawMenu`，fastboot 屏用的就是这套，属已验证绘制路径），
只有 R59 拿到 `menu key` 日志后才做，避免把「输入不通」误判成「绘制不通」。

## 1. R59 改动面（两处，均为可回退的小改）

| # | 文件 | 改动 |
|---|---|---|
| **D1** | `Library/avb/VerifiedBoot.c` | `EspFiles[]` 由 `STATIC CONST` 改局部；新增全局 `CHAR16 gEspBootPath[64] = L"\\boot\\boot.img"`，入口处 `EspFiles[0].Path = gEspBootPath` ⇒ **起哪个 boot.img 可在运行时选** |
| **D2** | `Application/LinuxLoader/LinuxLoader.c` | 新增 `LMenuSelect()`：在 `BoardInit()` 之后、`LEspForceBoot()` 之前读 ESP 上的 `\menu.cfg`（缺失则只有默认项 `\boot\boot.img`），用 `GetKeyPress` 轮询 `timeout` 秒（默认 3 s）：音量上/下移动、电源确认、超时选第 0 项；特殊项 `-fastboot` / `-poweroff` 直接执行。全过程写 `\loader.log`（`[L] menu entry n=` / `[L] menu key <scancode>` / `[L] menu boot <path>` / `[L] menu timeout`） |

`menu.cfg` 格式（ESP 根，纯文本，`#` 开头为注释）：

```
#timeout=5
Elden Linux (vk185)|\\boot\\boot.img
Elden Linux (vk184 alt)|\\boot\\boot2.img
Mu fastboot|-fastboot
```

## 2. 判据（零写盘，`fastboot boot` p59）

| 判据 | 期望 |
|---|---|
| 菜单生效（默认项） | 不按键启动 → `/proc/cmdline` 含 `elden_bootloader=esp`、`uname -r` = ESP `boot.img` 的内核；`\loader.log` 有 `[L] menu timeout` |
| 菜单生效（选择项） | 开机时按住**音量下**再放 → `\loader.log` 有 `[L] menu key 2`（`SCAN_DOWN`）与 `[L] menu boot \boot\boot2.img`；`uname -r` = 备选件（vk185 `00003`） |
| 输入通道可用 | `\loader.log` 出现任意 `[L] menu key` 行 —— **这是本轮唯一真正的新知识** |
| 不变式 | `boot_b` sha 不变、`/` 仍是 `/dev/sda17` |
