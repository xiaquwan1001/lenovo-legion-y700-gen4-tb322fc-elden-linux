## 3. 本轮拿到的四条硬事实

### 3.1 R29 几何确认正确（`PITFALLS #532` 可关闭）

屏上（OCR，第 2 发）：

```
[F] geom=1904x3040 bpp=32 s=4 ck=OK
[F] len=2B00000 panel=1614800 lim=1614800
[F] stride=1DC0 line=59400 cols=79 rows=63
```

- `panel = 1904*3040*4 = 0x1614800`，`lim == panel` ⇒ 预算夹取正确（旧版是 `lim=164800` 那一套矛盾数）。
- `line = 0x1DC0 * 12 * 4 = 0x16500`？不是 —— `line` 现在按 **scale 4** 算：`0x1DC0*12*4 = 0x59400` ✅
  与 `line=59400` 一致；`cols = 1904/(6*4) = 79` ✅；`rows = lim/stride/(12*4) = 63` ✅。
- 结论：**scale 4 下每行 365 568 B，整屏 63 行**，`[F]` 与算式完全对得上。

### 3.2 【自伤 #18】`[F]` 三行被刷了上百遍 —— 屏被我们自己的自检吃光

OCR 显示 `[F] geom=… / [F] len=… / [F] stride=…` 出现在**几乎每一条 `[I] xxx.efi base=…` 之前**。
根因：**每个 DXE 映像都链接了 `FrameBufferSerialPortLib`，各有自己一份静态变量**
（`m_Initialized`、几何缓存…）⇒ 每个驱动初始化控制台都打三行。
这就是「`[F]` 明明打了却被冲刷掉」的真因 —— 与「写穿」无关，是**我们自己的探针把屏吃光了**。
p36 已修：几何自检只进环（`SerialPortLogPutString`），只有 `ck=BAD` 才占屏。

### 3.3 崩溃前的位置与那串 I2C NACK 的真实含义

OCR 顺序（第 11–12 张图）：

```
[D07b] [D08] [S] setvar=Success
[I] found=1 size=0x2D400
[I] ? base=00000000CFC9B000 size=0004B000
[I] LoadImage=Success          ← BdsDxe 交给 LinuxLoader 成功
[I] cpu-hook=ok                ← R18 的异常处理器已接管
usb_repeater_reset, core_num : 0x0
se_id is 3 / qup_config: check fifo
usb_wcd_init, open inst|slalcore: 0xE0E00
usb_shared_wcd_i2c_reset → ERROR:NACK: SA:0x0E Inst:0x0001 0x03  （×数十行）
qup_fifo_cancel : Geni command not active : 0x00A8C000
usb_shared_i2c_read, read failed reg : 0x1A / wcd FW : 0x0
usb_redriver, Failed slave: 0x10   （第 6 图，更早一次）
ssusb_phy_init_success lane: 0x0
Dev_Common_Speed: Dev Bus Speed: High, state 2
```

解读（与 `1986`/`qup` 语义对齐）：

- `usb_wcd_init` 走的是 **USB 共享 I2C**（`se_id 5` / `qup_id 1`），而第 6 图更早的日志已给出
  `qup_open : h_ctxt is NULL, se_id 5, qup_id 1` / `open core 0x1 5, ERROR 11` / `Failed to init i2c: 12`
  ⇒ **QUP 句柄根本没建起来**，后续所有 `usb_shared_i2c_*` 都是 NACK，符合「句柄 NULL 后的连带失败」。
- 这解释了 `usb_redriver, Failed slave: 0x10`：redriver 的 I2C 从地址写不进去。
- **它不是本轮新问题**：与 2026-10-05 首轮 bring-up 记录的
  「`Failed to locate SCM protocol for Mailbox 14` / `Fail to init client handle to QBSS clock node` /
  `CPU_Vectors region not present in cfg file`」同族 —— Mu Pakala 移植层的**平台配置缺口**。
  本轮 OCR 又补了三条同族证据：`mbox_os_init: Failed to locate SCH protocol for Mailbox 14`、
  `ProdMode HUB not found`、`Fail to init client handle to QDSS clock node`，
  以及 `Error getting gEfiKernel1ProtocolGuid handle, Status: 0xE`、`pm8550b batt_vol: 0mV`。
- 另有 `RmvmDxe.efi … Merge Overlay: -3 / MergeRmDtbo Status: 1 / Gunyah Interface init error: Load Error /
  Skipping RmvmProtocol Install` —— 与 Gunyah 已结项裁决一致，不追。

**判据地位**：这段洪水**发生在 `cpu-hook=ok` 之后**（即 `StartImage(LinuxLoader)` 内部），
因此「崩在 EB 段 USB redriver 重初始化」这条旧归因**重新获得支持**，
但**仍未被证明是崩因** —— 需要 `posteb` 那条落盘记录才能定（本轮到不了）。

### 3.4 USB 端点被打死（新纪律）

连续 `oem sbread` 读 1200 B（60 次调用）之后，设备进入：

```
DwcSubmitURB:Trb: physical endpoint 3 is in invalid state 4
UsbfnDwcSubmitUrbNode: SubmitUrb Failed: 0x8000000F
UsbDeviceSend: Failed to submit data transfer: Device Error
DwcUpdateURB:Trb: TRB ring of EpIndex 3 is full
```

⇒ 这是 `PITFALLS #523`（EB 拆 USB 栈）的一个新形态：**不是 EB 造成的，是我们自己的高频读把 EP3 打死**。
新纪律：`oem sbread` **一次只拉一屏（≤ 512 B）**，块间 `sleep`，且**不要在同一固件会话里连续读整窗**。

## 4. 主机侧四个 bug（三个自伤，各吃一发上机）

| # | bug | 现象 | 修法 |
|---|---|---|---|
| 1 | **`ReadBlocks/WriteBlocks` 的 LBA 参数传了字节偏移** | `sbread st=Invalid Parameter`（ScsiDisk 判 `Lba > LastBlock`）；**写侧同 bug，意味着 logfs 一直没写进去** | `Base = LastBlock + 1 - (SB_LOG_WINDOW/BlockSize)`（块号）；读侧再除 `BlockSize` |
| 2 | `ReadBlocks` 的 `BufferSize` 非块大小整数倍 | `EFI_BAD_BUFFER_SIZE` | 按块对齐读进 bounce buffer 再拷出 |
| 3 | fastboot **响应缓冲 `MAX_RSP_SIZE=64`** | `OKAY` 后什么都不显示（载荷被截断） | 改 `FastbootInfo` 分块（20 B/块 → 40 hex 字符） |
| 4 | `oem` 的 `Arg` **带命令名/分隔符**（`sbread:0:60`），且 `sbread` 里含 hex 字符 | 解析出 `Len=0` → `Invalid Parameter` | 按 `:` 切段，取**尾部两个纯十六进制段**（倒数一 = len，倒数二 = off）；失败时把 `o=… l=…` 一起回给宿主（本轮正是靠这个把 #1 抓出来） |

## 5. 现在的状态与下一步

- **通道状态**：`logfs` 尾部 16 KiB 记录 + `oem sbread` 回读 **已实测可用**；
  宿主侧读端 `scripts/uefi-logfs-read.py`（`--len/--off/--raw/--serial`）。
- **未完成**：`tag=posteb` 记录尚未取到（第 4 发在读窗时把 USB 打死，未做真内核载荷那一发）。
- **下一步（p37，主机侧 0.5 h + 上机 2 发）**：
  1. 真内核载荷（`out/boot-elden-vk172.img`，82 MB，**一会话一发**）跑一次，让 `entry/preeb/posteb`
     三条记录都落盘；崩了就物理断电 → 起 Linux → `dd if=/dev/disk/by-partlabel/logfs bs=4096 skip=2016 count=4`
     （或重启进 UEFI 后用 `oem sbread` 分块慢读）。
  2. 若 `posteb` 存在 ⇒ 崩点在 EB 之后（交接参数/内核极早期），与 §3.3 的 USB redriver 段无因果；
     若不存在（且 `preeb` 在）⇒ 崩在 EB 之内，回到「EB 段 USB/I2C 重初始化」这条线，按
     `qmcs`/`se_id 5` 的 QUP 句柄缺失单独开题（与主线 qcom QUP/I2C 上游化共用证据）。
  3. `[F]` 已不占屏 ⇒ 屏预算全部留给 `[K]` 判据；顺带验证 §3.2 的修复。
- **止损不变**：p37 之后累计再 3 发无实质进展 ⇒ 收口，UEFI 回「非主线、不阻塞」。

## 6. 复现命令

```bash
# 构建（主机侧，~4 min/次；p34/p35/p36 各自独立配方）
PFX=p36 RECIPE=patches/uefi/p36-recipe.txt OUTDIR=out/r21-sbstop-p36 \
  BUILD_ARCHIVE=reports/artifacts/uefi-20261106R32-p36e/build \
  STAGES="26 27" scripts/uefi-r21-p7-ladder.sh --mkimg-only --rebuild

# 上机（零写盘，ABL 侧起 UEFI）
fastboot -s HA2EXB0E boot out/r21-sbstop-p36/uefi-preamble36-r1.img

# 读回落盘日志（**分块慢读，一次 ≤512 B**）
scripts/uefi-logfs-read.py --serial 51318dc0 --len 512

# 设备起 Linux 后（更省事）
dd if=/dev/disk/by-partlabel/logfs bs=4096 skip=2016 count=4 status=none | strings
```
