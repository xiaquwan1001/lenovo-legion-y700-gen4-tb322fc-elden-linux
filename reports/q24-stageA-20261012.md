## 2. 挂死形态判定（与历史 Q24 签名不同）

| 判据 | 读值 | 含义 |
|---|---|---|
| USB gadget 是否仍枚举 | `/sys/bus/usb/devices/5-1` = `TB322FC mainline 1d6b:0104`，NCM + 3×ACM 全在、驱动已绑 | **USB 外设侧仍活** |
| 是否重启/掉电 | `devnum` 恒 16、`active_duration` 连续增长（≈72 min，起点 08:08）⇒ **未重枚举、未重启** | 不是硬复位、不是掉电 |

⇒ 本次形态 = **整机挂死（hang）**，USB 枚举态残留；**不是**历史 Q24 的「硬复位 / 真关机（uptime 归零）」，也**不是** Q28 的 panel init 失败。与 `PITFALLS #106`（GUI 死挂）同一类，但 USB 仍枚举。

⚠ **不确定性（必须记录）**：命令 #2 无输出 ⇒ 无法确认它是否执行到 `modprobe`。因此**不能断言**「挂死由第二次 `{camcc,cambist}` 加载引起」。可能是：(a) #2 加载后遗留两模块在位、空闲约 1 min 后挂死；(b) #2 未执行、设备自发挂死；(c) 与相机模块无关的其他原因。**下次开机必须先做带日志的受控复现来判别。**

## 3. 阶段 A 新证据（4 条，均为实测）

| # | 证据 | 出处 |
|---|---|---|
| A-1 | **`camcc` probe 后 `state_synced = 0`**（永不 sync）——`{camcc,cambist}` 都在位时仍为 `0` | `both.txt` |
| A-2 | **`cambist` 设备无 `state_synced` 属性**（bound 后仍读空）——与 camcc 不同族 | `both.txt` |
| A-3 | ★**「死前共同签名」= cambist probe 的正常签名，不是死因**：`modprobe cambist` 瞬间 RPMh 一次性重报 `ebi/gfx/lcx/lmx/mss/nsp/nsp2/gmxc/mxc→0`、`mmcx→6`、`mx→5`、`cx→6`。**本次无熄屏、设备存活**，该签名照样出现；且 `mxc=0` 与稳态一致（`mxc=off-0`）。⇒ 既往把它称「死前共同签名」是**时间相关巧合**（它总在第二个 CC probe 时出现），**非因果** | `trace-votes.txt` vs `reports/q24-repro-20261011.md` §4 |
| A-4 | 稳态轨态（模块不在位）：`mx=on`、`mmcx=on`、`mxc=off-0`、`ebi/gfx/gmxc/lmx/lcx=off-0`、`cx=on` | `pre.txt` |
| A-5 | genpd 消费者：`mx` ← gcc + gpucc；`mmcx` ← dispcc + videocc + display-controller + dsi×2 + displayport-controller；`mxc` ← dispcc | 实测 `pm_genpd/*/devices` |

## 4. 结论修正

1. **既往「死前共同签名」的定性作废**：那串「投 0」是 **cambist probe 的常规行为**，与死亡无因果（`PITFALLS` 待补条目）。
2. **camcc `state_synced=0` 坐实**（H2 前提成立，但 A-3 表明单靠这把「夹持值」不足以解释死亡）。
3. **挂死形态**：本轮死法是 **hang（USB 枚举残留）**，与历史「硬复位/掉电」不同 ⇒ Q24 可能不止一种终态，取证判据需并列（`boot_id` + `devnum`/`active_duration` + USB 枚举 + 串口回显）。
4. 计划 h1（DT 绑定）**未被本轮触及**，仍是首选。
