## §1 输入盘点：v1 形状、否决理由、A/B 证据

### 1.1 v1 形状（已否决）

`patches/upstream/q28-dispcc-2026-10-22/0001-clk-qcom-dispcc-sm8750-reset-MDSS-blocks-at-probe.patch`：

- 位置：`disp_cc_sm8750_probe()` 内、`clk_taycan_elu_pll_configure()` **之前**；
- 动作：`of_machine_is_compatible("lenovo,elden")` 门控下，`regmap_write()` 直接断言三个 BCR
  （`DISP_CC_MDSS_CORE_BCR` 0x8000 / `DISP_CC_MDSS_CORE_INT2_BCR` 0xa000 / `DISP_CC_MDSS_RSCC_BCR` 0xc000），
  `msleep(50)` 后**逆序**释放；
- 机理：bootloader 交棒时 PLL 已锁、MDSS 块已出复位，内核在活状态上编程 ⇒ 冷起 command DMA
  超时（`status=0x2200200`）+ 面板 init `-5`，仅背光无 `card0`。

### 1.2 上游否决（Taniya Das，2026-10-22 22:52 +0800）

> These resets if required should be taken care or triggered from the Display SW driver.
> It is not on to the clock driver to drive these resets. If these are done the complete
> dispcc would be reset and when the PLLs gets reconfigured there should be a flicker
> observed on the display.

两点：① 复位职责属**显示 SW**，不属 clk driver；② dispcc 整块复位 + PLL 重配 ⇒ 闪屏。
我方 2026-10-28 回信已接受否决并承诺改形状（`reports/dispcc-battmgr-20261028.md` §C.1）。

## §2 v2 形状设计

响应否决两点（§1.2）的形状选择：

1. **职责归位（否决 ①）**：复位动作整体迁到显示侧既有 `msm_mdss_reset()`，
   `drivers/clk/qcom/dispcc-sm8750.c` **一行不动**（v1 的 35 行 clk 改动作废）。
2. **不用 dispcc 整块复位、不重配 PLL（否决 ②）**：v2 只驱动 MDSS 三个块级 BCR
   （CORE / CORE_INT2 / RSCC），均在 dispcc 寄存器空间内但只作用于 MDSS 块，
   **不触碰 PLL 寄存器、不重新编程 PLL**；且复位发生在 mdss probe 最前端，
   此时无任何显示流水线在跑，无闪屏面。
3. **通用机制取代板级门控**：删除 v1 的 `of_machine_is_compatible("lenovo,elden")`；
   改为 DT 描述（sm8750 mdss 节点列全三个 BCR）+ 驱动按 DT 全量复位。
   依据：上游 sm8650/sm8750 等 dtsi 已在 mdss 节点挂 dispcc 单 CORE 复位（§1.4），
   v2 是既有惯例的延伸而非新入口；门控形状在 elden DTS 不上游（§1.5）时会没有 in-tree 用户。
4. **binding 风险（已计入）**：`mdss-common.yaml` 的 `resets` 从 1 项放宽到
   `maxItems: 3`（三项描述，第一项仍是 MDSS core，既有单复位 DT 全部保持合法）。
   放宽是全局的（所有 msm/mdss 平台 binding 继承）；静态核查既有 dtsi 的 mdss
   `resets` 均 ≤1 项，dtbs_check 不受影响。
5. **顺序约束（最大风险，论证见 §5）**：复位时刻从 v1/A-B 有效臂的
   「dispcc probe 内、PLL 编程**之前**」变为「mdss probe、PLL 编程**之后**」。
   这是**未经上机验证的新假设**，作为开放问题 1（§6）。

## §5 顺序约束论证：为什么复位发生在 PLL 编程之后

**顺序事实链（静态可证）**：mdss 节点 `power-domains = <&dispcc MDSS_GDSC>` 且时钟
来自 dispcc ⇒ fw_devlink 强制 dispcc probe 完成后才 probe mdss；PLL 编程
（`clk_taycan_elu_pll_configure` ×2 + `clk_pongo_elu`）在 dispcc probe 内；
`msm_mdss_reset()` 是 `msm_mdss_init()` 第一步（`msm_mdss.c:381`），先于
ioremap/irq/时钟准备。⇒ 复位必然发生在 PLL 编程之后，这是 DT 拓扑决定的、不可回避。

**为什么这个时刻复位可行（响应否决 ②）**：

1. 三个 BCR 只作用于 MDSS 块（core / INT2 / RSC），寄存器在 dispcc 寄存器空间但
   复位线**不连接 PLL**；PLL 寄存器值与锁定状态在复位前后不变，无需重配；
2. 复位时刻无任何显示流水线在跑：panel 未 init、DPU 未启动、mdss 时钟未开，
   bootloader 留下的“活”画面随块复位回到已知零态，之后才由内核重建 ⇒ 无闪屏面；
3. 上游既有惯例即“PLL 之后复位 MDSS 块”：sm8650/sm8750 等 dtsi 的 mdss 节点
   本来就挂 `DISP_CC_MDSS_CORE_BCR` 并由 `msm_mdss_reset()` 在 mdss probe 执行；
   A/B 的 base 臂（9 次真机冷起）执行该动作未引入**新的**失败模式（其 5 次 STORM
   即本系列要修的问题）。

**为什么与 A/B 有效臂不同（最大风险，如实声明）**：A/B 里疗效臂（only0154/exp，
15/15 GOOD）的复位发生在 **dispcc probe、PLL 编程之前**；base 臂证明单 CORE
复位（PLL 之后）**不足以**治 STORM。v2 把 CORE+INT2+RSCC 三枚全部搬到 PLL 之后的
mdss probe —— “INT2/RSCC 在 PLL 后复位与 PLL 前复位等效、且补足 base 缺的那部分”
是**未经上机验证的新假设**（机理上说得通：A/B 的 2×2 解离表明疗效随“三 BCR 被
复位”而非随“复位时刻”，且 PLL 后复位不触 PLL 状态；但行为学疗效必须真机复测）。
归档为开放问题 1，真机 A/B（v2 vs base vs v1）留给下机上机 lane。

## §6 开放问题（留给上游，≤3 条）

1. **疗效等价性未上机**：v2 的复位时刻（mdss probe，PLL 编程后）与 A/B 验证过的
   时刻（dispcc probe，PLL 前）不同；INT2/RSCC 在 PLL 后复位的疗效需真机冷起
   A/B 复测（base / v2 / v1-形状）确认后再发上游。
2. **其他平台跟进**：sm8650 dispcc 有完全相同的三 BCR（`qcom,sm8650-dispcc.h:93-95`），
   sc7180/sc7280/sc8280xp/sm6350/sm8150 还有 `MDSS_RSCC_BCR`，但其 mdss 节点均只描述
   单 CORE 复位；是否/何时把这些平台也列全，留给维护者定（本系列只动 sm8750——
   唯一有 handover 行为学证据的 SoC）。
3. **20 ms 保持时长**：上游 `msm_mdss_reset()` 既有 20 ms（≈一帧）是按单 CORE 调的；
   全组三枚共用该时长是否足够（v1 曾用 50 ms）需要真机确认，必要时改成按帧数
   参数化。
