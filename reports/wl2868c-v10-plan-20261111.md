## §2 意见 ①：SYS_EN 预置（“preset LDOs enabled by wl2868c_probe() when SYS_EN is 0”）

### 2.1 sashiko 说的（逐字，`/tmp/sashiko-205554.txt:236-249`）

> [Severity: Medium]
> Doesn't seeding chip->enabled without checking whether bit 7 (sys_en) is
> set in value defeat the protection against preset LDO bits in
> wl2868c_enable()?
>
> When bit 7 is clear at probe time, any preset per-LDO bits in value are
> copied into chip->enabled even though all outputs are off and
> wl2868c_is_enabled() reports them as disabled.  The first wl2868c_enable()
> call for any single output then writes chip->enabled | bits together with
> bit 7, turning on all of the preset outputs and leaving them stuck on
> even after consumers disable their regulators.

### 2.2 当前代码怎么做的（v9）

```c
/* v9-0002-…patch:299-304  (hunk 行 299-304) */
+	ret = regmap_read(config.regmap, WL2868C_LDO_ENABLE, &value);
+	if (ret)
+		return dev_err_probe(dev, ret, "Failed to read the enable register\n");
+
+	chip->enabled = value & WL2868C_LDO_ENABLE_MASK;
```

- 播种行 = `v9-0002:304`，**无任何 `SYS_ENABLE` 判断**，直接抄 7 个 LDO 位。
- 宏：`v9-0002:104-105` —— `#define WL2868C_SYS_ENABLE BIT(7)` / `#define WL2868C_LDO_ENABLE_MASK GENMASK(6, 0)`。
- `wl2868c_enable()` 的写法本身是对的（`v9-0002:130-146`）：它把 `chip->enabled | bits` 与 `SYS_ENABLE` 一起写，注释（`:114-124`）明说「预置位在 SYS_EN 为 0 时不可见，所以只写消费者拥有的位」。
- `wl2868c_disable()`（`v9-0002:150-174`）：`ldos = chip->enabled & ~bits`，`ldos ? SYS_EN|lodos : 0`。
- `wl2868c_is_enabled()`（`v9-0002:176-188`）：`mask = SYS_ENABLE | enable_mask`，返回 `(value & mask) == mask`。

**为什么是真 bug（自洽性推演）**：设上电后 `LDO_ENABLE = 0b0000_0110`（firmware 预置 LDO2/LDO3，SYS_EN=0）。此时没有输出上电，`is_enabled()` 对 7 个 LDO 全部返 0。用户 enable ldo1：

```
ldos = (0b0000_0110 | BIT(0)) & 0x7f = 0b0000_0111
write 0x0e = SYS_EN | 0b0000_0111  →  LDO2、LDO3 跟着一起上电
chip->enabled = 0b0000_0111        →  LDO2/LDO3 的预置位从此“丢失”，consumer 再也不会关掉它们
```

即：**预置位被“洗白”进了受跟踪集合**，之后即使 consumer 把 ldo1 关掉（`ldos = 0`，写 0），LDO2/3 也确实是关的——但**在 ldo1 开着的那段时间里它们是被意外打开的**，而且 regulator core 认为它们从没被打开过（`is_enabled()` 之前返 0），属于“不受 core 管理的额外上电”，与驱动注释自称的不变量（“enabling one output cannot power another one”，`v9-0002:26-28` 提交信息）直接矛盾。sashiko 说 “leaving them stuck on” 指的是 SYS_EN 一直为 1 的期间。

### 2.3 v10 应怎么改

**核心一行：播种前先看 SYS_EN。** 但只加 `if` 不够——如果把 `chip->enabled` 直接置 0，则“firmware 真把某个 LDO 开着了”的场景会在 `enable(另一个)` 时被意外关掉（这是 v7 之前的老问题，v9 的注释 `:114-118` 就是在防它）。两种自洽写法，要选一个并在 commit message 里说清：

**方案 A（推荐，改动最小，与 11-08 草稿一致）**：SYS_EN=0 ⇒ `chip->enabled = 0`。理由：SYS_EN=0 时**没有输出真的上电**，预置位只是电压选择器旁寄存的使能位，不构成“core 认为已开”的状态；`is_enabled()` 也返 0，二者自洽。

## §3 意见 ②：reset 早于 vsys（“reset released before enabling vsys in wl2868c_probe()”）

### 3.1 sashiko 说的（逐字，`/tmp/sashiko-205554.txt:186-196`）

> [Severity: Medium]
> Does wl2868c_probe() release the reset line and wait 1 ms before enabling
> the vsys power supply below?
>
> If vsys is initially off, the reset deassertion and 1 ms startup delay
> happen while the chip is unpowered, and the subsequent device ID read runs
> immediately after devm_regulator_get_enable() with no startup delay.
> Because devres unwinds in reverse order, unbind or probe failure will also
> disable vsys before wl2868c_reset() asserts reset.

一句话拆成三个具体指控：(a) reset 释放+1 ms 延时发生在无供电时；(b) 首次 `regmap_read(DEVICE_ID)` 紧跟 supply enable 之后无启动延时；(c) devres 逆序拆解 ⇒ vsys 先关、reset 后置位。

### 3.2 当前代码怎么做的（v9）


行号事实：reset 动作在 **262-271**，vsys 使能在 **284**（偏后 22 行），ID 读在 **288**（偏后 4 行，无任何 `fsleep`/`usleep_range` 插入）。sashiko 三条指控**全部命中**。

补充旁证（devres 逆序的真实后果）：`devm_regulator_get_enable()` → `_devm_regulator_get_enable()` → `devm_add_action_or_reset(dev, regulator_action_disable, r)`（`build/base-7.2/drivers/regulator/devres.c:71-90`，其中 `:85` 是注册点；该文件与 pristine 7.2 逐字节同，`git -C build/base-7.2 show 25f7927e6:drivers/regulator/devres.c` 比对无差异）。v9 里 reset action 先注册、vsys action 后注册 ⇒ 卸载时 **vsys 先 disable**，然后才跑 `wl2868c_reset()`（`v9-0002:240-243`，把 RST_N 拉高）。顺序恰好相反。

根因一句：这是脚本式直线 probe，把“电源→reset→读 ID”的物理顺序写反了，而不是三个独立 bug。

### 3.3 v10 应怎么改

正确序（每种资源“拿+启用”的动作按物理时序注册，让 devres 逆序恰好等价于物理下电序）：

1. `devm_gpiod_get_optional(..., GPIOD_OUT_LOW)` —— 早拿，但**保持置位**（`wl2868c_reset()` 里 `gpiod_set_value_cansleep(data, 1)` = RST_N 拉高 = 复位有效；`v9-0002:240-243`）。
2. **控制供电优先**（见 §4：`vsys` → `vin7` 回退）——`devm_regulator_get_enable*`。
3. 供电起身后延时（datasheet 未到手，**待核**：暂沿用 1 ms）。
4. **然后**才 `devm_add_action_or_reset(dev, wl2868c_reset, reset)`，此时 action 里已经是“释放”语义——**⚠ 语义坑见下**。

⚠ **必须修的一个语义坑**：现在 `wl2868c_reset()` 是无条件 `set_value(1)`（拉高 = 复位有效），靠的是 `GPIOD_OUT_LOW` 的初值。v9 的写法里，“释放 reset”只是**不改 GPIO**（读完初值 0 就往那儿放着），从来没有显式 deassert。一旦把动作挪到供电之后，这个“靠初值隐式释放”的写法就变得无法阅读。建议显式化：

```diff
-static void wl2868c_reset(void *data)
+static void wl2868c_reset(void *data)
 {
 	gpiod_set_value_cansleep(data, 1);
 }
+
+static int wl2868c_power_off_reset(void *data)
+{
+	gpiod_set_value_cansleep(data, 0);
+	return 0;
+}
```

要点（每条对应 sashiko 的一个分句）：

| sashiko 分句 | v10 处理 |
|---|---|
| (a) reset 释放在无电时 | `GPIOD_OUT_HIGH` 初值+显式 `set_value(0)` 都在 supply enable **之后** ⇒ 释放在有电时 |
| (b) ID 读紧跟 enable 无延时 | 释放后 `fsleep(WL2868C_STARTUP_US)` 再读 ID；即便无 reset-gpios 的板，也应有延时（建议保留一个无条件的 `fsleep` 在 supply enable 后） |

- **延时宏化**：宏型名字（`WL2868C_RESET_RELEASE_US` / `WL2868C_STARTUP_US`）比裸 `fsleep(1000)` 好回信、好引用 datasheet 页码；**待核**：WL2868C 手册未在本仓存档（`rg -l -i "wl2868" RESOURCES/ reference/ | head` 无 datasheet），所以数值只能沿用 1 ms，并在回信里写“按厂商手册 §x.y 的 1 ms 保守值，无手册页码”。

## §4 意见 ③：vin7-supply 控制供电（“vin7-supply not enabled for I2C in wl2868c_probe()”）

### 4.1 sashiko 说的（逐字，`/tmp/sashiko-205554.txt:220-229`）

> [Severity: Medium]
> What happens on boards that power the control logic and I2C interface from
> vin7-supply without vsys-supply?
>
> The devicetree binding allows supplying either vin7-supply or vsys-supply,
> but wl2868c_probe() only enables vsys and leaves vin7 attached solely as
> the input supply of ldo7.  When vsys-supply is omitted,
> devm_regulator_get_enable() falls back to a dummy regulator while
> vin7-supply stays disabled during the initial register reads and whenever
> ldo7 is off, leaving the chip unpowered on the I2C bus.

### 4.2 当前代码怎么做的（v9）

- binding：`v9-0001:104-108` `anyOf: - required: [vin7-supply] / - required: [vsys-supply]`（**二选一**）；`vin7-supply` 的描述 `v9-0001:79-83` = “Input supply for LDO7 **and one of the two supplies of the internal control logic**”；`vsys-supply` `v9-0001:84-88` = “System supply, the other supply of the internal control logic…”。
- 驱动：**只取一次 `vsys`** ——`v9-0002:284` `ret = devm_regulator_get_enable(dev, "vsys");`。`vin7` 在驱动里只以 **`supply_name`** 出现一次：`v9-0002:231` `WL2868C_LDO(7, "vin7", 1504000, 256, 0x09, 0xff, BIT(6)),`。全文件 `grep -c vin7` = 1。
- 结果：vin7-only 板上 `_regulator_get` 走 `NORMAL_GET` → 无 lookup 命中 → `have_full_constraints()` 为真时拿 **dummy**（`build/base-7.2/drivers/regulator/core.c:2448-2459`，关键行 `:2455` 是 `dev_warn(dev, "supply %s not found, using dummy regulator\n", id)`）；dummy 的 enable 是空操作 ⇒ 控制逻辑直到 ldo7 被 consumer 打开前无电，`regmap_read(DEVICE_ID)`（`v9-0002:288`）会 I2C 超时。⇒ **成立**。
- （推演，待核）`have_full_constraints()` 为假（未开 `CONFIG_REGULATOR_*` 全套/无 `regulator_ignore_unused` 情形）时 `_regulator_get_common()` 直接返 `-ENODEV`（`core.c:2441-2445`：“incomplete constraints, dummy supplies not allowed”），则 vin7-only 板直接 probe 失败而不是静默错误——两种失败模式都不对。

### 4.4 v10 应怎么改

需求：(1) `vsys` 与 `vin7` **任一**存在即可；(2) 存在的那个要在驱动生命周期内保持 enable（两个都在时也要都 enable？**不**——只需 enable 被用作控制供电的那个；但两者物理上都参与“higher of VIN7 和 VSYS”，安全做法是**两个都取、两个都 enable**，谁在都不亏）；(3) 必须有可读的错误路径；(4) 不能吞掉 `-EPROBE_DEFER`。

**推荐写法（vsys 优先，vin7 回退；两者都在时只用 vsys 作控制供电，vin7 留给 ldo7 的 regulator tree）**：

```diff
@@ -239,6 +239,29 @@
+/*
+ * VIN7 and VSYS both feed the control logic and the I2C interface, which run
+ * from the higher of the two. The binding requires at least one of them, and
+ * whichever is present has to stay up for as long as the driver is bound:
+ * without it the device does not answer on the bus.
+ */
+static int wl2868c_enable_control_supply(struct device *dev)
+{
+	int ret;
+
+	ret = devm_regulator_get_enable_optional(dev, "vsys");
+	if (ret != -ENODEV)
+		return ret;
+
+	ret = devm_regulator_get_enable_optional(dev, "vin7");
+	if (ret)
+		return dev_err_probe(dev, ret, "No control supply\n");
+
+	return 0;
+}
+
 static int wl2868c_probe(struct i2c_client *client)
```

注意 `if (ret != -ENODEV) return ret;` —— 与草稿的 `if (sup == -ENODEV) sup = …; if (IS_ERR(sup))` 差别在于：

- `-EPROBE_DEFER`（`vsys` 的 provider 还没 probe）→ 直接返回，**不会**错降级到 `vin7`（若错降级，之后会拿到完全不相关的供电）；
- `0`（成功）→ 直接返回，不碰 `vin7`；
- 只有 `-ENODEV`（DT 里没有这个 supply）→ 才去看 `vin7`。

**替代写法（两个都 enable，更贴近“higher of”硬件语义）** ——若 reviewer 问“两个都接的板上 vin7 也要不要 enable”，这就成了正确形：

```c
	ret = devm_regulator_get_enable_optional(dev, "vsys");
	if (ret && ret != -ENODEV)
		return dev_err_probe(dev, ret, "Failed to enable the system supply\n");
	have_supply = !ret;

	ret = devm_regulator_get_enable_optional(dev, "vin7");
	if (ret && ret != -ENODEV)
		return dev_err_probe(dev, ret, "Failed to enable the vin7 supply\n");

	if (!have_supply && ret == -ENODEV)
		return dev_err_probe(dev, -ENODEV, "No control supply\n");
```

**选型建议**：先用第一种（**推荐**，代码短，reviewer 不会问 devres 拆解顺序）。它天然满足"至少一个"，且不改变两个都在时的现有行为（保持与 v9 对 elden 的实际行为一致 = 只 enable vsys）。回信里把第二种作为“如果你希望两个都 enable，我改成…”的备选写明，避免再一轮拉锯。

同步要改的文案：

1. `v9-0002:279-283` 的注释 “the system supply has to be up” → “the control supply (VSYS or, on boards without it, VIN7) has to be up”。
2. `v9-0002:32-36` 提交信息尾段 “so the \"vsys\" supply is enabled for as long as the driver is bound” → “so VSYS is enabled, falling back to VIN7 on boards that do not describe VSYS”。
3. `v9-0002:284-286` 的三行调用删掉，换成 `ret = wl2868c_enable_control_supply(dev); if (ret) return ret;`。

### 4.5 为什么不能用 `devm_regulator_get_enable(dev, "vsys")` + `regulator_get_optional()` 手工 enable

`devm_regulator_get_enable()` 是 `NORMAL_GET`（`devres.c:126-129`）⇒ 无 supply 时静默 dummy，永远不返回 `-ENODEV`，无法区分布有/未布。**必须**用 `_optional` 变体。这是本条意见的全部技术核心，回信里要把它写成一行结论。
