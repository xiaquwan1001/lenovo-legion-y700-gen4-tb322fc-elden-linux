## 1. 结论（三句话）

1. **`skip_l23_ready` 补丁有效**：`Timeout waiting for L2 entry` 从「每次 suspend 必打」变成 **0 次**。
2. **但 L2 超时从来不是「1.4 s 就醒」的原因**（静态分析 `reports/pcie-l2-static-20261020.md` §0 的怀疑成立）：
   实测 3 次 suspend 全部由 **BT `hci_uart_qca` 的 `qca_suspend` 3 s 超时（-110）** 弹出（`last_failed_dev=serial0-0`）；
   长时间挂起后的失败点则是 **ath12k resume -110**。
3. **屏蔽 BT 后 suspend 真能站住**：`rfkill block bluetooth` → 两次 suspend **success=2**，
   其中一次 **held 3 389 074 ms ≈ 56.5 min**（直到人工按电源键），`boot_id` 全程不变、无 panic。

## 3. 因果链（原文，vk130）

```
A2/A3（3.5 s 弹出）
[25.60] dwc3-qcom a600000.usb: port-1 HS-PHY not in L2              ← 次生
[25.67] ieee80211 phy0: PM: parent 0000:01:00.0 should not be sleeping   ← ath12k 驱动 bug
[28.64] Bluetooth: hci0: SSR or FW download time out
[28.64] hci_uart_qca serial0-0: PM: dpm_run_callback(): qca_suspend returns -110
[28.64] PM: Some devices failed to suspend, or early wake event detected  ★直接原因
A1（24.9 s 才弹出）
[50.14] ath12k_wifi7_pci: timeout while waiting for restart complete
[50.14] ath12k_wifi7_pci: failed to resume core: -110
[50.14] PM: dpm_run_callback(): pci_pm_resume returns -110
```

⇒ **两个独立缺陷**，与 PCIe L2 无关：
① BT `qca_suspend` 等固件进睡眠 3 s 超时（WCN7850/`hci_uart_qca`）；
② ath12k 长挂起后 resume 时 `restart complete` 超时。

## 4. 方法学修正（影响旧结论）

- 设备 RTC 与系统时钟**不在同一 epoch**（本次 `rtc0/since_epoch=225 770` vs `sys=1 792 543 996`，
  即设备侧时间停在 1970 而 userland 是 2026）。写 `/sys/class/rtc/rtc0/wakealarm` 必须用
  **RTC epoch**：`echo $(( $(cat /sys/class/rtc/rtc0/since_epoch) + N )) > wakealarm`。
  用 `rtcwake -m mem -s 30` 或 `date +%s` 写入 = 闹钟落在「几十年后」，**根本不会触发**
  ⇒ 旧报告「RTC 未参与唤醒 / 被别的东西弹出」的解释里，至少有一部分是**测试方法问题**，
  不是内核对 RTC 的处理问题。
- 设备侧 `dmesg` 时间戳用 monotonic（不含挂起时间），`/proc/uptime` 用 boottime（含）；
  核对驻留时长以 `date +%s%3N` 前后差为准。

## 5. 顺带复验：Linux 安全重启进 fastboot（G1-24）

```
ssh root@192.168.7.1 'sync; reboot2 bootloader'     →  `fastboot devices` 2 s 后出现 `HA2EXB0E`
```
`fastboot boot out/boot-elden-vk130.img` = Sending 83 704 KB / Booting 10.1 s，15 s 后 SSH 回来。
⇒ **「运行中的 Linux → fastboot」通道可靠**，可用于零写盘迭代，不需要按键。

## 6. 下一步

1. **量化掉电率（T9 原始目标）**：`rfkill block bluetooth` + **拔 USB** + RTC-epoch 闹钟（如 +30 min）
   → 用 `suspend-drain-rate.sh` 口径算 `%/h`。需要人工拔线/唤醒。
2. **BT suspend 治本或规避**：
   - 规避（今天就能用）：suspend 前自动 `rfkill block bluetooth`、resume 后恢复（OpenRC/elogind 钩子）；
   - 治本：查 `hci_uart_qca` 的 `qca_suspend` 为什么会走到 `SSR or FW download time out`（固件未就绪时是否该直接返回成功 / 是否应 defer）。
3. **ath12k resume -110**：`restart complete` 超时与 MHI 电源时序、PCIe L1.2 的关系；`hwmon parent phy0 should not be sleeping` 一并修。
4. `dwc3 port-1 HS-PHY not in L2`：USB PHY 在 suspend 时状态机未到 L2，可能与 HS 数据通路 mux 相关（M3-1 的两连接器拓扑）。
