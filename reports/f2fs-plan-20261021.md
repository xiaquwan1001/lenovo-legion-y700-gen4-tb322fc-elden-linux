# f2fs 迁移可行性评估 — Linux 根分区（TB322FC / elden）

> 状态：**只读研究 + 规划**（2026-10-21）。**本轮零设备写操作**：设备停留 fastboot（`fastboot devices` = `HA2EXB0E`），
> 未执行任何 fastboot flash/boot/oem、adb、EDL、reboot；所有结论来自主机侧读文件 / 静态解析 / 公开检索。
> 标记：**【已证实】**= 路径+行号或命令+输出；**【未证实】**= 有线索缺直接证据；**【推测】**= 推理，不得当结论。

## 0. TL;DR

1. **可行，内核侧已就绪**：`build/m1-73/.config` 有 `F2FS_FS=y` + `F2FS_FS_XATTR/ POSIX_ACL=y`（:10899-10902），依赖全满足；**唯一代码阻断项 = `/init` 把根挂载写死 `mount -t ext4`**（`initramfs/init:246`，在机 ramdisk 同处 `init:224`）。
2. **用户态基本齐**：主机缺 `f2fs-tools`（候选 1.16.0-2build1）；**设备 Alpine rootfs 已装 1.16.0-r4**（实解归档 → `./usr/sbin/mkfs.f2fs`）。
3. **第一硬约束是空间不是文件系统**：LUN0 已满载（`userdata` 256.7 GiB + `linux17` 193.0 GiB，后者 `last == last_usable`）⇒ 并存必须先切走 `linux17` 一块，或等 Phase B 回收 Android 分区。
4. **收益/风险都有外部数但不可照搬**：f2fs 随机写/fsync 优 ext4（FAST'15 最多 3.1×/2×，写量 −46%）；**高利用率是死穴**（97.5% 时 GC 致 ~30% 性能损失；填满后 4K 随机写掉到 ext4 的 5%）。
5. **结论 = P2（不阻塞 G1/G2/G3）**：现在只做两个前置（`/init` fstype 通用化 + 零写盘 `fastboot boot` 验证；主机 loop 跑熟 mkfs/GC/fsck），**真正切根并入 Phase B 的一次性 GPT 手术**。

### 1.2 Linux 根 = `linux17` / ext4

### 1.3 Android `userdata` 已是 f2fs（同一颗 UFS）

【已证实】`stock-src/twrp-tb322fc/android_device_lenovo_TB322FC-twrp-16.0/recovery.fstab:50`：
`/dev/block/bootdevice/by-name/userdata /data f2fs noatime,nosuid,nodev,`**`discard`**`,reserve_root=32768,resgid=1065,fsync_mode=nobarrier,inlinecrypt …,metadata_encryption=aes-256-xts:wrappedkey_v0,quota,checkpoint=fs`（`sysfs_path=…/1d84000.ufshc`）。
三条意义：① **f2fs 在这块 UFS 上是原厂量产栈**（256.7 GiB 单卷），不是实验组合；② 原厂用 `discard` ⇒ 预期支持 UNMAP（仍需本机实测，§4）；③ 原厂开 `inlinecrypt`/`wrappedkey`，我们的根**不需要**（`FS_ENCRYPTION` 保持 not set）。
另：Android `/data` 是 metadata 加密 f2fs、key 硬件包裹，主线拿不到裸密钥（`reports/m5-dm-default-key-20261013.md:180-186`）⇒ **不能**把 Android `/data` 当 f2fs 样本或复用其 fsck 结论。

### 1.4 仓库已定案（只做确认/差量）

- **确认**：缩 `userdata` 不可逆、f2fs 需重建；扩容优先回收 Android 分区（`DEVICE/README.md:113-116,153`）。
- **确认**：`resize.f2fs -s` 能缩但 ZUXOS 不认，Android 侧 bootloop（`PITFALLS/sessions/12-userdata缩容.md:9-10`、`RUNBOOK-BRINGUP/README.md:306`）。

## 2. 内核侧就绪度（config 现状）

> **路径更正**：任务书的 `build/m1-upstream/clean-tree-73/` **已不存在**（`TASKS/README.md:416` ⚠️MIGRATION-LOST）。现存等价树 = **`build/m1-73/`**（`git describe` = `v7.3-rc7-2-g24223e4`，即 `out/boot-elden-vk133.manifest` 的 `kernel=` 来源）。

【已证实】`grep -nE 'CONFIG_F2FS|FS_ENCRYPTION|CRYPTO_LZ4'` 结果：

- **`build/m1-73/.config`（在机）**：`CONFIG_F2FS_FS=y`（:10899）、`F2FS_STAT_FS=y`（:10900）、`F2FS_FS_XATTR=y`（:10901）、`F2FS_FS_POSIX_ACL=y`（:10902）；`F2FS_FS_SECURITY`/`CHECK_FS`/`FAULT_INJECTION`/`FS_COMPRESSION`/`UNFAIR_RWSEM` 均 not set（:10903-10908）；`F2FS_IOSTAT=y`（:10907）；`FS_ENCRYPTION`/`FS_VERITY` not set（:10913-14）；`CRYPTO_LZ4=y`（:11366）、`LZ4_COMPRESS=y`（:11566）、`ZSTD_COMPRESS=y`（:11569）。
- **`build/m3v2-7.3rc7/.config`（M3 上游树）**：`# CONFIG_F2FS_FS is not set`（:11054），其余同上。
- `patches/config-vk127-working-20261018`（在机内核那版存档）取值与 m1-73 逐项一致（:10885 起）。

结论（均【已证实】）：
1. **f2fs 内建 `=y`** ⇒ 根分区可用，不需 initramfs 带 `.ko`（避开 `PITFALLS #176` vermagic 失配坑）。
2. `XATTR+POSIX_ACL=y` ⇒ `rsync -aAX` 不丢属性（SELinux 标签除外；`F2FS_FS_SECURITY` 未设 ⇒ 无 `security.selinux`，Alpine 无 SELinux，**不阻塞**）。
3. `F2FS_FS_COMPRESSION` 未设 ⇒ **拿不到透明压缩**（f2fs 相对 ext4 的唯一额外空间收益）。开启需 `=y`+`F2FS_FS_ZSTD`（`CRYPTO_ZSTD=m`/`ZSTD_COMPRESS=y` 已具备）+ mkfs `-O …,compression`（**事后不可追加**）。
4. 依赖项 `fs/f2fs/Kconfig:3-11`（BLOCK/BUFFER_HEAD/NLS/CRC32/FS_IOMAP）已满足（`.config:11517 CRC32=y`、`:10909 FS_POSIX_ACL=y`）。
5. **M3 树没开 f2fs** ⇒ M3 要引导现存根需补 `F2FS_FS=y`（+XATTR/ACL）；未做，不阻塞在机 M1 树。

## 4. 硬件前提：UFS / 4096B 扇区 / discard / GC

- 【已证实】UFS 控制器：`sm8750.dtsi:6168-6169` `compatible = qcom,sm8750-ufshc / qcom,ufshc / jedec,ufs-2.0`，`lanes-per-direction=<2>`，PHY :6145；板级 `sm8750-lenovo-elden.dts:3046-3062`（两个节点 `status=okay` + 三路 LDO）。
- 【已证实】**主线无 sm8750 专用 drvdata**：`drivers/ufs/host/ufs-qcom.c:3013-3020` 的 of_match 只有 `qcom,ufshc`/sm8550/sm8650/sa8255p ⇒ 本机走 generic，不继承 sm8550/8650 的 `UFSHCD_QUIRK_BROKEN_LSDBS_CAP`+`no_phy_retention`（:3004-3011）。**对 f2fs 无直接影响**（quirks 管链路/省电），独立记账（§9-4）。
- 【已证实·代码】SCSI 层只在设备报告 thin-provisioning 时才开 discard/UNMAP：`drivers/scsi/sd.c:3397-3419`（`sd_discard_mode` 以 `lbpme` 开关）、`:3524-3545`（读 VPD B2 的 UNMAP/WRITE SAME 位）。
- 【未证实】本机 UFS 是否报 `lbpme`/UNMAP（设备在 fastboot，读不到 `/sys/block/sda/queue/discard_max_bytes`、`…/device/thin_provisioning`、`lsblk -D`）。【推测】原厂用 `discard` 挂 `/data` 且 UFS 为 4.0 级 ⇒ 大概率支持；「vendor 内核+设备自述」≠「主线 VPD 能读到」。若不可用：`nodiscard` 仍可用，只是回收落到 UFS 内部 GC，写放大更高。
- 【已证实·设计】`f2fs.rst`：GC 单位 = segment **2 MiB**（:48-50）；后台 GC 默认开、`gc_merge` 让后台线程接管前台 GC（:118-124）；`reserve_root` 默认 **12.5% user blocks**（:186-188）；`checkpoint=disable` ⇒ 意外关机回滚到挂载时状态且必须跑 GC（可 `EAGAIN`，:282-289）⇒ **根分区绝不使用**；`discard_unit=block` 默认（:360-365）；默认 **roll-forward recovery**（:126-129）。
- 【已证实】4096 B 逻辑扇区（§1.1）+ f2fs 默认 block 4 KiB（segment=512 blocks）⇒ 固定对齐、无 512e RMW 惩罚；ext4 默认 4096 同理 ⇒ **两者打平，不算 f2fs 优势**。

## 6. B. 收益 / 风险（外部证据）

| 编号 | 来源（**均为外部，非本机实测**） | 关键数字 | 边界 |
|---|---|---|---|
| E1 | Lee et al., *F2FS: A New File System for Flash Storage*（Samsung, USENIX FAST'15） | 移动系统随机写/fsync：优 ext4 最多 **3.1×（iozone）/2×（SQLite）**，真实负载耗时 −40%；SQLite WAL 场景**数据写量 −46%** | 2015 年手机级基准，**不得把倍数搬到 UFS 4.0** |
| E1′ | 同文高利用率实验（**风险侧**） | 利用率 80%→**97.5%**：GC 增多、性能损失 ~**30%**；填到 100% 后 4K 随机写 `F2FS normal` 掉到**低于 EXT4 的 5%**，adaptive（≈今日默认）仅与 ext4 持平 | **收益取决于留多少空闲** |
| E2 | *Advanced I/O Stack for Efficient Zone-based Mobile Flash Storage*（ACM TOS 2025） | F2FS **前台 GC 阻塞用户写**；块设备 GC 单位 = segment 2 MiB，需为 GC 预留空间 | zoned UFS 研究，阻塞路径通用 |
| E3 | Seo et al., *Is Garbage Collection Overhead Gone?*（HotStorage'23） | F2FS **保留过大 over-provisioned 空间**、**轻负载也主动 GC** | ZNS 为主，结论同向 |

映射到本项目：**收益**仅三条——① fsync 密集场景正是我们要跑的（greetd/phosh、`apk upgrade`、G2 Waydroid 的 SQLite）；② 写入量下降 ⇒ UFS 寿命/后台 GC 压力；③ 原厂已用 f2fs 量产 ⇒ 「能不能跑」不是风险，只剩「这棵树+这套参数对不对」。**风险**按下表。

| 风险 | 级 | 依据 | 缓解 |
|---|---|---|---|
| initramfs 写死 ext4 ⇒ 改分区后不能启动 | 高 | §5 阻断项 | 先通用化 `/init`，并**先在 ext4 上 `fastboot boot` 验证**（零写盘） |
| GPT 手术不可逆 / 4K 误算 | 高 | `gpt-surgery:8`、`DEVICE/README.md:122` | 用脚本（4K 内置+CRC 自校验）+ 先 `dd` 双表备份 |
| 高利用率 GC 延迟尖刺（E2），根分区终会满 | 中高 | E1′ | 使用率 **<85%**、开 `gc_merge`、必要时 `gc_urgent`/`atgc` |
| 误抄 Android 挂载参数（`checkpoint=fs` / `checkpoint=disable`、`nobarrier`） | 高（若误配） | `f2fs.rst:282-289` | 只开 `noatime`（+可用时 `discard`、`gc_merge`） |
| 空间放大 / over-provisioning | 中 | E3 | 接受默认 `reserve_root`，不在满盘跑 |
| 断电一致性无法本机验证（无 PLP）/ UFS discard 未证实 | 中 | §4 | 首版不做断电实验；上机首测 discard，不可用则 `nodiscard` |
| 回退路径变长（无 ext4→f2fs 转换器，反之亦无） | 中 | — | 新旧分区并存，旧 `linux17` 不删不格 |

## 7. C. 迁移步骤（新分区并存 → 验证 → 切换）

路线裁决：**R1 缩 `linux17`（ext4 离线缩容）→ 尾部新建 f2fs → 并存** 是唯一不需 EDL 全量备份且可回退的路线；
R2（回收 Android 分区，Phase B）前置 = EDL 包 + G1 全绿（`DEVICE/README.md:113-116`）⇒ **推迟、与 f2fs 合并成一次手术**；
R3（缩 `userdata`）已被 `DEVICE/README.md:153` + `PITFALLS #57/#58` 否决。

| 4 | **先缩 fs 后缩分区**（顺序不可反）：RAM-Alpine 内 `e2fsck -f /dev/sda17` → `resize2fs /dev/sda17 <N GiB 略小于目标>` | 是（仅 sda17 内） | `dumpe2fs -h`；回退 = 分区未缩前可长回 |
| 5 | 扩 `gpt-surgery-tb322fc.py` 增 `--shrink-part linux17 --new-part linux2 --new-gib N`：`SECTOR=4096` 不变；**不动 first/last_usable**（⇒ 备份表 LBA 不变，只重写 LBA0..5）；新分区 = `[new_linux17_last+1..last_usable]`，free slot 17 ⇒ `/dev/sda18`；两表 entries CRC 重算 | 否（先出 .bin） | 脚本自带 `self-check: both headers CRC OK` |
| 6 | `dd if=new_main0.bin of=/dev/sda bs=4096 seek=0 conv=notrunc` + 备份表同理 → `partprobe` | **是** | 重新 `list` 读回 + `/dev/sda18` 尺寸；回退 = `dd` 回原双表 |
| 7 | `mkfs.f2fs -l linux2 -O extra_attr[,compression]`（**label 必给**；压缩特性事后不可追加；flag 名先 `-h` 核对，§9-2） | **是** | `blkid` → `TYPE=f2fs LABEL=linux2` |
| 8 | RAM-Alpine：`rsync -aHAX --numeric-ids --one-file-system /mnt/old/ /mnt/new/`（`-H -A -X` 必带；`-x` 防跳 proc/sys/dev） | 是（写 linux2） | 第二遍 `rsync -aHAXn --delete` **必须零输出**；回退 = 删 linux2 重来 |
| 9 | **M2 零写盘切根**：`ROOTARGS=elden_root=LABEL=linux2 VERSION=f2fs1 bash scripts/build-boot.sh` → `fastboot boot` | **否** | §7.1 验收清单；回退 = 重启回 ext4 根 |
| 10 | M2 全绿后才持久化：`fastboot flash boot_b` + cmdline 改 `LABEL=linux2`；观察期 ≥2 周（`/sys/fs/f2fs/*/segment_info`、`dmesg\|grep -i f2fs`） | 是 | 回退 = 刷回 vk133；旧 `linux17` 保留可决回 |

### 7.1 验收清单（M2 必过）

1. `findmnt -no FSTYPE,SOURCE,OPTIONS /` → `f2fs /dev/sda18 rw,noatime[,gc_merge]`；`fsck.f2fs -f /dev/sda18` 下次 RAM 根跑 → clean。
2. xattr/ACL：`getfattr -d -m - /usr/bin/sudo`（`security.capability`）、`/home/*/.ssh` 权限 0700。
3. 功能级（必须持久变体，`PITFALLS #92/#93`）：greetd/phosh、Waydroid（G2）、相机模块加载。
4. 压力/GC：`apk upgrade`、4K 随机写后 `dmesg` 无 F2FS 报错、`dirty_segments` 不持续增长；`/sys/block/sda/queue/discard_max_bytes` 非 0 才可挂 `discard`。

### 7.2 三个必须避开的坑

1. **不用 `sgdisk`/`gdisk`** 改这张表（假设 512 B 扇区会误读；`gpt-surgery-tb322fc.py:8-9`）。
2. **不抄 Android 挂载参数**（`checkpoint=fs`/`nobarrier`/`inlinecrypt` 均 Android 语义；`checkpoint=disable` 断电回滚）。
3. **不只信 rsync 退出 0**：旧 ext4 根曾出现 `/etc` 文件被清成 0 字节（`reports/net-https-mtu-rootcause-20261018.md:184`）⇒ 搬完必须第二遍 dry-run `--delete` 对账。

## 8. D. 结论、优先级、最小可逆实验

**是否值得**：技术可行、关键项已就绪，但**换根文件系统不改变任何功能矩阵**（驱动/固件/显示/相机全不动）⇒ 对 G1 贡献 = 0，收益只在 fsync 密集负载与写放大（体验/寿命类）。且**贵的是 GPT 手术不是 f2fs**：LUN0 已满，切 60 GiB 就只有 60 GiB 新根，而「全都要」估算 105–180 GB（`DEVICE/README.md:139-150`）⇒ 小规模并存只能当实验，不能当生产根。

**优先级 P2（不阻塞 G1/G2/G3）**：
- **不做**整链迁移，也**不单做一次 GPT 手术**——把 f2fs 并入 Phase B（回收 `super_a/b` 等）的同一次手术，风险只暴露一次。
- **可做（收益独立于 f2fs）**：① `/init` fstype 通用化（mobian 换根路线直接受益）；② 主机装 `f2fs-tools` + 跑主机 loop 实验。
- **不做**：缩 `userdata` 换空间；开 `F2FS_FS_COMPRESSION`（需配套 mkfs 特性+参数矩阵，另一轮）；照搬 Android 挂载参数。

**最小可逆实验（三级）**：

| 级 | 实验 | 设备写盘 | 证明什么 | 回退 |
|---|---|---|---|---|
| **E0** | 主机：`apt install f2fs-tools` → `truncate -s 8G /tmp/f2.img` → `mkfs.f2fs -l t` → `mount -o loop,gc_merge` → fsync 压测 + 填 90% 看 GC（主机已有 `f2fs.ko`，`modinfo f2fs` 正常） | **无** | 工具链/参数/GC 行为 | 删文件 |
| **E1** | 设备：只换 initramfs（fstype 探测）+ `fastboot boot`，仍 ext4 根 | **无** | 新 `/init` 不回归；顺带消掉 §9-3 的 ramdisk 差异 | 重启回原镜像 |
| **E2** | 设备：`linux17` 缩 8–16 GiB → 新 f2fs 分区 → rsync → `fastboot boot` 以 `elden_root=LABEL=linux2` 切根 | **有** | f2fs 在真实 UFS 上可作根、能进桌面 | `dd` 回双表 + 刷回 vk133 |

> E2 是唯一有不可逆风险的一级，前置必须含：双表备份在手 + 旧根新归档 + E1 已绿。
