## §0 结论（先看）

| 问题 | 结论 | 判据等级 |
|---|---|---|
| `0x51000018`(MEM_APPEND) 本机 RM 认不认 | **认** —— stock `gh_rm_drv.ko` 自己就发它，而 stock Android 在本机可用 ⇒ RM 必认（注：我们自己的路径从未发 `18`，所以这一条是「反汇编 + 产线可用」推断，不是 kprobe 实测） | 反汇编 + 间接 |

### §2.2 iceland 16 补丁**没有引入任何新 RPC 消息 id**

`patches/0014-q90m/0001-…import…android17-6.18…patch` 里 `#define GUNYAH_RM_RPC_*` 共 **19 条，与 `build/daily/.../rsc_mgr_rpc.c` 逐字相同**（含 31/32/33/34）。

⇒ **逻辑结论**：iceland 那 16 个补丁（含 `q90s/0005 Never release memory that may still be dirty`、`q90v/0001 Refuse private anon memory…`）
**不可能**修好「RM 不认识某消息」类问题——它们改的全是**驱动侧状态处理与平台适配**，协议面一条没加。
所以「换 iceland/piano 代次」这件事，**只对「驱动状态机 bug」这一假设有判别力**，对「RM 太老」无效（这也解释了为什么 10-25 三次换代都是同一个 0xA）。

### §2.3 补丁/代次的流向差异（与 0xA 无关，但决定实验顺序）

| 差异点 | 我们的 6.6/7.3 移植栈 | android17-6.18（iceland import） |
|---|---|---|
| `SET_DEMAND_PAGING(0x33)` / `SET_ADDRESS_LAYOUT(0x34)` | `vm_start` 里**内联**调用 | 移到 `auth_vm_mgr_ops->pre_vm_init`（`gunyah_generic_pre_vm_init`） |
| `SET_BOOT_CONTEXT(0x31)` | `vm_start` 里 init 之后内联 | 移到 `pre_vm_start` 钩子 |
| 内存 parcel 生命周期 | g612：失败即回收本地 handle | piano/iceland：`-ENOTRECOVERABLE` + 保留 pin、`paged` 状态机 |

三者都**只是把同样的消息换个位置发**；10-25 的 kprobe 已证明「换位置前后 RM 都接受」，所以重排不改变 0xA。

## §3 `0xA` 定性：五条判据（J1–J5）

### J1 「RM 不认识这条消息」在协议层只有一个表达，我们从未见到
`build/gunyah-port-6.6-orig/gunyah/rsc_mgr.c:57-79` 的错误枚举里，**「未实现」= `GUNYAH_RM_ERROR_UNIMPLEMENTED = 0xFFFFFFFF`**，
`rsc_mgr.c:159` 把它映射成 `-EOPNOTSUPP`；而 `rsc_mgr.c:632-635` 对**任何**非 OK 回包都会打印
`RM rejected message <id>. Error: <%d 十进制>`。
全仓 `*.md|*.txt|*.log` 里 `RM rejected message` 只出现过 **3 种**组合（`grep -rnoE` 现查，共 15 行）：

```
10×  RM rejected message 5600000b. Error: 10    → 0xA MEM_INVALID（VM_INIT）
 3×  RM rejected message 56000009. Error: 3     → DENIED（SHARE+pVM 的 VM_CONFIGURE，RM 主动拒绝该组合）
 2×  RM rejected message 56000002. Error: 20    → 0x14（失败清理路径 dealloc vmid 的次生错误）
```

⇒ 若 RM 不认 0x32/0x33/0x34，我们会看到 `Error: -1` 且驱动在 `VM_CONFIGURE` 之后就 `goto err`，
**根本走不到 `VM_INIT`**。事实相反：走到了最后一步。**「RM 太老」否证。**

### J2 kprobe 抓到 RM 逐条接受（决定性证据）
`reports/gunyah-612-samebuild-20261025.md` §4（两臂 + 两个 DTBOFF 变体，序列逐字相同）：

```
alloc_vmid(01) → MEM_LEND(12) → VM_CONFIG_IMAGE(09) → SET_DEMAND_PAGING(33) → SET_ADDRESS_LAYOUT(34) → VM_INIT(0b ← 0xA)
pVM 臂另加：    SET_FIRMWARE_MEM(32) 也返回 OK（无 "Failed to configure pVM firmware"）
```

`gunyah_rm_call()` 对每次调用都检查 `rm_error != OK` 并返回错误、调用方 `goto err`
（`build/gunyah-port-6.6-orig/gunyah/vm_mgr.c:725-780`）⇒ **序列能走到 0b，就等于 12/09/33/34/32 全部返回 OK**。
这就是前序报告缺的那一环：**不再需要「vendor `.ko` 不用它」这种间接推理**。

> 序列按 `reports/gunyah-612-samebuild-20261025.md` 原样引用：SHARE 臂也出现 `12`、`13` 未出现 ⇒ 那条 userspace ioctl 实际走的是 lend helper（不影响本判据）。

### J3 我们的 hyp API 与 piano/iceland 同代（51/v1）
本机 dmesg 有 `gunyah: Running under Gunyah hypervisor 51/v1`（`reports/gunyah-mainline-rm-up-20261024.md`、`TASKS/sessions/2026-11-03-…`），
而 iceland 的 commit message 实测也是 **51/v1**（`reports/gunyah-b15-iceland-rmdrv-20261113.md` §1）。
⇒ 「RM 代次比 piano/iceland 老一大截」这个说法缺少任何版本证据支撑。

### J4 piano 的三组「状态机 bug 修复」本次路径**一个都没走到**
| piano/iceland 修复 | 对应代码路径在本次失败里是否被触发 | 判据 |
|---|---|---|
| `MEM_APPEND` 失败后本地 handle 与 RM 分叉（piano `-ENOTRECOVERABLE`、iceland q90s/0005） | **否** —— kprobe 序列里**没有 `18`**，`MEM_APPEND` 一次都没发 | 612-samebuild §4 序列 |
| `paged` 状态机 / `gunyah_vm_parcel_to_paged_abort()` | **否** —— abort 只在错误路径；`33` 返回 OK，进入 VM_INIT 前无任何错误 | dmesg 无 "Failed to set up gmem demand paging" |
| `VM_START` 前不得 unpin（口述所有权约定） | **本地语义** —— 提前 unpin 影响宿主页 pin 计数，**不改变 RM 侧 parcel 表** | 源码：pin/unpin 全在 `vm_mgr_mem.c` 本地 |

⇒ **「驱动状态机 bug 导致 0xA」这条假设，在已识别的三个 bug 上都不成立**（不能推广成「驱动一定无 bug」，见 §6）。

### J5 剩余解释（推断级）：RM 要的是「DONATE 型」所有权，主线给的是「LEND 型」
| 证据 | 内容 | 指针 |
|---|---|---|
| vendor 走 DONATE | `gh_rm_mem_donate` → 消息 `0x51000010`；`gunyah_loader.ko` 未定义符号引用它 | 612-samebuild §5 |
| vendor 还叠一层 loader hypercall | `gunyah_loader.ko` 里 `hvc #0x6045/4e/4f/50/52/53/63/65`（与 `RmVmDxe` 的 `MemShare`/`FwSetVmFirmware` 同族） | 同上 |
| vendor 的 VM 流程用 0x09+0x0a，不用 31-34 | stock `.ko` 反汇编（§2.1） | 本文件 |
| RM 的 memparcel 校验在 `VM_INIT`、且请求体只有 vmid | `rsc_mgr_rpc.c:464` `vm_init(rm,vmid)`；DTB/内存布局 7 个变体全不敏感 | gunyah-pvm-attempt §DTB 矩阵 |
| RM 对「内存模型 + auth 组合」确有策略性拒绝 | `SHARE + pVM` 在 `VM_CONFIGURE` 就 `DENIED(0x3)` | 同上变体 d |

⇒ **RM 在 `VM_INIT` 时按自己那张 parcel 表做整体校验，而主线 `LEND` 语义下它在表里看到的东西不被接受**：
「协议同代，但所有权模型不同」。这是**策略/语义不符**，不是版本太老，也不是已知驱动 bug。

`/tmp/msgid_scan.py`（本轮新写，同一份可复跑）：

```python
import re,sys,collections
fn=None; last={}; hits=collections.defaultdict(list)
hdr=re.compile(r'^([0-9a-f]+) <([^>]+)>:')
mz=re.compile(r'^\s*[0-9a-f]+:\s+[0-9a-f]+\s+mov(?:z)?\s+w(\d+),\s+#0x([0-9a-f]+)(?!, lsl)')
mk=re.compile(r'^\s*[0-9a-f]+:\s+[0-9a-f]+\s+movk\s+w(\d+),\s+#0x([0-9a-f]+),\s*lsl\s+#16')
for line in open(sys.argv[1],errors='replace'):
    h=hdr.match(line)
    if h: fn=h.group(2); last={}; continue
    m=mz.match(line)
    if m: last[m.group(1)]=int(m.group(2),16); continue
    m=mk.match(line)
    if m:
        r=m.group(1); hi=int(m.group(2),16); lo=last.get(r)
        if lo is not None and hi in (0x5100,0x5600,0x4700,0x5601):
            hits[(hi<<16)|lo].append(fn)
for v in sorted(hits):
    print("0x%08x\tn=%d\t%s"%(v,len(hits[v]),", ".join(sorted(set(hits[v])))))
```
