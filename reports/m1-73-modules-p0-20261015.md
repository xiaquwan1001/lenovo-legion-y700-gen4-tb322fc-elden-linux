### 1.3 ★ 本轮踩到并解决的两个构建陷阱（都可复现）

#### 陷阱 1：`make` 不带 `ARCH=arm64` 会按**主机 x86** 求值 Kconfig，**静默删掉整个 QCOM 栈**

- **现象**：在 `build/m1-upstream/clean-tree-73` 跑裸 `make -n modules`（只是想 dry-run），
  触发 `syncconfig`，把 `.config` 从 **4954 行压到 2881 行**：
  `CONFIG_ARCH_QCOM`、`CONFIG_DRM_MSM` **整行消失**，`.config` 与设备 `diff` 从 0 跳到 5265 行。
- **这正是 `PITFALLS #162` 的死内核形态**（vk81/82/83 作废的同型事故），也与 `PITFALLS #247`
  「`olddefconfig` 必须带 `ARCH=<目标架构>`」同源。
- **后果面**：`include/config/auto.conf` 与 `include/generated/autoconf.h` 一并被污染；
  `make syncconfig` **再跑一次还会继续错**（它从被污染的 auto.conf 反推）。
- **修复**：`cp .config.old .config`（`.config.old` 恰好是上一次好档、与设备 config diff=0）
  + **一律带 `ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-`** 重跑 `syncconfig`。
- **判据（编前必查）**：`grep -cE '^CONFIG_ARCH_QCOM=y' .config` = 1 **且** `diff <(sort .config) <(zcat /proc/config.gz)` = 0。

#### 陷阱 2：vermagic 多一个 **`+`** ⇒ 模块能被 `depmod` 索引、但**上机 insmod 必被拒**

- **现象**：模块 vermagic = `7.3.0-rc7-debug-ged6f232d10e3+`，而设备 `uname -r` = `7.3.0-rc7-debug-ged6f232d10e3`（无 `+`）。
- **机制**：`scripts/setlocalversion` 在 `CONFIG_LOCALVERSION_AUTO=n` 时走
  `scm_version --short` 分支 —— **若环境变量 `LOCALVERSION` 未设置**，且仓库不在带注解 tag 的干净态，
  **就追加 `+`**。本树是 git **worktree**，`git describe --always` 给出 `95c899a885`，故命中。
- **修复**：构建时**显式导出空 `LOCALVERSION=`**：
  ```sh
  export LOCALVERSION=
  make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) modules
  ```
  验证：`LOCALVERSION= make -s ARCH=arm64 ... kernelrelease` ⇒ `7.3.0-rc7-debug-ged6f232d10e3`（无 `+`）。
- **教训**：`depmod` 成功 **不代表**模块能加载；`depmod` 只看 `modules.dep` 索引，**不校验 vermagic**。
  必须 `modinfo <ko> | grep vermagic` 与 `uname -r` **逐字比对**才算过门。

### 2.2 未达成的：出流失败，根因已定位到**具体代码行**

`v4l2-ctl -d /dev/video16 --stream-mmap=3 --stream-count=3` ⇒ `VIDIOC_STREAMON returned -1 (Invalid argument)`。

dmesg：

```
qcom-camss ad27000.isp: Pixel clock is too high for VFE
qcom-camss ad27000.isp: Failed to power up pipeline: -22
```

出处 = `drivers/media/platform/qcom/camss/camss-vfe.c:1034-1037`（`vfe_set_clock_rates()`）：

```c
for (j = 0; j < clock->nfreqs; j++)
        if (min_rate < clock->freq[j])
                break;
if (j == clock->nfreqs) {
        dev_err(dev, "Pixel clock is too high for VFE");
        return -EINVAL;
}
```

### 2.3 ★ 关键定量事实：`min_rate` **远低于**所有表项上限 ⇒ 不是真的"时钟太高"

设备实读传感器控制：`V4L2_CID_PIXEL_RATE = 558933333`（= 672 MHz link × 4 lane × 2 / 10 bit）。

| 量 | 值 |
|---|---|
| `pixel_rate` | 558 933 333 |
| `bpp`（SGRBG10_1X10） | 10 |
| `tmp = pixel_rate × bpp / 64` | **87.3 MHz** |
| `min_rate`（含 margin） | ~100 MHz |
| SM8750 `vfe0` 表上限 | **833 MHz** |
| SM8750 `camnoc_rt_axi` 表上限 | **480 MHz** |

**87–100 MHz 对 833/480 MHz 的表，不可能"太高"。** ⇒ 说明送进比较的
`pixel_clock[j]` 里有**非传感器真实值的巨大数**，或者根本不是我们以为的那个 clock 在报错。

### 2.4 已锁定的代码级嫌疑（下一个可执行动作，零设备成本）

`camss-vfe.c:994` 的填充循环存在**未初始化读**：

```c
u64 pixel_clock[VFE_LINE_NUM_MAX];
for (i = VFE_LINE_RDI0; i < vfe->res->line_num; i++)   /* ← 只填到 line_num-1 */
        ...
```

而 `vfe_res_8750[]` 的 `line_num` 分布是：

| VFE | 类型 | `line_num` | 覆盖的 line 索引 |
|---|---|---|---|
| VFE0/VFE1/VFE2 | TFE Full | **3** | RDI0, RDI1, RDI2 |
| VFE3/VFE4 | TFE Lite | **4** | RDI0..RDI3 |

⇒ **在 VFE0/1/2 上用 RDI3 时，`pixel_clock[3]` 是未初始化栈值**（`VFE_LINE_NUM_MAX`=4），
`min_rate` 取 max ⇒ 垃圾大数 ⇒ 必然命中 `j == nfreqs` ⇒ `-EINVAL`。
这与"`min_rate` 实测应仅 87–100 MHz"的定量事实**完全自洽**。

> ⚠️ 本发实际走的是 **VFE4**（`line_num=4`，RDI3 在覆盖范围内），所以上述未初始化读
> **不足以单独解释本发**。两种可能：(a) 另有 clock 表项/`nfreqs` 取值问题；
> (b) 本发路径与假设的 VFE 不一致。**下一步必须先做一次的定向判别**（见 §3），
> 不得直接把 §2.4 当结论 —— 按 `.pi/AGENT-OPS.md` §3「一次正反判断」，此假设已登记、待证。

## 2.5 ★ S1 定向判别已完成（同上会话，单变量 = VFE 实例）

**拓扑事实（本轮实测澄清）**：CSID*N* 与 VFE*N* 是**固定 1:1 配对**（`msm_csid0` 只连 `msm_vfe0_rdi{0,1,2}`、
`msm_csid4` 只连 `msm_vfe4_rdi{0,1,2,3}`）；而 **csiphy3（后摄所在）可以路由到任意 CSID**。

| 通路 | VFE | `line_num` | RDI | 结果 | `Pixel clock is too high` |
|---|---|---|---|---|---|
| `s5kjns→csiphy3→csid4→vfe4_rdi3→/dev/video16` | VFE4 (Lite) | 4 | **RDI3** | `STREAMON → EINVAL` | **✅ 报错**（dmesg 2 次 / 4556、4581 s） |
| `s5kjns→csiphy3→csid0→vfe0_rdi0→/dev/video0` | VFE0 (Full) | 3 | **RDI0** | `STREAMON → EPIPE` | **❌ 完全不报**（计数仍为 2，无新增） |

**判别结论**：
1. `Pixel clock is too high for VFE` **只在 VFE4+RDI3 路径出现**，换到 VFE0+RDI0 后**彻底消失** ——
   这是**单变量**（仅 VFE/RDI 实例不同），故 §2.4 的 `line_num` 假设方向**被支持**：
   报错与 **`line_num` 未覆盖到 RDI3** 相关。
2. 但 **EPIPE 是新的、不同的失败**（VFE0 路径同样不出流）⇒ 出流障碍**不止一处**：
   `line_num` 覆盖问题只是**第一道**；解开后还有第二道（EPIPE，无任何 dmesg 打印，
   疑为 CSID/CSIPHY 侧配置或 `vfe0` 的 HW 就绪问题）。
3. ⇒ **不要**把「改 `line_num` 就能出流」当作结论；它最多解掉 EINVAL 这一层。
