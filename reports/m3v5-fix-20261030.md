## 2. A–J 逐项：改了什么（file:line，行号为改后 `build/m3v5-fix` 内容）+ 为什么

### A `dwc->lock` 内不得调 `dwc3_set_mode` —— `drivers/usb/dwc3/drd.c:539-597`

- `:556` `mutex_lock(&mux->lock)` → `:557-568` `spin_lock_irqsave(&dwc->lock)` 内**只**更新
  `port->seq/role`、`dwc3_role_mux_pick()`、`mux->desired_port`、取 `selected_role`，然后
  `:569 spin_unlock_irqrestore(&dwc->lock, …)`。
- `:584-585` 在**解锁后**（仍持 `mux->lock`）才 `dwc3_pre_set_role()` + `dwc3_set_mode()`。
- 为什么：`dwc3_set_mode()`（`core.c:335-347`，`:342` 取 `dwc->lock`）自己 `spin_lock_irqsave(&dwc->lock)`；防御式实现是**非递归**
  自旋锁（RT 下 rtmutex 同样不自递归）⇒ 第一次角色切换必硬死锁（IRQ 已关）。
  v3 review 要求的「`desired_port` 与它蕴含的模式请求同临界区」由 **`mux->lock`** 承担：第二个 `set()`
  在 `mutex_lock()` 阻塞，配对性不依赖 `dwc->lock` 跨调用。

### B 补 `dwc3_pre_set_role()` —— `drd.c:584`

- 与单连接器路径同序（对照 `drd.c:443`、`drd.c:472`）：**先 glue 通知，后 `dwc3_set_mode()`**，参数用**生效角色**
  `selected_role`（不是本端口请求的 `role`）。必须在 `dwc->lock` **外**：`dwc3-qcom.c` 的
  `dwc3_qcom_set_role_notifier()` 会 `pm_runtime_resume_and_get()`（可睡眠）。

### C `dwc3_mux_role_get()` 直接返回 `port->role` —— `drd.c:598-618`

- 去掉 `mux->active_port == port->state` 判定（`:612-615` 只 `role = port->role`）。
- 为什么：隐藏非活动端的待处理请求 ⇒ 连接器驱动 `get_role()` 读到 `NONE` ⇒ **不会**发 `set_role(NONE)`
  ⇒ 该端口 `role/seq` 永留 ⇒ `dwc3_role_mux_pick()`（`drd.c:511-527`）继续把数据路径选给**已拔线**端口，
  且 seq 压制后到的端口（饥饿）。

### D binding `then` 块要求控制器级 `usb-role-switch` —— `snps,dwc3-common.yaml:61-68`

- `required: [dr_mode, ports, usb-role-switch]`（`:68`），并加注释说明三处 gate
  （`core.c:94-98` 强改 peripheral、`core.c:2076-2077` `dwc3_get_extcon()` 属性判定、`drd.c:801-803` 不调 `dwc3_role_mux_init()`）。
- 为什么：过 `dtbs_check` 的 DT 集合 ⊋ 驱动真正走 mux 的 DT 集合；driver 侧**不动**（该属性本来就是
  `dwc3_drd_init()` 的唯一开关），把「控制器级属性」升级为 binding 硬要求。
- 未用 `usb-role-switch: true/const: true`：`const: true` 在 tree 内布尔 flag 上**无先例**，`required` 已足够。

### E 同角色换端口时清 SUSPHY —— `drivers/usb/dwc3/core.c:198-200`、`:280-281`

- `:171` 新增 `bool port_switch`；`:198` `port_switch = mux && mux_port != mux->active_port;`
  → `:200` early-out 条件改为 `desired_dr_role == current_dr_role && !port_switch`（语义等价，但把
  「同角色换端口」显式命名）。
- 在 GPIO 翻转（`:256-269`）**之后**、`dwc3_set_prtcap()`（`:271-286`）**之前**：`:280-281 if (port_switch) dwc3_enable_susphy(dwc, false);`
- 为什么：`dwc3_set_prtcap()`（`core.c:139-160`）只在 `:152-155` 的 `DWC3_GCTL_PRTCAP(reg) != mode` 时清
  `GUSB3PIPECTL.SUSPENDENABLE`/`GUSB2PHYCFG.SUSPHY`；同角色换端口 PRTCAP 不变 ⇒ 旧实例留在寄存器里的
  SUSPHY 设置被新实例继承，违背该函数自身注释（`:146-150`「切换期间须清零，core 初始化后再置」）。
  `write-then-clear` 语义不变（不把 GPIO 翻回去）。
- **状态**：机制已改；**是否真导致 PHY 时钟同步/`DCTL.CSFTRST` 超时仍未上机证实**。

### F fwnode 泄漏（`dwc->role_mux` 赋值上移）—— `drd.c:668-673`

- `dwc->role_mux = mux;` 移到 `mutex_init()` 之后、`fwnode_graph_for_each_endpoint()` **之前**。
- 为什么：`dwc3_role_mux_exit()`（`drd.c:620-637`）在 `dwc->role_mux == NULL` 时直接 return；
  原来 `dwc->role_mux` 在「拿完所有 fwnode 并校验」之后才赋值 ⇒ 两条 `err_put_ep`（`drd.c:680-687`）
  与缺端口校验（`drd.c:694-699`）都把已 `fwnode_handle_get()`（`drd.c:689`）的引用全泄漏。
  `err:` 里的 `dwc->role_mux = NULL` 保留（幂等）。

### G 注册与初始 `set_mode` 用 `mux->lock` 包住 + 错误路径顺序 —— `drd.c:702-742`

- `:702-708` 说明 + `mutex_lock(&mux->lock)`；`:709-725` 两路 `usb_role_switch_register()`；
  `:731` 初始 `dwc3_set_mode(dwc, mode)`；`:733 mutex_unlock()`。
  注册失败分支 `:719-723` 先 `mutex_unlock()` 再 `goto err`。
- `:738-741` 错误路径顺序改为 `cancel_work_sync(&dwc->drd_work)` → `dwc3_role_mux_exit(dwc)` → `dwc->role_mux = NULL`
  （原来「先清指针再取消 work」）。
- 为什么：`usb_role_switch_register()` 一返回，`class_find_device_by_fwnode()` 就能命中并并发 `set()`；
  该调用会改 `port->role`，随后被初始 `set_mode()` 静默改回默认角色 ⇒ 状态机分叉。`mux->lock` 关闭该窗口。
- **③（降级，写明限制）**：若 `__dwc3_set_mode()` 已建 host/gadget 而 probe 之后失败，`core.c` 的
  `err_exit_debugfs` 路径（`core.c:2451` 附近）仍不调用 `dwc3_core_exit_mode()`。本 lane **不改**：
  修它要动 `dwc3_probe()` 全量错误路径且无法在主机侧证明无回归；且 mux 路径的 `err:` 只可能发生在
  `dwc3_set_mode()` 之前（首枚 mode 请求尚未排队），窗口为零。**结论：v5 cover 里写明该限制**。

### H 去掉粘性 `mux->error` —— `core.h:1015-1030`、`core.c:256-269`、`drd.c:591-597`

- `core.h`：`struct dwc3_role_mux` 删 `int error;`（原 `:1029`），`struct dwc3_role_port` 加
  `unsigned int errors;`（`core.h:1021`，per-port 计数，doc 注明仅诊断）。
- `core.c:256-269`：GPIO 失败只 `dev_err_ratelimited()`（`:259-261`）+ 该端口 `errors++`（`:265`，在
  `dwc->lock` 内与 `active_port` 更新同一临界区）。
- `drd.c:591-597`：`dwc3_mux_role_set()` **恒 return 0**，不再读清共享错误字段。
- 为什么：单字段被两路共享 ⇒ port0 的 GPIO 失败会报给下一个调用 `set()` 的 port1；且该调用**已提交**自己的
  请求，`usb_role_switch_set_role()`（`class.c:83-88`）会据此认为本次切换失败且**不更新 `sw->role`**。

### I `-EPROBE_DEFER` 不被吞 —— `drivers/usb/roles/class.c:184-196`

- `if (!IS_ERR_OR_NULL(sw))` → `if (sw)`（`ERR_PTR` 为真 ⇒ 原样上抛），`fwnode_handle_put(ep)` 仍在返回前。
- 为什么：`usb_role_switch_match()`（`class.c:126-137`）对「属性在、设备未注册」返回 `ERR_PTR(-EPROBE_DEFER)`；
  旧判定把它当「没找到」，函数末尾 `return NULL`（`class.c:197`）⇒ 上层退化成 connection 匹配 ⇒
  消费者把「尚未注册」误判成「没有 role-switch」。

### J binding endpoint 校验面 + `mux-state` 互斥（`oneOf`）—— `snps,dwc3-common.yaml:40-46`、`:86-106`、`:107-116`

- **J-1（`:40-46`）**：`hs-port.patternProperties` 由 `'^endpoint@[01]$'` 改为
  `'^endpoint(@[0-9a-f]+)?$'`（与 `graph.yaml#/properties/port` 同名模式）。
  为什么：原来只有 `endpoint@0/@1` 套 `hs-endpoint`（含 `unevaluatedProperties: false`），
  **无编号 `endpoint` 与 `endpoint@2+` 逃出**严格校验（1/3-Med#1）。改模式比「再加一条
  `endpoint-base` 通配 pattern」更干净：两条 pattern 同时命中 `endpoint@0` 时，
  后者的 `unevaluatedProperties: false` 会把 `usb-role-switch/mux-state` 判成多余（这是**不能**用
  「通配 + 具体」双 pattern 的原因；也未采用正则负向前瞻，避免引入 tree 内无先例的写法）。
  `else` 分支（`:107-116`）同步改成同一模式，`port-select-gpios` 缺席时这些属性一律禁止。
- **J-2（`:86-106`）**：删掉两个 `if … const: 0 / then … const: 1` 的 `allOf` 块，改成一个 `oneOf`：
  两个分支各带 `required: [endpoint@0, endpoint@1]` + `(0,1)` / `(1,0)` 两个 `const`。
  为什么：旧写法只拒绝「双双为 0」，**两个端点同为 `<1>` 可通过校验**（`reports/m3-v5-recovery-20261030.md` §3.2 实测）。
  `oneOf` 同时拒绝 (0,0)、(1,1) 并强制互补；实测见本报告 §5。

## 3. 前置缺陷（必须先解，属**复刻基点自相矛盾**，不在补丁里）

复刻完成后先跑一次门禁②，**rc=2**：

```
drivers/usb/dwc3/dwc3-qcom.c:594:27: error: initialization of ‘void (*)(struct dwc3 *, enum usb_role)’ from
    incompatible pointer type ‘int (*)(struct dwc3 *, enum usb_role)’ [-Wincompatible-pointer-types]
drivers/usb/dwc3/dwc3-imx8mp.c:179:27: error: … （同上）
drivers/usb/dwc3/dwc3-imx.c:183:25: error: … （同上）
```

根因：`build/m3v5-daily` 的六个「v4 文件」来自 pristine 基线（`core.h` 里 `pre_set_role` 是 **void** 通知），
而同一棵树里 `dwc3-imx.c`/`dwc3-imx8mp.c`/`dwc3-qcom.c` 仍是 **elden payload v2**（`git 0f1fb1c9c1`）里
**已被 v3/v4 否决的 int-返回**签名 ⇒ 三处函数指针类型不兼容（gcc 15 默认 `-Werror=`）。
即：**daily 基点本身编不过**，这不是 A–J 引入的，也不是 v4 series 的一部分。

本轮最小适配（**不进补丁**，只在 fix 树内，供门禁跑通）：
`dwc3-imx.c:165`、`dwc3-imx8mp.c:161` 恢复 pristine 的 `static void …pre_set_role(...)`（去掉 `return 0;`）；
`dwc3-qcom.c:558-571` 改回 void，并把 `pm_runtime_resume_and_get()` 失败降级为
`dev_dbg(qcom->dev, "Failed to resume device\n")`（通知式回调无法上报错误），其余下游逻辑（vbus override）保持不变。
三文件**不纳入两枚补丁**：上游 pristine 本来就是 void，无需改动。
⇒ 复刻该树的正确做法应是「v4 六文件 + 三个 glue 文件的签名对齐」，本轮已在报告与本树内落实，
但 `git status` 里这 3 项仍是未提交改动（**故意**：它们是基点适配，不是待投递内容）。
