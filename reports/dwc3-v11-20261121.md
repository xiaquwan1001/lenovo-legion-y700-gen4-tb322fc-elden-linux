### 2.1 [Medium] 3/3：`dwc3_drd_exit()` 里 deselect 过早 — **接受**

原文（`logs/sashiko-27394096-comment-15007993.txt:42-51`，逐字）：

```
[Severity: Medium]
Should dwc3_role_mux_deselect() be called after the
switch (dwc->current_dr_role) block tears down the active host or gadget
instance?

When the mux controller has an idle state other than MUX_IDLE_AS_IS and
the active connector is not the idle port, mux_control_deselect() switches
the High Speed data lines back to the idle state while the host or gadget
instance is still running.  In __dwc3_set_mode(), dwc3_host_exit() or
dwc3_gadget_exit() runs before mux_control_deselect() so the active role
```

（原文在同一 comment 的上半段还给出被评的 hunk：`dwc3_role_mux_deselect()` 紧跟在
`cancel_work_sync(&dwc->drd_work);` 之后、`switch (dwc->current_dr_role)` 之前。）

**判定：接受（真问题，可静态核对）。**

**理由**：

- 顺序事实核对：`__dwc3_set_mode()` 里 deselect/select 段位于「角色 teardown 之后」——
  v10-0003 patch 的 `@@ -233,8 +249,60 @@` 段注释原文即
  「The previous host or gadget instance has been torn down above, so the shared High Speed data path can now be moved…」
  （`patches/upstream/dwc3-v10-20261120/v10-0003-…patch:106-118`）。
- `mux_control_deselect()` 的语义在主线里是「释放 mux 并恢复 idle 状态」
  （`drivers/mux/core.c`；`MUX_IDLE_AS_IS` 才表示不动）。若 idle 口 ≠ 当前口，
  deselect 会把 HS 差分线切到 idle 口，而 `usb_role_switch_unregister()`/`cancel_work_sync()` 之后
  `dwc3_host_exit()`/`dwc3_gadget_exit()` **还没跑** ⇒ 实例正在被拆但线已被切走。
- 这不是「理论担忧」：dwc3 unbound 前 host/gadget 仍在枚举/传输是常态（unbind 走的是 `dwc3_remove()`），
  中间窗口里有 IRQ/URB 活动。

**处置**：`dwc3_role_mux_deselect(dwc)` 与注释整体挪到 `switch (dwc->current_dr_role)` **之后**、
`free_irq(dwc->otg_irq)` 之前。见 `MANIFEST.md` §2.2（含 diff 与行号），落树后 `drd.c:944-954`。

**验证**：静态（顺序与 `__dwc3_set_mode()` 一致）+ G3 编译（`drd.o`、`dwc3_role_mux_exit.isra.0` 存在）。
**运行期次序仍未验**（需 kprobe `mux_control_deselect` vs `dwc3_host_exit` 的时序）—— 列在 §5 待放行/上机项。

### 2.2 [Medium] 1/3：`port@0` 无条件 `$ref: '#/$defs/hs-port'` — **部分接受（结构性风险真；引用的失败模式不成立）**

原文（`logs/sashiko-27394097-comment-15007992.txt:135-153`，逐字）：

```
[Severity: Medium]
Does applying $ref: '#/$defs/hs-port' unconditionally to port@0 cause a
dtbs_check regression for single-connector DWC3 nodes without mux-controls?

In JSON Schema, unevaluatedProperties: false inside hs-port only sees
properties evaluated within hs-port itself, not properties evaluated by
the allOf else branch ($ref: /schemas/graph.yaml#/properties/port).
Because /schemas/graph.yaml#/$defs/port-base omits endpoint and hs-port
only declares endpoint@0 and endpoint@1 (both requiring usb-role-switch
and mux-state), non-mux DWC3 nodes using port@0/endpoint (such as
arch/arm64/boot/dts/qcom/sm8250.dtsi) fail validation with endpoint
rejected as unevaluated, while non-mux nodes using port@0/endpoint@0 fail
because hs-port requires usb-role-switch and mux-state that
/schemas/graph.yaml#/properties/port rejects.

Should $ref: '#/$defs/hs-port' be applied to port@0 only in the
mux-controls then branch of allOf (as described in the else branch
comment), leaving top-level port@0 with only its description?
```

**判定：部分接受。**

- **接受的部分（结论与修法）**：把双连接器 schema 无条件套到 `port@0` 上是错的；应只在
  `mux-controls` 分支要求双 endpoint。这条**已实测复现**（见下「验证」）。
- **不接受的部分（论据/例子）**：两条具体断言不成立。
  1. 「`graph.yaml#/$defs/port-base` omits endpoint」——**假**。本机 dtschema 2026.9 的
     `port-base` 明确声明了 `endpoint: type: object`
     （`/home/xuqianhui/.local/lib/python3.14/site-packages/dtschema/schemas/graph.yaml:63-64`）。
     所以「非 mux 的 `port@0/endpoint` 会因 unevaluated 被拒」不成立。
  2. 「`qcom/sm8250.dtsi` 的节点会失败」——**假**。该文件的 dwc3 用的是**不带 reg 的**
     `port@0/endpoint`（`build/elden-tree/arch/arm64/boot/dts/qcom/sm8250.dtsi:4237-4243`），
     实测 `sm8250-mtp.dtb` 在 v10 schema 下 **0 诊断**（v10 门禁 G5 4/4、0；
     本轮 baseline/patched 对照同）。
  3. 真正会挂的是**带编号**的形状：单连接器节点写 `port@0/endpoint@0`（`reg` 有、无 role 属性）。
     这是本轮实测复现出来的那一半（`hs-port` 里 `endpoint@0` 带 `required: [reg, usb-role-switch, mux-state]`）。

**处置**：v11 顶层 `port@0` 只留 `$ref: graph.yaml#/$defs/port-base` + `unevaluatedProperties: false` +
`patternProperties '^endpoint@[01]$'`（端点 schema 里只 `required: [reg]`，
`usb-role-switch`/`mux-state` 互为 `dependentRequired`）；
双 endpoint、`#address-cells`/`#size-cells`、两个 role 属性**只**在 allOf 的 `mux-controls` 分支 `required`。
见 `MANIFEST.md` §2.1 表（新文件 L34、L454 起）。

**验证（实测，可复跑）**：

| 对象 | v10-as-sent schema | v11 schema |
|---|---|---|
| `gates/pos-nonmux-endpoint.dtb`（单口，`port@0/endpoint` 不带 reg） | **0 诊断** | **0 诊断** |
| `gates/pos-nonmux-endpoint0.dtb`（单口，`port@0/endpoint@0`，无 role 属性） | **3 条**（`'usb-role-switch' is a required property`、`'mux-state' is a required property`、级联 unevaluated） | **0 诊断** |

日志：`patches/upstream/dwc3-v11-20261121/logs/G6-v10sent-control.log` 与 `…/G6-dt-validate-samples.log`；
命令见 `GATES-v11.md` §2 G6。

### 2.4 [Low] 1/3：`dr_mode` 在 `required` 里覆盖了 `usb-drd.yaml` 默认 — **接受**

原文（`logs/sashiko-27394097-comment-15007992.txt:96-106`，逐字）：

```
[Severity: Low]
Does listing dr_mode in required reject DWC3 nodes with mux-controls that
omit dr_mode to rely on the default "otg" mode from usb-drd.yaml?

In usb-drd.yaml (and dwc3_get_dr_mode() when usb-role-switch is present),
dr_mode already defaults to "otg" when omitted.  Keeping dr_mode: const:
otg under properties while dropping dr_mode from required would still
reject "host" or "peripheral" without forcing board DTs to specify dr_mode
explicitly.
```

**判定：接受（真问题，已实测复现）。**

**理由**：`usb-drd.yaml` 里 `dr_mode` 有 `default: otg`；`dwc3_get_dr_mode()`
（`build/elden-tree/drivers/usb/dwc3/core.c`）在 `usb-role-switch` 存在时把「未指定」当 OTG。
把 `dr_mode` 列进 `required` 会让「省略 `dr_mode` + 有 `mux-controls`」这种合法树被 schema 拒；
而 `properties.dr_mode: const: otg` 本身已经能挡住 `host`/`peripheral`，`required` 是多余的。

**处置**：`required: [dr_mode, ports, usb-role-switch]` → `required: [ports, usb-role-switch]`
（v11-0001 patch 第 73 行；新文件 L34），`const: otg` 保留。见 `MANIFEST.md` §2.1。

**验证（实测）**：

| 对象 | v10-as-sent schema | v11 schema |
|---|---|---|
| `gates/pos-no-dr-mode.dtb`（mux 双口，省略 `dr_mode`） | **2 条**（`'dr_mode' is a required property` + 级联） | **0 诊断** |
| `gates/neg-dr-mode-host.dtb`（`mux-controls` + `dr_mode = "host"`） | 被拒 | **被拒**（`dr_mode:0: 'otg' was expected`）⇒ 收紧没有被放松 |
