# Q24 N2'：**两臂共 7/7 存活** —— `sync_state` 时机构型**不是**致死变量（2026-10-15 晚实测）

> 动机：`reports/q24-n1b-boottime-pairing-20261015.md` §3.3 提出 N2' ——
> 在「**开机态配对**（provider 已同步、按真实票投票）」构型下做一次**真实熄屏**，
> 以判定 `sync_state` 线是否与 Q24 致死有关。
> 本轮**同会话内做了两臂**（开机态配对 vs 运行期配对）+ 多次真实熄屏。
> 设备：U2 `HA2EXB0E`，`boot_b` = `m1-baseline-f3`（`7.3.0-rc7-debug-ged6f232d10e3`）。

---

## 0. 一句话

**两臂都存活，共 7/7**（开机态配对 3 发 + 运行期配对 4 发，每发都是**真实 DPMS off**、
配对在位、且判据用 `boot_id` 而非"uptime 看起来还在"）。
⇒ **`sync_state` 的"已同步 vs 夹到最高档"时机构型，不能预测 Q24 致死**。
这条线**作为致死解释已被关闭**（它仍是真实的**上游机制**，见 `#287`，只是与 Q24 致死无关）。

> ⚠️ **重要限定**：本轮**没有**在任何一臂复现死亡。这里报告的是**"该构型不足以致死"**，
> **不是**"Q24 已解"、也**不是**"Q24 不存在"。致死条件里仍有**未被本轮复现**的成分。

## 1. 实验设计（两臂，单变量 = 配对时机）

| | **A 臂：开机态配对** | **B 臂：运行期配对** |
|---|---|---|
| 怎么建 | `/etc/modules-load.d/camera.conf` = `camcc-sm8750` + `cambistmclkcc-sm8750`，**重启** | 先 `modprobe -r` 清空，再在运行期 `modprobe camcc-sm8750` + `cambistmclkcc-sm8750` |
| `rpmhpd pending` 消息 | **0**（provider 直接进已同步态，= N1b 构型） | **0**（但 provider 早在开机时已求值过，= N1 构型） |
| 配对在位 | ✅ 2/2（`lsmod`） | ✅ 2/2 |
| 熄屏手法 | `gdbus … ScreenSaver.SetActive(true)`（**真实 DPMS off**） | 同 |
| `idle-delay` | **0**（先 `cam-mode.sh blank disable`，确保熄屏是**我们主动**触发、非超时） | 同 |
| 发数 | **3** | **4** |

**判据（关键）**：用 **`/proc/sys/kernel/random/boot_id` 是否变化**判定死活 ——
比 `uptime` 可靠（`#209` 的死法会自恢复重启，`uptime` 归零才是真信号；而"SSH 还在"证明不了没死过）。

## 3. 解释（三条，按确定性排序）

### 3.1 确定的：`sync_state` 时机构型不是致死变量

A/B 两臂在**唯一变量（配对时机）**上相反，且都**真实熄屏**，结果**同为存活**
⇒ 该变量**对致死无判别力**。`reports/q24-n1b-boottime-pairing-20261015.md` §3.3 提出的
「存活 ⇒ 致死构型是夹到最高档侧」这一**预言被否证**（两臂都活）。

### 3.2 确定的：本轮的"配对 + 熄屏"**不等于**历史上的致死配方

`PITFALLS #212` / `reports/q24-repro-20261011.md` 的最小触发写的是
**「`camcc` + `cambistmclkcc` 配对 + 真实熄屏」**，而本轮**正是**这个配方却 7/7 存活。
⇒ 说明**该配方描述不充分**，致死还需要**当时存在的某个附加条件**。候选（未验证）：

- **完整相机栈**：`q24-repro-20261011.md` §2 那次致死用的是
  **「完整相机栈(20 模块) + 熄屏」**，不是"只有两个 CC"。本轮两臂**都只有 2 个 CC**
  ⇒ **模块集大小**可能是真变量（本轮是**有意的单变量简化**，但可能简化掉了致死的必要成分）。
- **display 子系统状态**：本轮熄屏时显示栈是 **Q28 坏发**（该 boot 的 `panel-init-fail` 计数非 0）
  —— 而 `q24-mech-20261012.md` 记录过"致死点随显示电源转换移动"。
- **相机 sensor 在位**：本轮没加载 `s5kjns`/`gc08a8`/`gt9764`/`cci`/`wl2868c`，
  即**没有真实时钟消费者**（N1 报告 §3.2 指出 sensor 是 cambist 的时钟消费者）。

### 3.3 方法学：`sleep-sweep.sh` 的"ALIVE"曾经是**假阳性**（本轮发现并修复判据）

本轮首次用 `scripts/sleep-sweep.sh` 跑 N2' 时得 **3/3 ALIVE**，
但核对 `boot_id` / `dmesg` 时间戳后发现：**重启根本没发生**
（`uptime` 单调、`boot_id` 不变、CC 未加载）⇒ 那 3 发"ALIVE"**什么都没测**。
根因见 `PITFALLS #288`（`reboot` 在本机当前状态会挂起）。
**⇒ 教训：自动化 harness 的 verdict 必须用 `boot_id` 这类**不可伪造**的判据复核，
不能只看它打印的 ALIVE/DEAD。**

然后做**真实的 `dpms On → Off` 跃迁**（先 `SetActive(false)` 唤醒、确认 `On`，再 `SetActive(true)`、
确认 `Off`），每次保持 ≥20–30 s。

|---|---|---|---|
| 1 | `On → Off` | 不变 | **存活** |
| 2 | `On → Off` | 不变 | **存活** |
| 3 | `On → Off` | 不变 | **存活** |
| 4 | `On → Off` | 不变 | **存活** |
| 5 | `On → Off` | 不变 | **存活** |

**净影响（必须写进 SSOT）**：

1. **`PITFALLS #212` 的最小触发口径在本台架当前状态下不可复现** —— 累计本轮
   **2 CC 臂 3/3 + 完整栈臂 5/5 = 8/8 存活**（外加 B 臂 4 发运行期配对，共 **12 发**）。
2. 这**不推翻**历史记录（`q24-repro-20261011.md` 的硬复位有 uptime 归零 + 模块清空 + 落 Q28 坏发的实证），
   而是说明：**致死还需要一个当前不在场、或已被某次改动移除的条件**。
3. **候选条件（未验证，按可测性排序）**：
   - **台架/镜像差异**：历史致死发生在 **`vk64`（7.2 血统）** 台架；本轮是 **`m1-baseline-f3`（7.3-rc7）**。
     ⇒ 「**换到 M1 树后 Q24 不再复现**」是一个**强候选**，且**零成本可回归验证**（退回 vk64 台架跑同一配方）。
   - **显示态**：本轮显示栈是 **Q28 坏发**（`panel-init-fail` 非 0）。`q24-mech-20261012.md` 记过
     "致死点随显示电源转换移动" ⇒ 显示态可能是**必要成分**。
   - **模块加载顺序/时序**：历史配方是"完整栈**运行期**加载 + 立刻熄屏"，本轮已尽量照做，
     但 OpenRC/session 启动阶段的具体时刻无法逐字复刻。
4. **建议的下一步（取代原 N3）**：
   - **N5（最高性价比）**：**在 `vk64` 台架上重跑本轮的同一配方**（完整栈 + 真实 `On→Off`）。
     若 **vk64 致死而 M1 存活** ⇒ 锁定「**M1 树上的某项改动消除了 Q24**」，
     可用 `clean/base → m1-73/baseline` 的提交集做二分 —— **这是把 Q24 从"玄学"变成"可二分"的最短路径**。
   - **N6**：在 M1 上换 **GOOD 显示态**复跑（排除 Q28 坏发这一混淆）。
   - 外部电气测量仍为兜底。

> ⚠️ **仍不得写"Q24 已解"**：本轮只证明「这套配方在当前台架**不足以致死**」，
> 未指名**哪个条件**被移除，也未证明历史上会死的那种机器状态不存在。
> 口径仍是 **未解**，但**靶点从"电气/时序"多了一个更强、更可操作的候选：镜像血统差异**。
