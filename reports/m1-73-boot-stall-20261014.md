# M1-7.3 启动停滞 96 s —— 根因定位（2026-10-14，编排者实测 + 更正）

> 触发：用户观察「背光亮 → 屏幕显示间隔很长」。本文件为该现象的唯一证据层。
> **本文件同时更正** `reports/m1-73-e1b-pllfix-20261014.md` 里「`insmod fsa4480` 阻塞 ~93 s」的错误归因。

## 0. 结论（数字先行）

- **M1 树 boot 慢与显示无关**：`fsa4480=y` 后面板 bring-up **4.05 s**、fbcon **5.46 s**（E1c/E1d/E1e 三发一致）。
- **userspace 到 96.5 s 才启动**：内核打印 `[96.449892] Freeing unused kernel memory` + `[96.499111] Run /init as init process`（E1e 发）。⇒ 之前看到的 `[m1-73e] hook start @ 96.91s`、`[init] root fs type=…@108.87s` 都是**结果**，不是原因。
- **主因 = WCN(WiFi) 的 MHI 等待超时**：`[4.902558] mhi mhi0: Wait for device to enter SBL or Mission mode` → `[96.079325] ath12k_wifi7_pci …: failed to set mhi state: POWER_ON(2)` → `-110` → probe failed；`kernel_init` 在 `async_synchronize_full()`（`init/main.c:1567`）等处等 probe ⇒ init 被推迟到 96.5 s。
- **日常 vk94 对比**：WCN 探针 **23.09 s** 起、**23.66 s** 就拿到 `chip_id/fw_version`（等待 0.4 s）⇒ 无停滞。M1 树则 **4.42 s** 枚举、chip 不应答、91 s 超时。
- **M1 上 WiFi 最终可用**：`[311.5]` 用户态 `ath12k-retry` 重试成功（`qmi TME-L power-on hardware-restricted (stock-compatible, continuing)` → `phy0 up (try 2) @316.5 s`），`wlan0` UP。

## 1. 更正（编排者自纠）

- ❌ 旧说法：「ramdisk 钩子里的 `insmod fsa4480` 阻塞 ~93 s」。**作废**：init 到 96.5 s 才被内核 exec，钩子自然在 96.9 s 才打印 `hook start`；insmod 实际只花 1.8 s（`hook start @96.91s` → `WARN insmod fsa4480 failed @98.75s`），fastrpc 6 s。
- ❌ 旧方法：「`ps -o etimes -p 1` 的 423 s ≈ uptime ⇒ PID1 自启动即在」。**误导**（PID1 的 starttime 代理不可靠）；判「init 何时起」只认内核 `Run /init as init process` 行。
- ✅ 保留：E1c（`CONFIG_TYPEC_MUX_FSA4480=y`）确实把**显示**从 95.3 s 提前到 4.05 s —— 因为原先 DP/typec 链的延迟探测被 96 s 的 init 停滞掩盖了。

## 3. 未决：为什么 M1 树 WCN 首探不应答

- 已排除：固件缺失（ramdisk 42M 与磁盘 44M 均含 `/lib/firmware/ath12k/PEACH` + `qca/tmel_peach_{10,20}.elf`）；`hardware-restricted` 本地补丁两树都在；ath12k `probe_type` 两树均未设置（非 driver 显式 async）。
- 待查（按可能性）：① M1(7.3) 的 PCIe/pwrseq 枚举**过早**（4.4 s vs 日常 23 s），chip 尚未就绪；② 7.3 在 PCIe/pwrseq/genpd 顺序上有回归；③ DTS WLAN 供电/复位时序差异。
- 判定手段（建议）：在 `pcie`/pwrseq 路径加时间戳探针；或对照两树 `drivers/pci/controller/dwc/pcie-qcom.c`、`drivers/power/sequencing/pwrseq-qcom-wcn.c` 与 wifi DTS 节点差异。

## 4. 修复方向（按代价排序）

1. **让 WCN 探针不再 gate init（快）**：`CONFIG_ATH12K=m` + 本地 Kconfig 调整（`ath12k/Kconfig` 的 `select PCI_PWRCTRL_PWRSEQ if HAVE_PWRCTRL` 会把 pwrseq 降为 `=m` → PCIe host 起不来，`PITFALLS #125`；实测 `olddefconfig` 确实降级）。代价：需编 `=m` 闭包（ath12k/mac80211/cfg80211/qrtr/mhi…）并打进 ramdisk overlay；预期 boot ~6 s、WiFi 交给用户态加载/重试。
2. **查清 ①（正路）**：修 M1 的 PCIe/WCN 枚举时序，使首探即成功（同时把 M1 的 WiFi 首探失败一并解决；对上上游也有价值）。
3. **暂时不动（仅记录）**：M1 臂 boot ~100 s 但仍能跑通实验。

## 6. E1g / E1h（ath12k=m 臂，2026-10-14 下午实测）

| 臂 | 内核/ramdisk | `Run /init` | 显示 | WiFi |
|---|---|---|---|---|
| **E1g** | `ATH12K=m`+`PCI_PWRCTRL_PWRSEQ=y`（本地提交 `fcefad3592`）；overlay 仅含 `ath12k.ko` | **4.486 s** | 好发：`dsi_isr`=41 / storm=0 / L1=0，GUI ~7 s | ❌ 无 `wlan0`；`/sys/bus/pci/drivers/ath12k_wifi7_pci` 不存在 |
| **E1h** | 内核不变；overlay +`ath12k_wifi7.ko` | **48.5 s（坏发）** | Q28 坏发：L1=3 @4.33 s、`dsi_isr`=0、storm=48、phoc=0 | `ath12k_wifi7(+)` 加载中；未等到 `wlan0` |

**关键发现**

1. **7.3 的 ath12k 拆成两个模块**：`ath12k.ko`（core，只 `EXPORT_SYMBOL(ath12k_pci_register_driver)`）+ `ath12k_wifi7.ko`（`drivers/net/wireless/ath/ath12k/wifi7/`，**真正注册 PCI driver `ath12k_wifi7_pci`**，`depends: ath12k`）。只装 core ⇒ 驱动目录不存在 ⇒ 既有 `ath12k-retry` 报 `can't create …/ath12k_wifi7_pci/bind: nonexistent directory`（`bind write failed` 循环）。
2. **init 时刻取决于发质量**：好发 **4.49 s**、坏发 **48.5 s** —— 坏发时 DRM/DPU 的 vblank/frame-done 风暴（call trace 刷屏）同样落在 `wait_for_device_probe()` 的等待里。⇒ 「M1 boot 时间」必须按发分档记录，单发不能当基线。
3. **`fsa4480=y` 与 Q28 的疑似耦合（样本不足，待并列采样）**：`fsa4480=y` 把面板 bring-up 从 95.3 s 提前到 **~4.0–4.3 s**；4 发里 3 发落 Q28 坏发（E1c：无 L1 但 `dsi_isr`=0；E1d/E1h：L1=3；E1g：好发）。**不下结论**，但「过早 bring-up 可能改变坏发率」需专门采样。
4. **WiFi 首探在 M1 树仍失败**（4.4 s 探测时 WCN 未就绪；日常 vk94 在 23 s 探测即 0.4 s 成功）。E1h 让 `ath12k_wifi7_pci` 驱动目录**存在**（retry 通路前提具备）；本次因坏发 + 时间盒未等到 `wlan0`。
