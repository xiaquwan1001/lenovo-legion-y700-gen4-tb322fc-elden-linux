## §3 上机判据（交给上机轮，不执行）
1. `Loader-r56.efi` 覆盖 ESP `/EFI/elden/Loader.efi`（FAT 零写盘，先记 sha）→ `fastboot boot` p59。
2. 屏（FrameBufferSerialPortLib 直涂 Display Reserved 区）出现：
   `[E] esp in` → `[E] esp boot 85594112` → （dtbo 已删，应见 `[E] esp dtbo none`）→ `[E] esp take`。
3. **`[E] esp take` = ESP-first 真跑过的唯一必要条件**（消除 R55 的两个盲区：RELEASE 不再剥标记、
   grub.cfg 已收单条目）。
4. `[E] esp miss <n>`：n = 14 (NOT_FOUND，文件缺/无 SFS) / 9 (OUT_OF_RESOURCES，85 MB pool 失败)，可归因失败。
5. 连 `[E] esp in` 都没有 ⇒ chainloader 没执行到我们的 PE，问题在 GRUB 侧。
6. 终判仍需三件套：内核起（ssh 通 / cmdline 含 `elden_bootloader=esp`）+ `boot_b` sha 不变
   （`4e38bc2c…`）。

## §4 风险
1. **Pname 修复只盖 MDTP/FFBM 口径**：ESP 路径仍跳过 AVB/verified-boot 屏/milestone（设计使然）。
2. `SerialPortWrite` 每次 `AsciiSPrint` + 直接涂屏，ESP 路径最多 5 行，对启动时序影响可忽略；
   但 FrameBufferSerialPortLib 的惰性初始化若在此阶段（DXE 前的 LinuxLoader 应用环境）行为不同，
   最坏是屏上无字——功能不受影响（不写坏任何东西）。
3. 85.6 MB `AllocatePool` 与 dtbo 语义两个旧风险未变（见 static-findings §5.1/§8，dtbo 已删、非阻塞）。
4. 本轮未上机、未提交 Mu git；BootLib.inf 是「必要时」授权的最小改动，若上游化需另行评估
   SerialPortLib 依赖是否该收敛到更高层。
