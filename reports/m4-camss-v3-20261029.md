## 2. 0004 的代码修复（sashiko #4 High + Medium；#8 不改）

### 2.1 修的是什么（两个独立缺陷，落在同一组函数里）

| finding | 原状 | 后果 |
|---|---|---|
| #4 High：AUP/RUP 位掩码累积 | `__csid_aup_update()` / `__csid_rup_update()` 只 `|=` 累积，`writel` 的是**累积位图**；只有 `__csid_aup_rup_clear()`（`INFO_RUP_DONE` 触发）才清 | ① **AUP 侧永远清不掉**：本代每 RDI 状态位只有 `INFO_RUP_DONE`(`BIT(23)`) 与 `INFO_CAMIF_SOF`(`BIT(4)`)，**没有 AUP-done 位**（`grep '^#define INFO_' camss-csid-980.c` 只出这两条 + `INFO_RST_DONE`）；② `CAMSS_INIT_BUF_COUNT` 的 qualifier 逐流写寄存器时，后一条命令会把前一条的位一起带上 → **重发陈旧 RUP/AUP 命令**、重复 latch 调用方没要求重 latch 的寄存器 |
| #4 Medium：三字段数据竞争 | `csid_device.{reg_update,rup_update,aup_update}` 被「进程上下文命令路径」与「硬中断 `csid_isr`」同时 RMW，无锁 | 丢更新（`|=` 被 ISR 的 `&=` 覆盖）→ 偶发 RUP 超时/丢帧 |

### 2.2 修法（终态代码）

```c
/* camss-csid-980.c: 写出去后立刻丢掉本流请求位（命令寄存器由硬件自行消费） */
static void __csid_aup_update(struct csid_device *csid, int port_id)
{
	unsigned long flags;

	spin_lock_irqsave(&csid->reg_update_lock, flags);

	if (csid_is_lite(csid)) {
		csid->reg_update |= CSID_LITE_AUP_RDI(port_id);
		writel(csid->reg_update, csid->base + CSID_LITE_RUP_AUP_CMD);
		csid->reg_update &= ~CSID_LITE_AUP_RDI(port_id);      /* ← v3 新增 */
	} else {
		csid->aup_update |= CSID_RUP_AUP_RDI(port_id);
		writel(csid->aup_update, csid->base + CSID_AUP_CMD);
		__csid_full_aup_rup_trigger(csid);
		csid->aup_update &= ~CSID_RUP_AUP_RDI(port_id);        /* ← v3 新增 */
	}

	spin_unlock_irqrestore(&csid->reg_update_lock, flags);
}
```

- `__csid_rup_update()` 同形（lite 清 `CSID_LITE_RUP_RDI`，full 清 `rup_update`）。
- `__csid_aup_rup_clear()`：只加锁，`&=` 语义不变（它现在是「清残留位 / 处理滞后的 RUP done」的兜底）。
- `camss-csid.h`：加 `#include <linux/spinlock.h>` 与 `spinlock_t reg_update_lock;`（注释：`serialises the update shadows of the 980 ops`）。
- `csid_subdev_init()`：`spin_lock_init(&csid->reg_update_lock);`。**初始化先于中断使能，已证**：
  `camss-csid.c:1107` `csid->res->hw_ops->subdev_init(csid)` →（980 的 `.subdev_init = csid_subdev_init`）在先，
  `camss-csid.c:1137` `devm_request_irq(...)` 在后，同一 probe 函数内顺序执行。

**为什么 write-then-clear 在本代是安全的（推理 + 上游旁证，仍未上机）**：命令寄存器是**一次性 write-1 触发的请求寄存器**，软件 shadow 清 0 **不会**回写硬件（gen3 的 `csid_subdev_reg_update(clear=true)` 正是「只清软件 shadow、不写寄存器」，见 `camss-csid-gen3.c:242-249`）。因此本地清位只影响「下一条命令带上谁」，不影响已发出的命令。

### 2.3 提交信息（0004 新增两段）

```
The update shadow registers are shared between the command path and the
interrupt handler, so they are taken under a per device spinlock.  The
command registers are consumed by the hardware on their own and there is
no completion interrupt for an AUP only request, so the bit of a stream
is dropped as soon as its command has been written out; keeping it would
let the qualifier loop of the next stream re-issue the command of the
streams configured before it.

The older generations are not converted here: they keep their current
unsynchronised pattern, which predates this series.
```

（第二段是主动回答 reviewer 必问的「为什么只锁 980」——gen2/gen3/680 同样无锁，属既有上游问题，v2 README 已定为独立补丁线。）

### 2.4 #8（vfe-gen4 ↔ csid_isr 竞争）为什么 0008 不改

调用链已证（grep）：

```
camss-vfe.c:570   ops->reg_update_clear(vfe, line->id)        ← 进程上下文（停流）
camss-vfe-gen4.c:141-147  vfe_reg_update{,_clear}()
      → camss.c:5368  camss_reg_update()  →  csid->res->hw_ops->reg_update(csid, ...)
      → camss-csid-980.c  __csid_aup_update() / __csid_aup_rup_clear()   ← 现在都在 reg_update_lock 内
```

- 结论：**0008 不需要任何改动**（与派工单预期一致）。

## 4. 是否需要重跑硬件出流验证（判断 + 最小验证命令，不执行）

**判断：需要。** 理由按强度排序：

1. **写进硬件的值变了**：`CSID_RUP_CMD`/`CSID_AUP_CMD`/`CSID_LITE_RUP_AUP_CMD` 从「累积位图」变成「单流位」
   ⇒ 多 RDI 同时需要 latch 时，硬件现在收到的是**多条独立命令**而不是一条合并命令。这是**行为变更**，纯静态证据无法排除「某些代硬件要求命令位保持到帧边界」的可能。
2. **新增了硬中断里的自旋锁**：`csid_isr` 每帧都会走 `__csid_aup_rup_clear`（`INFO_RUP_DONE` 已解掩码），锁内是 `writel`
   ⇒ 单帧中断延迟增加（预期 ns 级），需确认 30 fps 双摄下无 `command DMA timeout`/丢帧。
3. 0005 的 SOF/EOF 时序逻辑未变（hunk 仅平移），但 0005 与 0004 共用 `csid_isr`，回归要一起看。

通过判据（沿用 v2 §5 口径）：双摄 **90/90 帧、30.0–30.3 fps、错误计数 0→0**、帧内容 `NONZERO ≈ 99.7%`。
**额外**针对本次改动的加严项：把 `front/rear` 各跑两遍（第 2 次是「先停再起」，会走 `reg_update_clear` 路径 + qualifier 循环），

## 5. 0004 是否拆成两枚（锁 / 位清零）

**判断：不建议拆（保持单枚 0004）。** 理由：

1. 0004 是**新驱动落地**枚：累积+无锁是「一起进来」的初始形态，reviewer 看到的就是 `+482` 行新文件；
   若拆出「给刚加的代码加锁」这种纯追加枚，会引出「为什么不直接写对」的往返。
2. 拆开后 `0004b`（位清零）只有 6 行、但**必须挂硬件证据**才有意义；单枚 0004 = 一次上机验证覆盖两处改动，验证成本更低（§4 只需一轮 90 帧回环）。
3. 两处改动落在同一组 3 个函数里，拆分会产生 3 次同文件重写 → `git am` 冲突面与 bisect 成本上升，series 从 9 枚涨到 11 枚。

**若 maintainer 明确要求拆，按以下顺序与边界做**（每步可编译、可单独 bisect）：

| 枚 | 内容 | diff 规模（估） | 备注 |
|---|---|---|---|
| `0004` | 保持 v2 原状：加驱动，累积 + 无锁 | 不变 | 就是 v2 的 0004 |
| `0004a` | **只加锁**：`spinlock_t reg_update_lock` + `spin_lock_init` + 三函数 `lock/unlock`，`\|=`/`&=` 语义**一字不改** | +26 −0（2 文件） | 纯并发修复，机械可审；单独上机应也能出流（累积 bug 仍在，但不影响单流） |
| `0004b` | **只改位清零**：三处 `writel` 后各加一行 `&= ~...`，删掉/保留锁由 0004a 决定；同时改 `__csid_aup_rup_clear` 的注释 | +6 −1（1 文件） | **唯一需要硬件证据**的一枚；commit message 直接引用 §4 的 90 帧结果 |

顺序不可颠倒：先 0004a 再 0004b，否则 0004b 引入的 RMW 变化落在无锁代码上，bisect 到 0004b 时既变了语义又暴露竞争，归因不清。

**备选更优路径（本 lane 的建议，供编排/用户裁决，未实施）**：既然写了就清，三字段在锁外**恒为 0** ⇒ 它们连同锁都退化成「函数内局部变量」，

那样 #4 的 High 与 Medium **一起消失**（无共享态即无竞争，不需要锁）。代价：`camss-csid.h` 里 0004 新增的 `rup_update`/`aup_update` 两个字段变成无必要（`reg_update` 仍被 gen2/3/680 使用，保留），

## 6. 未证实项 / 风险 / 教训

**未证实（只有推理）**：
- 「命令寄存器是一次性 latch、软件清 shadow 不回写硬件」——依据是 gen3 上游实现（`csid_subdev_reg_update(clear=true)` 只清软件变量不写寄存器），
  **本代硬件未取证**。这是 §4 必跑的核心理由。
- 「多流并发时改成多条独立命令后硬件仍逐个 ack」——`INFO_RUP_DONE` 是**每 RDI 一位**，故理论上可逐条 ack；未上机验证。

**未做（明确记录）**：
- 未跑 pristine `git am` 9 枚：v3 只在 `build/m4-v3` 上验证了 `0005–0009`（**5 枚**）对改后 `0004` 的 `git am -3` 干净（rc=0），
  以及 `git diff ca3d71e71 HEAD` 只有预期 42 行。v2 曾做过 pristine 9/9 干净，v3 未重跑。
- 未跑 `dtbs_check`（0001/0009 未改）。
- 未做逐提交 9 次编译（理由见 §3.2）。
- **未上机**（本 lane 硬约束）。

**风险**：
- 若硬件实际要求「同窗口内合并命令」，write-then-clear 会退化为多发命令 → 表现为 `command DMA timeout` 或掉帧；§4 的错误计数差分能抓到。
- 锁内 `writel` 在硬中断里执行，最坏情况是增加几微秒中断延迟（单帧一次），30 fps 下不应可见；未实测。

**教训（本次真实发生的操作事故，已修复）**：
- 第一次改 0004 提交信息时，`git am` 已把 0005–0009 接到 0004 之上，此时再 `git commit --amend` **改到的是 tip（0009 DTS 枚）的提交信息**，
  导致历史里出现「DTS 枚却叫 add the 980 generation」+ 两枚同名提交。发现方式：`git log --oneline -9` 出现两条同名提交。
  修复：`git branch -f m4/v3-broken-<ts> HEAD` 留证 → `git reset --hard <0004 的父>` → `git cherry-pick <原 0004>` → `--amend` → `git am` 0005–0009。
  **规矩**：`--amend` 只能紧跟在「自建该枚」之后执行；`git am`/`cherry-pick` 批量接枝后再 amend 等于改 tip。
