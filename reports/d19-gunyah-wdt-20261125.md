## 1. 为什么是这颗（静态证据链，全部在本次树内复核过）

1. **驱动在树里**：`build/daily/drivers/watchdog/gunyah_wdt.c`（主线件，SMCCC vendor-hyp）
   - `Kconfig:2382` `config GUNYAH_WATCHDOG`：`depends on ARCH_QCOM || COMPILE_TEST`、`depends on HAVE_ARM_SMCCC`、`select WATCHDOG_CORE`；
   - `Makefile:107` `obj-$(CONFIG_GUNYAH_WATCHDOG) += gunyah_wdt.o`；
   - 四个 SMCCC func id：`CONTROL 0x0005 / STATUS 0x0006 / PING 0x0007 / SET_TIME 0x0008`（`ARM_SMCCC_OWNER_VENDOR_HYP`，fast call）；
   - `watchdog_ops`（`gunyah_wdt.c:158`）= `start / stop / ping / set_timeout / get_timeleft / restart`，`timeout` 3→32 s（`max_timeout=32`，
     hyp 只认 ≤0x8000 ms 的值），`magicchar` 走 `WDIOF_MAGICCLOSE`（`V` 关闭即停狗）；
   - `restart` 优先级 = `watchdog_set_restart_priority(wdd, 0)` ⇒ **不注册 restart handler**（不与别的重启路径抢），只作 watchdog。
2. **平台设备由 `qcom_scm` 注册，且本机 DT 不会挡住它**：
   `drivers/firmware/qcom/qcom_scm.c:2497 qcom_scm_gunyah_wdt_init()`（`qcom_scm_probe()` 第 2942 行调用）先
   `arm_smccc_hypervisor_has_uuid(c1d58fcd-a453-5fdb-9265-ce36673d5f14)`，再**在 DT 里查 `qcom,kpss-wdt` / `arm,sbsa-gwdt` 存在就退出**
   （`:2509-2521`），否则 `platform_device_register_simple("gunyah-wdt")`（`:2528`）。
   ⇒ 我复核了本次编出的 `sm8750-lenovo-elden.dtb` 与 vk189 打进镜像的 dtb：**两者都没有任何 `watchdog` 节点**，
   所以这条 bail-out 不触发，平台设备会注册（与 2026-10-24 在机实测 `ls /sys/bus/platform/devices | grep gunyah` → `gunyah-wdt` 一致）。
3. **通道已在真机证明可用（历史阳性）**：`reports/gunyah-stage0-positive-20261024.md` §2 —— 2026-10-24 自编 `gunyah_wdt.ko`
   在 U2（`7.3.0-rc7-debug-vk127`）`insmod` 成功、驱动绑定、`watchdog0` 出现、`rmmod` 干净；`probe()` 第一句就是
   `STATUS`（`-EOPNOTSUPP` 直接 `-ENODEV`）⇒ **probe 过 = SMCCC vendor-hyp 调用真的返回 0**。
4. **为什么现在才有意义**：D19 的痛点不是「没有 watchdog 驱动」，而是日常线 `.config` 里这行是 `not set` ⇒ 设备上根本没有
   `/dev/watchdog`，hang 只能人肉 POR。本 lane 只做「把它编出来 + 打包 + 写清上机判据」，不动别的配置。

**A. 零风险（只证明「设备在、驱动能绑、调用不被拒」）**

```
scp out/gunyah-wdt-20261125/gunyah_wdt.ko root@192.168.7.1:/tmp/     # 主机侧
ssh root@192.168.7.1 '
  uname -r                                   # 必须 = 7.3.1-debug-vk189-suspend-g4da9a8b69fc8
  insmod /tmp/gunyah_wdt.ko; echo insmod_rc=$?
  lsmod | grep -x "gunyah_wdt.*"  ;  readlink /sys/devices/platform/gunyah-wdt/driver
  ls -l /dev/watchdog /dev/watchdog0
  dmesg | grep -iE "gunyah|watchdog" ')
```
判据：`insmod_rc=0`；`readlink` = `…/bus/platform/drivers/gunyah-wdt`；`/dev/watchdog`（misc，id 0）+ `/dev/watchdog0`（cdev）都在；
dmesg 无 `probe failed` / `status check failed`。**这一步不动狗**（`probe()` 末尾自己 `stop()`）。

**B. 低风险（证明写路径通，且能干净收手）** —— `magicclose` 语义：写 `V` 再关 fd = 停狗。

```
ssh root@192.168.7.1 'sh -c "
  exec 3>/dev/watchdog || exit 1
  printf x >&3; sleep 8; printf x >&3; sleep 8
  printf V >&3; exec 3>&-
  echo magicclose_rc=$?"'
```
判据：16 s 内**不复位**、命令返回 0，`rmmod gunyah_wdt` 干净。风险注：open 即 arm（默认 32 s），
所以这步已经短暂"上了膛"；若 ping 通道坏而 enable 生效，最坏情况是 32 s 后复位（RAM 核 ⇒ 回落 `boot_b`，不污染任何槽）。

**C. 破坏性（一次性、显式 opt-in：证明「真会咬」）** —— 这步替代「hang 只能物理 POR」的验证。

```
GWDT_BITE=1 sh -c '
  exec 3>/dev/watchdog || exit 1
  printf x >&3; sleep 20; printf x >&3     # 两次 ping，证明喂狗通道
  sleep 45                                  # 超过 max_timeout=32 ⇒ 期望复位
  printf V >&3'                             # 走到这里 = 狗没咬（阴性结论），主动收手
```
判据：**复位发生** ⇒ 下次 `fastboot devices`/SSH 回来、`uname -r` 回到日常核（或仍在 BL）；
**没复位** ⇒ 结论 = "SMCCC 调用通但 hyp 侧不复位整机"，同样是有价值的负结论，且狗已被 `V` 摘掉，不留后患。

**在无人循环里怎么用**：新增设备侧探针 `probes/gunyah-wdt-probe.sh`（**本 lane 不写**，上机那轮再落），
内容 = A 段 + B 段 + 一条「存活探针」（`cat /proc/uptime` 前后差值 ≥ 窗口长度 ⇒ 系统没被复位），挂到
`scripts/autotest-cycle.sh --image <本件> --test probes/gunyah-wdt-probe.sh --rounds 2`。这样每一轮都以「狗可喂/可摘」为前提，
hang 类实验（例如故意让测试核在某个 ioctl 上死等）第一次有了**自动脱身**手段 —— 但只有在 C 段确认「真会咬」之后才敢把无人循环交给它。

**回退**：零写盘件，`boot_a/boot_b` 未被写；`scripts/to-bootloader.sh`（= `systemctl reboot --reboot-argument=bootloader`，
`PITFALLS #722`）随时回 BL；真 hang 且狗不咬 ⇒ 仍只能物理 POR（= 现状，本 lane 未改变这一点）。

## 6. 风险与未知（都留待上机/后续裁定，本 lane 不预设结论）

1. **「Gunyah watchdog 复位」是否等于整机 POR？未证**。hyp 层可能只复位当前 VM 而不复位 SoC；若只复位 VM，Linux 侧到底是
   重启、复位回 ABL、还是直接死掉（黑屏/USB 掉）都不确定。C 段判据按「能回到可观测状态」写，不假设一定是 POR。
2. **`WDT_CTRL` 语义**：驱动注释说 bit0 = enable，**bit1 恒置 1（Gunyah 保留位，必须为 1）**；`DISABLE = BIT(1)`、`ENABLE = BIT(1)|BIT(0)`。
   这套编码只在 QTI 下游件里对得上，本机 hyp 是否照此实现**未逐位验证**（2026-10-24 只证明了返回 0）。
   若 bit1 语义不同，`start()` 可能"开着但不算数"（→ C 段阴性）。
3. **与 `q28-boot-watchdog` 的关系**：那是**用户态脚本**（`rootfs/persistent-overlay/q28-boot-watchdog.sh`，靠 DP/USB 状态判断
   "启动失败就重启"，现根里可能不存在），与本驱动**不共享任何内核接口**，不会撞同一个 `/dev/watchdog`（脚本不用它）。
   真要担心的是反过来：一旦本驱动上机且被 `systemd`/`watchdog.service` 之类的用户态 keeper 接管，会与 `q28-boot-watchdog` 的
   重启决策叠加（两套都会复位）。本 lane 不开 `CONFIG_WATCHDOG_NOWAYOUT`、也不加任何 keeper，故默认"没人开狗就没狗"。
4. **`CONFIG_WATCHDOG_SYSFS` 未开 ⇒ 没有 `/sys/class/watchdog/watchdog0`**：`wdctl` 在本件上**不可用**，
   `timeleft`/`bootstatus` 只能走 `WDIOC_GETTIMELEFT` 等 ioctl（要现写小工具）或从 `/dev/watchdog` 行为反推。
   这是**刻意**的（SYSFS 不是本驱动依赖，开了等于给所有 watchdog 加一个面 = 第二个变量）；若下一轮想让 `wdctl` 可用，
   单独加一行 `CONFIG_WATCHDOG_SYSFS=y` 的片段重编即可（届时是"两变量"，需在 manifest 里分开记）。
5. **UTS 变了 ⇒ 与设备现 `/lib/modules` 目录名不匹配**（§5 前置）。不部署模块树也能上机（本机 root/UFS/USB gadget 是 builtin），
   但 WLAN/触屏/音频等 `=m` 会全体缺位；判据要按「这套功能缺位是 UTS 不匹配造成，不是本驱动造成」读。
6. **`max_timeout=32 s`**（hyp 只收 ≤0x8000 ms）：想让"hang 后自动脱身"的窗口更长，得在 hyp 侧改，不在 Linux 侧。
   反过来说 32 s 对无人循环够用（D19 单轮 ≈90 s 的量级），但**别把它当长延时看门狗**用。
7. **本次重编 dtb ≠ vk189 dtb（28 B，ramoops/pmsg/iommu）**：本 lane 未裁定哪份才对（只选择沿用 vk189 那份）。
   如果以后要重打"整套本树"的件，这个差异必须先查清（尤其 `ramoops 8 MiB→4 MiB` 会影响 hang 后的 pstore 取证容量）。

## 父代理上机复核（2026-11-25 20:0x–20:1x）：**驱动能加载，但 hyp 侧是空实现 ⇒ 不能当看门狗用**

设备窗内用候选件零写盘上机：`fastboot boot out/gunyah-wdt-20261125/boot-elden-gunyah-wdt.img`
（UTS `7.3.1-debug-vk189-suspend-g4da9a8b69fc8`，`elden_root=LABEL=linux`，起机 25 s 内 SSH 可达）。

| 步 | 观测 | 判读 |
|---|---|---|
| `insmod /tmp/gunyah_wdt.ko` | rc=0；`/dev/watchdog`、`/dev/watchdog0` 出现；`lsmod` 见 `gunyah_wdt` | **驱动探测绑成功**（与 2026-10-24 阶段 0b 一致） |
| `/sys/class/watchdog/watchdog0/*` | **属性文件全部不存在**（`identity`/`timeout`/`state`… ENOENT） | 因为 `CONFIG_WATCHDOG_SYSFS` 未开（class 目录在、属性不在）⇒ `wdctl` 读不到东西 |
| ioctl `WDIOC_GETTIMEOUT` / `SETTIMEOUT(10)` | 10 / 返回 10 | 超时设置链路通 |
| ioctl `WDIOC_KEEPALIVE` ×N | 全部 rc=0 | 喂狗 SMC 被接受 |
| ioctl `WDIOC_GETTIMELEFT` | **恒等于 timeout（8/8、10/10），从不递减** | ⇒ `GUNYAH_WDT_STATUS` 的「距上次喂狗秒数」恒为 0 ⇒ **hyp 侧状态查询是空实现** |
| **过期测试**：设 8–10 s、停止喂狗后 45 s | **设备没有复位**（进程自己打印 `survived 45s`，boot_id 不变） | ⇒ **`GUNYAH_WDT_CONTROL/SET_TIME/PING` 全部返回 0 但什么都不做** |

**结论（负面但明确）**：本机 Gunyah hypervisor **没有为这个 VM 实现看门狗**——SMC 走通、返回值像成功、实际不计数也不复位。
所以 `CONFIG_GUNYAH_WATCHDOG=m` **不能**解决 D19 的「hang 类实验只能物理 POR」。
**并且有反作用**：把模块留在设备上会误导 systemd —— 本轮的 `systemctl reboot` 日志出现
`Using hardware watchdog 'Gunyah Watchdog', version 0, device /dev/watchdog0` + `Failed to set watchdog hardware timeout to 10min: Invalid argument`
（驱动 `max_timeout=32 s`，systemd 要 10 min）。⇒ **不要在每日配置里开它**，本次候选件只作证据保留。

### D19 的下一个候选（按代价排序）

1. **APSS watchdog（`qcom-wdt` / kpss-wdt）**：上游 `drivers/watchdog/qcom-wdt.c` 支持 `qcom,apss-wdt-<soc>` + 回退 `qcom,kpss-wdt`（`x1e80100`/`glymur` 等已有节点），
   而 **`sm8750.dtsi` 里没有 watchdog 节点**（`grep -c watchdog = 0`）⇒ 需要一篇 DT（+ 可能一篇 binding）的同批提交：**这既是 D19 的解，也是 §7 可投的上游小系列候选**。
   待核：本机 APSS WDT 基址/时钟（vendor DTB 里应有 `watchdog@` 节点可抄）、是否被 XBL 关掉（`dmesg: Hard watchdog permanently disabled` 那句是 lockup detector，不是硬件狗，别混）。
2. **PMIC `qcom-pmic-wdt`**：本机 DT 同样无节点，且 PMIC 型号（PMIH010x）上游无 WDT 支持 ⇒ 不优先。
3. **放弃硬件狗、改用「可观测 hang 判据」**：`autotest-cycle.sh` 已有 SSH 超时判据；再加一条「boot 后 N 秒内必须看到 journal 心跳行」，即可把 hang 与「起得慢」区分开（零内核改动，**可立即做**）。

### 顺带记两条候选核件的使用边界

- 候选核件 UTS 与在机模块树不同 ⇒ 依赖模块的功能（WiFi/uinput/BT）在该 boot 里都不可用；
  实测影响：`lisgd-edge-swipe` 与 `ydotool` 各失败数十次（`failed to open uinput device: No such file or directory`），
  **这不是回归**，是模块树不匹配的必然结果（`CONFIG_INPUT_UINPUT=m`）。零写盘实验里请忽略这类循环。
- 候选件的 cmdline 用 `LABEL=linux` 是对的（见 `PITFALLS #728`：旧件 `LABEL=linux17` 会停 initramfs）。
