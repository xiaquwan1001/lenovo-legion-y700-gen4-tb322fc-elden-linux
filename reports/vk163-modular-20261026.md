# vk163 — 驱动模块化在 7.3 日常线落地（上机验证通过）

> 日期：2026-10-26（主机侧构建/验证）
> 设备：`HA2EXB0E`（U1），验证时根 = `f2fs @/dev/sda18`（`linux18`），`boot_b` 全程未写
> 镜像：`out/boot-elden-vk163.img`（85 811 200 B，sha256 `70fefa73…b04c396`，manifest 同目录）
> 结论：**7.3 日常线（`build/vk151` @ `24223e4`）的载荷驱动全部翻成 `=m`，在**生产根**上零写盘启动后
> 音频/WiFi/BT/触屏/触觉/背光/相机/显示全部正常，且 `mod-loop` 热换环重新可用（触屏驱动实测）**。

## 0. 为什么做这一轮

`patches/fragment-modular.config` 是 2026-10-04 在 **7.2 `clean/base`** 上验证的（vk89）。
2026-10-10 之后日常线迁到 **7.3 `m1-73`/`vk151`**，那份片段没有跟过来 ⇒ 在机 `boot_b`（vk152）的
`/proc/config.gz` 实测仍是 `ATH12K=y / SND_SOC_QDSP6=y / INPUT_AW86927=y / TOUCHSCREEN_…=y /
BACKLIGHT_AW99706=y`。也就是说：

* 「30 秒热改一个驱动」的 `mod-loop` 在日常线上**根本用不了**（驱动是内置的）；
* 每次改触屏/触觉/背光/音频/无线都要**重编内核 + 重做 boot 镜像 + 重启**；
* 上游化（M 系列）要按模块出补丁时，没有「同一份代码既能内置又能模块」的验证路径。

## 2. 三条与旧笔记相反、必须更正的结论

### ① BT 不需要改源码就能模块化

旧片段注释写「`BT_HCIUART_QCA` 是 bool 并 `select BT_QCA` ⇒ hci_qca 只能内置，要改就得把 bool 改 tristate」。
**实测：不用改 Kconfig**。`hci_qca.c` 不是独立驱动，它是 `hci_uart.ko` 的协议实现
（`drivers/bluetooth/Makefile: hci_uart-$(CONFIG_BT_HCIUART_QCA) += hci_qca.o`），所以
`CONFIG_BT_HCIUART=m` 时整个 `hci_uart.ko`（含 h4/qca 协议）就是模块，bool 子项保持 `=y` 即可。
`select BT_QCA` 把 helper 库 `btqca.o` 也拉成模块（`BT_QCA=m`），5 个 `EXPORT_SYMBOL_GPL` 供其引用
（`Module.symvers` 实测 `qca_uart_setup … EXPORT_SYMBOL_GPL`），`nm -u hci_uart.ko` 里 5 个 `U qca_*` 全部可解析。
⇒ 热改 BT = `mod-loop drivers/bluetooth --reload hci_uart`（先 `rfkill block bluetooth` + 停 bluetoothd）。

### ② `PCI_PWRCTRL_PWRSEQ` 的 `=y` 钉不住，而且**不需要**钉

* 钉不住：该 symbol 在 Kconfig 里**没有 prompt**（`drivers/pci/pwrctrl/Kconfig:9` 只有 `tristate`），
  `ATH12K=m` 的 `select` 会在 **kbuild 自己的 syncconfig** 里把它重算成 `m`——
  手工往 `.config` 追加 `=y` 只在「不触发 syncconfig」的窗口内有效（`grep` 看到 `=y`、编出来仍是 `m`；
  本轮先踩到一次：快照里是 `=y`，`make` 之后 `.config` 又变回 `m`）。
* 不需要：真正给 WCN7861 供电的是 `CONFIG_POWER_SEQUENCING_QCOM_WCN=y`（内置，
  `drivers/power/sequencing/pwrseq-qcom-wcn.c`，ath12k 调 `pwrseq_qcom_wcn_set_ol_cpr()`），
  而 `pcie-qcom.c` **一次都没用 pwrseq**（`grep -c pwrseq drivers/pci/controller/dwc/pcie-qcom.c` = 0）。
  ⇒ `PITFALLS #125` 里「ath12k=m ⇒ pwrseq 变 m ⇒ WiFi 全无」的因果链**只在「模块根本不在设备上」时成立**，
  与 `=y/=m` 无关。本轮实测：`pci_pwrctrl_pwrseq` 以模块加载，`wlan0` 正常出现、`rfkill` 正常、NM 认到 wifi 设备。

### ③ 载荷加载器必须区分 builtin 与 loaded

见 §1 表格最后一行。否则在非模块化内核上会得到「7 个模块全部 loaded」的假证据——
本项目的归因纪律（「配置态 ≠ 驱动坏」）要求这里必须诚实。

## 3. 上机验证（零写盘）

```bash

make -C build/vk151 -j24 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- LD=ld.lld \
     LOCALVERSION=-debug-vk163 Image.gz dtbs modules
make -C build/vk151 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- LOCALVERSION=-debug-vk163 \
     INSTALL_MOD_PATH=$PWD/out/modstage-vk163 INSTALL_MOD_STRIP=1 modules_install
rsync -a out/modstage-vk163/lib/modules/<UTS> root@192.168.7.1:/lib/modules/   # 设备侧 depmod -a
# 打包（ramdisk 必须是仓库 /init 的 initramfs-full；见 PITFALLS #407）
KDIR=build/vk151 VERSION=vk163 RAMDISK_KIND=full RAMDISK=$PWD/out/initramfs-full-elden.cpio.gz \
     ROOTARGS='elden_root=LABEL=linux18' bash scripts/build-boot.sh
```

### 3.1 `mod-loop` 热换（模块化的实际收益）

```bash
KDIR=$PWD/build/vk151 LOCALVERSION=-debug-vk163 bash scripts/mod-loop.sh \
     drivers/input/touchscreen --reload novatek-nvt36xxx-spi
```

输出要点：`tree KV == device KV`（逐字）→ 只编该目录 → 上传 → `depmod` → `rmmod+modprobe` →
`[mod] reloaded novatek-nvt36xxx-spi`；设备侧 `dmesg` 重新出现
`firmware SRAM transfer complete / cascade auto-copy complete / boot-ready asserted / firmware version 1a.01`，
输入节点 `NVTCapacitiveTouchScreen` 重新注册。**改触屏参数从「重编内核+重启」降到秒级。**

## 4. 设备现状与遗留

* **未写盘**：`boot_b` 仍是 vk152（kernel sha `b6a074ff…` 读回一致），槽属性 `retry=6 succ=1` 未变；
  `fastboot boot` 结束后按 §5 的方式退回 `boot_b`，设备现运行 vk152（`uname` = `…-vk127…`，42 模块）。
* 设备上**新增**（非破坏性）：`/lib/modules/7.3.0-rc7-…-debug-vk163/`（1539 `.ko`，89 MB，可随时删）与
  `/usr/local/sbin/payload-modules-load.sh`（生产内核上是 no-op，见 §2③）。
* **是否把 vk163 刷进 `boot_b`**：本轮**不做**，属用户决策。收益 = 日常线从此「改驱动不重启」；
  代价 = 日常态多 66 个模块的加载时序（音频/WiFi 在 `/init` 里 load，时序已实测无误，但**尚未做 POR 冷起复现**）。
* 未覆盖：`DRM_MSM`/panel 仍 `=y`（`patches/fragment-modular-video.config` 备着）——显示是 Q28 的敏感面，
  本轮不动；相机已经在 `=m`（vk152 起）。
* 下一步建议顺序：① 用户批准后把 vk163 刷 `boot_b`（先 `--yes` 备份，`slot-attr` 基线已在）→ 真 POR ≥3 发；
  ② 音频真实出声（`speaker-test`/闹钟）与 Waydroid 容器音频复测；③ 把 `mod-loop` 用法写进 `RUNBOOK`；
  ④ 按 M3 把「触屏/背光/触觉」这类纯叶驱动整理成上游可提交的模块化补丁（现在有了热验证通道）。
