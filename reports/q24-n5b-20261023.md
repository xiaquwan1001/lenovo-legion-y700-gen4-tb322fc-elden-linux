## 3. 两次「致死/失效」的签名（本轮最大增量）

### 3.1 run2-R2：`dpms Off` 后 **ADSP/CDSP 双双 fatal → SoC 硬复位**（新签名）

串口死亡窗（`logs/n5b-vk64-20261023-133658.log.round2.serial`，t≈315 s）：

```
[  315.728037][  T177] remoteproc remoteproc1: recovering cdsp
[  316.536801][  T135] qcom_q6v5_pas 6800000.remoteproc: watchdog received: sys_m_smsm.c:322:err fatal notification received from TZ
[  316.537635][  T135] remoteproc remoteproc0: crash detected in adsp: type watchdog
[  316.537713][  T171] remoteproc remoteproc0: recovering adsp
[  316.548085][   T10] ucsi_glink.pmic_glink_ucsi pmic_glink.ucsi.0: failed to send UCSI write request: -5
===== serial closed /dev/ttyACM0 (rc=0) 2026-10-23T13:37:55+08:00 =====
```

- 复位后 `uname` = `7.3.0-rc7-…vk127…`（回落到 boot_b = vk147），`powerlog_hits=0`、`pstore_entries=0` ⇒ **HARD RESET**，符合 Q24 判据。
- **旧口径里没有这条**：此前记录的死前末帧是 `phoc` 使能 `disp_cc_mdss_*` + NoC/BCM 票爆发（`PITFALLS #207/#208`）。本轮首次抓到 **`sys_m_smsm.c:322` 的 TZ fatal 通知 + adsp watchdog 崩溃**，说明「相机栈在位 + 熄屏」时 **ADSP 侧先被判死**，随后才是 SoC 复位。
- 归因层级：**TZ 主动通知**（不是 Linux 侧 panic、不是 PMIC/WDT）。这与 `M7`「复位原因源（AOP/CPUCp/smem scatter）查证」待办直接相关 —— 建议下一轮在 `dpms Off` 前后抓 `smem` scatter / `q6v5` 的 fatal reason，而不是继续在 clk 侧打靶。

### 3.2 14:41-R1/R2：**熄屏后 4–6 s 硬复位**（无末帧 = 真静默复位）

两发都在 `SetActive(true)` 之后第一次读 `dpms` 就拿不到连接器节点（`dpms=<空>`），紧接着 `boot_id` 已变。
即：**死亡窗口 < 6 s**、串口没有任何过渡行（`==> 与 #197「无痕硬复位」一致`）；两发 `powerlog_hits=0`。

- 其中 R1/R2 的判定发生在**唤醒**那一步（`SetActive(false)` 后 4 s 才确认 boot_id 变化）⇒ 与历史口径
  「配对 → 熄屏存活 → 唤醒致死」**一致**；本轮 ADSP TZ fatal 那条（§3.1）则是**熄屏瞬间**就崩。
  ⇒ Q24 至少有**两个相位**：(a) 熄屏瞬间（ADSP 先 fatal）；(b) 熄屏后唤醒（无末帧静默复位）。

### 3.3 run1-R3：**DPU vblank timeout + `reset failure: -22` 风暴 → 设备失去 SSH**（Q28 同族，非 Q24 硬复位）

`logs/n5b-vk64-20261023-132617.log.serial`（t≈95 s）：

```
[drm:dpu_encoder_phys_vid_wait_for_commit_done:550] [dpu error]vblank timeout: 4208c0
[drm:dpu_kms_wait_for_commit_done:531] [dpu error]wait for commit done returned -110
[drm:dpu_encoder_phys_vid_prepare_for_kickoff:576] [dpu error]enc35 intf1 ctl 1 reset failure: -22
```

- 发生在「唤醒（`SetActive false`）」阶段，随后 SSH 不可达；**没有** ADSP fatal、**没有** boot_id 证据（当时脚本丢失了判活窗口）。
- 与 Q28「bonded DSI 命令路径」不同，这是 **DPU/INTF 侧 commit-done 超时 + hw recovery 不完成**，属**唤醒路径**失效。文件里只有串口证据，**不可当 Q24 死亡计入**。

## 4. 脚本缺陷（已修，`scripts/n5b-vk64-death-rate.sh`）

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `ScreenSaver.SetActive(true)` 在**刚开机**的会话里静默 no-op | run1-R1/R5 都是 `dpms On -> On`，被记 `INVALID-NO-BLANK`，**白丢 2 发**（phoc 在但 ScreenSaver 名字还没 own） | 3 次重试（每次 `SetActive false` → 读 `On` → `SetActive true`）+ **`echo off > card0-DSI-1/dpms` 兜底**（同一条 DPMS 路径） |
| 空读数被当成 `INVALID` | run1-R3 `dpms  -> ` 实际是**设备已失去 SSH**，脚本却按「没熄屏」丢弃；14:09 那轮 **4 发真死亡全部被记成 INVALID-NO-BLANK** | **每次读 `dpms` 之后都核 `boot_id`**（不是只在读空时核）；变了 ⇒ DEAD |
| 冷启动早期 `SetActive` 不生效的误判 | 我曾据此加「uptime≥150 s + 6 次就绪探测」，结果把死亡窗口拉长、还额外制造 blank/wake 暴露 | 已撤掉；改回单轮 1 次 blank + 3 次重试（仅当 `boot_id` 未变时才重试） |
| `reboot2 bootloader` 在**刚刚硬复位后 11 s** 就下发 | run2-R3/R4 连续 `SETUP-FAIL`，设备彻底不枚举（见 §5） | **待修**：`boot_vk64` 前要求「uptime ≥ 60 s 且 phoc 在」，否则先等；或改用 `fastboot boot` 前先确认 `slot-retry` 健康 |

### 4.3 第三种「假阴性」：**显示栈已坏的 boot** 被记成 INVALID

15:07–15:30 共 6 发 `INVALID-NO-BLANK`，实测其中至少 4 发是**显示栈坏**而不是 no-op：

- `dmesg | grep -cE 'vblank timeout|reset failure'` = **507**（另一发 15）；
- `phoc` 在但 `gdbus GetActive` **一律 Timeout**；`echo off > .../dpms` ⇒ `Permission denied`（非 DRM master）；
- `reboot2 bootloader` **静默无效**（`boot_id`/`uptime` 均可证未重启）⇒ 显示/glink 异常后 shutdown 挂住；逃生 = `sync; echo b > /proc/sysrq-trigger`（实测 25 s 进 fastboot）。

⇒ 已在脚本里加**显示健康门**（`dpu_err>50` 或 `GetActive` 无响应 ⇒ `SETUP-FAIL` + `force_reboot_vk64`），并把这三种假阴性写进 `PITFALLS #368/#369`。
