## 2. Rob 意见的准确含义

原文（`out/mail-20261111/robh-20261110T1636Z-raw.txt`，行 96–131，逐字）：

```
> 	usb@a600000 {
> 		port-select-gpios = <&tlmm 29 GPIO_ACTIVE_HIGH>;

Use the gpio mux binding.

> 		ports {
> 			port@0 {			/* HS path, connector 0 */
> 				endpoint {
> 					remote-endpoint = <&usb_0_dwc3_hs>;
> 					usb-role-switch;
> 					mux-state = <0>;
> 				};
> 			};
> 			port@1 {			/* Super Speed, QMP PHY */
> 			};
> 			port@2 {			/* HS path, connector 1 */
> 				endpoint {
> 					remote-endpoint = <&usb_1_dwc3_hs>;
> 					usb-role-switch;
> 					mux-state = <1>;
> 				};
> 			};

ports are for separate data streams. Endpoints are for mux'ed data 
streams. This looks like the latter, so port@0 should have 2 endpoints 
and port@2 dropped.

Rob
```

拆成三层，**每层要求的动作不同**：

- **L1（结构性，硬要求）—— ports vs endpoints 的语义**：`ports` 描述的是「控制器身上彼此独立的数据流」
  （= 物理上可以同时存在、互不排斥的多个 bus）。`endpoint` 描述的是「同一条数据流上、经过 mux 之后的可选分支」。
  我方把 GPIO 选通的两个 connector 写成 `port@0` 与 `port@2`，等于声称它们**能同时通电、各自独立跑一套数据流**，
  这与板子事实（同一对 D+/D− 分时复用）矛盾。正确形状：**`port@0` 里放 2 个 endpoint**（`endpoint@0`、`endpoint@1`），
  `port@2` 删掉。
  - 关键点：这正是 `graph.yaml` 原生支持的形状 —— `port-base.patternProperties` 含 `'^endpoint@[0-9a-f]+$'`，
    且 `port-base` 的 description 明写「If there is more than one endpoint node ... then '#address-cells' and
    '#size-cells' are required」（`dtschema/schemas/graph.yaml`，本机副本
    `/home/xuqianhui/.local/opt/dtschema-venv/lib/python3.12/site-packages/dtschema/schemas/graph.yaml:52-73`）。
- **L2（GPIO 表达，硬要求）—— 「Use the gpio mux binding」**：`port-select-gpios` 是我方自造的 vendor 属性，
  把「用一个 GPIO 选两路」重写成私有 binder。上游已有这个模式的标准表达 = **mux-controller / gpio-mux**。
  他的意思不是让我换名字，而是「不要新造属性，用现有 mux 框架」。（具体选哪个 binding 见 §5）
- **L3（不要求的）**：Rob **没有** 对 3/3 的仲裁逻辑、2/3 的 role-switch 查找、或 `dr_mode=otg` 约束提任何意见。
  反对面 = binding 形状 + GPIO 表达。这一点决定了我方 v9 的工作量（见 §1 小结：24 hunk 里只有 3 个真被推翻）。

**Mux state 往哪放？** Rob 删掉 `port@2` 后，我方原来的 `mux-state = <0>/<1>` 需要一个新落点。两条候选：

1. 留在 endpoint 上（`endpoint@0 { mux-state = <0>; }`）—— 属性名无论如何要换成 mux 框架的术语（待核，见 §5）。
2. 完全不放在 dwc3 节点上，由 **gpio-mux 子节点的 `mux-states`/id** 提供顺序，dwc3 用
   `mux_control_select(mux, state)` 选，endpoint 则纯粹用 `remote-endpoint` 表达连接。Rob 的「Use the gpio mux binding」
   指向后者。

## 6. 风险 / 待核 / 需上游确认

### 6.1 真风险（已实证，会卡住 v9 落地）

**R1（高）—— `mux_control_select()` 是一把锁，不是「写个电平」。**

证据：`linux/drivers/mux/core.c:357-393`。它注释明写：
> On successfully selecting the mux-control state, it will be **locked until there is a call to
> mux_control_deselect()**. If the mux-control is already selected when mux_control_select() is called,
> the caller will be **blocked** until mux_control_deselect() ... is called (by someone else).

实现上真的是 `down_killable(&mux->lock)`（core.c:381）+ `up(&mux->lock)`（core.c:497）。
而今天的 `dwc3` 设计（v8 `core.c` hunk 3e）是 **每次模式切换写一次电平、不释放**。
直接替换 ⇒ 第二次 `mux_control_select()` **永久阻塞**（没人 deselect），
且 `__dwc3_set_mode()` 在 `mutex_lock(&dwc->mutex)` 与 `pm_runtime_get_sync()` 区间内（core.c:178-190）——卡在这里会拖死整个 controller 的子设备。

可选解法（需上游确认选哪个，见 6.3 Q1）：

- **(a) select/deselect 配对，mux 锁窗口只覆盖「改选」瞬间**：在 `__dwc3_set_mode()` 里
  `mux_control_select(mux->ctrl, port)` 后立即 `mux_control_deselect(mux->ctrl)`。
  但因为 `deselect()` 会把 state 改回 `idle_state`（core.c:487-498），所以 **DTS 必须不能给
  `idle-state`**（默认 `MUX_IDLE_AS_IS` = -1 ⇒ deselect 不改硬件，正确）。
  这是最小改动，推荐。
- **(b) 不自持 mux，改用 `mux-state` + 单独 `mux-gpios` 并行读取**：不推荐，等于绕开框架。
- **(c) `mux_control_try_select()`**（core.c:434-463）：非阻塞版，但如果被人拿着就直接回 `-EBUSY`，
  两种 connector 争用时会丢掉请求。

**R2（中）—— mux 框架没有「读当前 state」的 API。**

证据：`grep -n "get_state" linux/include/linux/mux/consumer.h linux/drivers/mux/core.c` **无任何命中**；
可用的只有 `mux_control_states()`（core.c:315，返回 state 总数）+ 内部 `mux->cached_state`
（core.c:139/154/180/328/492，不导出）。
而今天 v8 在 `drd.c:613` 用 `gpiod_get_value_cansleep(select)` **读回初始电平** 作为 `desired_port`，
这个能力用 mux 框架 **不可实现**。

影响：`dwc3_setup_role_mux()` 里的 `mux->desired_port = ret;`（drd.c:621）没有对应写法。
处理方案（推荐）：初始 `desired_port = -1`（表示「未知」），并在第一次 `__dwc3_set_mode()`
无条件 select 一次（因为 `port_switch = mux_port != mux->active_port` 且初始 `active_port = -1`，天然成立）。
**这意味着 v9 放弃「开机读回实际电平」这个 feature** —— 但如果同时仍要 `mux-state` 表达每 connector 对应哪个电平，
那就要靠 DTS 里两个 endpoint 的 `mux-state` 互斥校验，而不是靠读回。

**R3（中）—— `mux-state` 作为自定义属性名仍然是我方造的。**

今天的 `mux-state` 属性是 v8 自己定义的（`snps,dwc3-common.yaml:28-34`），而 mux 框架里
`mux-states` 是**消费者属性名**（`mux-consumer.yaml:60-62`）、**不是** endpoint 属性。
因此走 gpio-mux 后，「哪个 connector 对应 level 0/1」这件事有两条不同表达，必须二选一：

1. **靠 gpio-mux 的 state 编号**（推荐，最符合 Rob）：endpoint 只写 `remote-endpoint` + `usb-role-switch`，
   level 由 `mux->ports[i]` 的 **下标** 决定（下标 = gpio-mux 的 state）。这样 `mux-state` 属性**完全消失**，
   binding 更简洁，但需要 dts 里 endpoint 顺序与 GPIO 电平的对应关系成为隐含约定（靠 label 命名/注释说明）。
2. **保留 endpoint 上的 `mux-state`**（保留 v8 的显式性）：但属性名应该在 `mux-consumer` 术语体系下重命名，
   或至少加说明「it is the same state space as the mux controller」。需上游确认能不能留。

**R4（低）—— `gpio29` 的 `bias-pull-down`（`sm8750-lenovo-elden.dts:2204`）与 `idle-state` 的交互。**
今天靠 `bias-pull-down` + 上电默认低电平保证「未初始化时默认走 connector 0」。
若走了 mux 框架且 DTS 不写 `idle-state`（= `MUX_IDLE_AS_IS`），行为与今天等价；
若写了 `idle-state = <0>`，则每次 `deselect()` 都会回 0 —— 这反而可能是想要的（见 R1(a) 反面）。
**待核**：到底该不该写 `idle-state`。（本报告 §4.1 片段里写了 `idle-state = <0>`，与此处 (a) 方案矛盾，此项**未定**，需上游确认后再定稿）
