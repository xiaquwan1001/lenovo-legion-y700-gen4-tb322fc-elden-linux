# UEFI p37：真启动一发 + `posteb` 缺失的物理解释（2026-11-07）

> 线：G1-29（UEFI 间接引导）。承接 `reports/uefi-p34-p36-logfs-20261106.md` §5 的 p37。
> 本轮 = **1 发零写盘 `fastboot boot`**，无新构建（件 = p36 preamble，sha `bf559e97…`，67 219 456 B）。
> 记录：`reports/trials/20261107T022330Z-uefi-p37-posteb-probe.json`。

---

## 0. 一句话结论

**p37 拿到了 `preeb`、拿不到 `posteb`，而且这次不是"证据被冲走"而是"它就崩在那儿"**：
崩点 = `BootLinux` 内一次 `gBS->AllocatePool` 调用 **branch 到地址 0**（`pc=0`，`esr=86000007` = 指令异常/翻译 fault level 3），
`gBS` 由 `0x43a10` 全局取到、成员偏移 `+0x40`（= `EFI_BOOT_SERVICES.AllocatePool`）**取出来是 0**
⇒ 最自然的解释是**该调用发生在 `ExitBootServices` 之后**（EB 后 `gBS` 已失效），即"EB 之后立刻死"，
与 `reports/uefi-onboard-walkthrough-20261106.md` 里「崩在 LinuxLoader」是**同一处**，现在**精确到指令与符号**。

## 2. logfs 里到底有什么

```
SBLOG01 tag=preeb len=8192
...（[I] base/size 模块装载表 + [F] 帧缓冲几何自检，满 8 KiB 环形内容）
[K] dtb=B4063000 m=EDFE0DD0 sz=259D2 k=A8080000      <- 末条
```

- `tag=entry` **0 条**、`tag=posteb` **0 条**（全盘 `grep -a` 计数）。
- `m=EDFE0DD0` = FDT 魔数 `0xd00dfeed`（小端）**正确**；`sz=0x259D2` = **154 066 B**，与板 DTB 量级一致；
  `k=A8080000` = 内核装载地址。
  ⇒ 交接参数在这一层**没有可指摘之处**（p36 §5 的"若 posteb 在 ⇒ 查交接参数"分支不成立）。
- `preeb` 记录里的 `[I] ? base=… size=…` 是本轮的**关键新数据**：完整模块装载表（24 条）。

## 3. 崩溃归因（静态可复算）

1. 屏上 `x30 = 0xCFCD2B28`；模块装载表里 `base=0xCFCCE000 size=0x46000` ⇒ 命中区间 `[0xCFCCE000, 0xCFD14000)`。
2. 该 `size` 与构建产物 PE `SizeOfImage` 逐一对表：**唯一命中 0x46000 的是 `LinuxLoader.efi`**
   （`build/uefi-woa-prep/repos/7-mu-lenovo/Build/PakalaPkg/RELEASE_CLANGPDB/AARCH64/QcomModulePkg/Application/LinuxLoader/LinuxLoader/DEBUG/LinuxLoader.efi`，286 720 B）。
   ⇒ `LR = LinuxLoader + 0x4B28`。
3. `LinuxLoader.map`：`0x4A88` 起的 LTO 合并块首个符号 = `BootLinux` ⇒ **`BootLinux + 0xA0`**。
4. 反汇编该地址（`llvm-objdump -d LinuxLoader.efi`）：

```
4b28: adrp x8, 0x43000
4b30: ldr  x8, [x8, #0xa10]   ; x8 = gBS（map: 0x43A10 = gBS）
4b44: ldr  x8, [x8, #0x40]    ; EFI_BOOT_SERVICES + 0x40 = AllocatePool
4b50: blr  x8                 ; ⇐ 跳出后 pc=0
```

5. `pc=0` + `esr=86000007`（EC=0x21 指令异常 from lower EL，IFSC=0x07 = translation fault level 3）= **`blr` 到 0**，
   与"`gBS->AllocatePool` 读出 NULL"完全一致。
6. `[K] dtb=…` 标记在源码里紧贴 `SB_STOP(40)`（该处注释：**"全流程最后一个有 gBS 的点"**），
   而 `posteb` 转储在 `ShutdownUefiBootServices()` 之后 ⇒ **崩点落在"最后用 gBS"与"EB 后转储"之间**。

**判读**：EB 路径已经走进去（否则 `gBS` 应有效），但 `gBS` 在 EB 之后被 DxeCore 失效，
而 LinuxLoader 里仍有一次 `gBS->AllocatePool`（要么在 `ShutdownUefiBootServices()` 尾部，要么在 EB 返回后的清理路径）。
⇒ 与 p36 的「USB redriver/I2C NACK」**无因果**（那条是 USB 栈的噪声），也与 QUP 句柄线false 关联。
遗留不确定（诚实标注）：`LR` 落在 `BootLinux` 块首 +0xA0 与本轮"源码行 1182 才打 `[K]`"存在矛盾，
最可能原因是 **LTO 把该函数拆成冷/热两段**，`0x4A88` 是冷段的段首（map 只给到块级符号）。
⇒ p38 用**打印**判别，不再靠静态推断（见 §4）。

## 4. 下一步（p38，主机侧 ~1 h + 上机 1–2 发）

1. **在 EB 前后各插一条无 gBS 依赖的标记**（直接 `SerialPortWrite` + ring）：
   - `SbMark("preEB-call")` 紧贴 `gBS->ExitBootServices()` 调用之前；
   - `SbMark("postEB-ret")` 紧接返回之后（**紧接着就 dump ring 到 logfs**，不等后续流程）；
   - 若 `postEB-ret` 都不出现 ⇒ 崩在 `gBS->ExitBootServices()` 调用自身（则打印 `gBS`/`gBS->ExitBootServices` 两个值再试）。
2. **打印 `gBS` 与两个成员**（`AllocatePool` / `ExitBootServices`）在 [K] 之后、EB 之前：
   判据 = 若 `gBS` 已为 0 或成员为 0 ⇒ 说明**EB 在这条路径上被更早的调用做过**（例如 `LoadImage` 里某个 path）；
   若均非 0 而 `blr` 后 pc=0 ⇒ 说明是**另一个** `blr` 目标为 0（则需在 `blr` 前打 `%lx` 双保险）。
3. 通道侧：**这一轮之后不再用 `oem sbread`**（一读就打死 USB，且已确认是 USB 栈自身问题）——
   一律走 `dd` 读 `logfs`（断电重启后 1 条命令，`scripts/uefi-logfs-read.py` 的 offset 口径需同步改成 `skip=8372224 bs=1`）。
4. 止损：p37 之后**再 3 发无实质进展即收口**（沿用 §7 既有线；本轮已用掉 1 发）。
