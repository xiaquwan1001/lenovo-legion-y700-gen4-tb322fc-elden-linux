## 2. 关键取证手法（本轮新增，可复用）

`fastboot fetch` 在本机不可用，所以 ESP 走**EDL 分块读 + 本地 FAT 解析**：

```bash
# eldenesp = LUN0 第 17 项（first LBA 123609088，4096 B 扇区）；用 --lun=0！用 --lun=4 会读到别的数据（本轮踩过）
cd ~/edl/bkerler-edl
L=~/下载/tb322fc/xbl_s_devprg_ns.melf
for i in $(seq 0 15); do   # 16 × 32 MiB = 512 MiB；单发 512 MiB 一次读会让设备失联（见 §5）
  python3 edl.py --loader=$L rs $((123609088+i*8192)) 8192 --lun=0 /tmp/esp-chunk.bin || break
  cat /tmp/esp-chunk.bin >> /tmp/esp-full.bin
done
```
再用 python 按 BPB 解析 FAT32（`bps=4096`，data 起始 = `(rsvd+nfat*fatsz)*bps`）读目录项/簇链即可。

`logfs` 这次**无判读价值**：三次读回 md5 全相同（`0e9778ae…`），与 `PITFALLS #602`（最近的启动根本不写 logfs）一致。

1. **镜像坏了** → `boot_b` 与非零的好件逐字节相同；`boot_a` 是 `ANDROID!` 头（自研件，非原厂）。

3. **AVB / vbmeta** → 全程 `orange` 态，`vbmeta_b` 公钥拒绝是解锁常态（`#484` §8.3 已证）。

   （但 ESP 只剩 **1.2 MiB 空余**（318/131072 个簇），且 `EFI/BOOT` 里堆了 **28 个 `.bak`**（最大 9.5 MB），

## 8. EDL 工具侧的既往缺陷 + 本轮用第二把尺子复核（2026-11-16 22:xx）

> 触发：用户提示「也可能是 edl 工具本身有逻辑缺陷」。既往资料在 `reports/edl-toolchain-survey-20261101.md`
> 与技能 `qualcomm-edl-flashing`，本轮**新增两条实测**并换了工具做正控。

### 8.1 既往已知缺陷（已登记，别当新发现）

| 工具 | 缺陷 | 出处 |
|---|---|---|
| bkerler `edl.py` | `cmd_program()` 在设备**拒绝** `<program>` 时仍返回 True；`getlunsize()` `TypeError`；`skipresponse` 让 qfil 每隔一张镜像失败 ⇒ **写路径不可依赖**（issue #808/#809/#810，自 2026-08 零处理） | `reports/edl-toolchain-survey-20261101.md` §2、§4.5（结论「bkerler 仅保留 loader/Diag 用途」） |
| bkerler `edl.py` | `qfil` **静默只写一部分分区**却退出 0（TB321FU 两次实测）；`gpt <dir>` 会打印成功但**一个字节都不写** | 技能 `qualcomm-edl-flashing` §Pitfalls |
| bkerler `edl.py` | `rs/ws` 的 LBA 单位 = **4096 B**（不是 512），默认按 512 心算就会读错位置；`edl-ng` 同类问题（issue #25 忽略 storage info / 默认扇区大小错） | 技能 §Pitfalls、survey §2 |
| 共性 | **写后无校验**（qdl 有设备端 `sha256` / `--skipblock=sha256`）⇒ 项目纪律 = 每次写都 EDL 读回比 sha | survey §2、§3 |

### 8.2 本轮新增两条（都指向工具/用法，不指向设备）

1. **单次读 512 MiB 分区不可靠**：`edl.py r eldenesp` 两次都**没有产出**（一次 600 s 超时无文件、一次连接被中断），
   改成 **16 × 32 MiB 分块**（`rs <LBA> 8192 --lun=0`）一轮跑完 512 MiB。⇒ 大块读必须分块；
   `edl.py` 没有 `--out-chunk-size` 之类开关，**qdl 有 `-u/--out-chunk-size`**。
2. **`--lun` 用错不会报错**：我第一次拿 `--lun=4` 去读 `eldenesp`（它其实属 **LUN0**，
   LBA `123609088`）⇒ 读回的是 LUN4 上某处的 XML 头 4 KiB，**工具不报任何告警**。
   正确定位 = `printgpt` 里看分区属哪个 LUN 表（LUN0 表里 `eldenesp first=123609088`）。
   这条是「工具静默给错数据」的真实案例，与技能里 `#LBA 单位`、`gpt 静默不写` 同族。

### 8.3 第二把尺子：`qdl` 在设备端算摘要（推荐固化成默认动作）

```bash
cd ~/edl && ./qdl/build/qdl -R -s ufs ~/下载/tb322fc/xbl_s_devprg_ns.melf sha256 4/321824+24576
# → 06c081ca4af94915339bf02a0209dbe374fe5cd7111c29588e7de8773807dc8b   （= bootslot-b/boot_b.img）
```

`sha256 <lun>/<lba>+<sectors>` 让**设备端**算摘要，**不经 USB 传数据** ⇒ 既绕开「大块读」这一类
传输侧问题，又比「读回再本地 hash」强（后者只证明传输一致，不证明 flash 内容一致）。
本轮结果 = **`boot_b` 内容与主机件一致，由第二个独立工具（qdl，非 edl.py）确认**。
同时 `edl.py r boot_b` 三次独立读 sha 完全相同 ⇒ 读路径本身也没坏
⇒ §1 的「镜像内容清白」不再依赖单一工具。

### 8.4 落到纪律（下次开 9008 窗口时照做）

1. **默认用 `~/edl/qdl/build/qdl`**（tag v2.9）做读/校验：`read`、`sha256`、`-u` 分块、`--dry-run`；
   `edl.py` 只留给 loader/Sahara 与 GPT 小写（survey §4.5 的原结论）。
2. 分区寻址前先 `printgpt` 确认**属哪个 LUN** + 用 4096 B 块算 LBA；对不上就停下（工具不会替你报错）。
3. 任何 `w`/`ws` 之后：`qdl sha256` 或读回比 sha，**不信任退出码**。
4. 大块传输一律分块（≤32 MiB/发），失败按技能里的「幂等标记 + 一次断电一格」处理。
