## 2. 12 条 finding 逐条静态核实（文件行号以 `build/m3v5` 现行内容为准）

### 2.1 [High] `dwc->lock` 递归自死锁 —— **已证实（确定性）**

- `drivers/usb/dwc3/drd.c:557` `spin_lock_irqsave(&dwc->lock, flags);`
- `drivers/usb/dwc3/drd.c:574` `dwc3_set_mode(dwc, dwc3_role_mux_mode(dwc, selected_role));`（**仍在锁内**）
- `drivers/usb/dwc3/core.c:317-330` `dwc3_set_mode()` 内 `core.c:322` **再次** `spin_lock_irqsave(&dwc->lock, …)`
- 锁类型：`drivers/usb/dwc3/core.h:1252` `spinlock_t lock;`（非递归；RT 内核下为 rtmutex，同样不自递归）

⇒ **第一次任何一路角色切换就会自旋死锁（IRQ 已关，硬锁死）**。
解析：v3 的 sashiko 曾要求「`desired_port` 与 `desired_dr_role` 放进同一临界区」（`reports/mail-triage-20261019.md:226` ②），
v4 用「持 `dwc->lock` 调 `dwc3_set_mode()`」实现该要求 —— **修 A 引出 B**：正确做法是用 `mux->lock` 保证配对，
`dwc->lock` 只保护单字段。

### 2.2 [High] 合规 DT 走不到 mux 初始化（`role mux unreachable`）—— **已证实（确定性）**

三处 gate 都只看**控制器节点**的 `usb-role-switch`：

| 位置 | 代码 | 后果（无控制器级 `usb-role-switch` 时） |
|---|---|---|
| `core.c:94-98` | `if (mode == USB_DR_MODE_OTG && !dwc->edev && (!IS_ENABLED(USB_ROLE_SWITCH) \|\| !device_property_read_bool(dwc->dev, "usb-role-switch")) && !DWC3_VER_IS_PRIOR(DWC3, 330A)) mode = USB_DR_MODE_PERIPHERAL;` | `dr_mode` 被强改 **PERIPHERAL** |
| `core.c:2058-2060` | `dwc3_get_extcon()` 同属性判定 | 不走 role-switch 分支（无 edev 时仍会往下找 phy 的 extcon） |
| `drd.c:766-768` | `if (ROLE_SWITCH && device_property_read_bool(dwc->dev, "usb-role-switch")) return dwc3_setup_role_switch(dwc);` | `dwc3_role_mux_init()` **永不被调用** |

而 v4 binding（`patches/upstream/m3-v4-20261026/0001-…patch`，`allOf` 第二块）在 `port-select-gpios` 存在时只
`required: [dr_mode, ports]` + 端点级 `usb-role-switch`，**未要求控制器级 `usb-role-switch`**。
⇒ 「过 `dtbs_check` 的 DT」与「驱动真正走 mux 路径的 DT」**不是同一个集合**。
（1/3 的 3×Medium 第 3 条与 3/3 的第 2 条 High 是同一根因的两面。）

本机板 DTS 不在 `build/m3v5` 中（该树只含 3 枚上游补丁），故**无法在主机侧验证实际板级 DT 走哪一支**；
`arch/arm64/boot/dts/qcom/sm8750.dtsi:2917` 的 `usb-role-switch;` 在 `usb@a600000` 节点内 ⇒ **v2/v3 形状下可用**，
但那是「靠板子多加一条属性掩盖 binding 缺口」，上游 review 必然追问。

### 2.3 [High] 注册早于初始模式请求（init race）+ 错误路径缺 mode 清理 —— **已证实（机制/窗口）**

- `drd.c:685` `usb_role_switch_register()`（两路循环）→ `drd.c:698` `dwc3_set_mode(dwc, mode)`（初始默认角色）
- `core.c:322-327`：`desired_dr_role = mode` 是**单字段覆盖**、无版本号/队列
  ⇒ 若连接器驱动在 685 与 698 之间调用 `set()`（`dwc3_mux_role_set` → `dwc3_set_mode(请求角色)`），
  698 会把它**静默改回默认角色**，而 `port->role` 仍是请求值（状态机分叉）。
- 错误路径：`drd.c:703-705` `dwc3_role_mux_exit(dwc); dwc->role_mux = NULL; cancel_work_sync(...)`
  —— **先清指针再取消 work**，与 `__dwc3_set_mode()` 竞争（`core.c:169` 已缓存 `mux` 指针，无 UAF，但会与 teardown 交错）。
- 若 `__dwc3_set_mode()` 已跑过 `dwc3_host_init()`/`dwc3_gadget_init()` 而 probe 随后失败：
  `core.c:2451-2457` 的 `err_exit_debugfs` **不调用 `dwc3_core_exit_mode()`** ⇒ xHCI/gadget 留在注册态。
- 「谁会在 685 与 698 之间调用 `set()`」：`usb_role_switch_register()` 完成后设备即可被
  `class_find_device_by_fwnode()` 命中（`class.c:113-114`），并行的 TCPC/connector 驱动 probe 即可 `set()`；
  时序竞争**成立**，但**本轮未构造运行期复现**（无设备、无 KASAN/lockdep 样本）。

### 2.4 [High] 同角色换端口时 SUSPHY 未清 —— **机制已证实；硬件后果未证**

- `core.c:189-193`：early-out 只在 `role 相同 && port 相同` 时跳过 ⇒ 同角色换端口**会**进入 teardown 路径。
- teardown：`core.c:200-212` 调 `dwc3_host_exit()` / `dwc3_gadget_exit()`；
  `dwc3/host.c:231`、`dwc3/gadget.c:4981` 各自 `dwc3_enable_susphy(dwc, true)`（置 SUSPENDENABLE/SUSPHY）。
- 随后 `core.c:241-265` 软复位 + `core.c:265` `dwc3_set_prtcap(dwc, desired_dr_role, false)`；
  但 `core.c:152-155`：`if (DWC3_GCTL_PRTCAP(reg) != mode) dwc3_enable_susphy(dwc, false);`
  ⇒ **同角色时 PRTCAP 未变 ⇒ 不清 SUSPHY**，接着 `dwc3_gadget_init()`/`dwc3_host_init()` 在 SUSPHY 使能下重初始化。
- 代码注释自身（`core.c:147-151`）写明 DRD 切模式期间这两位置须清零 ⇒ **代码内不一致成立**。
- 「是否真会 PHY 时钟同步 / `DCTL.CSFTRST` 超时」属硬件行为，**本轮无设备证据，记为未证**。

### 2.5 [High] `dwc3_mux_role_get()` 隐藏非活动端的待处理角色 —— **已证实（状态机缺陷）**

- `drd.c:595-598`：`if (mux->active_port == port->state) role = port->role;` 否则恒 `USB_ROLE_NONE`。
- 触发链（sashiko 原例）：port0 活动 → port1 请求角色（`ports[1].role/seq` 已置）→ port1 先拔线。
  连接器驱动（例 `drivers/usb/typec/tipd/core.c` 的 `cd321x_update_work()`）先 `get_role()` 得 `NONE`
  ⇒ **不会**发 `set_role(NONE)` ⇒ `ports[1].role` 永留。
- 之后 port0 断开时 `dwc3_role_mux_pick()`（`drd.c:508-525`）会把数据路径选给**已拔线**的 port1，
  并使后续 port0 连接被 seq 排序压制 ⇒ **饥饿**。
- `usb_role_switch_set_role()`（`class.c:70-92`）在 `set()` 返回非 0 时**不缓存** `sw->role`，与本条叠加放大不一致。

### 2.6 [Medium] `fwnode_handle` 泄漏 —— **已证实（确定性）**

- `drd.c:667` `mux->ports[state].fwnode = fwnode_handle_get(ep);`
- `drd.c:671-676`：校验循环（缺端口 → `-EINVAL`）与 `dwc->role_mux = mux;` **之间**存在窗口；
- `drd.c:702-705` 错误路径 `dwc3_role_mux_exit(dwc)` 在 `drd.c:607-611` **先判 `dwc->role_mux`**，
  此时仍为 `NULL` ⇒ 直接 return ⇒ **已 `get` 的引用全部泄漏**（`err_put_ep` 只还当前 `ep`）。
- 亦包括 `drd.c:658-662`（`mux-state` 读取失败 / 越界 / 重复）两条 `goto err_put_ep` 路径。

### 2.7 [Medium] `mux->error` 上报错误且竞态 —— **已证实**

- 写：`core.c:241-243` `WRITE_ONCE(mux->error, ret)`（**不持任何锁**）；清：`drd.c:575-576` 在 `dwc->lock` 内读清。
- 单字段被两路共享：port0 的 GPIO 失败会报给**下一个调用 `set()` 的 port1**。
- 语义错：`drd.c:571-577` 已把新请求的状态与 `dwc3_set_mode()` 提交完毕，再把**上一次**的错误当返回值，
  `usb_role_switch_set_role()`（`class.c:83-88`）会认为**本次**切换失败且不更新 `sw->role`。

### 2.8 [Medium] 缺 `dwc3_pre_set_role()` —— **已证实**

- 单连接器路径：`drd.c:443`、`drd.c:472` 都在 `dwc3_set_mode()` 之前调 `dwc3_pre_set_role(dwc, role)`。
- mux 路径 `drd.c:555-580` **完全没有**该调用。
- glue 侧：`core.h:1704-1708` → `glue_ops->pre_set_role`；`dwc3-qcom.c:605-608` 注册 `dwc3_qcom_set_role_notifier`
  （其内 `pm_runtime_resume_and_get()`）⇒ **必须在 `dwc->lock` 外调用**，正与 §2.1 的死锁区冲突。

### 2.9 2/3 [High] `!IS_ERR_OR_NULL(sw)` 吞掉 `-EPROBE_DEFER` —— **已证实（确定性）**

- `class.c:104-115` `usb_role_switch_match()`：属性缺失 → `NULL`；属性在但设备未注册 → `ERR_PTR(-EPROBE_DEFER)`。
- `class.c:187` `if (!IS_ERR_OR_NULL(sw)) { … return sw; }` ⇒ `-EPROBE_DEFER` 被当作「没找到」继续扫描，
  函数末尾 `return NULL`（`class.c:190`）⇒ 上层 `usb_role_switch_get()`/`fwnode_usb_role_switch_get()`
  （`class.c:203-215`、`232-244`）退化成 connection 匹配，最终**返回 NULL 而非 defer** ⇒ 消费者把 role-switch 当「不存在」。
- 修法就是把该判定改成 `if (sw)`（ERR_PTR 为真 ⇒ 原样上抛）。

### 2.10 1/3 三条 Medium（binding）—— **代码/schema 层证实；仅 1 条做了实测**

1. **`port@0` 的端点校验面变窄**：`$defs/hs-port`（v4 0001 patch 内 `$ref: /schemas/graph.yaml#/$defs/port-base`）
   只对 `^endpoint@[01]$` 套 `$defs/hs-endpoint`；原 `/schemas/graph.yaml#/properties/port` 会对
   `^endpoint(@[0-9a-f]+)?$` 套 `endpoint`（含 `unevaluatedProperties: false`）⇒
   **无编号 `endpoint` 与 `endpoint@2+` 失去 `unevaluatedProperties: false`**；`else` 分支也只禁 `endpoint@[01]` 上的两属性。
   *本轮未构造该反例 DTB，仅按 schema 结构推定。*
2. **then 分支未要求控制器级 `usb-role-switch`**：与 §2.2 同根因（代码已实证 gate 在该属性上）。
3. **`mux-state` 互斥漏洞**：两个 `if` 都只测 `const: 0` ⇒ 只拒绝「双双为 0」，
