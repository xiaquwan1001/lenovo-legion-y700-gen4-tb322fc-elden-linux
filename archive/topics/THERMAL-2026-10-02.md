# THERMAL-2026-10-02.md — SM8750 (TB322FC/elden) 温控重标定 + GPU cooling + 监控守护

承接 `.pi/missions/thermal.md`（task-13）。**一句话结论**：把每 CPU/GPU 热区从
「105 °C 单点 passive」改成 **70/82/90/105 °C 四级、递增 cdev state**；
同样 CPU 8 线程 + GPU 压测下，CPU 稳态由事故的 **93–103 °C** 降到 **80–82 °C**（峰值 82），
GPU ≤66 °C / DDR ≤64 °C / 电池 ≤38 °C，频率无剧烈抖动。GPU cooling 原已绑定，本次补齐分级。

## 1. 现状盘点（只读，实测）

### 1.1 CPU/GPU 频点与 cooling device

| 资源 | driver | 频点表 | cdev | max_state |
|---|---|---|---|---|
| policy0（6×性能核 cpu0-5） | `scmi` | 16 档，最高 3 532 800 kHz | `cooling_device0` = `cpufreq-cpu0` | 15 |
| policy6（2×prime cpu6-7） | `scmi` | EM 16 档（可用 ≤4 089 600；boost 4 204 800/4 320 000） | `cooling_device1` = `cpufreq-cpu6` | 15 |
| GPU `3d00000.gpu` | `devfreq` | 14 档（160 MHz … 1100 MHz） | `cooling_device2` = `devfreq-3d00000.gpu` | 13 |
| WiFi | `ath12k_thermal` | — | `cooling_device3` | 100 |

**关键点**：state↔freq 映射为 `idx = max_state - state`（`cpufreq_cooling.c` / `devfreq_cooling.c`），
且冷却设备用的是 **Energy Model 表**（不是 `scaling_available_frequencies`）。cpu6 的 EM 有 16 档
（含未开放的 4.2/4.32 GHz），因此两个 CPU cluster 的 state **不能照搬**——本补丁按各自 EM 表分别标定（§2.2）。

### 1.2 改动前 DTS（`geelong…`→ 实际文件见 §2.1）

`sm8750-lenovo-elden.dts` 里 24 个热区（12×cpu-0-*、4×cpu-1-*、8×gpuss-*）各只有一个：

```
passive { temperature = <105000>; hysteresis = <5000>; };
cooling-maps { map0 { trip = <…>; cooling-device = <&cpu0/cpu6/gpu THERMAL_NO_LIMIT THERMAL_NO_LIMIT>; }; };
```

`hot`=120 °C、`critical`=125 °C 定义在 `sm8750.dtsi`，未改动。

### 1.3 热区全景（55 个）

CPU 16 + cpuss 4 + gpuss 8 + aoss 4 + modem 4 + camera 2 + video 1 + ddr 1 + nsphvx/mx 7 +
PMIC 8 + `qcom-battmgr-bat`。除 CPU/GPU/WiFi 外**均无 cooling device**。

### 2.2 四级 trip 与 state 标定

| trip | 语义 | policy0 (max 3.5328 GHz) | policy6 (max 4.0896 GHz) | GPU (max 1.1 GHz) |
|---|---|---|---|---|
| 70 °C | 轻度 | state **5** → 2 400 000 (68 %) | state **7** → 2 841 600 (69 %) | state **5** → 734 MHz (67 %) |
| 82 °C | 中度 | state **8** → 1 785 600 (51 %) | state **11** → 1 958 400 (48 %) | state **8** → 525 MHz (48 %) |
| 90 °C | 重度 | state **10** → 1 363 200 (39 %) | state **13** → 1 401 600 (34 %) | state **10** → 389 MHz (35 %) |
| 105 °C | 兜底 | state **15** → 384 000 | state **15** → 1 017 600 | state **13** → 160 MHz |

- 70/82/90 用 `hysteresis = <3000>`，105 用 `<5000>`；`polling-delay-passive = <100>`。
- 每个热区的 4 个 `mapN` 都绑本域 cdev；`cooling-device = <&cdev S S>`（lower=upper=S，即该级定点限频）。
  同一 cdev 的多级实例由 thermal core 取 **最大 state** 聚合，升温逐级加深、降温逐级释放。
- GPU 热区（8×`gpuss*`）同样四份 map → `&gpu`。

## 3. 验证

### 3.1 state → freq 直接实测（逐档写 `cooling_device*/cur_state` 后读回，再复位）

```
cpu0 : state 0->3532800  5->2400000  8->1785600  10->1363200  15->384000
cpu6 : state 0->4089600  7->2841600 11->1958400  13->1401600  15->1017600
gpu  : state 0->1100MHz  5->734MHz   8->525MHz   10->389MHz   13->160MHz
```

全部与设计一致，测试后 cdev 复位到 0、max_freq 复原。

### 3.2 压测 #1：CPU 满载 + GPU（`out/thermal/run1.log`）

- 命令：`DURATION=360 INTERVAL=2 /root/thermal/thermal-stress.sh`（`stress-ng --cpu 8 matrixprod` + `es2gears_wayland`×1）
- 期间 load avg ≈ 9.5，全程 `thermal-watch` 2 s 采样，175 个样本。

| 指标 | 结果 |
|---|---|
| 峰值 CPU | **82 °C** |
| 稳态（触发限频的 119 个样本） | 均值 **80.8 °C**，min 80，max 82 |
| 峰值 GPU / DDR / 电池 | 66 / 64 / 38 °C |
| cdev0（性能核）state 分布 | state5 ×79（2400 MHz）、state8 ×40（1785 MHz） |
| cdev1（prime）state 分布 | state7 ×6（2841 MHz）、state11 ×113（1958 MHz） |
| GPU cdev2 | 全程 state0（66 °C 未达 70 °C 阈值） |

逐分钟摘要：

```
min   n   cpu_max cpu_mean gpu_max ddr p0max p6max  states
11:18 22    81     80.7     66     64  2400  2841   cpu0@[5,8] cpu6@[7,11]
11:19 21    81     80.9     66     64  2400  2841   cpu0@[5,8] cpu6@[7,11]
11:20 22    81     80.8     66     64  2400  1958   cpu0@[5,8] cpu6@[11]
11:21 21    81     80.3     66     64  2400  1958   cpu0@[5,8] cpu6@[11]
11:22 22    81     80.5     66     64  2400  1958   cpu0@[5,8] cpu6@[11]
11:23(末)    82     77.5     66     64  ——（负载收尾，状态释放）
```

**结论**：70 °C 与 82 °C 两级已在真实负载中触发并稳定住温度；90/105 两级在本次环境（室内环境温度、
Limits 已达动态平衡 82 °C）未被触发——属于兜底档，其限频能力已由 §3.1 逐档验证。

### 3.3 压测 #2：GPU 定向（`out/thermal/gpu.log`）

`CPUS=1 GPU_N=3 DURATION=150`：CPU 峰值 70 °C（触发 cpu0@5/cpu6@7），**GPU 峰值仅 56 °C**。
`es2gears_wayland` 负载太轻，未能在合理时间内把 GPU 推到 70 °C。GPU cooling 的**绑定与分级**已由
§3.1 直接映射验证；实机热触发需更重的 GPU 负载（如游戏/glmark2，Alpine 源无 glmark2）。

## 4. 其余热点评估

| 热区 | 空闲 | 压测峰值 | cooling device | 结论 |
|---|---|---|---|---|
| `ddr-thermal` | ~43 °C | 64 °C | 无 | DDR 无独立降温手段，且它是「被动受热」；CPU/GPU 降频时同步回落。**不另加 trip**，纳入监控。 |
| `qcom-battmgr-bat` | ~33 °C | 38 °C | 无 | 电池无 cdev；充电热由 PMIC/充电器硬保护 + 既有 `scripts/charge-ctl.sh`（`input_current_limit`/`charge_control_end_threshold`）管理。**监控**。 |
| `pm8550*`/`pmih0108` | 37 °C | 37 °C | 无 | PMIC 自带 95/115 °C 报警 trip（`sm8750-pmics.dtsi`），**不动**。 |
| `modem0-3`/`camera0-1`/`video`/`aoss*`/`nsphvx/mx` | 41–46 °C | 64 °C | 无 | 桌面/无 modem 场景非热源；继承 120/125 °C hot/critical。**监控**。 |

未新增这些热区的 passive trip：它们没有可用的 cooling device，加 trip 也只能挂到 CPU/GPU cdev，
会与 CPU/GPU 自身热区重复触发，反而造成过度降频。

## 5. 用户态监控守护

### 5.1 `scripts/thermal-watch.sh`

- 周期采样所有 `thermal_zone*/temp` + CPU/GPU `scaling_cur_freq`/`scaling_max_freq` + 非零 cdev state；
  落日志 `/var/log/thermal-watch.log`，按 `INFO/WARN/ALERT` 分级。
- 可选 `AUTO_FALLBACK=1`：超 `ALERT` 自动写 `scaling_max_freq` 兜底，回落 `WARN-5` 后恢复原值（默认关，
  内核分级限频已足够）。
- 环境变量：`INTERVAL`(5s)、`LOG`、`WARN`(80)、`ALERT`(92)、`AUTO_FALLBACK`、`FALLBACK_CPU0_KHZ`/`FALLBACK_CPU6_KHZ`。

```bash
# 设备上手动运行
scp scripts/thermal-watch.sh root@192.168.7.1:/root/thermal/
ssh root@192.168.7.1 'INTERVAL=2 /root/thermal/thermal-watch.sh'          # 前台
ssh root@192.168.7.1 'nohup /root/thermal/thermal-watch.sh >/dev/null 2>&1 &'   # 后台
ssh root@192.168.7.1 'tail -f /var/log/thermal-watch.log'                  # 查看
```

> 设备曾实测的一个坑：`/tmp` 在重启后清空 → 脚本建议放持久根 `/root/thermal/`。

### 5.2 开机自启（可选，未固化）

设备是自研 `/init`（非 systemd/OpenRC 服务链），最稳妥是在 `/init` 启动桌面后追加一行后台：
`nohup /root/thermal/thermal-watch.sh >/dev/null 2>&1 &`（需重编 ramdisk 才生效，本次未做）。
`/etc/local.d/` 存在但未接入自研 `/init`，故未使用。压测时手动起即可。

### 5.3 `scripts/thermal-stress.sh`

一次性 CPU+GPU 压测驱动：`DURATION`(420s)、`CPUS`(nproc)、`GPU_N`(1)、`INTERVAL`(2s)、`LOG`。

## 7. 遗留 / 风险

1. **90 / 105 °C 档未在实机压测中触发**（82 °C 档已达平衡），仅经 state→freq 逐档验证；更高环境温度
   或更重 GPU+CPU 混合负载下才会用到。
2. **GPU cooling 未实机热触发**：现有用户态 GPU 负载（es2gears/vkgears）太轻，峰值 66 °C。
3. **频率抖动**：平衡点在 82 °C 阈值附近，性能核在 state5(2400)/state8(1785) 之间以秒级来回切换
   （2 s 采样中约 2:1）。幅度不大，但对时延敏感场景可把 82 °C 的 hysteresis 加到 5000 或把 70 °C 档
   提到 state 6，使其在 70 档即达平衡、避免跨级抖动。
4. 电池/充电、DDR、modem/camera 等未加 trip（无 cdev，见 §4），仅纳入监控。
5. DTS 改动未 git commit（仓库惯例：本地改动 + `patches/` 存档）。若他人重编 DTB 会自动带上本改动。
6. 首次压测（11:14）被 AudioPilot3 刷 vk37 的重启打断——已确认非温控/内核崩溃；重建后 360 s 完整跑通。
