## 1. 实机证据（2026-10-03，U2 运行 RAM vk40re，SSH `192.168.7.1`）

- `/sys/firmware/devicetree/base/reboot-mode/` 存在：`compatible=nvmem-reboot-mode`、
  `mode-bootloader=0x02`、`mode-recovery=0x01`、`nvmem-cells=<reboot_reason>`。
- `/sys/bus/platform/drivers/nvmem-reboot-mode/reboot-mode -> devices/platform/reboot-mode`：**驱动已绑定**。
- nvmem 设备 `spmi_sdam1`（DT `nvram@7100`），cell `reboot-reason@48,1` 当前值 `0x00`。
- `/sys/kernel/reboot/mode` 读 `cold` —— 这是内核 reboot_mode（cold/warm/hard/soft）的 attr，
  `kernel/reboot.c` 暴露，**与本特性无关**（易误认，勿用）。
- `init`（busybox/Alpine 3.24.2）；`/sbin/reboot` 是 busybox，**不接受 reason 参数** → 需自备触发器。

### 机制如何工作（mainline `drivers/power/reset/reboot-mode.c`）
`kernel_restart(cmd)` → reboot-notifier → `get_reboot_mode_magic()` 把 **cmd 字符串**与 DT `mode-*`
属性名匹配（`bootloader`/`recovery`…）→ `reboot->write(magic)`。即：**只有带 reason 字符串的
`reboot(2)`（`LINUX_REBOOT_CMD_RESTART2`）才能触发**，普通 `reboot -f` 不行。

### 槽位实读（`eldroid-bootctl slot info`）
```
boot_a  byte6=0x72 retry=6 active=0 succ=1 unbootable=0
boot_b  byte6=0x2f retry=5 active=1 succ=0 unbootable=0   ← 当前活动槽=b，mainline 未 mark-successful，正倒计时
```
`slot active` = **b**。即重启会回 b 槽（`boot_b` 当前 = `boot_b-vk34recon.img`，已知基线）。
⚠️ `succ=0` 表示每启动一次 retry −1；现有 **5** 次额度，用完 ABL 置 unbootable → 停 fastboot。
→ 立刻可做：`eldroid-bootctl slot mark-successful b`（= 用户要的“重置槽位启动次数”）。

## 2. EDL 路线（已暂缓，留档）

上游 SM8750 的 EDL 正解 = **PSCI SYSTEM_RESET2 vendor reset**（2026-05 系列 `psci-reboot-mode`）：

```dts
&psci {
        reboot-mode {
                mode-bootloader = <0x80010001 0x2>;   /* fastboot */
                mode-edl        = <0x80000000 0x1>;   /* EDL / Firehose */
        };
};
```
**本树现状**：`drivers/power/reset/psci-reboot-mode.c` **不存在**；`psci.c` 的 `SYSTEM_RESET2`
写死 `reset_type=0`（architectural），**无 vendor 出口**。备选 `qcom,dload-mode=<&tcsr 0x19000>`
（上游 2026-01 补丁；本树 `sm8750.dtsi` 无，`hamoa.dtsi` 可作模板）也无用户态触发。
→ **暂不立项**；将来若要，再移植。

> **已知死路（勿重试）**：写 `misc` 的 BCB `bootonce-bootloader` 后 `reboot -f`，**ABL 不采纳**
> （`PITFALLS` #88 / `AUDIT3` §7，2026-10-03 实测）。

## 3. 交付物

### 3.1 `scripts/eldroid-bootctl`（已交付；设备 `/usr/local/bin/`）
单文件 Python（ctypes 调 `reboot(2)` RESTART2；slot 子命令转发 `slot-attr.py`）：
```
eldroid-bootctl reboot <bootloader|recovery|system|edl>   # edl 占位、默认拒绝
eldroid-bootctl slot info
eldroid-bootctl slot active
eldroid-bootctl slot set-active <a|b>
eldroid-bootctl slot mark-successful [a|b]                # 省略=当前活动槽
eldroid-bootctl slot set-retry <0..7> [a|b]
```
- 写操作要求 root，**写前自动 dd 备份 GPT 前 34 扇区到 `/root/gpt-*.bin`**。
- 已在设备上验证 `slot info`/`slot active`（只读，输出正常）。

### 3.2 `scripts/flash-recovery.sh`（已交付）
从 Linux 里 `dd` 写 recovery 分区（默认 `recovery_b`），尺寸校验 + 写后 sha256 回读，
可选 `--reboot` 调 `eldroid-bootctl reboot recovery`。**无需 AVB 签名**（理由见 §6）。

## 6. TWRP 现状与安装计划（2026-10-03 实测）

### 6.1 现状：TWRP **尚未**装在设备上
| 对象 | 证据 | 结论 |
|---|---|---|
| 设备 `recovery_a` (`/dev/sde25`) | ramdisk_size=16034315，sha `3807dd63…` | **原厂** |
| 设备 `recovery_b` (`/dev/sde57`) | ramdisk_size=16034316，sha `3fc66edd…` = U2 stock dump | **原厂** |
| `twrp/twrp.img` | ramdisk_size=52339414（52 MB），sha `dfaf3dde…` | **TWRP**（community 3.7.1-16） |
| `backup/stock-259/recovery_{a,b}.img` | 与 `twrp/twrp.img` **同 sha** | ⚠️ **命名误导**：这俩其实是 TWRP，不是 stock；恢复时勿当原厂用 |

### 6.2 为什么写 `recovery_b` 不用签名
- 当前 `vbmeta_b` 已是自签（pubkey `fc1e3b33` = `bootslot-b/avb.key`），**Flags=3**（verification 全关），
  且描述符只覆盖 `boot`/`dtbo`，**不含 recovery**。
- `vbmeta_a` 是原厂（`8fcb864f`，Flags=0，**含 recovery 描述符**）→ 写 `recovery_a` 会破 a 槽校验（且
  current-slot 会变 a，正常启动转 Android）。
- current-slot=**b** ⇒ recovery 目标天然是 `recovery_b`。

### 6.3 安装步骤（用户执行；也可改用 `fastboot flash recovery_b`）
```bash
# 1) 装 TWRP 到 recovery_b（Linux 内 dd，写后 sha 回读）
scripts/flash-recovery.sh twrp/twrp.img
# 2) 重启进 recovery（验证 SDAM reason 是否被采纳；最坏进 stock recovery，可正常重启回）
ssh root@192.168.7.1 eldroid-bootctl reboot recovery
# 3) 期望进 TWRP；若仍进原厂 recovery → SDAM 路未生效，转 S2b（PSCI）
```
> TWRP 曾记录的“只有 current-slot=a 才能起”（`PITFALLS` #59）来自当时 b 槽损坏的年代；
> 现 b 槽可正常引导 mainline，故优先试 `recovery_b`。若 TWRP 起不来再评估 a 槽代价。

### 7.2 `reboot(2)` EINVAL 的坑（已修）
现象：`eldroid-bootctl reboot recovery|bootloader` → `reboot(2) errno=22 EINVAL`。
根因：Alpine 用 **musl**，其 `reboot()` 是**单参数**封装 `int reboot(int cmd)`；用 4 参数调它
（magic1/magic2/cmd/arg）会把 `magic1` 当成 `cmd` → 内核判 magic 不合法 → EINVAL。
修法：改成直调 `syscall(SYS_reboot, ...)`（aarch64=142；`libc.syscall` 在 musl 上可用）。
验证：设备上 `libc.syscall(142,0,0,0,None)` 返回 errno=**22（EINVAL，magic 不对）** 而非 38（ENOSYS）
⇒ 确已到达 `SYS_reboot`。已同步设备 `/usr/local/bin/eldroid-bootctl`。

### 7.3 桌面两个问题（根因诊断，待修）
会话栈 = `seatd + dbus-daemon + gnome-session-b + phoc + phosh + gsd-*`，**无 systemd / elogind**。

| 现象 | 根因 | 证据 |
|---|---|---|
| **长按电源键 / 关机无反应**（60 s 倒计时不启动、"立刻关机"无效） | **logind 缺失**：只装了 `libelogind`（库），**没装 `elogind` 守护进程**；phosh-session-manager 调 logind/systemd 关机 → 超时 | `/run/phosh.log`: `phosh-session-manager-WARNING: Failed to shutdown: Timeout was reached`；`dbus-send … org.freedesktop.login1` = `ServiceUnknown` |
