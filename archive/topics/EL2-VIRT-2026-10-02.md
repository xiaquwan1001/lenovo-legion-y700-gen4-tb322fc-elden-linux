# EL2 硬件虚拟化可行性调研 — TB322FC / SM8750 (elden)

> **任务编号**：task-3
> **日期**：2026-10-02
> **性质**：高阶可选，**非阻塞**。仅只读探测 + 文献调研，未做任何刷写/解锁实验。
> **一句话结论**：**KVM 基本不可行**（EL2 被高通签名 Gunyah 永久占用，签名链不可绕过）；**替换/禁用 Gunyah 基本不可行**（hyp 分区受 XBL 签名校验）；唯一可行的"硬件虚拟化"是**沿用 vendor Gunyah、经其 RM 接口在主线 Linux 里跑 guest VM**（非 KVM，需移植下游 gunyah 主 VM 驱动 + crosvm，工作量大、仅支持 protected VM，效果脆弱）。

---

## 1. 可行性结论（先行）

| 目标 | 结论 | 依据 |
|---|---|---|
| **KVM（内核直接拿 EL2）** | ❌ **基本不可行** | 内核实际起在 EL1；EL2 被 vendor Gunyah 占用；hyp 分区受 XBL 签名校验，无法移除/替换 |
| **替换为开源 Gunyah** | ❌ **基本不可行** | `hypvm.mbn` 由 XBL 签名验证，改 hyp 分区 = 砖/红屏（社区明示） |
| **禁用 Gunyah 进入 EL2** | ❌ **基本不可行** | 无 `fastboot oem`/`setenv` 开关；secure boot 链锁死；无 SM8750 手机侧先例 |
| **经 vendor Gunyah 跑 guest VM** | ⚠️ **部分可行，非 KVM** | 本机（SM8750/Y700 四代）已有 Android 侧先例（crosvm + `/dev/gunyah` 跑起 Debian 12.8）；但主线 Linux 需移植未 upstream 的 gunyah 主 VM 驱动，工作量大 |

**总结**：本设备无法获得 KVM。EL2 是"高通领地"，主线 arm64 Linux 无法把它夺回给内核。若真需要"硬件虚拟化"，唯一现实路线是 **Gunyah-guest 方案**（下面 §6），但它是高工作量、且最终不是 KVM。

---

## 2. 现状证据（2026-10-02 设备只读探测，主线 Linux 7.2.0）

### 2.1 当前异常级别 = EL1（关键铁证）

```
# dmesg
[    0.010571] CPU: All CPU(s) started at EL1
[    0.000000] CPU features: detected: Broken CNTVOFF_EL2
[    0.010597] CPU features: detected: Enhanced Counter Virtualization (CNTPOFF)
[    0.010605] CPU features: detected: Enhanced Virtualization Traps
```

- **`All CPU(s) started at EL1`**：内核运行在 EL1，不在 EL2。KVM 前提（EL2）不成立。
- `Broken CNTVOFF_EL2` / `ECV` / `EVT`：SM8750 CPU 的虚拟化扩展在，但 EL2 被占用。

## 3. 固件侧证据（`~/下载/tb322fc/` EDL 全量包 + GPT）

| 资产 | 分区 | 含义 |
|---|---|---|
| `hypvm.mbn`（8 MiB） | `hyp_a` / `hyp_b` | **Gunyah 超管理器镜像**（XBL 加载，EL2） |
| `imagefv.elf` | `imagefv_a/b` | Image Firmware Volume（pvmfw 承载） |
| `pvmfw.img` | `pvmfw_a/b` | protected VM firmware（AVF） |
| `abl.elf` / `uefi.elf` / `uefi_sec.mbn` | abl/uefi | UEFI 引导（ABL），在 EL2 下跑，跳转内核 |
| `xbl_s.melf` + `xbl_config.elf` | xbl/xbl_config | 一级引导（SBL），**负责加载 hyp** |

**关键逆向线索**：`xbl_config.elf` 内字符串 `ImemHypOffset`——XBL 从 IMEM 读取 hyp 偏移并加载，证实 hyp 的加载点是 XBL（早于 ABL，处于 secure boot 链内，签名校验）。

### 引导链（Qualcomm SM8xxx，生产机）

```
PBL(ROM,签名校验) → XBL(xbl_s,签名) → [加载 hypvm.mbn → Gunyah 运行在 EL2]
                  → ABL(UEFI, 签名) → 内核(EL1, 在 Gunyah 之下)
```

- **RM（Resource Manager）是 root-VM**，负责创建 Primary VM（HLOS = 我们的主线 Linux）并控制创建次级 VM 的权限。
- RM 通过 SCM SMC（`qcom_scm`）与 Primary VM 通信；社区日志里 RM 的 RPC 节点为 `hypervisor:qcom,resource-manager-rpc@940e2b5e1215cfb9`。

---

## 4. 为什么 KVM 不可行（根因）

1. **EL2 归属不可逆**：Gunyah 由 XBL 在 secure boot 链内加载并占据 EL2；Linux 只能拿到 EL1。KVM 需要内核在 EL2（或 VHE 下驻留 EL2），二者互斥。
2. **hyp 分区签名锁定**：`hypvm.mbn` 被 XBL 签名校验。删除/篡改 hyp 分区 → 黑砖或红屏 boot 失败，**即使 bootloader 已解锁（ABL 解锁无效，因为签名链在 XBL/PBL 层）**。
3. **无软件开关**：本机 cmdline/GPT/XBL 配置中不存在 `fastboot oem` / `setenv` 之类的"禁用 hypervisor"开关；`androidboot.verifiedbootstate=orange` 只表示 ABL 层解锁，不覆盖 XBL 的 hyp 加载与签名。
4. **社区一致结论**（见 §7 引用）：8 Gen 2 起的手机，EL2 交给 Gunyah 是"系统不信任内核"的设计（DRM/闭源 LLM 抗篡改）；`/dev/gunyah` 替代 `/dev/kvm` 正是此意的体现。

---

## 5. "替换为开源 Gunyah" 为什么不可行

- Gunyah 源码开源（`quic/gunyah-hypervisor` + `quic/gunyah-resource-manager`），但其**运行实体在 hyp 分区，受 XBL 签名校验**。
- 替换成自编译开源 Gunyah → 无法通过 XBL 签名 → 砖。
- 老 SoC（MSM8916/8939）的 `qhypstub` 先例能自签 hyp，是因为那些是**无 secure boot 的 32 位时代 SoC**；SM8750 不适用。

---

## 6. 唯一现实路线：Gunyah-guest（非 KVM，⚠️ 高工作量）

**思路**：不夺 EL2，而是让主线 Linux 以 **Primary VM（HLOS）** 身份，通过 `qcom_scm` → RM 接口，用 Gunyah 创建**次级 VM**。这与 Android 的 AVF/pvmfw 是同一机制。

**已在同类/本机设备验证的先例**：polygraphene/gunyah-on-sd-guide 的环境就是**本机**——"Lenovo Legion Tablet Y700 gen4 / Snapdragon 8 elite / Android 15 / 已解锁 + root"，用 `crosvm --hypervisor gunyah --protected-vm-without-firmware` 成功跑起 **Debian 12.8 (6.15.3)**（见 §7.2）。

**要在主线 Linux 复现，需要的组件**：

| 组件 | 现状 | 缺口 |
|---|---|---|
| Gunyah **主 VM 侧**驱动（`rsc_mgr`/`vm_mgr`/`vcpu`/`irqfd`/`ioeventfd`） | **未进主线**（Elliot Berman 的 "Drivers for Gunyah hypervisor" 系列停在 v16/v17 patch/RFC，2024 年仍在评审）；本树 `linux`（7.2.0）**完全没有** `drivers/virt/gunyah/`，只有 `drivers/watchdog/gunyah_wdt.c` | 需移植 Qualcomm 下游 Android 内核的 gunyah 驱动，或打未合入的 patch 系列 |
| VMM | QEMU 不支持 Gunyah，须用 **crosvm**（gunyah 后端，Android 内置于 `/apex/com.android.virt/bin/crosvm`） | 需在 Alpine/aarch64 上编译 crosvm（带 gunyah 后端） |
| 内核配置 | 现 `CONFIG_GUNYAH_WATCHDOG` 未开，主驱动 config 无 | 需开 `GUNYAH`/`GUNYAH_RM`/`GUNYAH_VM_MGR` 等 |
| DT 节点 | 需 gunyah hypervisor + RM RPC 节点 | 现主线 DT 只有 reserved-memory，无 RM 驱动节点 |

**关键限制（社区实测，8 Elite）**：
- 生产机 Gunyah **只支持 protected VM**（普通 VM 需 `--protected-vm-without-firmware` 这种 workaround）。
- 跑起后 virtio / 图形加速 / 内存锁定仍不稳（OOM、virtio 问题、`virtio_gpu` 未通），详见 §7.1/§7.2。
- guest 内核同样起在 EL1（guest 内也**无** KVM，无嵌套虚拟化）。

**工作量评估**：**数天到数周**（移植下游 gunyah 驱动 + 编译 crosvm + 调试 RM/内存/virtio）。收益是"能跑 Linux guest"，但**不是 KVM、不是裸机 EL2**，性能与稳定性都不如 KVM。

**变砖风险**：**此路线不碰 hyp/XBL/ABL，风险低**——只在用户态 + 内核模块层操作，最坏是 guest 崩、不影响宿主；回退 = 关掉 gunyah 驱动/不加载 crosvm 即可。真正高风险的是"禁用/替换 hyp"，那一步**绝对不要做**。

## 7. 社区先例与引用

1. **polygraphene/gunyah-on-sd-guide**（https://github.com/polygraphene/gunyah-on-sd-guide）
   — 环境就是**本机**（Y700 gen4 / SM8750 / Android 15 / 解锁 + APatch）。`crosvm + /dev/gunyah + --protected-vm-without-firmware` 成功运行 **Debian 12.8 (6.15.3)**；给出 OOM（`ulimit -l unlimited`）与 RM 拒绝（`gunyah_rsc_mgr ... RM rejected message 51000015`）的解法。
2. **lyc8503《Running Linux/Windows on ARM via Gunyah Virtualization》**（https://blog.lyc8503.net/en/post/android-virtualization-on-snapdragon/，2026-06）
   — OnePlus 13（8 Elite）。关键结论：Gunyah 8 Gen 2 起支持、8 Elite 才成熟；`/dev/gunyah` 而非 `/dev/kvm`；**"Gunyah 开源，但 hyp 分区受 XBL 签名校验，直接改 → 黑砖/红屏，即使解锁 ABL 也没用"**；生产机只支持 protected VM。
3. **msm8916-mainline/qhypstub**（https://github.com/msm8916-mainline/qhypstub）
   — 老 MSM8916/8939 开源 hyp 替身启用 KVM；**仅适用于无 secure boot 的旧 SoC，SM8750 不适用**。
4. **TravMurav/Qcom-Secure-Launch**（https://github.com/TravMurav/Qcom-Secure-Launch）
   — Snapdragon **X Elite（笔记本 SoC）** 存在 `/chosen/radxa,enable-kvm` + `smc(0x2000121,0,0,1)` 让 Gunyah 归还 EL2 的机制（Radxa Orion O6）。**注意：这是 X Elite / 开发板路径，SM8750 手机 SoC 未见等效开关**，但作为"高通确有归还 EL2 的 SMC 通道"的反面证据值得记录。
5. **qualcomm-linux/meta-qcom PR #2935（el2gh compatibles）**
   — Qualcomm 开发板（无 secure boot）上，`<soc>-el2` 走 KVM（EL2）、`el2gh` 走 Gunyah，可选。生产机无此选择。
6. **Elliot Berman《Drivers for Gunyah hypervisor》v16/v17**（https://lwn.net/Articles/963370/）
   — 主 VM 侧 gunyah 驱动（rsc_mgr/vm_mgr/vcpu）**至今未合入主线**；RM 源码在 `quic/gunyah-resource-manager`。
7. **HN 讨论（8 Gen 3 虚拟化）**（https://news.ycombinator.com/item?id=38088856）
   — "Windows 能在 8 Gen 3 上虚拟化，只因它把一个**签名 blob/applet** 装入 EL2，作为进 EL2 的 shim"——再次印证 EL2 只对高通签名的代码开放。

## 8. 结论与建议

- **本任务判据**："可实现 / 需引导链改动 / 基本不可行 / 未知" → 对 **KVM 与"替换/禁用 Gunyah"**：**基本不可行**；对 **"Gunyah-guest 跑 VM"**：**部分可行（高工作量、非 KVM）**。
- **建议**：把"主线 Linux 跑 VM"列为 **极低优先级可选探索**，仅在音频/TF/WiFi 长稳等主线事项全部收口后，若确有需要（如隔离跑 Android 之外的系统）再启动 §6 路线。**不要**尝试改 hyp/XBL（会砖）。
- **非阻塞**：本结论不影响当前任何主线工作（显示/GPU/音频/充电/Waydroid/OOB 均与 EL2 无关）。
