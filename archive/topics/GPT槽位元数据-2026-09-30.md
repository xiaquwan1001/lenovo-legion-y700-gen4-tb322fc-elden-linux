## 0. 一句话结论（数字先行）

**tb322fc 的 A/B 槽状态存在 GPT 分区项的 attribute 第 6 字节里，不在 `misc`。**

- 实测：每重启一次，**当前槽的 `boot_*` 项 byte6 减 `0x08`**（retry 3-bit 从 7 数到 0）。
  观察到 `0x37 → 0x2f → 0x27 → 0x1f`（retry **6→5→4→3**）。
- 数到 0 后 ABL 置 **bit7=UNBOOTABLE** → 停在 fastboot；这与历史故障值 **`0x87`** 完全吻合。
- **根治 = 给当前槽的 `boot_*` 项置 `bit6=BOOT_SUCCESSFUL`**，ABL 便不再倒计时。
  一行工具：`python3 scripts/slot-attr.py mark-successful b`。

## 1. 权威位定义（AOSP / Qualcomm `gpt-utils.h`）

```
#define AB_FLAG_OFFSET (ATTRIBUTE_FLAG_OFFSET + 6)   // attribute 第 6 字节 = bit48..55
#define AB_PARTITION_ATTR_SLOT_ACTIVE    (0x1<<2)    // 0x04
#define AB_PARTITION_ATTR_BOOT_SUCCESSFUL(0x1<<6)    // 0x40
#define AB_PARTITION_ATTR_UNBOOTABLE     (0x1<<7)    // 0x80
#define AB_SLOT_ACTIVE_VAL               0x3F        // 激活时写入的整字节
```

| bit | 掩码 | 含义 | 说明 |
|---|---|---|---|
| 7 | `0x80` | UNBOOTABLE | 置 1 → ABL 认为该槽不可启动 |
| 6 | `0x40` | BOOT_SUCCESSFUL | 置 1 → **不再倒计时**（`markBootSuccessful`） |
| 5..3 | `0x38` | tries_remaining | 3 bit，上电默认 **7**，每次启动尝试 -1 |
| 2 | `0x04` | SLOT_ACTIVE | 当前活动槽 |
| 1..0 | `0x03` | OEM 保留 | 激活时随 `AB_SLOT_ACTIVE_VAL=0x3F` 一起置 1；无独立语义 |

激活一个槽 = 写 `0x3F`；标成功 = `|0x40`；一次启动尝试消耗 1 个 retry（`-0x08`）。

## 2. 实测证据（GPT 直接 dump，4 KiB 扇区）

`backup/slot-probe/retry/`，b 槽在跑 Linux：

| 时刻 | `boot_a` byte6 | `boot_b` byte6 | 说明 |
|---|---|---|---|
| linux-b 初始 | `0x72` | `0x37` | a: succ=1, inactive, retry 6 · b: active, retry **6** |
| 重启 #1 | `0x72` | `0x2f` | b retry **5** |
| 重启 #2 | `0x72` | `0x27` | b retry **4** |
| 重启 #3 | `0x72` | `0x1f` | b retry **3** |

- **只有 `boot_a`/`boot_b` 变**；`init_boot/abl/uefi/dtbo/recovery/…` 的 byte6 跨重启**零变化**
  （`init_boot_a=0x7b, abl_a=0x7b, …, init_boot_b=0xff`）。
- `misc`、`uefi` 变量区跨重启 **0 字节差异**（`cmp -l` 全 0）；
  只有 GPT 的 header-CRC / entries-CRC 字段在变（4113–4116、4185–4188 即两处 CRC）。
- 预测序列 `0x3f→0x37→0x2f→0x27→0x1f→0x17→0x0f→0x07`，再下一拍 → **`0x87`（bit7=1）**；
  这正是历史“卡 fastboot”时读到的 `0x87`，闭环。

## 3. 根因（为什么一晚重启就卡 fastboot）

1. Linux 槽 b 的内核**不会调用 boot_control 的 `markBootSuccessful`**（自编 mainline 没这套 HAL/init）。
2. 于是 `boot_b.byte6` 的 bit6 永远是 0 → ABL 每启动一次就把 retry 减 1。
3. retry 归 0 → ABL 置 bit7=UNBOOTABLE → 不再尝试 b → **停 fastboot**。
4. 对照：Android 槽 a 的 byte6 有 bit6（`0x72`/`0x77`），所以它不会被倒计时。

**这与 `misc` 无关**：`misc`(sda7) 只用于 Android BCB（`bootonce-bootloader`），
之前 PITFALLS #71 里“写 misc 偏移 2048 的 bootloader_control”的待办 **作废**。

## 4. 修复方案

### 4.1 根治（推荐）：标记 b 槽启动成功

用新增的 `scripts/slot-attr.py`（自研，处理 4 KiB 扇区 + 双份 GPT CRC）：

```bash
# 在设备上（Linux 里，root）：先看
python3 scripts/slot-attr.py show
# 置位 boot_b：active + successful + retry=7  → byte6 变 0x7f
python3 scripts/slot-attr.py mark-successful b
# 只补 retry（不改成功位，适合临时）
python3 scripts/slot-attr.py set b --retry 7
# 干跑
python3 scripts/slot-attr.py --dry-run set b --retry 7
```

离线改 GPT 镜像：全局参数放子命令前，如
`python3 scripts/slot-attr.py --image lun0-gpt.bin show`。
脚本同时改写 primary + backup 的 **entries 与 header**，并重算两处 CRC（已用合成 GPT 校验通过）。

**动手前先备份**：`dd if=/dev/sda of=~/lun0-gpt.bak bs=4096 count=34`（前 34 扇区）
和 `lsblk` 找到末 34 扇区一并备份；改完 `partprobe /dev/sda`。

### 4.2 备用（不写分区）：

- `fastboot --set-active=b` 只把 byte6 重置成 `0x3F`（retry=7），**不置成功位** →
  只推迟、不根治（约 7 次重启后复发）。
- `fastboot boot <img>`（RAM）永远可用，是保底通道。

### 4.3 已在 Linux 上打通的旁路：

自签 `vbmeta_b`(flags=3) + `scripts/flash-b.sh` 直写 `boot_b`，绕开 AVB，与本修复不冲突。

## 5. 仍待确认（不阻塞）

1. `bit0/bit1`（`0x03`）是否真无意义 —— 现有数据里 active 时恒 1、inactive 时 a 清 0 / b 变化，
   暂按“随 active 一起写”处理，脚本已复刻该行为。
2. 非 boot 分区 byte6 的 `bit7`：b 分区恒 `0x80`（`a=0x7x / b=0xFx`），但 b 槽能正常启动 →
   说明 ABL 的 bootable 判定**只认 `boot_*`（可能含 recovery/init_boot）**，非 boot 分区的 bit7 不是“不可启动”。
   脚本只改 `boot_<slot>`，规避该不确定性。
3. Linux 侧是否要把自检写进 `/init`：**不需要**了 —— 成功位是一次性持久标记，
   置位后永久生效，无需每启一次写一次。
4. 若将来把 Linux 挪到 a 槽、Android 回 b 槽，记得对新的 Linux 槽重复 `mark-successful`。
