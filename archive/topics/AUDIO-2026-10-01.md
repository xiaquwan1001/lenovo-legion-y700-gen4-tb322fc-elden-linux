# 音频（AudioReach）根因与修复 — 2026-10-01

> 承接 `AUDIO-2026-09-30.md`（当时结论：ADSP/APM 服务层问题，未定位）。
> 本轮**找到并修复根因**：不是 SMMU、不是固件、不是 ACDB，而是 **GPR 源端口（service id）**。

## 0. 一句话结论

**SM8750 的 ADSP 固件只应答「下游（downstream）静态 GPR 客户端端口」——APM=3、PRM=7；
主线内核用 APM=1、PRM=2 发请求，被 DSP 直接丢弃。**
因此 `APM_CMD_GET_SPF_STATE` 超时、`APM_CMD_SHARED_MEM_MAP_REGIONS` 失败，PCM 缓冲区无法映射。

修复：让 `q6apm` 的 GPR 源端口**跟随 DT `reg`**，并把 `sm8750.dtsi` 的两个服务端口改成 3 / 7。

## 1. 根因证据链

### 1.1 现场症状（`AUDIO-2026-09-30.md` §11/§15 复现）

```
qcom-apm gprsvc:service:2:1: CMD timeout for [1001021]        # GET_SPF_STATE 超时
qcom-apm gprsvc:service:2:1: Error (1) Processing 0x0100100c cmd  # SHARED_MEM_MAP_REGIONS 被拒
q6apm-dai: DBG memory_map ... addr=0xfff00000 sid=-1 phys=0xfff00000   # 地址<4GiB，SID 也无冲突
```

- 服务号 `gprsvc:service:2:1` = ADSP 域(2) + **IID 1**。
- 服务调用**有响应**（map 收到 `status=1`），但 **GET_SPF_STATE 完全无响应** → 典型「端口被丢弃」。

### 1.2 与上游工作对照（关键）

上游同 SoC 项目 `blu-sharky/linux-piano`（Xiaomi Pad 8 Pro，同为 SM8750）PR #15 明确写道：

> The SM8750 ADSP firmware only answers GPR requests from the downstream static client ports
> (**APM 3, PRM 7**); a request from the mainline port 1 is dropped, so q6apm times out on
> `APM_CMD_GET_SPF_STATE`.

其修复（已合并、CI 验证声卡起）就是：`audioreach_alloc_apm_cmd_pkt()` 改用可配置的 APM 源端口，
`apm_probe()` 里用 `gdev->svc_id`（即 DT `reg`）设置它。

### 1.3 逐项排除（本轮完成的「依次查」）

| 检查项 | 结论 | 依据 |
|---|---|---|
| **SMMU SID / stream-map** | ❌ 非根因 | DT `iommus` 展开后与主线一致（4 个 SID：0x1001/0x1081/0x1041/0x1061）；map 请求的 `status=1` 是 DSP 回复，与地址/SID 编码无关（§15 已用 `sid=-1` 反证） |
| **ADSP 固件加载** | ❌ 非根因，固件正确 | 设备 `adsp.mdt`/`adsp.b00/b09/b43`/`adsp_dtb.mdt` 的 sha256 **与厂商 EDL 全量包 `backup/fw/modem/image/` 逐一相同**；`remoteproc0: adsp is now up`、`audio_pd` PDR up |
| **ACDB 配置** | ❌ 非根因（本轮首次排除） | 设备无任何 `*acdb*`；但 APM/SPF 是 ADSP 核心服务，`GET_SPF_STATE` 发生在开机 6.9s（用户态之前），与校准数据无关。ACDB 只影响后续图的校准参数，不影响服务响应 |
| **GPR 源端口（service id）** | ✅ **根因** | 见 §1.2 |

## 2. 修复内容

生成 patch：`patches/0005-q6apm-gpr-downstream-client-ports.patch`（4 文件，+45/-8）

### 2.1 `sound/soc/qcom/qdsp6/audioreach.c` / `.h`

新增可配置的 APM GPR 源端口：

```c
static uint32_t audioreach_apm_src_port = GPR_APM_MODULE_IID; /* 默认主线值 1 */
void audioreach_set_apm_src_port(uint32_t port) { audioreach_apm_src_port = port; }
uint32_t audioreach_get_apm_src_port(void) { return audioreach_apm_src_port; }
```
`audioreach_alloc_apm_cmd_pkt()` 由硬编码 `GPR_APM_MODULE_IID` 改为 `audioreach_apm_src_port`。

### 2.2 `sound/soc/qcom/qdsp6/q6apm.c`

- `apm_probe()`：`audioreach_set_apm_src_port(gdev->svc_id);`（跟随 DT `reg`）。
- `q6apm_get_apm_state()` / `__q6apm_map_memory_fixed_region()` / unmap：
  由硬编码 `GPR_APM_MODULE_IID` 改为 `audioreach_get_apm_src_port()`。

### 2.3 `arch/arm64/boot/dts/qcom/sm8750.dtsi`

```
q6apm: service@3 { reg = <3>; ... }   /* was service@1, GPR_APM_MODULE_IID=1 */
q6prm: service@7 { reg = <7>; ... }   /* was service@2, GPR_PRM_MODULE_IID=2 */
```

- `q6prm` 无需改驱动：它本就用 `gdev->svc.id` 作源端口，改 DT `reg` 即可。
- 只改 SM8750 的 dtsi，**不动 `include/dt-bindings/soc/qcom,gpr.h`**（避免影响 sm8650/sm8550 等其它 SoC）。

### 2.4 同时清理（本地实验遗留）

- 还原 `q6apm-dai.c` 的 `pdata->sid = -1` 强制项与 DBG 打印（该实验基于错误假设）。
- 移除 elden DTS 里为此假设加的 `q6apm-audio-mem` reserved pool 与 `memory-region`（未再被引用）。

### 4.3 仍未解决：`SHARED_MEM_MAP_REGIONS` status=1

kprobe 实测 map 报文（`q6apm_map_memory_fixed_region` + `gpr_send_pkt`）：

```
phys = 0x1fff00000  (lsw=0xfff00000, msw=0x1)   sz=0x80000   graph_id=0
GPR : src_port=3  dest_port=1  opcode=0x0100100C (SHARED_MEM_MAP_REGIONS)
resp: GPR_BASIC_RSP_RESULT  status=1
```

已排除：**不是 GPR 端口**（已确认 src=3）、**不是地址/SID**（§15 用 `sid=-1`/msw=0 同样失败）、**不是包结构**（`audioreach_alloc_apm_pkt` 不带 APM 头，报文长度自洽）。

剩下最可疑的是 **DSP 侧对共享内存映射的格式要求**：

- 对照**厂商可工作的 Android**：`audio-pkt.c` 的 `APM_CMD_SHARED_MEM_MAP_REGIONS` 用
  `property_flag & 0x4`（**OFFSET 模式**），并用 `msm_audio_get_phy_addr()` 把 ION offset 换成
  **物理地址**再填 `shm_addr_lsw/msw`——即 **msw 是物理地址高 32 位，不是 SID**。
- 主线用 `property_flag=0`（physical/IOVA 模式）+ `msw = SID`，与厂商是两套约定。

→ 下一步实验（各约 3 min：只改 DT/参数 → `make qcom/sm8750-lenovo-elden.dtb` → 重打 boot → flash）：
1. 给 q6apmdai 挂一个 **<4GiB 物理保留池**（`shared-dma-pool`，修好上次 `dma_mem=0` 未挂上的问题），
   传**物理地址**、msw=0（或试 `property_flag=0x1/0x4`），验证 status 是否变 0。
2. 用 ftrace 追 `q6apm_send_cmd_sync`，确认 `APM_CMD_RSP_SHARED_MEM_MAP_REGIONS` 未被误分类。
3. 若仍失败：怀疑本机 ADSP 的 SPF/APM 未完整初始化（`GET_SPF_STATE` 无响应），
   需确认主线是否漏加载 `dspso`（厂商由 `adsp_loader_dlkm` 加载 ADSP 音频框架模块）。

> 说明：本轮回合把「ADSP/APM 服务不通」的主要已知原因（GPR 客户端端口）修好并上机验证；
> 但**出声仍需解决 map status=1**，这是与 tplg/后处理并列的下一层深坑。

## 5. 续查（2026-10-01 深夜，vk33/vk34）：GET_SPF_STATE 与 map 的**真正根因 = 缺 APM 命令头**

承接 §4.3，用 ftrace/kprobe 直接追 GPR 往返（`gpr_send_pkt` / `apr_callback`），定位到**本树 `q6apm.c` 相对上游的一处陈旧差异**，与 SMMU/地址/property_flag/dspso 均无关。

### 5.1 追踪证据（kprobe，vk33）

在设备上挂 kprobe 后手动重触发，抓到 ADSP 应答：

```
gprsend: op=0x01001021(GET_SPF_STATE) src=3 dst=1 size=40   # 24 GPR + 16 APM 头
apmrx:   len=0x1c op=0x02001007(APM_CMD_RSP_GET_SPF_STATE) src=1 dst=3   # ✅ 正常应答
```

### 5.2 根因（三方对照）

`q6apm_get_apm_state()` 构造 GET_SPF_STATE 包时：

| 来源 | 调用 | 包大小 |
|---|---|---|
| 本树（改前） | `audioreach_alloc_apm_pkt(...)` | 24（**无** APM 头）|
| 上游 v6.6 / v6.12 / master | `audioreach_alloc_apm_cmd_pkt(0, ...)` | 40（**带** 16B APM 头）|
| 厂商 `android_kernel_lenovo_sm8750` | 同上 | 40 |
| linux-piano（SM8750，已出声）| 同上 | 40 |

**SM8750 的 ADSP 要求 APM 命令头存在**，收到 24B 的包直接丢弃 → 超时。
同一差异也存在于 **MAP / UNMAP**：本树用 `alloc_apm_pkt`（44B 包），上游/piano 用 `alloc_apm_cmd_pkt`（60B 包）。

> 结论：§4.3 猜测的「物理保留池 / property_flag / dspso」均非根因；是**数据包格式陈旧**。

### 5.3 修复（`patches/0009-q6apm-apm-cmd-header.patch`，3 处）

- `q6apm_get_apm_state()`：`alloc_apm_pkt` → `alloc_apm_cmd_pkt`
- `__q6apm_map_memory_fixed_region()`：同上
- `__q6apm_unmap_memory_fixed_region()`：同上

（保留本树 0005 的「src_port 跟随 DT」改动；payload 仍写 `GPR_HDR_SIZE`，与 piano 逐字节同构。）

### 5.5 新暴露的下一层阻塞：tplg 的设备子图未注册

开 PCM 时 ASoC 打印：

```
find BE for widget MultiMedia1 Playback ... try BE: Secondary MI2S Playback / Left Playback / Right Playback
MultiMedia1 Playback: ASoC: no valid Playback path
MultiMedia1 Playback: ASoC: found 0 new BE paths
no backend DAIs enabled for MultiMedia1 Playback
```

DAPM 取证：FE 子图（`stream0..4.*`）**已注册**，但 tplg 的 **I2S 设备子图未注册**：

- `amixer -c0 controls` **无** `SECONDARY_MI2S_RX Audio Mixer MultiMedia1`（只有内核静态的 `WSA_CODEC_DMA_RX_0 Audio Mixer …`）。
- DAPM widget 里无 `SECONDARY_MI2S_RX Audio Mixer` / I2S device-SG 的 `i2s_rx*`。
- tplg 二进制本身**含**这些字符串（sha256 `5051028889ff…`，与源码 m4 一致），即包没错，是**加载时被丢弃**。

→ 下一层要查：tplg `DEVICE_SG_ADD(..., dai-name SECONDARY_MI2S_RX)` 的 DAI 名/接口 token 与内核 `q6apm-lpass-dais` 的 BE 别名是否匹配（DTS `link-name = "Secondary MI2S"`）。DPCM 找不到 FE→BE 路径，故该 I2S 设备子图/混音器没建起来。
