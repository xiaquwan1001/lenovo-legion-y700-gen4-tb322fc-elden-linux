# 音频（AudioReach）— tplg 设备子图未注册根因与修复 — 2026-10-02

> 承接 `AUDIO-2026-10-01.md`（§5.5 结论：FE 子图已注册，但 tplg 的 I2S 设备子图未注册）。
> 本轮**纠正前序误判并定位根因**：问题不在 tplg 加载/匹配阶段的"丢弃"，而是
> **冷启时根本没有加载我们的自定义 tplg** —— 加载的是 boot ramdisk 里遗留的 MTP 占位 tplg。

## 0. 一句话结论

**冷启加载的 tplg 是 MTP 占位拓扑（`Lenovo-Y700-Gen4-tplg.bin.zst`=1526B，内容是 MTP/QRD 拓扑），
不是我们的自定义拓扑（10436B，只在 sda17 rootfs）。**
`firmware_loader` 在 boot 早期（~6.9s，ADSP probe 时）从 **initramfs（Alpine rootfs ramdisk）** 里
按 `Lenovo-Y700-Gen4-tplg.bin.zst` 回退加载了 MTP 占位 → 运行时 DAPM 全是 codec_dma/WSA 设备子图，
根本没有 SECONDARY_MI2S 后端 → DPCM `no backend DAIs enabled`。

前序文档把 MTP 的 5 路 FE（`stream0..4`）误判为"我们的 tplg 的 FE 已注册"；实际那是 MTP 拓扑。

## 1. 根因证据链

### 1.1 现场实测（2026-10-02，设备 vk34）

运行时 DAPM widget（`/sys/kernel/debug/asoc/Lenovo-Y700-Gen4/gprsvc:service:2:3/dapm/`）：

```
stream0..4.*                       # 5 路 FE（MTP 是 MM1..5；我们只有 MM1/MM2）
device105.codec_dma_rx1  …         # WSA_CODEC_DMA_RX_0 = 105
device113.codec_dma_rx1  …         # RX_CODEC_DMA_RX_0  = 113
device110/120.codec_dma_tx1        # VA/TX_CODEC_DMA_TX
RX_CODEC_DMA_RX_0 Audio Mixer / WSA_CODEC_DMA_RX_0 Audio Mixer
MultiMedia3/4 Mixer
```

**没有** `device18.i2s_rx1`、`device18.logger1`、`SECONDARY_MI2S_RX Audio Mixer`。

对照 dt-bindings（`include/dt-bindings/sound/qcom,q6dsp-lpass-ports.h`）：
`SECONDARY_MI2S_RX=18`、`WSA_CODEC_DMA_RX_0=105`、`RX_CODEC_DMA_RX_0=113`。
→ 运行时加载的是 **MTP/QRD 拓扑**，不是我们的（我们的 `DEVICE_SG_ADD` 用 `SECONDARY_MI2S_RX`→`device18`）。

### 1.2 为什么加载了 MTP 拓扑

1. 内核 tplg 名（`topology.c:audioreach_tplg_init`）：
   `qcom/<card->driver_name>/<card->name>-tplg.bin` = `qcom/sm8750/Lenovo-Y700-Gen4-tplg.bin`
   （`driver_name="sm8750"`，`card->name="Lenovo-Y700-Gen4"`）。
2. 设备当前 `/lib/firmware/qcom/sm8750/Lenovo-Y700-Gen4-tplg.bin` = 我们的自定义（10436B，
   sha256 `5051028889ff…`）。
3. 但 **boot ramdisk** `out/rootfs-vk11.cpio.gz` 里只有
   `Lenovo-Y700-Gen4-tplg.bin.zst`（1526B）= 原始 MTP 占位（scout 文档早已发现三个占位 tplg sha256 相同）。
4. `CONFIG_FW_LOADER_COMPRESS_ZSTD=y` → `firmware_loader` 请求 `…-tplg.bin` 未命中时
   回退加载 `…-tplg.bin.zst`。boot 早期（ADSP probe，~6.9s）根还是 initramfs，所以加载了 ramdisk 里的 MTP 占位。

### 1.3 动态调试复核（unbind/bind 重触发）

对 `firmware_loader/*`、`soc-topology.c` 开 dynamic debug 后 unbind/bind 声卡：

```
Loading firmware from /lib/firmware/qcom/sm8750/Lenovo-Y700-Gen4-tplg.bin
direct-loading qcom/sm8750/Lenovo-Y700-Gen4-tplg.bin   size=10436
Loaded FW: …/Lenovo-Y700-Gen4-tplg.bin, sha256: 5051028889ff…   ← 这次是 sda17 里的自定义 tplg
ASoC: creating DAPM widget stream0.wrsh_ep1 … stream1.* …
ASoC: creating DAPM widget device18.logger1
ASoC: creating DAPM widget device18.i2s_rx1
ASoC: creating DAPM widget SECONDARY_MI2S_RX Audio Mixer
```

→ **我们的自定义 tplg 一旦真正被加载，能正确注册 I2S 设备子图**（device18 + mixer 全建出来了）。
问题纯粹是"冷启没加载它"。

> 注意：重触发（unbind/bind）会因 ADSP 图状态残留导致 `SHARED_MEM_MAP_REGIONS` status=1
> → `Buffer Allocation failed` → `can't create pcm`。这是**重触发伪象**，冷启无此错
> （当前 vk34 冷启 dmesg 无 map 错误、声卡完整注册）。故必须冷启验证。

## 2. 修复

**把自定义 tplg 打进 boot ramdisk，替换掉 MTP 占位。**

1. 解包 `out/rootfs-vk11.cpio.gz` → 删除 `lib/firmware/qcom/sm8750/Lenovo-Y700-Gen4-tplg.bin.zst`，
   放入自定义 `Lenovo-Y700-Gen4-tplg.bin`（10436B，`scripts/audio-tplg/build.sh` 产物）。
2. 重新打包为 `out/rootfs-overlaid.cpio.gz`（62841458B，含自定义 .bin、无 .zst 占位）。
3. `VERSION=vk35 bash scripts/build-boot.sh` → `out/boot-elden-vk35.img`（83562496B，内核同 vk34 不变）。
   sha256 `e1a0fd61ec1b33c9f4e771411d58a7525cf6753fe3dc5c1edf769ea57199edeb`。

> 内核/tplg 源**零改动**：tplg m4 写法与上游 `Google-SC7180-…-SEC-I2S-…` 逐字同构，
> DAI 名匹配正确（BE DAI `stream_name "Secondary MI2S Playback"` == tplg `aif_in` 的
> `stream_name "Secondary MI2S Playback"`）。上一轮担心的"DAI 名不一致"不成立。

## 3. 验证结果（刷 vk35 冷启，2026-10-02）

```bash
scripts/flash-b.sh out/boot-elden-vk35.img --reboot   # ✅ 18s 回到 Linux
```

| 冷启 map 错误 | ✅ 无 `SHARED_MEM_MAP_REGIONS` 报错（声卡完整注册）|

**tplg 设备子图未注册 → 已修复。**

## 3.5 新暴露的下一层阻塞：APM_CMD_GRAPH_OPEN 被 DSP 拒绝（status=1）

开 mixer 后 `aplay -D hw:0,0`：

```
qcom-apm gprsvc:service:2:3: Error (1) Processing 0x01001000 cmd   # APM_CMD_GRAPH_OPEN
qcom-apm gprsvc:service:2:3: DSP returned error[1001000] 1
q6apm-dai ...: No graph found with id 0        # ← 误导信息，实为 GRAPH_OPEN 失败
q6apm-dai ...: ASoC error (-22): at snd_soc_component_open()
```

DPCM 已找到 BE 路径（不再 `no backend DAIs`），卡在 **ADSP 拒绝 GRAPH_OPEN**。
对照 `blu-sharky/linux-piano` PR #16（SM8750 已出声，2026-10-01 合入）——它带了 43 个
linux-msm 上游 commit 才打通 SM8750 AudioReach 扬声器，本树（7.2.0 主线）**缺失**这些：
- `ASoC: qcom: qdsp6: add topology-driven Audio IF support`（67605cbf8dfe，topology.c +109）
- `ASoC: qcom: qdsp6: Zero-initialize AudioReach module config`（9c9fb79f9769）
- `ASoC: qcom: audioreach: compute active channel maps from channel_map`（c663014e452d）
- `ASoC: qcom: q6apm-lpass-dais: Add MI2S clock control`（cc8495c1d45a）
- 等 43 项（TDM/LPR/Audio-IF/LPI-MI2S/q6v5 handover IRQ…）

→ 下一层工作 = cherry-pick 上述 commit（尤其 Audio IF / TDM topology 支持）+ 重编内核。
（本树 `topology.c` 无任何 `LPAIF/TDM/AUDIO_IF` 处理，`q6apm-dai.c:217` 的 `struct audioreach_module_config cfg;` 未零初始化，均与 piano 一致地缺失。）

## 6. 结论

1. **tplg 设备子图未注册 → 根因是冷启加载了 ramdisk 里的 MTP 占位 tplg，不是我们的自定义 tplg。已修复（vk35）并上机验证。**
2. 前序文档「FE 子图 stream0..4 已注册、I2S 设备子图被丢弃」是误判——那 5 路流是 MTP 拓扑。
3. 修复后 aplay 前进到新阻塞：ADSP 拒绝 `APM_CMD_GRAPH_OPEN`（status=1），需 cherry-pick linux-msm/piano 的 AudioReach 上游补丁（43 commit）。

# 续（2026-10-02 下午）：GRAPH_OPEN 已过，BE GRAPH_START 超时 → 改在 prepare 启动（vk39）

## 7. 本轮结论（先给答案）

| 层次 | 结论 |
|---|---|
| GRAPH_OPEN(status=1) | **前一轮已修**：自定义 tplg 的 **container capability 用了 legacy CD(0x2)**，改 `LPASS_VER_COMPAT=110000`（=新 GC 容器类型）后 **GRAPH_OPEN status=0**。AudioPilot3 于 vk37 验证。**不是「缺 43 个 upstream commit」**。 |
| 新阻塞 GRAPH_START | **BE graph（id=18, Secondary MI2S）在 trigger 里 `APM_CMD_GRAPH_START(0x01001002)` 5s 超时（-110）**；FE graph（id=0）start 正常。 |
| 根因 | 本树把 BE `graph_start` 放在 **trigger**（commit `b54a38af7138`，为修 DP/PipeWire）。但**原厂 vendor kernel 把 `q6apm_graph_start()` 放在 `q6apm_lpass_dai_prepare()` 末尾且根本没有 trigger 回调**。ADSP 要求 **sink(BE) graph 先于 source(FE) graph 启动**（FE 在自己的 prepare 里就已 start）→ BE 留到 trigger 再启动时，ADSP 5s 不回 `GRAPH_START` 响应。 |
| 修复 | 新增 `q6i2s_prepare()`：先调公共 prepare，再在**末尾 `q6apm_graph_start()`**，置 `is_port_started`；仅用于 `q6i2s_ops`（DP/HDMI/DMA 仍走 trigger，避免重蹈 `b54a38af7138` 的 DP 回归）。= `patches/0011-q6apm-mi2s-start-graph-at-prepare.patch`。 |
| 验证 | vk39 冷启：`GRAPH_OPEN`→`GRAPH_ADD`→`GRAPH_PREPARE`→**`GRAPH_START` 全部 status=0**；连播 3 次无错；`SEC_MI2S_IBIT` 时钟在流期间 enable=1/rate=1536000；`aw88461` 的 SYSST（PLL lock + amplifier ready）无报错。 |

## 8. 关键证据（vk39 冷启）

修复前（vk38debug，BE 在 trigger 启动）：
```

qcom-apm ...: CMD timeout for [1001002] opcode        <- APM_CMD_GRAPH_START 超时
q6apm-lpass-dais ...: Failed to start APM port 18
```

修复后（vk39，BE 在 prepare 末尾启动）：

```
qcom-apm ...: DBG cmd op=1001001 rsp=1001001 status=0   # GRAPH_PREPARE
qcom-apm ...: DBG cmd op=1001002 rsp=1001002 status=0   # GRAPH_START (BE) ✅ 不再超时
qcom-apm ...: DBG cmd op=1001002 rsp=1001002 status=0   # GRAPH_START (FE)
```

时钟（流期间 `clk_summary`）：


连播：

> `amixer -c0 cset numid=8 on   # 'SECONDARY_MI2S_RX Audio Mixer MultiMedia1' (BOOLEAN on,off)`

## 9. 关于「cherry-pick piano PR #16 的 43 个 commit」

**不作本路径修复。** 已核对 `blu-sharky/linux-piano` PR #16（base 0ab0724，51 commits）：其 43 个 linux-msm 上游 commit 主体是 **LPAIF TDM / Audio-IF / LPI-MI2S / TDM bit clock / q6v5 handover IRQ**，服务于 piano 的 **FS19xx TDM 功放**路径；与本次 I2S GRAPH_OPEN/START 问题无关。本树已含其中的 `q6apm-lpass-dais: Add MI2S clock control`（`q6i2s_set_sysclk` + `of_q6apm_parse_dai_data` 均已在树中）。

## 12. 结论

1. **音频 APM 图已打通**：BE(FE) `GRAPH_OPEN`/`GRAPH_PREPARE`/`GRAPH_START` 全部 status=0，`aplay`/`speaker-test` 可完整播放不再报错。
