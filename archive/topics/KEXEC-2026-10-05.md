## 0. 一句话结论

**`kexec_file_load`（`kexec -s -l`）装载成功，但 `kexec -e` 把整机挂死**；而**现有"无输出"证据无法定位到失败分支点**（控制台是 `ttyGS0` USB gadget，kexec 时必断）。
主机侧查实 **2 个缺陷**：① `--dtb` 对 file-load **是空操作**（⇒ `iterate.sh dtb` 环经 kexec 不成立、RUNBOOK §8 该条错误）；② 本树**缺上游 `VA_BITS_52 + !LPA2` 的 kexec 修复**（`1537e55728ec`），本机配置正好命中触发条件。
**根因需一次带「能在跳转期间存活的 console」的上机取证才能定论**（方案见 §5）。

## 2. 主机侧发现（本轮的实质产出）

### 2.1 `--dtb` 是空操作 ⇒ `iterate.sh dtb` 环经 kexec 不成立

- `kexec_file_load(2)` 系统调用签名为 `(kernel_fd, initrd_fd, cmdline_len, cmdline_ptr, flags)`，**没有 DTB 形参**。
- arm64 的 file-load 路径由**旧内核**用 **live DT** 重建新 FDT：
  `drivers/of/kexec.c: of_kexec_alloc_and_setup_fdt()` → 删旧 `kaslr-seed`、注入新随机 `kaslr-seed`（`drivers/of/kexec.c:480`）、写 `linux,booted-from-kexec`（:512）。用户给的 DTB 文件**不进入新内核 DT**。
- 上游设计即如此（2018 引入 `kexec_file_load` 时明确"用户不得显式指定第二内核的 DT"，见 LWN `Articles/772126`）。
- **影响**：
  - `scripts/kexec-boot.sh` 第 80 行 `kexec -s -l $D/Image --dtb=$D/dtb …` 的 `--dtb=` **无效**（kexec-tools 静默接受，故 RC=0）；
  - `scripts/iterate.sh dtb`（只改 DTS 的"最快环"）**不可能生效**；
  - `RUNBOOK-BRINGUP.md` §8 表格第 368 行"**1 DTB** `iterate.sh dtb` … `make dtbs` 秒级 + kexec ~1 min"**错误**；§8 "kexec 热重载"三条也未提此限制。
- **正确口径**：DTB 迭代只能走 `--boot`（fastboot 零写盘）或 `--flash`；kexec 只能迭代内核代码（`=y`）与 initrd，且新内核用的是**运行内核当时的 live DT**（含 ABL 参与后的结果）。

### 2.2 本树缺上游 `VA_BITS_52 + !FEAT_LPA2` 的 trans_pgd 修复

- 本树 `arch/arm64/kernel/machine_kexec.c:132` 仍是：
  ```c
  rc = trans_pgd_create_copy(&info, &trans_pgd, PAGE_OFFSET, PAGE_END);
  ```
- 上游修复（Breno Leitao，2026-08-28；Will Deacon 2026-09-03 合入 arm64 for-next/fixes，commit **`1537e55728ec`**）：
  ```c
  rc = trans_pgd_create_copy(&info, &trans_pgd,
                             _PAGE_OFFSET(vabits_actual), PAGE_END);
  ```
  > "kexec_file_load() fails on arm64 if we have `CONFIG_ARM64_VA_BITS_52` but it runs on a !FEAT_LPA2 host … `trans_pgd_create_copy()` uses the compile time `PAGE_OFFSET` (VA 52) instead of the actual VA size (48 …). With the fifth level folded, `pgd_none()` is always false, so the walk cannot skip the 15 extra PGDIR_SIZE slots, and they all alias back to the same table: the whole kernel page table gets cloned **16 times**, KASAN shadow included. Without KASAN it does not blow up, it just wastes ~RAM/32 in page tables."
- **本机配置正好命中触发面**：`CONFIG_ARM64_VA_BITS=52`、`CONFIG_ARM64_4K_PAGES=y`、`CONFIG_PGTABLE_LEVELS=5`、`CONFIG_ARM64_LPA2=y`（能力编入，运行时是否启用看 CPU）；`CONFIG_KASAN` **未开**。
- **是否等效本机挂死**：上游 RK3576 测试（同配置、无 KASAN）显示"修前仍能 kexec（只是慢/耗内存 ~RAM/32）"，**故该 bug 大概率不是挂死主因**，但它① 是本树里**唯一命中我们精确配置的已知 kexec 缺陷**，② 修复仅 2 行、零风险，**应作为对照项之一先修**。
- 待设备上确认的一点：SM8750 运行时的 52 位 VA 是否真的启用（即有无 FEAT_LPA2）。判据一条命令：
  ```sh
  dmesg | grep -i '52-bit Virtual Addressing'   # 期望看到 "(LPA2)"；无则运行时回落 48 位、命中 bug
  ```

### 2.3 已排除的相关上游修复

- "kexec/hibernate 临时映射需可写"（清除 RDONLY 位）**本树已有**：`arch/arm64/mm/trans_pgd.c` 用 `pte_mkwrite_novma()` / `pmd_mkwrite_novma()`（`copy_pte`/`copy_pmd`）。⇒ 排除。
- `trans_pgd_idmap_page()`（TTBR0 idmap）对本机成立：reloc 控制页物理地址 < 2^47，`max_msb=47`，走 48 位 idmap（`trans_pgd.c:218`）。⇒ 排除。

## 3. arm64 kexec 执行路径与三个可疑分支点

`kernel_kexec()`（`kernel/kexec_core.c:1138`）实际顺序：

```
kernel_restart_prepare("kexec reboot")      // reboot notifier chain (SYS_RESTART)
migrate_to_reboot_cpu()
syscore_shutdown()
pr_notice("Starting new kernel\n")          // ← 里程碑 A（kexec_core.c:1203）
machine_shutdown() = smp_shutdown_nonboot_cpus(reboot_cpu)   // PSCI CPU_OFF；失败则
                                            //   "Failed to offline CPU%d" + BUG_ON(num_online_cpus()>1)
kmsg_dump(KMSG_DUMP_SHUTDOWN)
machine_kexec()  →  pr_info("Bye!\n")       // ← 里程碑 B（machine_kexec.c:174）
                    → relocation(turn off MMU) → 新内核 el1 入口
```

三个分支点：

| 分支 | 区间 | 机制 | 备注 |
|---|---|---|---|
| **B1** | `Starting new kernel` **之前** | reboot notifier / `syscore_shutdown` 挂 | **基本排除**：`syscore_shutdown()` 普通 reboot 也走（`kernel/reboot.c:292`），而本机 reboot 正常 |
| **B2** | `Starting new kernel` 之后、`Bye!` 之前 | 次级 CPU **PSCI CPU_OFF 未生效** ⇒ `Failed to offline CPU…` 或 `BUG_ON(num_online_cpus()>1)` → oops 硬挂 | **Gunyah 是否允许 primary VM 的 vCPU 执行 PSCI CPU_OFF = 未证**（SM8750 的 PSCI 由 EL2 的 Gunyah 处理，`EL2-VIRT-2026-10-02.md`） |
| **B3** | `Bye!` 之后 | relocation / KASLR / 新内核早期 boot（memmap、hyp 状态、GIC、KASLR 重定位） | **arm64 社区最常见**（NXP i.MX、RPi 等大量"Bye! 后无输出"报告） |

> 判定原则：**只要拿到一条能在切换期间存活的 console 上的最后一行**，就能定位到 A/B 之间还是 B 之后。

## 5. 上机最小取证方案（**需报备放行**）

**前提与安全**：设备现由另一 agent 持有 → 待放行；全程**零写盘优先**（`fastboot boot` RAM 变体 / 持久变体按需）、`panic=15`、物理复位与 `fastboot boot <旧 img>` 作带外回退；fastboot 命令**手敲单条**（`AGENTS.md`）。

**步骤 0（不 kexec，最安全）— 可逆 hotplug 预检（区分 H2）**
```sh
# 设备内，任一持久系统；观察是否打印 "psci: CPU%d killed"、且能恢复
for c in 7 6 5 4 3 2 1; do echo 0 > /sys/devices/system/cpu/cpu$c/online; done
cat /sys/devices/system/cpu/online
for c in 1 2 3 4 5 6 7; do echo 1 > /sys/devices/system/cpu/cpu$c/online; done
```
若 CPU_OFF 正常 ⇒ H2 大幅弱化。

**步骤 1 — 建立"活得过切换"的 console**（本方案成败关键）
- 首选：物理 UART（若有现成焊点/线）直接抓 SoC UART。
- 备选：`console=tty0`（帧缓冲）→ 挂死时**拍屏幕**取最后几行；同时把 `ttyGS0` 上的 `respawn` getty 去掉、宿主停 ModemManager，保证 gadget 串口干净（不污染、不与被杀进程争用）。
- 新内核 cmdline 必须带 **`earlycon`**（否则新内核 console 驱动注册前无输出）。

**步骤 2 — 同源基线（单变量）**
在当前 RAM 系统上，`kexec -s -l` 装**与运行内核完全同源的 Image**（取自该 build 的 `linux/arch/arm64/boot/Image`，`LOCALVERSION` 一致），`--load-only` 先验 → 再 `-e`；cmdline 追加 `earlycon nokaslr maxcpus=1`。记录 A/B 里程碑。
> `maxcpus=1` 让运行内核只有 1 个 CPU，直接绕开 B2；`nokaslr` 排除 KASLR 重定位。

**步骤 3 — 按结果单变量放开**
- 能切换 ⇒ 逐项回退：去 `maxcpus`（测 H2）→ 去 `nokaslr`（测 H1/KASLR）→ 换新内核（测 H3）。
- 不能切换 ⇒ 读最后一行：
  - 无 `Starting new kernel` → B1（回头查 notifier）；
  - 有 A 无 `Bye!` → B2；
  - 有 `Bye!` 无新内核横幅 → B3。

**步骤 4 — 对照修复项**：把 §2.2 的 2 行 patch 编进一个 vk 版本，重复步骤 2，作为 H4 对照。

预计 1 次上机、30–60 min。
