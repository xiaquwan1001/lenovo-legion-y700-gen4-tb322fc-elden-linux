# 复盘：2026-10-02 swarm 子代理反复"秒退/崩溃"根因

> 现象：pi-messenger-swarm 派出的子代理运行 ~30–90s 后 `status: completed, exitCode: 0`，
> 任务被 `agent crashed - task auto-unclaimed` 自动回退。前后共发生 3 轮（09:55、10:23、10:33）。
> 一度误判为"模型 deepseek-v4-pro 导致失败"。实际是**两个独立问题叠加**。

## 一、根因 1（主因）：API 限流 429

从 worker 的 JSON 事件日志（`/tmp/pi-messenger-swarm-agent-logs/CanaryWin2-*.log`）读到：

```
stopReason: error
errorMessage: 429: {"message":"Rate limit exceeded for api_key: <redacted>...
  Limit type: requests. Current limit: 20, Remaining: 0.
  Limit resets at: 2026-10-02 02:33:33 UTC", "code":"429"}
auto_retry_start attempt1 delayMs=2000 / attempt2 4000 / attempt3 8000 → auto_retry_end success=false
agent_settled
```

- ustc_ai 端点对每 api_key **限 20 次请求/滚动窗口**。
- pi 默认 `retry.maxRetries=3`（2s/4s/8s 退避），**在窗口复位前就放弃**，agent 于是"干净退出"（exitCode 0）。
- 4 个 worker + 主会话并发时几乎必然打爆 20 次窗口 → 表现成"随机秒退"。
- 验证：并发 6 个 curl 全 200（未超限）；单个 worker 日志里 429 出现即退出。

**修复**：项目与全局 `settings.json` 增加
```json
"retry": { "enabled": true, "maxRetries": 8, "baseDelayMs": 3000, "maxAgentDelayMs": 60000 }
```
并把 `.pi/pi-messenger.json` 的并发上限降为 **3**（再降请求速率）。新派 worker 才生效。

## 二、根因 2：共享 harness 被跨项目 SIGTERM，管道断裂杀 worker

- 本机两个项目（lobcorp-remake 9877 / y700-elden 9878）各跑一个 harness，但**共享同一份 node_modules**，
  且都写同一个日志 `/tmp/pi-messenger-swarm.log`。
- 10:22:54 日志出现 `received SIGTERM, shutting down (preserve=true)`，随后 9877、9878 两个 harness 先后重启；
  此时 y700 的 3 个 worker 全部 `agent crashed`。
- harness 的 `SIGTERM` 处理设计上**保留** spawn（不主动杀），但 worker 的 **stdout 是管道**；
  harness 一死管道断开 → worker 写入触发 SIGPIPE → 进程退出。

**修复（LOCAL PATCH）**：`dist/swarm/spawn.js`
- worker 的 `stdio` 从 `['ignore','pipe','pipe']` 改为**重定向到日志文件**，并 `detached: true`；
- 另起 `tail -f` 读取该文件供 harness 解析进度（`attachHandlers(..., progressStream)`）。
- 重新应用脚本：`scripts/apply-swarm-patch.sh [--restart]`；补丁存档：
  `patches/pi-messenger-swarm-detach-spawn.patch`、`patches/pi-messenger-swarm-spawn.js.patched`。

**验证**：连续两次 `kill -TERM <harness>` + 重启，3 个在跑 worker **全部存活**并被新 harness `runningSpawns:3` 重新接管。
（注意：`pi-messenger-swarm --stop` 走 `/quit` 不带 preserve，会**主动杀掉** worker；重启务必用 `kill -TERM` 或 `--restart` 的 preserve 路径。）

## 三、附带发现

- **协调会话桶漂移**：任何在项目目录里跑的 pi 进程都会改写 `.pi/messenger/session-id`，
  导致 CLI 解析到新桶（#sage-yak-5）而看不到任务板。`scripts/swarm.sh` 已每次调用前把该文件钉回原桶
  `01a0f868-28d4-7683-9444-6604cb9137f5`。
- **worker 冒充协调者**：`swarm.sh` 曾硬编码 `PI_AGENT_NAME=SageYak`，worker 一旦调用该脚本，
  `task claim` 会被记为 SageYak。已改为 `${PI_AGENT_NAME:-SageYak}`。
- 无关结论：模型本身可用（`deepseek-flash-2` 手动跑 agentic 循环正常，10 轮 15 次工具调用无错）。
